# AI_RTS 的 RSI 自校验开发循环（常驻强制流程）

> 本文件是项目级 Agent 工作流规范，适用于 DeepSeek Harness、Cursor、Codex 以及人工协作者。
> **每次开发任务都必须参考本文件；只有文档类改动可以跳过真实 Match，但仍必须说明未运行项。**
> 它借鉴 RSIGame 的 recursive self-improvement 思路，但验收口径以本项目的
> `skills/闭环验证工作法.md`、`AGENTS.md` 和真实 Match 证据为准。

论文参考：<https://arxiv.org/html/2609.39045v1>

## 1. 解决的问题

一次性让模型“读需求、改代码、跑一个测试”会产生三个错觉：

1. 模型把自己的假设当成了需求，根本没有证明目标行为被复现。
2. 目标测试变绿被误认为整体没有回归。
3. 新截图、日志或 JSON 没有确认 mtime，旧证据被误报成新结果。

本流程把一次任务拆成**局部循环**和**全局循环**。同一个模型可以依次扮演多个角色，但每个角色必须留下独立产物；关键改动必须由新会话或独立探针复核。

## 2. 两层循环

### 2.1 局部循环：Explore → Diagnose → Edit → Replay

每一轮只处理一个可观察方向，不允许“顺便把所有地方都改一遍”。顺序固定：

| 角色 | 必须做什么 | 必须留下什么 |
|---|---|---|
| Controller | 从计划、当前 checklist 和上一轮证据中选一个方向；写出可证伪假设、预算和停止条件 | `round-XX/direction.md` |
| Explorer | 从干净基线启动真实 Match，按确定步骤复现，做正向和反向场景；采集状态、日志、截图和 mtime | `round-XX/exploration.json`、截图、原始日志 |
| Editor | 只在目标已被证据定位后编辑；说明每个改动对应的假设和不变量 | `round-XX/patch.md` |
| Verifier | 重放同一条轨迹，再跑相关回归；打开并肉眼检查关键截图；检查旧证据污染和残留进程 | `round-XX/verification.md` |

**硬门槛：** Explorer 没有复现，Editor 不得凭猜测改；Verifier 没有重放，不能声称修复；只有构建成功不能算通过。

### 2.2 全局循环：Checkpoint → Compare → Promote/Reject → Stage

每一轮结束都生成候选检查点，但不默认接受：

1. 保存 `candidate` 的提交/工作树哈希、测试结果、截图索引和 checklist 变化。
2. 与当前 `champion` 比较。任何硬门禁失败（启动失败、解析错误、僵尸房、目标行为未复现、相关回归）都直接拒绝候选。
3. 只有硬门禁全过且质量向量不退化，才提升为新的 champion。否则从 champion 继续，不从坏候选继续堆补丁。
4. 连续 **3 轮没有提升 champion**，视为当前阶段饱和：暂停重复微调，回到 champion，要求 Controller 提出新的高层方向或结束本阶段。该阈值沿用 RSIGame 的 checkpoint saturation 思路。

### 2.3 关键补丁必须“改一项、开新局、复验旧链路”

这是对所有游戏代码任务的强制收紧，详细门禁见 `skills/闭环验证工作法.md` §1.5。以下变更不能等到一批改完再验证：移动/避障/碰撞/出生/缩放/建造/导航/攻击/视野/经济/生产/网络/线程/缓存、共享 API、场景和配置。

每个关键补丁都必须按以下顺序执行：

1. 保存 champion 的源码 hash、基线运行结果和本轮唯一假设。
2. 精确编辑后立刻解析/编译；失败就停在 Editor，不得继续改别的模块。
3. 在**新启动的独立进程**中运行无头真实 Match，使用正常 Match 场景或同等真实对局入口，让真实单位/建筑、命令和 physics tick 发生。孤立函数、假节点、静态 JSON 或只启动测试场景不能替代真实对局闸门。
4. 验证受影响的新行为，同时重放至少一条已知旧功能轨迹；按范围检查出生/位移/到达、碰撞/导航、攻击伤害、采矿/生产、建造/选择、退局重开和清理。记录模拟秒/墙钟秒、实际实体数、命令计数、退出码、实例/PID 和 `cleanup_ok`。
5. S1 无头局失败，候选立即 `reject`，回到 champion；不得在坏候选上继续堆补丁。S2 相关回归和边界回放未通过，不得晋级；S3 独立复核和全量回归未通过，状态只能 `needs-review`/`blocked`。

无头对局必须有 watchdog 和本轮 PID 所有权。超时保留原始日志并只清理本轮进程；样本/产物必须校验 mtime 新鲜，旧 JSON、旧截图、旧日志不能冒充当前证据。关键视觉改动仍需可见截图并实际打开；关键性能改动同时验证 FPS、长帧和模拟速度，不能只看 FPS。

## 3. 证据与评分

### 3.1 硬门禁（任一失败即拒绝）

- 修改文件已逐个解析/编译通过。
- 真实 Match 能启动，且结束后没有实例登记残留、孤儿进程或僵尸房。
- 目标场景的正向断言通过，反向闸门仍然拦截非法操作。
- 关键截图已生成、mtime 晚于本轮开始时间，并且 Agent 实际打开查看。
- 受影响套件 rc=0，且没有 forbidden output；关键改动有独立复核。

### 3.2 质量向量（用于比较，不替代硬门禁）

每轮记录以下维度的 `before → candidate`：

| 维度 | 示例口径 |
|---|---|
| 目标行为 | 建造、碰撞、出生、寻路、攻击、视野等真实 Match 结果 |
| 回归 | 相关套件通过数、独立复核结果、反向断言 |
| 视觉 | 模型/碰撞/蓝图/特效截图是否与目标一致 |
| 运行稳定性 | 启动时间、帧率、错误日志、进程/实例清理 |
| 性能 | 负载下帧时间、单位数量、导航或避让耗时 |

不得用一个总分掩盖硬门禁失败；不得为了“绿测试”放宽判据。

## 4. Checklist 是可积累记忆

每个任务在 `agent/runs/<run-id>/checklist.md` 维护问题表；每一项必须有证据链接：

| ID | 现象 | 假设 | 证据 | 优先级 | 当前状态 | 验证结果 |
|---|---|---|---|---|---|---|
| C-001 | | | | P0/P1/P2 | open/in-progress/fixed/rejected | |

规则：

- 新发现的问题先进入 checklist，再决定是否改代码。
- `fixed` 只能由 Verifier 写入，并附带本轮截图、日志和 rc。
- `rejected` 必须说明是旧证据、环境干扰、判据过期还是需求不成立。
- 同一问题失败两轮后，Controller 必须换诊断角度；连续三轮未提升则触发阶段饱和。
- 任务结束把可复用教训提炼到闭环报告，不把整段临时日志复制进技能文件。

## 5. AIRTS 专用回放矩阵

对于尺寸、碰撞、建造和寻路改动，至少覆盖：

1. 真实 Match 中的最小复现。
2. 正向/反向成对断言（应允许的允许、应拒绝的拒绝）。
3. 近距离、边界距离、旋转后、不同单位/建筑类型。
4. 相关导航、局部避让、建造和启动完整性套件。
5. 可见截图：模型、碰撞形状、逻辑半径、carve/建造范围和特效必须能区分。
6. 独立探针或新会话复核，不能只复读主线结论。

形状、导航、避让、逻辑半径、建造 footprint、速度、射程和视野仍按现有闭环工作法分别取权威值；本 RSI 流程不允许把它们合并成一个“万能缩放系数”。

## 6. 产物目录与最小合同

```text
agent/runs/<run-id>/
  baseline.md
  checklist.md
  champion.json
  round-01/
    direction.md
    exploration.json
    patch.md
    verification.md
    *.png
    *.log
```

`champion.json` 至少包含：`run_id`、`ref_or_tree_hash`、`created_at`、`hard_gates`、`quality_vector`、`evidence`、`reason`。没有证据路径的字段不得写成 `pass`。

## 7. 失败处理与停止条件

- **未复现：** 先修探针/启动链路，不改产品代码；记录 `blocked: reproduction`。
- **目标变好但回归：** 拒绝候选，从 champion 重来，缩小补丁。
- **测试假红/并发干扰：** 按现有运行器规则单跑复核，不能直接改判据。
- **证据过期：** 删除本轮结论，重新生成并校验 mtime。
- **三轮无提升：** 换阶段或停止，保留 champion 和全部失败轮次。
- **资源、端口、进程状态异常：** 先清理并报告环境问题；禁止按端口或映像名盲杀。

最终回复只能引用闭环报告；若有未验证项，状态必须是 `needs-review` 或 `blocked`，不能写“已完成”。
