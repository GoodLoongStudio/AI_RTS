# 闭环验证工作法（项目强制规则）

> 用户口径（2026-09-30）：「你先做好，闭环验证好，我再看，以后一直要这样」。
> 本文件是**强制规则**，适用于本仓库的一切改动（尺寸、数值、玩法、UI、工具）。

## 0. 一句话

**没跑通闭环验证的东西，不许说"做完了"，也不许拿给用户看。**

## 1. 什么叫"闭环验证通过"（六条全过才算）

| # | 要求 | 具体做法 |
|---|---|---|
| ① | 改动**落地** | 精确编辑写入文件；对改动文件逐个跑 `godot_validate_script`（GDScript）或 `dotnet build`（C#）|
| ② | **运行时实测数值** | 写探针场景（`tests/automated/_Probe*.tscn`）在真实 Match 里量，不靠推断、不靠静态读文件 |
| ③ | **截图肉眼确认** | 起可见实例 → 截图 → **打开图看**，描述你看到了什么；禁止用状态查询代替看图 |
| ④ | 相关套件 rc=0 | 改动会影响的每个套件都要跑（`python tools/run_parallel_suites.py --godot <exe> --jobs N --serial "<长套件>" --ids ...`）|
| ⑤ | 全量回归 | `--ids` 列全 17+ 套件；并行道红、串行复核绿 = 竞争假红（运行器自动甄别）|
| ⑥ | 独立复核（关键改动） | 找**另一个会话/智能体**用**自己的探针**复现，不信主线的结论 |

## 1.5 关键补丁的阶段性闸门（防止“拆东墙补西墙”）

本节是对上表的强制细化。**关键补丁不是等一批改动完成后再统一测试，而是每个逻辑补丁完成后立即开一局新的无头真实 Match。** 以下改动一律视为关键补丁：移动、避障、碰撞、出生/缩放、建造、导航、攻击/射程/视野、经济/采矿/生产、对局生命周期、网络同步、性能线程/缓存，以及会被多个系统调用的共享 API、场景或配置。

### 单补丁循环

1. 先保存当前 `champion` 的 tree/file hash 和可运行基线；本轮只允许一个逻辑假设和一组紧密耦合的小改动，不得同时“顺便”重构其他系统。
2. 编辑后立即做静态解析/编译。通过后**重新启动独立进程**运行无头真实 Match，必须加载正常 `Match` 场景或同等真实对局入口，生成真实单位、建筑和玩家命令；纯函数测试、假节点、直接调用内部方法或只启动一张探针场景，不能替代本闸门。
3. 无头对局至少验证：开局出生数和位置、命令响应/实际位移、碰撞/导航/到达、攻击伤害或资源生产中的一个受影响链路、退局/重开清理。按改动范围增加正向和反向断言；记录 wall-clock、模拟秒/墙钟秒、错误日志、退出码、实例登记和 PID。
4. 同一轮至少重跑一条已知旧功能的回归轨迹，不能只验证新功能。状态 JSON、日志和截图/视频产物必须比本轮开始时间新；不能以“文件存在”或旧产物当证据。
5. 关键视觉改动还必须开可见实例截图并实际打开查看；无头通过不代表视觉通过。关键性能改动必须同时看帧时间、模拟速度和行为，不得只看 FPS。
6. 任何一个硬门禁失败，候选立即 `reject`，停止在坏候选上继续打补丁；从当前 champion 重新建立下一轮。共享工作区禁止 `git reset/checkout` 粗暴回滚，只回滚本轮自己记录的精确补丁或使用隔离 worktree。
7. 连续两轮“新断言通过但旧功能退化”时必须暂停编辑，重新画出调用链和不变量；连续三轮 champion 无提升则换诊断方向，不得靠继续加例外条件掩盖回归。

### 阶段闸门

| 阶段 | 必须通过 | 不能替代的证据 |
|---|---|---|
| S0 基线 | 当前 champion 可启动、可退局、无僵尸房；记录旧功能结果 | 不能用静态编译代替 |
| S1 补丁后冒烟 | 新鲜无头真实 Match + 受影响链路正反断言 + 一条旧功能轨迹 | 不能只跑 isolated unit test |
| S2 阶段复验 | 相关套件、异常/边界场景、同一命令回放，必要时截图 | 不能只看平均 FPS |
| S3 晋级 | 独立复核、全量回归、candidate/champion 比较、清理验证 | 不能以“修复一个现象”宣布完成 |

**未通过 S1 不得进入下一项编辑；未通过 S2 不得把候选合并进 champion；未通过 S3 状态只能是 `needs-review`/`blocked`。**

## 1.6 动态玩法不能仅用截图验收

玩家试玩及移动、转向、碰撞、采矿往返、生产出生、战斗、特效时序等验收，读取 `skills/airts-temporal-playtest/SKILL.md`。使用低帧率连续录像、输入动作时间线和状态数据，并实际按时间段回看。默认 5 FPS，短事件按需用 10-15 FPS；录像频率不是游戏帧率，不能修改 physics tick 或模拟速度来配合录制。

先验证点选、框选、右键移动和持续按键等输入链路；输入受阻只能标 blocked，command-level 接受不证明玩家 UI 已通过。录像录完不等于看完，报告必须引用问题发生的视频秒数、实际打开的解码帧和对应数据。无头仍作逻辑回归补充，截图仍用于静态尺寸/布局，均不能替代动态过程证据。

## 2. 反面清单（都是本项目真实踩过的坑，逐条禁止）

1. **用状态查询代替看图**：曾据"资金 −900、单位列表出现矿场"就报"建造成功"，而截图里那栋楼根本没正常显示。
2. **多行 eval 静默失败当成功**：桥接的 eval 返回 `result:null` 时不要当成"执行了" —— 要另找可验证的路径（探针场景）。
3. **往 `.tscn` 插节点插在 `[node ...]` 与它的 `script = ExtResource(...)` 之间**：会把脚本行抢给新节点，造成"原节点丢脚本、每帧报错刷屏 + 新节点行为诡异"。
4. **用正则批量删代码/诊断**：曾留下 3 处孤儿续行，全项目解析失败约 9 分钟。必须精确编辑 + 逐个文件解析校验。
5. **边改边跑套件**：改动进行中跑回归会得到"混合树"的无效读数。跑之前查源文件 mtime（近 3~5 分钟内有写入就别跑）。
6. **把"新口径断言失败"当成"行为回归"**：先分类再动手 —— 见 §3。

## 3. 口径纪律（改数值时最容易翻车的地方）

**改一个尺寸/数值，必须四处同步**：① 场景（视觉 + 碰撞形状 + 逻辑半径 + 选圈 + 标记）② 配表 `config/balance/*.json`（footprint / 视野 / 服务半径）③ **断言与期望表** ④ 文档。

**断言失败先分类**（不许放松判据）：
- **判据过期**：断言里写死了你刚改掉的数值 ⇒ **更新到新口径**（并在注释里写明"随 XX 口径更新"）。
- **行为回归**：代码路径真的坏了 ⇒ 修代码，不许改判据。

**硬不变量**（不许为了"看起来合理"而破坏）：
- `UnitRadiusCoverageSmokeTest`：物理形状必须覆盖实际会参与接触的视觉地面 hull；但 `Movement.radius`、`MovementObstacle.radius`、导航 carve 外扩和建造 footprint 是不同语义，不能只因都叫 radius 就强行相等。每个值必须有来源和贴边实测。
- `TerrainNavigation / AirNavigation._safety_checks`：navmesh 的 `agent_radius` 必须等于 `Constants.Match.*.Navmesh.MAX_AGENT_RADIUS`，且**机动单位半径 ≤ 该上限**（这是烘焙上限语义，不能只改一边）。
- `Match._setup_and_spawn_unit`：出生只接受"世界位置 + 旋转"，带缩放的基必须剔除。

## 3.5 解析校验的边界（2026-10-01 踩坑）

`godot --headless --quit-after N` 的启动体检**只能发现启动期加载的脚本**的解析错误 ✗。
懒加载脚本（例如 `Movement.gd` 只在生成单位时加载）坏了，启动体检**看不出来** ✓，
表现为"体检干净、套件全红" ✗。
⇒ 改完脚本后必须跑**至少一个会加载它的套件**（移动类改动跑 navigation-stability / local-avoidance）✓。

## 3.6 探针读数的"新鲜度"纪律（2026-10-01 踩坑）

探针写出的 JSON/PNG **必须校验是否真的刷新**（比对 mtime/时间戳）✓，否则会引用**上一轮的旧结论** ✗。
本任务踩过两次：金矿探针的"空地面截图"（机位没生效）、四方向探针的 stale JSON（解析错误导致长期没写新数据）✗。
⇒ 规则：**读探针产物前先看 mtime**；若与本次运行时间不符，先修探针，再谈结论 ✓。

## 4. 并发纪律（本仓库有多个会话同时改）

- 动笔前查目标文件 **mtime**（近几分钟被改过 = 别人在写）。
- 事先声明**写入范围**，跨范围先报备。
- 发现"我改的代码不生效"时，先确认**是不是被别人改回去了**，再怀疑自己。

## 7. 违规样例（本文件存在的理由）

- 报"建造成功"却没看截图 ⇒ 实际建筑放大 3 倍、根本没正常显示。
- 报"可视化做好了"却只有扁平圆盘 + 一个圆柱，且因 `.tscn` 插错位置从未真正运行。
- 报"矿车能采矿了"却只跑了一个夹具，没做真实对局闭环。

# 附：碰撞体定制约定（RA3 式，2026-09-30 基线；2026-10-01 起须逐实体复核）

> 本节记录的是历史 A/B 结果和当时的工作假设，不是允许跳过逐单位测量的全局硬编码。若与 `agent/plans/2026-10-01-per-unit-collider-clearance-plan.md` 冲突，以逐单位运行时证据为准。尤其不能因为旧测试中圆柱更不容易堵路，就把过大的圆形避让圈当成模型碰撞盒。

## 分层：物理 ≠ 导航 ≠ 避让

| 层 | 载体 | 取值口径 |
|---|---|---|
| **物理/检测形状** | `CollisionShape3D` | 逐实体选贴合本体的盒、圆柱、球、胶囊、简化凸体或少量组合，不能按类别硬规定全部移动单位用圆柱。项目读取器、实际移动、导航、逻辑占位与建造必须支持所选形状；未支持不得静默漏读或回退为大圆。Area 的检测形状不等于自动移动阻挡。 |
| **导航挖洞（carve）** | `MovementObstacle` | 必须记录 authored vertices/碰撞 bounds、世界变换和 `agent_radius` 外扩。圆形洞只是一个候选近似；不能因历史方洞 A/B 较易堵路，就让圆洞远大于本体。 |
| **避让/个人空间** | `Movement.radius` / `MovementObstacle.radius` | 与模型大小可以不同，但必须分别量化其“个人空间/静态障碍/逻辑推出”语义。配表 `footprintRadiusMeters` 只有在语义相同且测量证明时才复用，不能自动强制同值。 |

## 硬规则

1. **移动单位不要未经 A/B 就统一换 BoxShape3D**：旧测试中简单方盒对向交错较差，但窄长车辆仍应按真实地面 hull 选圆柱、胶囊、OBB 或复合形状；建筑也不能只凭类别默认方盒，必须贴本体并验证。
2. **炮塔半径只算底座**：早期按整包 AABB 取半径，被炮管撑到 3.3/3.0/3.0 ⇒ 收紧到 1.2/1.1/0.9。
3. **改尺寸四处同步**：场景（形状 + 逻辑半径 + 选圈）→ 配表 footprint → 断言表（`UnitRadiusCoverageSmokeTest` 的 `COLLISION_RADIUS_M` / `AVOIDANCE_RADIUS_M`）→ 文档。
4. **别往配表塞 schema 不认的字段**：`unitTypes[].radiusMeters` 不是合法字段（`UnknownProperty`），一旦写入整份配表被拒、**所有对局套件连锁失败**（还曾引发 .NET Fatal error）。逻辑半径的真正来源是 **场景里的 `Movement/MovementObstacle.radius`**（`Unit.gd:_get_radius`）。
5. **量尺寸要用稳定的运行时 skin envelope**：蒙皮网格的 `mesh.get_aabb()` 可能是绑定姿态，骨骼关节包围盒也不是完整蒙皮包络。应在资源加载和姿态稳定后按实际顶点/运行时几何测量；无法稳定测量就标 `unknown`，不能拿骨骼盒直接冒充真值。
6. **判断"夹具红"先看负载**：`movement-recovery`、`local-avoidance` 在 12 并发下会假红，单跑/4 并发即绿 —— 复跑前先用 `--jobs 4` 或单跑确认。

## 3.7 跑探针时**不要弹控制台窗口**（2026-10-06 用户反馈）

- 现象：用 `Godot_..._console.exe` 起探针会**弹出 "Godot Engine (Console)" 窗口**，
  用户在做别的事时会被反复打断（用户原话：这个弹窗能不能不弹，影响我做其他事）。
- 规矩：**所有**探针/取证启动一律加 `-WindowStyle Hidden`（日志用 `-RedirectStandardOutput` 照收 ✓）：
  `Start-Process -FilePath $godot -ArgumentList ... -PassThru -WindowStyle Hidden -RedirectStandardOutput x.log`
- 只有**用户明确要求看画面**时才开可见窗口（那时也不用 console 版，避免弹 cmd）。

### 2026-10-10 补充：用户聊天和操作电脑不能打断测试

默认采用 `skills/airts-temporal-playtest/SKILL.md` 的非干扰模式：隐藏的是辅助控制台，不是把需要录像的 GPU 窗口最小化；独立游戏窗口后台/非激活，用户可以继续聊天、打字和移动鼠标。禁止自动抢前台、置顶、反复恢复窗口和系统级输入注入；DCS 中会 `warp_mouse` 移动真实光标的接口也不能用于此模式。

优先后台独立窗口捕获和不影响 OS 输入的引擎接口；若不支持正常玩家 UI 就注明 command-level/blocked，不能为了做完测试要求用户停止用电脑。`screen` 抓屏和原生输入需先得到用户对独占前台时段的明确同意。非干扰验收要有游戏后台持续刷新的视频/状态证据，不能把用户切窗口误报为游戏 BUG。
