## 1. 发现：窗口只覆盖 61~73%，且截掉的正是后期

`arrival_latency.analyse(archive, 1028, 11868)` —— 这个窗口是我早期为了
"跨档案可比"而固定的。但各局实际长度远超它：

| archive | tick 范围 | 窗口覆盖 |
|---|---|---|
| `b4d1ef8d` | 627 .. **15536** | 73% |
| `ab487d43` | 589 .. **18373** | **61%** |
| `81893e7b` | 610 .. **15580** | 72% |
| `9d887277` | 572 .. **17992** | **62%** |

⇒ **每局有 27~39% 的 tick 被排除**，而且**排除的是后期** ——
那正是单位最多、协调负担最重、停滞最容易发生的阶段。

## 2. 影响量化：p95 被低估 **13~44%**

| archive | 窗口口径 cont / p50 / p95 | **全窗口 cont / p50 / p95** | p95 变化 |
|---|---|---|---|
| `b4d1ef8d` | 46 / 21.833 / 65.0 | 49 / 21.467 / 65.0 | ≈0 |
| `ab487d43` | 493 / 0.85 / **3.717** | 731 / 0.933 / **5.367** | **+44%** |
| `81893e7b` | 426 / 0.833 / **8.25** | 565 / 0.95 / **9.333** | **+13%** |
| `9d887277` | 460 / 0.883 / **5.967** | 659 / 1.067 / **8.217** | **+38%** |

**p50 也上升约 0.1 秒**（0.83~0.88 → 0.93~1.07）——
即**全窗口下 p50 已接近或超过 1 秒**。

## 3. 这意味着什么

1. **我此前报的所有 p95（3.4~8.25s 那一族）都是"窗口口径"**，
   真实值更高（全窗口 5.4~9.3s）。
   **门禁结论不变（都远未达标）**，但**数值要更新**。
2. **"p50 ≈ 0.85s 达标"这个印象要修正**：全窗口 p50 是 **0.93~1.07s**，
   已经**贴着或越过 1 秒**。
3. **跨档案比较仍有效**（所有档案用同一窗口），但**绝对水平**要按全窗口读。
4. 这也解释了为什么 `b4d1ef8d` 只有 46 个样本 —— 它本就短，
   窗口只覆盖 73%，而它的到达事件又少（原生 AI 在场，见 C-164）。

## 4. 处置：**改用全窗口作为标准口径**

- 从现在起，延迟分析**默认用全窗口**（`0 .. 极大`），
  **不再用固定窗口** —— 理由：固定窗口为"可比"牺牲了"完整"，
  而**截掉后期**恰恰砍掉了最该看的阶段。
- 跨档案可比性用"**每局自身全长**"来保证（每局都全量分析，不截断）。
- 历史读数**不追溯重算全部**（那是几十个表的重跑），
  而是在主报告加一条**统一标注**：凡窗口口径的数，p95 需按本表上调。
