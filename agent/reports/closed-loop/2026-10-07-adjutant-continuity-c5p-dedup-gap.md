# 阶段 C5p：协调侧去重**只盖住两条路径**，重复下发靠游戏幂等兜着（round-54）

日期：2026-10-07。状态：**needs-review —— 查清了 round-53 那条边界的答案：
重复下发**不是有意的心跳**，而是**去重守卫没有覆盖到那些路径**。
协调侧的 `_repeat_suppressed` 只在 2 处被调用，而 `bt-*` 与并行填充
（`rules_fallback`）的意图**不经过它**；真正拦住重复的是**游戏侧的幂等账本**。**

## 1. 先算清"本该被拦"这件事

`_order_signature`（去重指纹）= `单位集合|动作|目标`，目标**取整到米**：

```python
units = ",".join(sorted(...)); action = ...
key = "%.0f,%.0f" % (pos[0], pos[1])      # 取整到米
return "%s|%s|%s" % (units, action, key)
```

`bt-scout-Unit_1-19` 的 **10 次下发，目标全是 `[40.0, 0.9]`** ⇒
**米格键恒为 `"Unit_1|scout|40,1"`，从头到尾没有变过**
（我原本怀疑"目标在米格边界抖动导致指纹变"，**实测否定了这个猜想**）。

而 `ORDER_REPEAT_WINDOW_TICKS = 900`，那 10 次下发的时间跨度是
**11405 → 11955（550 tick）**，**完全落在窗口内**。

⇒ **按现有去重规则，第 2 次起就该被拦住。**

## 2. ⭐ 为什么没拦住：`_repeat_suppressed` 只有 **2 个调用点**

全文件检索：

| 行 | 所在函数 |
|---|---|
| `1658` | `_run_micro_layer`（微操层） |
| `1897` | `_tactical_via_task_patch`（战术补丁） |

而**`node_arbitrate_intent`（仲裁节点）里没有任何去重调用** ——
我在该函数体内检索 `_repeat_suppressed` / `_remember_order` / `recent_orders` /
`dedup` / `duplicate` / `重复`：**零命中**。

⇒ **两条路径绕过了它**：

1. **`bt-*`（行为树）意图**：`bt-scout-Unit_1-19` 正是这一类；
2. **并行填充意图**（`rules_fallback` 的经济/生产/侦察/军事四轨）。

这两类都要经过 `node_arbitrate_intent` → `node_dispatch_to_godot`，
但**中间没有"这条指纹最近发过"的检查**。

## 3. 那为什么没出事？——**游戏侧幂等账本在兜**

`node_dispatch_to_godot` **仍然会**为每条命令调 `_remember_order`（记指纹），
所以指纹是**记了**的 —— 只是**没人查**。

真正兜住重复的是**游戏侧的幂等账本**（`DebugControlServer.gd:2231`，按 `intent_id`）：
它把第二次起返回**缓存旧回执**（`intent_replay = true`，round-53 实测 **794 条里 27 条 = 3.4%**）。

⇒ **整条链是"协调侧漏拦 → 游戏侧兜住"**。这解释了 round-53 的两个数：
- **重复下发 60 条（dispatch 口径）**；
- **其中 27 条被游戏判为回放**（`runner.out` 口径）；
- 剩下的差额是**幂等账本有淘汰**（`ADJUTANT_INTENT_LIMIT`）导致的，
  即"重复发了、且游戏也没认出来、于是**可能又执行了一次**"。

**最后这一类是本轮最值得注意的**：它不是无害的重复，而是
**可能真的重复下发命令**。
