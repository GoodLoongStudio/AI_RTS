**两条结论**：

3. 分层后**真停滞 100% 是战斗单位**（`stall 分层: {'combat': 35}`），
   与用户"兵走一小段后等很久"的抱怨完全一致。

## 3. 逐条追到根因：`bt-attack_move` 的**意图 id 跨轮重复**，而下发按 id 去重

最长的一个真停滞个案 **`Unit_36`（64.6 秒）**，时间线（全部来自档案）：

```
t=9386   attack_move  Accepted  bt-attack_move-Unit_36-10     ← 命令下发并被接受
t=9551   arrival      （空档起点：到达了）
t=9578   micro_control_added  ['bt-attack_move-Unit_36-10']   ← 又生成**同一个 id**
t=9703   micro_control_added  ['bt-attack_move-Unit_36-10']   ← 还是同一个 id
t=9820   micro_control_added  ['bt-attack_move-Unit_36-10']   ← 还是同一个 id
         ...（此后 35 秒里**一条新意图都没有**）...
t=11728  micro_control_added  ['bt-attack_move-Unit_36-13']   ← 换了新 id
t=13425  attack_move  Accepted  bt-attack_move-Unit_36-14     ← 终于又有命令
```

同一份 `commands.jsonl` 里，这个单位在那段时间**只有 3 条**命令：
`t=9386`（两次）与 `t=13425`。

**因果链（三条事实拼起来）**：

1. `t=9386` 命令被接受 → 单位开始走向目标；
2. `t=9551` 用**旧的宽容差**（`max(1.5, radius*1.25)`）报了"到达"，而游戏侧
   `is_navigation_finished()` **从未为真**（round-08 实测：522 条 arrival 的
   `navigation_finished` 全为 false），游戏那条订单**没有结束**；
3. 生成侧重发的意图 id **一字不差**（`-10` 重复三轮）⇒ 下发层按 id 去重 ⇒
   **没有再下发**；而游戏侧那条订单仍在"进行中"，单位就停在容差边缘；
4. 这份旧的早到达信号在 2–3 米处**提前**宣告了回合结束，于是**既不推进、也不重规划**，
   直到行为树自己换了 id（35 秒后）或 `HOP_HOLD_MAX_TICKS` 超时。

⇒ 这与 round-08 的判断**互补**：round-08 修的是"采样容差比游戏宽 → 提前报到达 +
永久锁存"；本轮证明了**同一条链在生产里的后果**：一个提前的、游戏侧其实没结束的
"到达"，会让单位静置到下一个**新 id** 出现为止。生成侧那 35 秒的空窗是**直接原因**，
而"提前到达"是**触发器**。

## 4. 下一步（round-13）——两个候选，必须选一个做

**候选 α（推荐）**：让 `bt-attack_move` 的意图 id **按目标点稳定**而不是按轮次序号。
现在 id 里的 `-10/-13/-14` 是**方案序号**，同一目标重复生成时 id 会变或不变但语义不变；
真正该做的是：**同一目标、同一单位、未到达 ⇒ 不重复生成**（生成层去重），
**到达后换了目标 ⇒ id 必变**（保证能下发）。这样"重复 id 被下发层去重"就不再是问题，
同时不破坏"半路不许改令"。

**候选 β**：把"到达"的判定**只认游戏侧的订单结束**（`navigation_finished` 为真，
或订单终态回执），不再用容差推断到达。代价是 arrival 事件会变少（round-08 已实测
容差收紧后 arrivals -49%），但"提前宣告到达"这个触发器会消失。

两者不冲突，但**一轮只做一个**。α 的风险小、可测（漏斗里 `bt-attack_move` 的
564→473 应该收敛），β 更根本但会牵动"到达证据"这条链，需要更大的验证面。

## 6. 未验证 / 边界

- 五个档案各 1 局，`gap_classify` 的"行程 vs 停滞"用的是 **arrival 事件的 pos**（二元 `[x,z]`），
  空档内**没有 arrival** 时无法区分"原地不动"与"在移动但没到任何点"；
  我用"位移 ≤0.5m 视为没动"的判据 —— 对"空档内 0 次 arrival"的样本，
  这在定义上等价于"没有证据表明它动过"，**不等于**"证明了它完全静止"。
  要钉死需要逐 0.25 秒坐标采样（round-04 那种），本轮没做。
- `Unit_36` 的因果链是从**三条事实**（命令账、到达账、生成账）拼出的；
  中间"游戏侧那条订单仍在进行中"是**推断**（依据是 round-08 实测 `navigation_finished`
  全为 false），不是本轮直接观测到的。round-13 应把 `navigation_finished` 逐条落账来钉死它。
- `dispatch_done` 的 receipts 只覆盖日志窗口内的部分，所以漏斗里的"下发"数是**下界**。
