## 1. 找到的漏洞（代码级，可复算）

`movement.note_arrival` 在**没有路线**时直接 early-return：

```python
entry = previous_route(state, unit)
if not entry:
    return                       # ← 路线没作废，**也不会有任何释放动作**
```

而"结束移动段意图"这段逻辑原先**内联在到达分支的尾部**，因此只对"走到尾部的到达"生效。
到达分支里有**两条 `continue` 出口**会绕过它：

1. **无路线出口**（`note_arrival` 自己 early-return）；
2. **去重出口**（1 秒窗口内同 `unit|target` 键）。

于是"路线早被别的原因作废"的到达**什么都不做**：意图继续活着、单位继续留在
`busy_units` 里，军事轨第一道出口 `if not _free(name): continue` 每轮跳过它。

**实测证据（`archive_353bf7a3`，`Unit_16`）**：

```
t=2121  attack_move Accepted  rule-fill-advance-Unit_16-2121
t=2129  arrival  dist=0.22  target=[36.09, 54.27]
t=2189..3893   advance_skipped reason=busy  ×26   blocker=rule-fill-advance-Unit_16-2121
t=3974  attack_move Accepted  rule-fill-advance-Unit_16-3974     ← 30.75 秒后
```

而该局 `arrival_note == arrival_events`（**798 = 798**）⇒ **到达都记了账**，
所以问题**不在投递**，在"释放动作没有覆盖这条路径"。
`arrival_seen` 的 `no_route` 占 **98/696 ≈ 14%** —— 这条路径不是边角。

**这是结构性错误**：把释放动作挂在**某一条出口**上，而不是挂在"到达"这个**事实**上。

## 2. 修复

把内联循环提成 `_close_movement_intents(state, intents, unit)`，并在**三条出口都调用**：

| 出口 | 旧行为 | 新行为 |
|---|---|---|
| 正常尾部 | 释放 ✓ | 释放 ✓ |
| **无路线** | **什么都不做** | **释放 ✓** |
| **去重** | **什么都不做** | **释放 ✓** |

口径不变：只结束移动段（`MOVEMENT_SEGMENT_ACTIONS`），
`ACTION_ATTACK`（点攻击驻留）不在此列 —— 到达不代表驻留任务完成。
新增计数 `movement_stats.arrival_released_intents`。

守门测试（`ArrivalDedupTest`，6 例全绿），新增 2 例：
① **无路线的到达也必须释放**（正是 `Unit_16` 那一类）；
② 被 1 秒去重窗口挡掉的到达也要释放。

> 写第②例时我第一版搞错了：我拿"**同一条事件**再投一次"去触发去重，
> 但那其实是 `fast_event_seq` **游标**挡下的（在进入到达分支之前就 `return`），
> 压根到不了 `deduped` 出口。已改成"两条**不同 seq**、同 `unit|target`、落在 1 秒窗口内"。

## 4. ⚠ 但总指标变差了，而且按我自己的规则**不能下结论**

| run | cont | p50 | **p95** | ≤1s |
|---|---|---|---|---|
| `353bf7a3`（修复前） | 433 | 0.867 | **3.77** | 58.9% |
| `c5429e2c`（修复前） | 336 | 0.867 | **6.00** | 55.7% |
| `8c6f5071`（修复前） | 451 | 0.967 | **4.95** | 52.3% |
| **`5bb15970`（修复后）** | 387 | **0.767** | **18.85** | 58.4% |

p95 从 3.4~6.0 秒跳到 **18.85 秒**；中位反而更好（0.767，最低）。

**round-22 我自己定的三条规则正在这里生效**：

> ③ 单局差异小于 p95 极差（**32.67 秒**）时**不得**作为因果证据。

18.85 与 3.77~6.00 的差异只有 **~13 秒**，**小于那个极差**。
所以我**不能**说"这次修复让 p95 变差了" —— 只能说"**这一局的读数是 18.85，落在已知噪声范围内**"。

同时我**也不能**说修复有效：目标指标达成了，但最终要交付的是门禁 p95。

## 5. 我的判断（明确标为判断，不是结论）

有两个方向相反的机制在起作用，本轮**无法区分**：

- **有利**：意图在到达时被释放 ⇒ 单位不再被 `busy` 白挡 26~50 轮（§3 已证）；
- **不利**：释放得越早 ⇒ **重规划越频繁**（`invalidations` 186、`planned` 1505），
  而下发/规划预算是**全队共享**的 ⇒ 可能把预算从"接续"挤到"重规划"上，
  反而拉长别人的等待。

这正是 round-19 我推断过的"共享下发预算"，但这次是**反方向**。
要证实/证伪它，需要的不是再跑几局猜，而是**把每轮的被拒/重规划数与下发批次数一起落账**
（round-20 就列为遗留项，到现在还没做）。

## 6. ⚠⚠ 本轮末尾又抓到一个**更严重的**静默缺陷（必须写在这里）

跑完整回归时，`test_graph_state_channels` 报出我新增的两个状态键未声明。
补上声明后，我**多跑了一步 round-trip 探针**（这一步救了本轮）：


**`to_dict` 是逐字段挑着写的**，不是枚举 dataclass ⇒ 我加的这两个字段
**每轮都被清空**，而声明类守门测试**查不出来**（它只扫"有没有声明"）。

后果（必须说清）：**`depleted_resources` 与 `advance_cursor` 在
round-19 / 21 / 22 / 23 的所有真实对局里都是每轮归零的**，也就是说：

- round-19 的"换矿"修复 **等于从未生效**（`resource_usable_by` 永远看到空账）；
- round-21 的"轮转" **等于从未生效**（游标每轮从 0 开始）。

这与 round-22 的结论**恰好自洽**：我当时用服务间隔指标发现"轮转无可测收益"，
现在有了机制解释 —— **它根本没运行**。所以 round-22 那条"轮转无收益"要**改成**
"轮转未生效（缺陷），生效后的效果**尚未测过**"。

已修：`to_dict` / `from_dict` 两处都补上，并新增
`test_roundtrip_preserves_learned_ledgers` 把它固化（**声明测试不够，必须 round-trip**）。
