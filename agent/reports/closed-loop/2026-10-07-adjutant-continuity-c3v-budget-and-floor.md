## 1. 悬着的假设与判定结果：**不成立**

round-23 修掉"到达不结束意图"后，**目标指标达成**（`busy` 否决占比 79.3% → 73.4%），
但 **p50 / ≤1s 变差**（0.867 → 1.217、58.9% → 44.7%）。当时提了两个相反方向：

- **有利**：到达即释放 ⇒ 单位不再被 `busy` 白挡 26~50 轮；
- **不利**：释放越早 ⇒ 重规划越频繁 ⇒ **挤占全队共享的下发预算**。

工具 [budget_correlation.py](agent/runs/2026-10-07-adjutant-continuity-fix/round-26/budget_correlation.py)：
把 `round_delta` **按 tick 求和**（口径见 C3u），定义该 tick 的"重规划压力" =
`invalidations + arrival_released_intents + planned`，按中位分**低/高**两组，比"慢接续（≥5s）占比"：

```
archive_62213f9e（p50 0.87 / p95 4.68）
  低压力  样本=406  慢接续=32  占比=7.9%
  高压力  样本=262  慢接续=19  占比=7.3%
```

**7.9% vs 7.3%** —— 高压力组甚至略低。⇒ **"共享下发预算被挤占"不成立。**

**这条否定结果的价值**：
- 它**排除了一个具体机制**，而不是又留一个悬案；
- 它**避免了一次基于错误假设的改动** —— round-25 的遗留项写着
  "若确认不利 ⇒ 给到达释放配节流"。**现在确认不成立，就不该加那个节流**：
  加它只会凭空引入一层延迟，把"少白挡"的收益一起削掉。
- 它**侧面支持 round-23 的修复**：释放意图本身没带来可测副作用。

同时这也印证 round-24 我当时的保留态度（"只有 p50/≤1s 支撑、无同配置另两局、
不宣称结论"）：那次 p50 变差**更可能就是局间波动**。

## 2. 更重要的发现：接续延迟的**下界**是决策频率

工具 [cadence_floor.py](agent/runs/2026-10-07-adjutant-continuity-fix/round-26/cadence_floor.py)：

| 指标 | `62213f9e` | `353bf7a3` |
|---|---|---|
| 决策轮数 | 179 | 184 |
| 相邻轮间隔 中位 / p90 | **1.40s / 1.87s** | **1.32s / 1.78s** |
| 接续延迟 中位 / p95 | 0.87s / **4.68s** | 0.87s / **3.77s** |
| **到下一轮的等待** 中位 / p95 | 0.70s / **1.45s** | 0.68s / **1.38s** |
| 接续 p95 ÷ 等待下轮 p95 | **3.23** | **2.72** |

两条结论：

1. **存在一个结构下界**：一个单位到达时若刚好错过本轮生成，就必须**等到下一轮**；
   当前决策周期中位 **1.3~1.4 秒**。所以"接续延迟"**不可能普遍低于 ~1 秒** ——
   门禁 `p95 ≤ 1s` **低于本系统的决策周期**。这不是"实现得不够好"，
   而是**门禁口径与决策频率的关系**，必须先说清楚再谈达标
   （prompt §4 要求"时间口径要说明白"，这正是该说明的地方）。
2. **但延迟明显高于这个下界**（3.2 倍）：接续 p95 = 4.68s vs 等待下轮 p95 = 1.45s
   ⇒ 单位**平均要多等 2~3 轮**才被服务到。这与"每轮产出上限
   `PARALLEL_FILL_CAP = 8` + 单位数 40~60"的**排队**图像一致
   （round-21 已从另一条路径发现同一件事：服务顺序固定 ⇒ 排队）。

## 3. 分布形态（说明"p95 不是被极值撑起来的"）

`62213f9e`（451 个接续样本）：

| 档 | 例数 | 占比 |
|---|---|---|
| ≤1s | 250 | 55.4% |
| **1–2s** | **107** | **23.7%** |
| **2–5s** | **74** | **16.4%** |
| 5–10s | 10 | 2.2% |
| >10s | 10 | 2.2% |

**40.1% 落在 1–5 秒**，全是战斗单位。所以要把 p95 压到 1 秒，
要动的**不是尾巴**（>5s 只占 4.4%），而是这 40% 的"多等 1~4 轮"。

## 4. 下一轮（round-27）的三条路（我倾向第 1 条）

1. **把门禁口径与决策频率的关系讲清楚，并给出可达目标**：
   当前周期 1.3~1.4s ⇒ 理论上"等一轮"的 p95 ≈1.4s。
   要么提高决策频率（1.4s → ≤0.5s 才可能 p95≤1s），要么把门禁定义成
   "**决策轮内**的接续延迟"（到达被处理之后到下发之间的时间）。
   这是一个**口径决策**，需要用户确认 —— 我不擅自改判据（prompt §4：不许把判据改绿）。
2. **缩小排队**：让"刚到达的单位"在下一轮**排到前面**（现在是按固定顺序 + 轮转，
   到达并不获得优先权）。这就是 prompt §3-C 原文的
   "**arrival 触发下一段优先服务**" —— 我前几轮查过这条但一直没实现。
   配合 §2 的下界，这可把"多等 2~3 轮"压到"等 1 轮"，
   即 p95 从 4.68s 降到 ~1.5s 量级。
3. 若要真正 ≤1s：还要提高决策频率（架构层，属阶段 B 的"搬出控制线程"）。

  下发批次已在 `batch` 字段里，本轮**没有**联合它做多元分析。

  若存在"决策了但没写档"的轮，这个下界会被**高估**（等待算得更长）。
  这是一个已知的口径依赖，我没有独立核验写档是否覆盖每一轮。
- 慢接续阈值取 5 秒是**我的选择**；但 7.9% vs 7.3% 这种"几乎相等"的形态
  不太可能因阈值反转。
