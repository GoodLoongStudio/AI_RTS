## 1. 我要解释什么

round-47 量到：p50 **前 2.46 → 后 0.93（−62%）**，分水岭在 round-13~15。
本轮想确定**是哪一条改动**带来的。

## 2. 结论：**无法归因到单独一条**（原因如下）

| 障碍 | 说明 |
|---|---|
| 多条改动同期 | round-13（候选 α：前压 id 跟目标走）、round-15（release / skip）在同一区间，**没有单变量对照局** |
| 历史归档不可重跑 | 要分离必须"只回退一条、重跑"，而当时的代码状态已不可复现 |
| 两种 id 机制**并存于同一局** | 见 §3 —— 同一局里 bt 轨与规则轨用的是**不同**的 id 策略，无法按"局"分组 |

⇒ **我明确不宣称"是候选 α 带来的"**。这是本轮结论的一部分，不是回避。

## 3. ⭐ 查实：`rule-fill-advance` 轨**没有**用稳定 id 机制

round-13 的候选 α 引入了稳定 id（**槽位 + 目标哈希**）。
它在 `behavior_tree.py` **确实存在且在跑**：

```
behavior_tree.py:683  def _advance_slot(bb, point=None) -> int:
    hold = max(1, int(bb.get("advance_hold_ticks") or ADVANCE_HOLD_TICKS))
    slot = int(bb.get("server_tick") or 0) // hold
    return slot * TARGET_HASH_SPAN + _target_hash(point, span=TARGET_HASH_SPAN)
```

但 `rules_fallback.py` 的并行填充军事轨**仍然**用**每轮变化的 `tick`** 造 id：

```
rules_fallback.py:3599   _add("rule-fill-advance-%s-%d" % (name, tick), ...)
rules_fallback.py:3687   _add("rule-fill-advance-%s-%d" % (name, tick), ...)
```

### 3.1 实测证据（同一单位连续命令的 id 后缀）

| archive | 轨 | 连续 id 后缀 | 读法 |
|---|---|---|---|
| `ab487d43` | **规则轨** | `2048, 2186, 2323, 2323, 2465, 2590` | **每 ~140 tick 换一个 id** |
| `ab487d43` | bt 轨 | `9860, 13114, 16931, 18721, 19669, 20339` | **跨 ~3000+ tick 才换**（≈900 tick 槽位） |
| `a864c83a` | **规则轨** | `1826, 1977, 2102, 2236, 2352, 2481` | **每 ~140 tick 换一个 id** |
| `a864c83a` | bt 轨 | `13728, 16899, 17765, 17957, 18879, 20205` | 跨大步才换 |

⇒ **两条轨的 id 策略不同**：bt 轨用稳定槽位，规则轨每轮新 id。

### 3.2 为什么这件事值得记

`_target_hash` 的注释写明了**原 30 秒停滞的机制**：

> "意图 id 里除了'槽位'还得带**目标**…… `_advance_waypoint` 是按单位当前位置重算的 ——
> 单位一动，航点就变，但 id 不变 ⇒ 游戏按 `intent_id` 做幂等缓存 ⇒
> **新目标被当成旧命令丢掉**（实测 `archive_f2c668c0` 的 `Unit_36`：64.6 秒停滞期间
> 生成侧反复产出 `bt-attack_move-Unit_36-10`（同一个 id），而 `commands.jsonl` 里
> 那段时间**只有两条命令**）。"

规则轨**每轮换 id**，所以它**不会**踩"id 不变导致新目标被丢掉"这个坑
（方向上是安全的）；但代价是**每条命令都是"新意图"** ⇒
**每轮都重置该单位的路径** —— 这与 `hop_in_progress`（"到位再下一条"）的意图相抵。

⇒ **两条轨在语义上不一致**：一条追求"id 稳定以免丢命令"，另一条追求"每轮新命令"。
**哪一条对，取决于游戏侧幂等缓存的行为** —— 而 round-13 的实测说**是前者**
（候选 α 引入了稳定 id，同期门禁首次出现实质改善）。

**但我没有做单变量对照**，所以 §3 的"哪条对"仍是**推断**。

## 4. 一个可做的、不改行为的观测（留给下一轮）

`rule-fill-advance` 与 `bt-attack_move` **作用于同一批单位**（都是作战单位的前压）。
可以把每个单位的"命令来源序列"打出来，看：
- 规则轨的新 id 是否**打断了** bt 轨已建立的路径；
- 出现 30 秒停滞的单位，是否**在停滞前最后一刻被规则轨的新 id 覆盖**。

这是**只读分析**（用已有归档 + `intent_id` 前缀），不改产品代码。
