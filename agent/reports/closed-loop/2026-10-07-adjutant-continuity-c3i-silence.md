不再是"被当成在路上"，而是"到达后 20~30 秒里生成侧一条前瞻意图都不产出"。**

上位：[C3h 报告](agent/reports/closed-loop/2026-10-07-adjutant-continuity-c3h-advance-id.md)。

## 1. 先验的证据：停滞时**槽位在换**（所以不是"换 id 也不管用"）

工具 [slot_transitions.py](agent/runs/2026-10-07-adjutant-continuity-fix/round-14/slot_transitions.py)。
`_advance_slot = slot * TARGET_HASH_SPAN + target_hash`，所以 id 里**同时编码了槽位**
（`id_tick // 4096` 就是槽位号），可以直接从归档还原。

| 档案 | 真停滞 | 槽位变过 | 槽位没变 |
|---|---|---|---|
| `a864c83a`（round-13 修复后） | 24 | 10（42%） | 14（58%） |
| `707eb88f`（round-11，修复前） | 63 | **0（0%）** | 63（100%） |

⇒ round-13 的修复**确实让槽位开始变化**（0% → 42%）。

## 2. 证伪假设：**"槽位每 15 秒才换"不是剩余停滞的原因**

round-13 的遗留猜测是"`ADVANCE_HOLD_TICKS = 900`(15 秒) 本身内建了最坏空等"。
本轮实测把它**证伪**了：

- `a864c83a` 里 **58% 的剩余停滞样本，整个空档内槽位一次都没变**；
- 更直接的是：**这些样本在空档内生成侧一条 `bt-attack_move` 都没有**
  （`distinct_slots = 0`）。

⇒ 空等不是"槽位没换"，而是**前压分支在那 20~30 秒里根本没产出**。
调小 `ADVANCE_HOLD_TICKS` **不会**解决它 —— 这一点值得写下来，
因为它是本轮**避免了**的一次"拿阈值当修复"。

## 3. 逐例复核：停滞的形式是"**生成侧静默**"

用 [stall_branch_probe.py](agent/runs/2026-10-07-adjutant-continuity-fix/round-14/stall_branch_probe.py)
统计空档内该单位出现的**全部**意图（含非前压分支）：

| 分类 | 例数 | 占比 |
|---|---|---|
| 空档内 0 条意图 | 0 | 0% |
| 只有非前压分支 | 3 | 12% |
| 有前压分支 | 21 | 88% |

看起来"88% 有前压"，但**逐例核到具体窗口后，含义完全变了**。以 `Unit_17`（27.8 秒）为例：

```
窗口 2124..3790
生成侧：t=3790  ['bt-attack_move-Unit_17-20192']     ← 只有这一条，且正好是接续时刻
命令：  t=1977  rule-fill-advance-Unit_17-1977
        t=3790  rule-fill-advance-Unit_17-3790        ← 接续
        t=3947  bt-attack_move-Unit_17-19239
```

⇒ 那"1 条前压"**就是接续本身**（在窗口末尾才出现），空档**中段一条都没有**。
`Unit_19`（28.9 秒）同样：窗口 `2286..4022` 内**唯一**一条是 `t=4022`
的 `rule-fill-advance-Unit_19-4022`，也是接续那一笔。

**所以剩余停滞的真实形态是**：

> 到达之后，生成侧**停止产出**该类单位的推进意图，直到 20~30 秒后
> 才重新产出**一条** —— 而那条就是"接续"。

这与前几轮的形态**不同了**：不再是"被当成在路上所以跳过"（那个已经修了），
也不是"槽位没换"（已证伪），而是**生成侧静默**。

## 4. 下一步（round-15）——把"静默"的成因钉在生成侧的一个具体条件上

现在问题收敛得很干净：**为什么到达之后 20~30 秒内，生成侧不再产出该单位的推进意图？**
`_parallel_intents` 的军事轨里，单位被 `continue` 掉只有四个地方：

| 出口 | 条件 | 怎么看 |
|---|---|---|
| `not _room()` | `len(out) >= PARALLEL_FILL_CAP(8)` | 每轮生成量可测（已落账） |
| `not _free(name)` | 在 `busy` / `used` / `suspended` 里 | **`busy` 最可疑** |
| `not combat_types` 判定 | 类型不在 `combat_ids` | 可测 |
| `_en_route` / `waypoint` 为空 | 已加 `advance_skipped` 逐条留痕 | **能直接读** |

**最可疑的是 `_free`**：`busy = busy_units(state)`，如果到达之后**旧意图仍然活着**
（还没过期/没被标完成），单位就在 `busy` 里 ⇒ 每轮被 `continue` ⇒ 静默到意图 TTL 到期。
意图 TTL 由 `ttl_ticks` 决定（默认 3600 tick = **60 秒**，但实测静默是 20~30 秒，
所以还差一个环节：可能有别的路径把它清理掉）。

⇒ **round-15 第一件事**：把 `_free` 的**否决也逐条留痕**（与 round-12/13 对
`_en_route` 做的一样），并同时落上**原因**（`busy` / `used` / `suspended`）。
这样"静默"立刻就能归因到具体条件，不用再猜。
**仍然不许**动任何阈值。

## 6. 未验证 / 边界

- **各 1 局**。`a864c83a` 与 `707eb88f` 是不同对局，0% → 42% 的槽位变化率
  与"生成量/兵力"耦合，不能当严格 A/B；但"修复前 0%、修复后 42%"同向，
  且与 round-13 的机制解释一致。
- `_trace_advance` 写进 `state[ADVANCE_TRACE_KEY]`，**归档不落盘**（`rounds.jsonl`
  不写它），所以本轮它只是给后续轮次/离线检查用的；本轮的槽位结论走的是
  **id 反解**（不依赖该埋点）。
- "生成侧静默"是**观测到的现象**（空档内生成侧确实没有该单位的推进意图）；
  **成因仍未证实** —— `_free`/`busy` 只是当前最可疑的出口，下一轮靠留痕判定。
- 空档内"0 次到点 + 位移 ≤0.5m"的真停滞判据不变（等价于"没有证据表明它动过"）。
