# 开局约 400 FPS、长局约 40 FPS：实时诊断

日期：2026-10-11。状态：诊断完成，游戏源码未修改，永久修复未实施。

## 结论（measured）

当前主线程热点是 `source/net/DebugControlServer.gd:191` 的连接维护，而不是此次场景中的步兵动画。服务端 `_clients`、`_buffers` 留存约 11,100 个失效连接对象，每一个渲染帧都扫描这些历史对象。

`_process` 的连接循环（208 行）在调用 `get_status()` 前没有调用 `StreamPeerTCP.poll()`。客户端通常每次请求创建短连接、收到答复后关闭；服务端对象的状态未刷新，继续显示 STATUS_CONNECTED，无法进入清理分支。对象和字典条目随请求次数累积，每帧开销随历史连接数增长，符合越玩越卡的表现。这里的 11,100 是 Godot 保留的对象数量，不等于操作系统同时保持 11,100 个连接。

## 实例与证据

- 用户正在运行的源码实例 PID 34352，命令行 `--path G:/AIRTS/AI_RTS`，当前场景 `/root/Match`，端口 24579 / 9090。
- Match ID：`0eb67e68-5ebe-4c3c-82d4-e9fd332d6009`，PlainAndSimple 512×512，单人无敌方；采样时约 46 个单位/建筑实体。
- 用户截图约 43 FPS；实时 perf 一次采样约 45 FPS、process 22.61ms。分段测量期间帧率有所波动，不能混作固定状态。
- 临时启用既有 PerfBuckets，3966.328ms 内 127 个渲染帧，`debug_process` 累计 3,272,929us，平均 **25.771ms/帧**，约占该窗口墙钟时间 82.5%。诊断开关随后恢复 false，没有重置原计数。
- 同窗口动画累计 5,738us、镜头 14,456us、视觉剔除 21,579us、小地图 process 5,401us；这些均远小于通信服务。
- 连接检查：`_clients=11099`，随后 `_clients=11102`、`_buffers=11102`；截图排队数 0。独立调用 selection 同步 47us、sample tick 927us，不足以解释主热点。
- 抽查最早 8 个对象，调用 `poll()` 前状态全部为 2（CONNECTED），调用后全部为 0（NONE），返回错误码均 0；证实失效状态未及时更新。抽查只刷新这 8 个对象，它们由原有逻辑回收；没有断开活跃客户端或重启服务。
- 对 11,097 个对象模拟现有**只读空扫描**三次，耗时分别 **22,201 / 22,686 / 22,710us**，可用字节总数均 0。扫描本身即可解释主要帧耗时；该探针三次扫描会给单次诊断帧增加短暂开销，不用此帧作正常 FPS 证据。
- 操作系统同时间采样只有 34 个 24579 CLOSE_WAIT 条目，再次表明对象数与活跃 TCP 数不能混淆。

## 根因代码与客户端行为

服务端：`source/net/DebugControlServer.gd:208` 每帧 duplicate 全数组、遍历 get_status/get_available_bytes/字典读取，只在非 CONNECTED 时 erase；该文件未发现 poll 调用。

客户端：`tools/dbgctl.py:38` 使用每请求 connect + finally close。副官生产调用入口 `source/adjutant_coordinator/deploy/godot_tcp.py:70` 同样使用短连接上下文管理。这种客户端行为合法，服务端必须正常回收，不应归咎于客户端正常关闭连接。

## 修复方案（未实施）

1. 每次检查 peer 状态前调用 poll，处理返回错误与断开状态，回收对应 buffer。保持现有 JSON 行请求、长度前缀响应协议、副官白名单和指令语义。
2. 批量回收采用一次线性遍历/保留活跃数组等现有合适模式，避免对 11,000 个对象逐个 Array.erase 引发 O(N²) 清理卡顿；检查待截图/当前客户端引用的生命周期。
3. 补充合理的连接数、接收缓冲和单帧请求预算；明确背压/错误返回，不能丢弃合法副官命令来提高 FPS。idle timeout 只能在明确协议边界下补充，不能代替 poll。
4. 客户端连接复用可作为后续减少分配的候选；不是根因修复的必要前提。本轮没有多线程重构的证据需求，先消除无效主线程工作。
5. 同类 StreamPeerTCP 服务一并只读审查状态刷新问题，按各自协议修复，避免盲目全局替换。

- 请求结束后连接数量应回到合理稳定基线，不应与累计请求数线性增长；空闲维护开销应不再与历史请求数量相关。
- 分别验证持续连接、半包/多行、客户端中途断开、重新连接、buffer 上限和背压；不能只测一次请求。
- 真实副官探索/移动/选中玩家接管链路回归，确认命令延迟、移动进展与响应协议不退化。按现有流程退出并复验第二局。
