## 3. 逐例：`Unit_16` 的 30.75 秒空档（`353bf7a3`）

```
t=2121  attack_move Accepted  rule-fill-advance-Unit_16-2121   ← 命令下发并被接受
t=2129  arrival  dist=0.22  target=[36.09, 54.27]              ← 到了（0.22 米）
t=2189..3893  advance_skipped  reason=busy  ×26                 ← 连续被挡
t=3974  attack_move Accepted  rule-fill-advance-Unit_16-3974   ← 才有下一条
```

**占住它的是哪条意图**（`blocker_action` / `blocker` 已逐条留痕）：

```
blocker_action = {'attack_move': 26}
blocker        = rule-fill-advance-Unit_16-2121  ×26
```

也就是说：**就是 2121 那条前压意图本身**，在它的路线已经被到达作废之后，
**仍然留在 `active_intents` 里算"活着"**，于是 `busy_units` 一直把它算进去，
军事轨第一道出口 `if not _free(name): continue` 每轮跳过它。

这与 round-15 修的那条**形态相同**、但**没有被那次修复覆盖**：
round-15 把"到达即结束**移动段**意图"从"只对侦察段"放宽到
`MOVEMENT_SEGMENT_ACTIONS = {move, attack_move, scout}` —— 而
`rule-fill-advance-*` 的 action **就是 `attack_move`**，本该被覆盖。

### 3.1 一个我没能定论的关键点（如实写）

我查了该到达是否真的被处理：

- `events.jsonl` 里 **t=2129 的 arrival 存在**（dist=0.22）；
- 但 `decisions.jsonl` 里 **窗口 [2000, 4100] 内没有 `arrival_seen` 记录**；
- 该档案 `arrival_seen` 的 tick 范围是 **1319..18022**（696 条），
  所以 2129 **落在范围内**，不是被日志上限挤掉的。

两个可能，本轮**无法区分**：

- **A**：`arrival_seen` 那条决策确实产生了，但在归档时被更晚的条目挤出保留窗口
  （`arrival_seen` 的 tick 序列在 1995 与下一个之间有跳空 —— 与 `advance_skipped`
  的最小 tick 是 680 相比，`arrival_seen` 的密度低得多，被挤掉是可能的）；
- **B**：这条到达**没走到** `node_ingest` 的到达分支（例如 `unit` 字段为空、
  或它进的是另一条事件通道），于是 `note_arrival` 从未调用、意图从未被结束。

**A 与 B 的修法完全不同**（A 只是观测问题；B 是真 bug），所以下一轮必须先定论它。
最直接的判据：给到达分支加一个**有界的计数器**（`arrival_note` 已有！
`movement_stats.arrival_note`）—— 看它是否等于 `arrival_events`;
若相等则说明**处理了**（A 成立，意图被别的路径留活）；
若不相等则说明**漏处理**（B 成立）。

## 4. 另一条独立线索：30 秒这个数字又出现了

`Unit_16` 与 `Unit_11` 的停滞都是 **30.75 秒**，`Unit_10` 是 **29.92 秒** ——
又回到 `HOP_HOLD_MAX_TICKS`（1800 tick = **30.0 秒**）附近。
这与 round-21 我"证伪 30 秒保险"的结论**不冲突**：
round-21 否掉的是"**所有**停滞都由保险放行"（簇内到达跨度大、时长依次递减，
那是排队）；而这里 `Unit_16` 是**单例**、时长精确贴 30 秒 ——
两种形态**同时存在**：

- **排队型**（多单位、簇状、时长递减）→ round-21 已定位并加了轮转；
- **卡住型**（单例、贴 30 秒、`busy` 连续否决）→ **就是本条**，还没解决。

所以"30 秒"不是被证伪了，而是**被细分成了两种形态**，其中一种仍在。

## 5. 下一轮（round-24）的最小验证（不改产品代码也能做）

1. **定论 A/B**：读该档案 `rounds.jsonl` 的 `movement.arrival_note` 与
   `arrival_events` 是否相等（这是**现成的**字段，不用重跑）。
   - 相等 ⇒ A：到达都记了账 ⇒ 意图是被**别的路径留活**的
     （查 `active_intents` 的状态机：谁把它从 `completed` 又写回 `active`？）；
   - 不相等 ⇒ B：有到达没记账 ⇒ 查 `node_ingest` 的 `unit` 字段与事件通道。
2. 若 A：**"到达之后意图被复活"**是一个新的、可测的路径 —— 用
   `IntentBatch`/`merged_from` 的账去查；
3. 若 B：那就是 round-15 的修复没有覆盖到的**事件投递缺口**。
4. ⚠ 仍**不许**动任何阈值（尤其不许把 `HOP_HOLD_MAX_TICKS` 调小）。
