# RA3 逆向研究：寻路、电脑玩家与大规模作战的可复用机制

日期：2026-10-11  
研究对象：`D:/Red Alert 3/Data/ra3_1.12.game`，SHA-256 `EC230C6AE1EAEE30B0B4FA6BA29D417C974ECAE46D6715DFBE786A815935C165`  
范围：只读 Ghidra 反编译、官方本地 Schema 与 AIRTS 当前实现对照。没有修改 RA3 安装，也没有修改 AIRTS 游戏代码。

## 结论先行

RA3 能同时运行多个电脑玩家和大量单位，关键不是某一个“神奇寻路算法”，而是下面这套组合：

1. **分层决策**：战略状态/目标选择、战术编组、团队招募、单位微操分层，团队是主要决策粒度，单位不是每次都独立重新规划。
2. **分散更新**：AI 管理器只在对象启用且到期时更新；不同控制器有不同更新节奏。移动、战斗、经济和基地建设不会全部在每个渲染帧完整重算。
3. **有预算的寻路**：请求被分成普通、攻击、安全、编队单位、修补、绕行、路径成本检查、快速无碰撞等模式；寻路管理器维护累计工作量，超出总预算或某类配额时把请求标记为稍后处理。
4. **共享路径上下文**：普通/分层搜索从同一地图和上下文进入，团队或延长路径的请求可复用中间状态；单位拿到路径后持续移动，不需要每帧重新搜索。
5. **粗到细的空间搜索**：反编译能看到以 16×16 网格块为边界的层级入口，以及局部邻接格/边界候选的修补逻辑。它更接近“先解决区域连通，再在局部细化”，而不是每辆车都对整张地图做一次完整 A*。
6. **工作线程基础设施**：EA Job Manager 会按处理器数量创建工作线程（少于 2 个时仍创建 2 个），线程通过事件等待任务。当前证据证明了通用任务系统存在，但尚未证明 RA3 的每一次 AI 或路径搜索都由这些线程执行。

这套设计使每一帧的工作量近似“本帧到期的决策 + 本帧允许的路径预算 + 已经产生的移动执行”，而不是“电脑玩家数 × 全部单位数 × 全量搜索”。这就是规模差异的来源。

## 直接反编译证据

### AI 更新不是每帧全量决策

`FUN_008D1020` 对三个子接口（对象偏移 `+0x20`、`+0x7C`、`+0xA4`）重复执行相同流程：

1. 调用虚表 `+0x0C` 检查是否启用；
2. 调用虚表 `+0x10` 检查是否到期；
3. 只有两个条件都满足，才调用虚表 `+0x08` 安排下一次截止时间，再调用 `+0x18` 执行更新。

`FUN_00893050` 把下一次截止时间设为全局计数器 `DAT_00CD8CE4 + 0x50` 加一个间隔；`FUN_0088A200` 比较截止时间与同一计数器。这里可以确认“按截止时间分散更新”，不能仅凭地址推断计时单位。

`FUN_008D6DD0` 遍历已有战术数组并调用战术更新；`FUN_008C95A0` 根据战术状态和时间差触发回调，并通过 `FUN_00600A80` 计算下一次时间。它表现出状态机和延迟重试，不能简化为每帧扫描所有单位。

官方 Schema 与这些入口吻合：

- `AssetTypeAIMicroManager.xsd`：默认 `UpdateTime=1s`、`MaxTeamIdleTime=30s`、`MaxUnitIdleTime=10s`；还规定目标保持时间、视野搜索半径、撤退和特殊能力延迟等独立节奏。
- `AssetTypeAIPersonalityDefinition.xsd`：目标过期默认 15s，战略目标上限 32，基地受攻击更新 200ms、基地内敌人更新 1s、合作监控 5s。
- `AssetTypeAITeamTemplate.xsd`：每个团队有 `MinUnits/MaxUnits`、单位类型上限、优先级、释放策略、是否允许战斗中招募、移动类型和必需的 MicroManager，并可按目标点或基地排序。
- `AssetTypeTargetHeuristics.xsd`：目标按敌方建筑/单位/受攻击对象/扩张点等启发式选择，再按距离、对地威胁、对空威胁、随机或距敌方最近排序。

这解释了为什么 RA3 的电脑玩家看起来像“同时在做很多事”：多数时刻是在执行已经形成的团队任务，只有到期、状态变化、目标失效或队伍停滞时才重新决策。

### 寻路请求有模式、有总预算、有类别配额

`FUN_006A2350` 是寻路模式分发入口，反编译中的分支名称直接保留了设计意图：

| 模式值 | 反编译字符串/用途 |
|---:|---|
| 0 | `NORMAL` |
| 1 | `ATTACK` |
| 3 | `SAFE` |
| 4 | `HORDE UNIT`，编队单位 |
| 5 | `PATCH`，修补 |
| 7 | `MOVE AWAY FROM`，脱离/远离 |
| 8 | `CHECK PATH COST` |
| 10 | `COLLISION FREE QUICK` |

当请求需要层级模式时，它先调用 `FUN_0069B880` 构造 Hierarchical 实现；普通模式调用 `FUN_0069B9A0`。两个构造器使用不同虚表（`0xC18AC0` 与 `0xC18BB0`），说明不是同一个算法入口套参数，而是不同的策略对象。

`FUN_006B3C90`（extend 分发器）是最重要的规模证据：

- 读取全局寻路设置 `DAT_00CE3E2C+4` 与当前上下文累计工作量 `this+0x18`；
- 超过总预算时，模式 10 使用独立计数器/上限 `settings+0x34`，模式 7 使用另一组 `settings+0x38`；
- 超出配额时把请求的 `input+0xB8` 设为 1 并返回，表示稍后继续，不是无界地在当前调用中硬算；
- 未超限时建立共享上下文，按模式构造搜索对象，执行 `FUN_006B38A0/006B3B10`，最后把本次 `input+0xC0` 累加回上下文工作量。

这可以可靠地称为**有界、可延期、按模式配额的寻路工作调度**。源码没有足够符号证明这些字段的实际单位，所以不能把它们写成“毫秒预算”。

`FUN_0069B5E0` 执行一个搜索对象：先检查多个虚表条件，再遍历候选/工作项，成功时提交结果；每次执行把本次消耗 `param+0x19` 加入父上下文的 `+0xC0`。这与 `006B3C90` 的累计预算形成闭环。

层级和局部搜索的证据来自 `FUN_006AB980` 等函数：它以 16 为步长换算区域坐标，围绕候选节点检查四个边界方向和多组邻近偏移，并在局部有效节点上继续检查/连接。结合 `FUN_0069B880` 的 Hierarchical 构造，可确认“区域级入口 + 局部细化/修补”的结构；目前不能把它命名成某个未经证明的 HPA*、HAA* 或 Flow Field 变体。

`FUN_0068D380` 还包含“Unexpected queue size”和 0x200（512）项环形队列的序列化/回绕逻辑。这证明存在固定容量队列结构，但尚未证明它就是所有实时寻路请求的唯一队列，因此不能拿它单独解释全部吞吐。

### 多线程：寻路批处理确实有 Job 分支，但不要过度解读

`FUN_00545190` 初始化 Job Manager；`FUN_00B312E0` 调用 Win32 `GetSystemInfo`，按处理器数量循环创建名为 `Job Manager - Job Thread` 的线程描述，最少为 2 个；`FUN_00B32C40` 在线程循环中通过虚表取任务，空闲时 `WaitForSingleObject` 等待事件；`FUN_00B32C90` 创建线程对象和事件。更底层的 `FUN_00B31EB0` 还初始化了 0x20 个（32 个）JobInstance 槽位和优先级队列结构；这说明是通用任务后端，不代表同时有 32 个活动 CPU 核心。

这次定向批次还补到了寻路批处理的连接：`FUN_006B4160` 有明确的串行/Job 两条分支。串行分支每次以 200 字节步进处理寻路输入，调用 `FUN_006A2350`，累计每项 `+0xC0` 成本并在总预算达到时停止。另一分支把同一个 `FUN_006A2350` 作为回调交给 `FUN_00B31390`，通过 `FUN_00B311A0` 准备 Job 状态、`FUN_00B311F0` 运行/等待任务，并用 `FUN_00B30F00` 释放本轮 Job 资源。随后仍会收集结果、按同一个寻路预算停止。也就是说，**RA3 的寻路批次具备可切换的并行执行路径，且并行不会绕过预算**。

这说明 RA3 有可复用的 CPU 任务基础设施，能把适合的工作放到多个 worker 上，并在没有任务时睡眠；而 `FUN_006B4160` 又直接把寻路批次接到了这套后端。仍然不能说“所有 AI 都在 worker 上”：AI 战略状态、目标排序、队伍状态和 Scene/对象写回是否进入 Job Manager，当前证据没有覆盖。更准确的表述是：**RA3 对寻路批次提供了串行/Job 可切换执行，同时用同一套预算与结果收集约束它；其余 AI 子系统是否并行要逐链确认。**

## 为什么它能支持多个电脑玩家和大量单位

从工程角度，规模来自五个乘法项被拆开了：

1. **电脑玩家数量只放大自己的到期控制器**，而不是每个 AI 每帧重复完整世界扫描。
2. **编组把单位决策摊薄**：目标、战术、撤退、招募和路径大部分按 Team 处理；单位只处理自己的移动、攻击和特殊状态。
3. **目标集合有上限和过期时间**：战略目标有上限 32，目标会过期，避免无限积累旧目标。
4. **路径搜索可延期并按类型限额**：短期内不能完成的请求不会把整帧拖死；快速检查、攻击路径和普通路径也不会混为一锅。
5. **持续执行代替重复求解**：路径生成后，单位沿航点移动；只有路径失效、卡住、目标改变或状态切换才需要修补/重算。

因此 RA3 的“同时作战”不是每一帧让所有单位都获得全新智能，而是让大量单位保持稳定执行，同时把有限的重决策预算分给最需要的队伍。

## 对 AIRTS 的直接启示

AIRTS 当前已经有一些相同方向的部件：`SimpleClairvoyantAI.gd` 有 `battlefield_scan` 和 `own_forces_scan` 的物理帧缓存，`AiCadence.gd` 会随电脑玩家数量降低控制器刷新频率；`GeneratedTerrain.gd` 有 AStarGrid2D、路径缓存和简化；`Movement.gd` 有逻辑路径请求预算和待重试状态。这些机制方向是对的，下一步不应继续盲目加一个更大的全局缓存或单纯把预算数字调大。

更值得补齐的是：

### P0：把副官决策改成“团队任务 + 状态回执”

- 先把己方单位按任务/编组维护稳定 Team，目标、队形、集结点和任务状态以 Team 为主；
- 单位报告 `moving / waiting_path / blocked / fighting / arrived / dead`，副官只在超时、状态变化、目标失效或编组明显停滞时重派；
- 正常移动时不能因为一次查询为空就给每个单位单独重新下令；
- 用命令接收、首次位移、到达、重派原因和路径等待时长做时序证据。

### P0：建立“路径请求调度器”，不要让每个单位直接抢 A*

- 将请求分为 `normal / attack / safe / formation / repair / escape / quick_check`；
- 每 physics tick 只允许固定总工作量，并为卡死脱离、快速可达检查保留小配额；
- 超预算的请求必须留在队列中，下一 tick 继续，不能在调用方同步阻塞；
- 同一 Team、同一地图版本、相同起点区域和目标区域的请求可共享区域路径/局部结果，但要在建筑变化或导航版本变化时失效；
- 记录 `queued → started → completed/deferred/cancelled`，将路径等待和计算耗时分开。

### P1：确定线程边界，再做多线程

可以迁移到 worker 的只有纯数据阶段：区域图查询、候选点评分、路径简化、队形槽位分配、目标排序。worker 只读带版本号的地图/单位快照，主线程提交结果时检查版本；SceneTree、Node、导航服务器、物理体和渲染对象继续在主线程提交。

先做单线程基线、再做 worker A/B：比较主线程帧时间、长帧、模拟速度、命令延迟和结果一致性，不能只看总 CPU 利用率。若没有可重复收益，就保留清晰的单线程预算调度。

### P1：把路径层拆成区域层与局部层

当前 `GeneratedTerrain` 的 AStarGrid2D 路径缓存是起点格到终点格级别；可逐步增加地图版本号、区域入口缓存和局部修补缓存。建筑增删只使受影响区域失效，不要清空整张地图的所有路径。AIRTS 现有路径网格和缓存已经是可演进基础，不建议立刻替换整个导航系统。

## 证据强度与限制

**直接证实**：到期更新流程、寻路模式分发、累计工作量与模式配额、Hierarchical/Normal 两种策略对象、处理器数 Job Manager worker、AI Schema 中的 Team/MicroManager/目标节奏字段。  
**工程解释**：RA3 通过“团队决策 + 分散 cadence + 有界寻路 + 持续执行”获得规模，这是由多个直接证据共同支持的架构解释。  
**尚未证实**：具体层级算法名称、每个路径函数的实际时间单位、寻路 Job 分支在当前发行配置中的开关值、AI 战略/微操是否进入 Job Manager、运行时真实线程占用和 RA3 在某硬件上的最大单位数。
