## 三、修改 1：补齐运行时决策追踪

### 目标

从某次分支选择出发，能一路查到任务、命令、回执、后续事实和最终去向；也能反向查询一个失败结果来自哪个目标和哪次尝试。相同 tick 的多轮、跨轮异步返回、重试及暂停都不能串错。

### 实施要求

1. 优先复用现有标识；不足时补充带版本的追踪合同。至少关联 session/run、round、node/span、goal、task/parent_task、attempt、plan_version、command、receipt 和 observation。ID 不能只由 tick 构造；任务身份保持连续，每次重试另有 attempt。异步请求从提交到返回／采纳／拒绝保留原关联，不按最近时间猜因果。
2. 记录实际节点 enter/exit/error、执行状态、选择的 edge、候选入口条件逐项值／结果／缺项、结构化 reason_code，以及短中文解释。区分可选、被排除、实际选择、实际执行和未到达。
3. 同时记录世界 tick／模拟时间与单调时钟耗时，注明各自用途；用完整轮次和序列号保持事件顺序。异常、超时、取消和玩家打断不能漏掉退出状态。
4. 结果证据引用真实权威观测或事件，明确是 owned-player 可知事实、回执还是世界结果。不得向模型输入全图敌情等越权调试信息。未采集字段写 unknown，禁止用空值、0 或邻近事件冒充已测事实。
5. 全量追踪保存到可流式读取的记录，不塞进模型每轮上下文。内存历史、重复事件及磁盘写入必须有明确限额／轮转策略；仅聚合重复轮询，不丢失状态变化、失败原因和关键证据。诊断写入异常需可见且不改变原任务结果。
6. 扩展现有时间回放：可按时间、任务或节点检查实际路径；至少区分成功、正常等待、失败／超时、受阻、未知。显示最后进展与等待时长、选边原因，点击可查看完整可观测输入／输出及原件。中文解释与原始结构化记录同时保留；不要要求或编造模型内部隐含推理。
7. 新旧日志用 schema/version 兼容。旧样本仍按旧证据能力显示，不能为旧样本补造 node span 或因果 ID；源码推导路径与实测路径保持区别。

### 验收

- 一条真实任务可完整关联「提交 → 返回 → 采纳或拒绝 → 命令 → 回执 → 实际结果」，未下发的任务也有明确终态或等待原因。
- 覆盖重复 tick、异步乱序返回／旧结果、重试、异常、玩家打断、重开对局和状态恢复，不产生跨任务／跨对局关联。
- 新日志回放中的高亮有对应事件；缺失数据明确标缺失。旧 2,078 轮仍能打开，旧证据不被改写。
- 记录开启追踪前后的轮次耗时、写入量及内存保留上限；不能引入每轮全历史扫描、无界缓存或阻塞游戏主线程的写入。

## 四、修改 2：把任务分支接成可执行闭环

### 目标

让程序根据实际事实判断成功／等待／失败／超时，并沿明确的边进入推进、诊断、恢复或受阻状态。模型的自然语言理由不能代替状态判定。

### 实施要求

1. 先列出现有状态、判据和调用关系，复用现有任务状态机；缺失语义以兼容方式补齐。建立一份权威的节点／转移合同，至少定义入口条件、成功判据、进展指标、无进展期限、总期限、失败／超时目的地、重试预算和退出条件。保留显示文案，但转移执行可测试的谓词和目标标识。
2. 程序循环必须包含：读取新事实 → 检查当前任务前提 → 选择可执行分支 → 建立／保持任务 → 合法性与资源检查 → 下发并记回执 → 用后续事实核验结果。
3. 对结果分别处理：有成功证据则关闭并推进；有真实进展且未到期限则保持；明确失败、超时或持续无进展则进入诊断；有合法替代方案则按预算恢复；无可执行方案或证据不足则 blocked/degraded，并保存缺项及重评条件。不要每轮直接重置计时器或重试预算。
4. `last_progress` 只由任务相关的实际变化更新。重复输出、计划保持、命令 Accepted 或重复回执本身不能刷新实际进展时间。建造进度、相关移动／载量／交货等使用任务类型对应的权威指标，避免无关活动掩盖停滞。
5. 期限使用明确的时钟：正常暂停和玩家接管不消耗游戏进展等待预算；模型网络超时可用单调墙钟单独处理。加载恢复、时钟重置或过期异步结果不能延长旧任务、重启失败循环或修改已结束任务。
6. 恢复必须重新核验前置条件、资源、权限和目标可达性。已证实失败的方案按原因、次数、冷却及条件变化限制；替代方案耗尽则明确受阻，不能无休止重试或直接绕过门禁。调度循环仍应能继续响应玩家、退出和清理。
7. 依赖结果的上层目标必须收到本任务的失败／恢复状态，避免底层失败却上层被当成成功。仅补本阶段所需反馈，不顺便展开全局战略重构。
8. 对活动任务和相关事实增量作判定，尽量复用本轮已有 facts；全历史留给回放，不增加模型上下文负担。配置化期限和预算，给出单位、取值依据和测试边界，不凭猜测硬编码「等 N 秒就算失败」。

### 验收

- 正常建造／采矿／移动中的真实进展不会被误判超时；到期且无进展、明确失败能分别沿 timeout/failure 边进入诊断。
- 多次重复输出或 Accepted 回执不能让停滞任务永远保活。
- 失败方案在预算内可恢复，耗尽后受阻；条件变化可重新评估，正常状态不会每轮重复恢复。
- 暂停／接管／退局／重开正常；断线或缺失观测按 unknown／证据不足处理，不虚报完成。
- 以新运行时日志生成实际分支图和时间表，能指出每个失败场景在哪里发生、为何选边、最终落在哪里；不能只用静态图和模拟 JSON 验收。

## 五、修改 3：修正经济恢复入口与里程碑

### 目标

经济链失败时能进入诊断与可执行恢复，不再必须先受袭或先损失工人；区分采集任务分配、经济链搭建和真实交货，防止提前推进阶段。

### 实施要求

1. 对当前经济链及其权威事件重新梳理，明确工人采集、矿场建造、矿车生产／部署、首次交货各自的事实来源和进展判据。核验当前玩法是否支持无需矿场的合法收入链，不能把某种建筑一概设为所有经济状态的前提。
2. 保留原有受袭后恢复能力，新增经过证据与时间窗判断的经济异常入口，例如关键经济任务失败、应当交货却长期没有交货且无实际进展、关键经济设施或执行单位损失。M01 已完成、工人不少、没有受袭不能单独阻止对这些异常的诊断。
3. 检查 D2 的阶段过滤、`has_worker`、主线节点晋升及其他候选检索路径，保证入口计算、候选列表、模型菜单、执行门禁和回放解释一致。不能仅把 `needs_recovery` 改为 true 而实际仍选不到／执行不了。
4. 区分「需要经济恢复」与「某条恢复动作现在可执行」。零工人、资金不足、无建造者、无可见资源或路径不可达时，应给出实际缺项及可行替代路线／受阻状态，不能为了开放 D2 而绕过资源、权限或单位前提，也不能把所有异常强制映射到同一动作。
5. 对 M01 及其消费者做语义审计：把「采集命令已分配／接受」与「经济循环已建立」分开。可以保留 M01 的原有分配语义并增加独立就绪判据，也可以有依据地修正定义；必须列明受影响的阶段推进、依赖和旧状态兼容，不能只改日志文字、随意改 ID 或放宽测试。
6. 命令接受只标 assigned/accepted；建筑成功要有完工观测，生产成功要有部署实体，经济运转要有相应权威交货／资源入账证据。若当前观测缺少必要字段，最小补充权威事件链；不要以余额净变化替代收入，余额可能同时受支出影响。
7. 长期健康状态可退化为异常：已有的首次交货或历史 done 不能永久屏蔽后续经济中断；保留历史完成事实，同时维护当前健康状态。恢复后及时解除异常，避免正常经济持续被拉回恢复分支。
8. 没有敌人的单人房也应能验证经济建立和故障恢复；首次建造／首次交货的正常等待不能因为初始交货为 0 就立刻判失败。门槛要结合游戏进度、任务状态、观测新鲜度和实际时间窗。

### 至少覆盖以下正反场景

| 场景 | 必须证明的结果 |
|---|---|
| 原案例：6 工人、M01 done、矿场失败、零交货 | 能进入经济异常诊断，显示可执行恢复分支或准确受阻原因，不再由旧两项条件永久屏蔽 |
| 从未受袭，但关键经济链失败 | 不依赖 under_attack_total 才能识别和评估恢复 |
| 正常开局，尚未第一次交货但持续有进展 | 合理等待，不误报无进展或循环重建 |
| 收入和支出同时发生，余额不变 | 按实际交货／入账证据判断，不能误判零收入 |
| 采集命令 Accepted，尚无交货 | 任务分配成立，不能据此证明经济链已建立 |
| 曾经交货，随后关键经济链中断 | 历史完成不被篡改，当前异常仍可触发恢复 |
| 受袭且工人不足 | 保留原恢复场景的正确行为 |
| 零工人／无建造者／资源不足／路径不可达 | 不生成非法动作；可行替代或明确受阻，失败可追踪 |
| 恢复后观察到实际交货和持续进展 | 异常解除，能退出恢复，不每轮重复下单 |
