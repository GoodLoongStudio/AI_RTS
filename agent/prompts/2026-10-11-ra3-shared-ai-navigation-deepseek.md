## 0. 最高优先级：优化不能以回归和更卡为代价

用户特别强调：这是性能和指挥效率优化，不能改完出现一堆 BUG 或比原来更卡。**先保住能玩的行为，再减少重复工作，再验证更复杂的分层/并行方案。** 下文列出的是需要评估和验证的机制，不是一次性重写导航、移动、AI 和网络的授权。

共用编组/反馈/调度合同必须覆盖副官和电脑；具体实现优先复用。区域层、缓存和 worker 要逐项用 AIRTS 的热点证据决定是否新增。没有收益或安全门禁失败的方案应拒绝，不能为了“都移植了”强行启用。必须完成评估和可行候选验证，不能只写“以后再做”；否证的机制如实标 `rejected-with-evidence`，不冒充已实现或已达性能目标。

### 0.1 先锁定基线，不拿 Git HEAD 当可玩版本

S0 先记录当前源码、相关未提交改动、配置、C# DLL、模型/引擎身份和可重放命令。champion 是**实际验证过的工作树状态**，不是默认 HEAD，也不是旧截图或旧打包版。涉及修改的文件保存原始字节与 hash；共享工作区撤销前再次比对，发现他人写入时不得用整文件覆盖。

基线有旧 BUG 时单独列出，不能宣布全局基线健康。待测旧链路至少有一条已通过的轨迹；旧 BUG 影响测量可靠性就先处理验证入口或最小前置问题，不顺便重写多个系统。基线与候选测试期间源码/DLL 被改，则该组数据无效，重新测量。

在自己的 `agent/runs/<run-id>/acceptance-contract.md` 写下数值合同再编辑：每档负载的帧时间/长帧、命令响应、队列最大年龄、模拟速度、到达/卡住、经济/战斗、内存与退出时限。字段不得留空或事后放宽。合同说明阈值来自既有玩法、目标帧预算还是重复测量波动，不能编一个无法验证的保证。

先把 AI 决策/查询、路径计算、局部避让/RVO、模型等待及渲染分桶。减少求路不代表解决 RVO 或物理追帧热点；记录目标成本占比与可重叠时间，估算该项优化对整局的收益上限。共用合同可以渐进补齐，但不能为一个低占比热点引入全系统替换，或把 RA3 机制当 1000@30 的保证。

### 0.2 逐步启用，始终只有一条权威执行链

沿既有 FeatureFlags/配置方式为高风险新后端保留可测试的回退；以每个 Match 的配置选择实现，禁止未验证就更改所有用户的默认行为。最小启用顺序为：旧后端基线 -> 独立纯数据对照 -> 小规模电脑 -> 小规模副官 -> 两者共存 -> 玩家受影响导航 -> 压力/长局/联机。每个范围经过门禁后再扩大，最终被接受的共用机制要覆盖两个 AI。

纯数据对照可复算一小批请求，但影子实现不得下命令、扣资源、改变队伍/位置或额外调用模型。**生产帧和正式性能样本不同时跑新旧两套重搜索。** 测试对照的开销、诊断日志、录像和 profiler 开销单独注明；详细插桩默认关闭或有界采样，不逐单位逐帧打印。

失败时先在本轮测试实例选择最后通过的实现，拒绝候选；需要撤补丁就精确撤自己的内容，不恢复整个工程到旧提交。验证开关关闭后的旧行为，以及“入队 -> 切换/取消 -> 旧结果晚到”不会重复执行。默认不在活跃玩家对局热换后端；先取消旧代际、隔离结果再重新开始测试。回退路径同样有队列/工作预算，不能超时后每单位立刻同步重算全图，引起更大的尖峰。

### 0.3 阶段晋级必须同时通过四道门禁

| 门禁 | 判据 | 失败处理 |
|---|---|---|
| 正确性 | 无新增解析/崩溃、非法路径/穿行、权限泄露、重复执行、玩家接管被抢回、僵尸房；受影响正反断言和旧链路通过 | 任一出现即拒绝，不能用 FPS 抵消 |
| 性能 | 同条件至少 3 组配对 A/B 或 A-B-A，收益超过基线波动；小规模及目标负载同时测总成本与 p95/p99/长帧 | p95/p99 可重复退化超过 5% 直接拒绝；波动大于 5% 先稳定环境/补样本，不放宽成退化许可；5% 是工程门禁，不是实测结论 |
| 响应与玩法 | 命令/路径最大等待有上限，队列能排空；模拟速度、到达/卡住、探索、采矿交付、生产和伤害满足 S0 合同 | 禁止少下命令、少活动、减少产兵或让模拟落后来刷 FPS |
| 长时与清理 | 正常负载至少 15 分钟模拟且不少于 5 分钟墙钟，另验证退局重开 3 次；任务/缓存容量有上限，无持续累积及迟到写回 | 超时/错误即停止并保留证据；只清理本轮进程 |

每个小补丁先做短无头真实 Match 和相关回归；长时门禁用于共享后端/线程候选默认启用前和最终晋级，不要求每个日志补丁跑全矩阵。先 50/100 再 300/1000，某档严重超时就停止扩容，保留该档实测，不靠无限等待完成表格。

已达玩法预算的场景不能因优化重新越界；退化未超过 5% 也不是自动接受，仍须满足无可重复响应/玩法退化与整局净收益。基线已经远超预算的压力档可以凭净改善晋级局部候选，但继续标目标未达，不能阻止必要的小步改进，也不能把门禁改为更低规模。

整体功能优化至少有用户能受益的证据：例如持续探索不再长等、相同负载尾帧下降或容量提高。只有接口/内核提取的中间补丁可按“功能等价准备工作”保留，但必须无可重复性能退化，不计性能成果，不借此扩大重构。

对照分两层：固定合法命令回放验证执行/导航输出；正常决策轨迹验证两种 AI 的实际效果。相同权威裁决输入的资源、伤害、权限结果应一致，浮点/路径/耗时容差先锁定；不同合法路径和决策可能改变交战时序，正常 AI 的进攻选择也可能不同，不能要求两局随机战斗逐帧相等，也不能只看胜负便说无回归。

## 4. 持久编组、任务反馈和到期调度

### 4.1 持久编组和任务

将现有编组生命周期收敛到权威来源，两个 AI 用薄适配器消费同一合同，避免 Python、GDScript 和 C# 各保存互相矛盾的权威状态。不要仅把每个单位包装成单人 Team 来凑接入率。

至少有等价于这些含义的字段：`match_id/player_id/team_id`、成员稳定 ID、成员/控制代际、任务 ID、目标、移动能力、路线版本、阶段和进展。不强制新增重复字段；现有字段可复用。

任务反馈区分 `queued/waiting_path/moving/engaging/arrived/blocked/failed/cancelled`；死亡是成员生命周期，正常战斗、采矿、等待施工/生产、玩家接管分别有原因。`Accepted` 只表示权威受理，不表示到达或任务完成；未返回状态不能直接当空闲或失败。

队伍中死一个单位不重建整队，不按每轮枚举顺序更换 team_id；增援、拆队、撤退和手动接管必须可解释。空中、地面、两栖及不同净空/速度兼容性分开；共享目标不意味着全体使用同一物理路线。

### 4.2 不反复短程重派，不长期等待模型

副官发出长期目标后，程序持续执行安全任务和必要的局部路段，模型选择与下层执行分离。不能等下次 Laya/战略输出才推进健康任务。保留现有安全中继、连续可见前缀和威胁判断；连续推进靠合法路段衔接、及时反馈、预取与有效路线复用，不靠删门禁、拉长未知区域跳跃或给隐藏敌情。

主力与无人机侦察分开：无人机仍承担正常探图；不能为减少模型/调度负担让一个兵走一点等几十秒。任务进度用沿路进展、剩余路径、队伍成员分布和新增覆盖衡量，绕障碍时直线距离暂时变大不能误报卡死。正常移动/战斗不重派；路径失效、真正停滞、目标失效或重大事件才重规划。

玩家手动命令即时提高控制代际，取消旧路径工作/结果；两个 AI 都不得用迟到结果抢回控制。模型超时不释放仍在推理的工作槽，也不启动第二份模型强行并发；已有有效任务继续，缺少新意图的单位通过现有合法回退处理。

### 4.3 到期调度和公平性

按模拟 tick 安排到期，确定性地错开玩家、Controller 和 Team 的相位；合并同任务重复事件，有界优先级加老化/轮转，避免普通任务被紧急事件永久挤掉。

保持当前难度、生产、出击、侦察和 AiCadence 语义，不用延长决策周期或降低活动单位数获得 FPS。优化“同一拍重复计算”和“很多拍集中在同一帧”。事件触发补足基地遇袭、目标失效与受阻的响应，但不能变成每单位每帧全场扫描。

到期/闲置/路径年龄按对局模拟时间；网络请求超时、进程 watchdog 和推理退避仍用可靠的单调墙钟。暂停期间不把部队判卡死，IO 也不能因游戏暂停永久失去超时能力。

## 5. 共用寻路队列、分层路线和复用

### 5.1 统一调度

先登记全部求路入口：副官导航查询、电脑可达性与移动、真人命令、Movement 重算、HUD 路线显示。诊断重复求路后接入同一生产导航后端；HUD 可消费已有结果，不触发第二套权威求路。

请求包含来源、身份、稳定 request/command/team/member ID、目标和控制代际、地图/导航版本、移动域/能力与净空类别、优先级、排队模拟 tick、搜索模式。模式可先合并等价类别，不为复刻 RA3 写空壳算法；普通、攻击至合法射程、修补/脱困、快速可达/成本查询的语义至少明确。

全 Match 只有一份总计算额度与明确子配额；有界队列、去重、取消、过期清理、拥塞原因和公平老化。副官、电脑和真人不能各自偷偷绕过预算。紧急配额也有上限，正常队列必须可持续服务；真人新指令及时使旧任务失效。

队列满时按既有回执合同明确返回可恢复等待/拒绝及原因，已受理的命令不得静默丢失；同代际的新目标可合并/取消旧请求，但不能误删不同成员或不同玩家的有效任务。队列繁忙不等于不可达、不等于单位空闲；上层不得因此每 tick 重派更多请求。

**预算要能限制实际工作，不只是每帧允许 N 次调用。** 多个路径请求成本不同，调用一次同步 `AStarGrid2D.get_id_path` 仍可能产生长帧。记录查询数、扩展工作量（能取得时）、单查询耗时、排队时长和最长等待，采用可暂停搜索切片或经验证的有界后台批次。同步引擎调用不能伪装成已可暂停；后台完成前保持既有有效路径/合法等待，不阻塞主线程。

### 5.2 区域层与局部层

先证明全图搜索/重复局部细化是剩余热点，再在现有网格基础上试验区域连通/出入口走廊，局部细化到实际航点。区域尺寸由当前 512×512 地图、格距、实体净空和实测确定，不照搬 RA3 的 16 格。若少量直达检查和现有缓存已满足预算，保留它们并记录区域层为何暂不新增。

同域、同能力/净空、同有效起止区域的队伍可复用区域走廊；每个单位仍有自己的起点接入、最终阵位、局部避让及精确阻挡。不能直接把第一辆坦克的航点数组复制给全军。攻击路线必须到合法射程/目标可达区，不能走进目标模型中心。

保留已验证的直达检查、现有 A* 和路径简化作为基础或有界回退。优先使用现有/成熟搜索实现；确需切片化时只抽取搜索内核，并用旧求路器/独立参照核验可达性、净空和路径结果，不同时重写移动、物理和网络。区域路线失败不等于整个目标不可达；小样本与完整搜索参照检查漏路、错误拒绝和绕路倍率。参照复算仅用于独立验证，不让每次生产寻路又额外执行完整 A*。

### 5.3 版本、失效和局部修补

缓存 key 至少覆盖实际影响路径的地图身份、障碍版本、移动域、能力/净空、搜索语义和目标约束。区域图、区域走廊与逐单位局部路径分开，不能只用起终点坐标。

建筑放置、完工/拆除、通路封闭、死亡障碍变化时更新受影响区域与连接依赖；复用跨区走廊要验证所有依赖。旧任务结果在提交前复核，不能因为计算时路线合法便穿过后来建的建筑。无法证明局部失效范围正确时先保留安全的全局失效，再渐进优化，不能错误命中缓存。

阻塞时先判断临时队列/友军交通与永久障碍，能修补局部段就修补，目标/拓扑失效再全局重算。连续失败有界退避并返回原因；不可达不无限重试，不反复瞬移/抖动。保留现有碰撞、转向、受限窄口与出生合同，不扩大穿模权限换到达率。

## 6. 多线程必须落到可测的计算阶段

必须认真评估多线程，但不能以开线程为目标。先区分主线程执行、锁/worker 等待、渲染/帧限制等待；核验引擎 RVO/导航已有线程设置。若瓶颈是已有 worker 的等待或线程竞争，再开线程可能更慢，应先定位调用栈和依赖。只有存在可并行的实测纯数据热点，才小范围提取内核、验证等价并做同步/worker A/B；不适合或无净收益时保留预算内同步实现，记录证据和剩余热点。未评估、未验证不得写成“多线程完成”。

worker 可做区域/网格搜索、候选评分、队形槽位分配、威胁汇总和路径简化，输入必须是已经合法过滤、深度不可变的纯数据快照；不要把 Node、Godot Dictionary、共享 AStarGrid2D、SceneTree、骨骼、导航服务器、物理或渲染对象直接交给线程。快照采集、合法性裁决、命令与变换写回在主线程。

关键规则：

1. 统一后台活跃计算额度，按批次建任务，不每玩家/每单位/每帧开 Task 或线程。先单 worker，再对比 2 个；依据拓扑/画像调整，24 逻辑线程不等于 24 物理核心。
2. 主线程不调用阻塞式 `.Wait/.Result/join` 等后台结果；按帧收完成队列，仍受主线程提交额度限制。线程数量、等待和结果转换都计入总成本。
3. 带 `match_epoch/request_id/order_generation/nav_revision` 或现有等价字段。地图改变、Stop、玩家接管、队员死亡、换局立即使旧结果失效；旧回调绝不能写新 Match。
4. 不机械要求所有结果的 snapshot_id 等于当前帧，否则持续移动时会全部过期。按任务真正依赖的版本验证，动态安全在主线程重查；必要时受控重排，不能永远重算。
5. 稳定 tie-break 和权威提交次序，线程结果不能按抢先完成顺序任意改变资源/命令仲裁。提交 tick 和导航待完成语义要可记录回放；支持的联机模式不能新增跨机器计算差异导致分歧。
6. Python 线程主要用于 IO/推理调度，不假定 GIL 下纯 Python 搜索可多核提速。保留现有异步模型池，不另开模型实例，不把 Godot 调用移入 Python worker。
7. 保留线程关闭开关，用同一个纯计算内核回退。换局按本轮任务所有权取消/排空，维护有界内存；不可取消的长任务不能变成隐藏泄漏或退出卡死。
8. 默认保留 OS 调度；有主线程竞争证据再试进程内 CPU 集合。不得永久绑定共享 .NET 池、修改全局池上限/系统电源计划，或更改用户模型服务的全局配置。
9. 改成同一批快照前先核验数据依赖：原循环的后项若读取前项已提交的状态，统一快照会改变算法。恢复提交顺序并不能恢复这些依赖；保留串行段或单独证明分阶段等价，不并行顺序推出/仲裁等有依赖的写操作。
10. 同时限制排队请求数、活跃任务数、单批大小、未消费结果和快照/缓存字节；消费者慢时实行背压并返回明确等待状态。取消无效任务不代表内存可立即释放，worker 退出前不得复用其输入/输出缓冲区。主线程提交批次也有额度，避免一次完成洪峰卡住一帧。
11. 先查实际联机模型。主机权威下只让权威端选择/提交结果，客户端不能各自重新裁决；确定性锁步下不能由各机的 worker 就绪墙钟决定提交 tick。稳定排序只解决顺序，不解决提交时刻差异；未证明确定性计算/提交协议前，该模式保留旧确定性后端。两端状态摘要、重放和迟到结果测试未过不得默认启用。

真实副官模型与引擎可能争用 GPU、PyTorch/BLAS 内部线程和日志 IO。分开记录 GPU 推理、模型/传输等待、Godot 主线程与 worker；不把模型已关闭的成绩当共存收益。优先复用已有隔离运行方法，不结束用户实例，不自动训练/下载/替换模型或使用收费外部服务做压测。

## 7. 必须按顺序实施的阶段

S0：当前入口与基线。证明三种命令来源，识别重复求路/查询、帧尖峰、排队和模型等待；定义测量口径、响应/行为预算及 champion。先列热点排序、成本证据、保护项和本轮唯一候选，写完整 acceptance-contract；不预先假定瓶颈必在 A* 或必须新建某种架构。

S1：共用持久编组、任务反馈与到期/事件调度。两个 AI 均接入；正常推进行为、玩家接管、模型超时及旧任务继续执行通过。现有成熟部件经证明满足合同可直接计为复用，不再重写。

S2：共用公平路径队列、分类配额、去重/取消与连续执行。接入三种来源，不能排好队后又在 Movement/副官检查/HUD 绕行搜索。证明不会永久饿死或队列越跑越长。

S3：评估并按热点试验区域走廊、局部细化/修补、依赖失效与安全复用。先验证同步内核，队伍共用规划工作，单位保持各自最终阵位与安全；新增建筑、窄口、混合能力及不可达均通过。无收益或失败则拒绝该候选，不能把所有玩法强制迁到它。

S4：有合适热点时实施同算法纯数据 worker 接入与线程 A/B，包含副官真实模型共存、长局和联机权威回归。无收益/不适合以证据拒绝，不能“线程已创建”或“已考虑”便结束。保留此前通过的优化，线程候选失败不意味着全工程回到任务起点。

S5：全量/独立复核、对局清理、玩法验收与长期规范。仅将已验证的共用合同、线程边界和失败教训提炼到现有相关 skills；暂未实测的优化写 candidate，不能写成普遍有效。

每阶段更新同一计划，内部一轮一个假设/一个关键补丁。**静态通过后立即新开独立无头真实 Match**：至少受影响正反行为 + 一条旧链路，失败只撤本轮精确补丁，不能在坏候选上继续堆。必要的相关套件通过才能推进；最终独立复核和全量未闭合时整体只能 needs-review。

第一次实施报告必须先交付 S0 证据与第一个小候选结果，不能等一次大改后才报告。后续按闸门自主推进，不在日常可逆开发中反复请求批准；没有通过上一门禁就不能进入下一编辑项。

## 8. 双入口验收和性能矩阵

不要把所有组合盲目相乘。先小样本固定种子/命令，逐阶段扩大。最低代表性覆盖：

- 正常 1 AI、3 AI 的采矿、建造、生产、侦察、防守与持续交战，保留现有难度/出兵节奏；
- 副官真实正常模型、模型迟到/超时/无效、降级回退；真实模型需证明有实际推理/合法命令，不以加载成功替代；
- 真人框选/移动/Stop/改目标/接管；命令级与 UI-player 分别标注；
- 50、100、300 单位代表负载，逐步到 1000 单位混合压力（通过合法夹具构造真实实体和正常命令，测试扩容不进入普通玩法）；目标保持 1000 单位 @30 FPS，不能自作主张下调成小规模完成；未达到要报告当前容量、热点与剩余阶段，不能凭 RA3 研究承诺达标；
- 两队交叉、窄桥/窄口、基地出口、U 形障碍、混合速度/半径、空地分队、目标消失、建筑动态封路/拆除、导航版本改变；
- 退局重开、暂停恢复、runner 断线重连、旧结果晚到；支持的联机权威与两个客户端观察；
- 至少一次固定 3AI + 正常副官的长局样本，覆盖经济发展和持续作战；记录实际墙钟与模拟时间，不能只截开局几十秒。使用正常负载，不靠超高推理频率造压力。

每项以实施前锁定的预算评分：frame/主线程 p50/p95/p99/max、长帧、模拟秒/墙钟秒、physics ticks/frame、命令到首次位移 p95、到达/失败率、路径排队 p95/最大等待、队列峰值/年龄、查询/展开/缓存命中、后台 CPU/等待、采矿交付/产兵/伤害、新视野和重复重派，以及内存/连接/任务清理。

比较同地图、种子、相机、画质、物理频率、单位组成、模型/device、日志和 VSync/FPS 条件；收益至少重复 3 次超过噪声。不要过滤 >500ms 的帧，不将 process/physics/nav 重叠计时直接相加，不把 headless/fixed-FPS 当渲染 FPS。分阶段保留普通可渲染样本，并测不录制的性能成绩；5 FPS 视频用于动态行为证据。

不能只给“AI 桶减少 40%”就声称用户游戏流畅。必须看到整局尾帧/容量的真实收益，副官响应、队列年龄、命令延迟、经济/战斗结果没有越界退化。

以下故障必须主动注入并验证，不依赖正常场景恰好碰见：worker 返回前 Stop/改目标/玩家接管；旧 Match 结果在新局晚到；单位死亡或换队；建筑封路且路径缓存正好命中；队列满/结果队列积压；worker 异常/慢任务/取消；模型长期不返回；低核或限制本轮 worker 数时的回退。断言明确包括“旧结果没有写入”“没有多执行一次”“等待有结束条件”，不是只检查日志有 cancel 字样。

相关套件从当前 `config/full_regression_suite.json` 选择：rule-ai-*、world-query-runtime、adjutant-*、navigation-stability、local-avoidance、movement-recovery、生产/建造/采矿/换局，加 `tests/core` 和 `source/adjutant_coordinator/tests` 对应合同。新增测试要验证交错/迟到/取消/权限等行为，不能只镜像实现。

判绿必须 `rc=0 + 正确 marker + forbidden output 为空 + 无超时/崩溃 + 新鲜产物`。基线红项同场景对照归因，不放宽断言，不笼统称无关。关键性能采样串行或明确隔离，不能用几个压力局互相抢 CPU 的结果评分。

## 9. 用户操作电脑和测试的边界

辅助进程从启动时隐藏控制台并重定向日志；不要弹 CMD、抢前台、置顶、移动系统鼠标或注入全局键盘。默认无头逻辑复验；必要的可渲染性能/短动态复验使用本轮拥有的后台非激活实例和指定窗口录像，后台不支持输入就标未验证。

用户此前明确完整试玩由其亲自进行；不要擅自长时间接管电脑做自动“玩家审计”。给用户阶段试玩轨迹与要看的现象；自动化关键逻辑回归仍须完成。不得因用户聊天/切窗口而把测试输入问题报成游戏故障。

每局记录 PID/端口/Match 身份、模块/hash、开始结束/mtime、真实实体数、命令和结果、watchdog、cleanup_ok。只结束本轮拥有的进程，不能按 godot/python/ollama 名称批杀，也不能关闭用户游戏/副官。

## 10. 交付物与不能偷换的完成标准

更新关联计划，在 `agent/runs/<自己的 run-id>/` 保留 baseline、checklist、champion、每轮 patch/verification、原始 JSON/日志/视频；分阶段报告写 `agent/reports/closed-loop/<run-id>-stage-N.md`，最终报告链接全部阶段。

最终必须有“机制 × 副官 × 电脑 × 真人受影响导航”的接入表，包含真实入口、配置、实测与未闭合项。表中要能回答：持久编组是谁维护，任务完成谁确认，到期节奏在哪里，谁消费路径队列，谁共享区域走廊，哪些任务在 worker，旧结果谁拒绝，换局谁清理。每项标 `reused-verified / implemented-verified / rejected-with-evidence / unverified`；只有前两项是完成接入。默认开启的实现必须与门禁通过的配置一致，不能只证明开关关闭时绿。

**仅接入一个 AI、另一个只写 TODO；线程只开不使用；模型关掉才顺畅；队列预算只限制调用次数但同步大搜索仍卡帧；部队少活动/减少产兵；缩碰撞、关迷雾、减物理 tick、改速度/视野或降画质，都不算完成。**

完成标准是两个 AI 共用的实际行为与经验证的整局优化，拒绝无益的复杂方案是正确决策；这不代表未测项已完成，也不代表 1000@30 已达标。最终报告必须给保留实现、拒绝理由、开关/回退验证和新增 BUG 清单（没有发现也说明验证范围）。若任何新增回归、可重复更卡或联机未通过，保持最后已验证配置，整体标 needs-review，不能默认启用坏候选。

开始执行 S0，确认现有实现后逐阶段实施。报告进展时给具体已接入入口、旧新指标和下一道门禁；不以建议再开一个任务代替当前阶段必要工作。
