# 电脑玩家与整局CPU协作优化：三阶段验收计划

日期：2026-10-11（北京时间）。状态：规划完成，产品未实施，性能收益未实测。

本任务以对手电脑玩家的规则 AI 为优化入口，覆盖经济、建设、生产、侦察、防御和进攻，同时纳入它与导航/物理、渲染提交、AI副官的CPU资源协作。用户最终目标是整局更流畅，降低卡顿并保持模拟和指挥响应；电脑AI耗时降低是分项证据。副官的模型、聊天和战略逻辑保持当前合同，本轮可评估自己测试进程的线程/CPU预算，不能修改用户配置、重写副官或整套移动系统。

## 1. 线程结论

推荐 **主线程采集和执行 + C# 有界后台决策执行器**。每局所有电脑玩家共享执行器，首版只允许 **1 个正在执行的决策任务**；后期有实测依据时再比较 2 个并发任务。这里的 1 是并发计算上限，不承诺固定到某一个 CPU 核，也不要求每个电脑玩家创建专属线程。

后台任务使用 .NET 托管执行器，纯 C# 计算便于测试和避免 GDScript/C# 反复转换。普通线程优先级；不擅自开高优先级或按逻辑核心数开满。若机器已有适用的共享执行器，先复用，不另造第二套调度系统。Godot WorkerThreadPool 作为实施时可比较的替代，不能同时维护两套 AI 池；本计划默认 C# 受控执行器。

```text
主线程：合法观察数据 + 难度配置 + AI状态 + 既有模拟时间
                     ↓ 不可变、无节点引用的数据包
后台执行器：统计/评分/选择/生成计划 → 返回命令意图与候选状态
                     ↓ 有界结果邮箱，不调用场景节点
主线程：校验当前权限/资源/订单/生命周期 → 原有命令入口执行 → 回执
```

| 工作 | 所在线程 | 原因 |
|---|---|---|
| SceneTree、Node、Timer、信号、变换、骨骼、资源实例操作 | 主线程 | 当前实现有场景依赖，不能直接搬运 |
| 查询会话授权、从真实节点采集观察、情报记忆更新 | 主线程，先维持现有边界 | 当前查询服务并非线程安全的纯函数 |
| 已获准观察数据中的数量统计、兵种需求、工人分配候选、威胁/目标评分、巡逻点排序、计划选择 | C# 后台执行器 | 可转换为独立纯数据运算；逐模块移植并验证 |
| 资源扣款、真实建造放置检查、生产入队、Gather/Move/Attack/Construct 等命令 | 主线程原有 Gateway/Runtime | 保留权威校验、碰撞/导航合法性及顺序 |
| 实际寻路、RVO、物理、伤害结算、渲染、网络权威同步 | 现有系统 | 此次没有证据支持迁移这些系统 |

**把计算移到后台只能降低主线程阻塞，未必减少总 CPU。** 重复查询、全场扫描、对象分配与桥接转换也要减少；快照采集、索引维护、排队、校验提交、GC 全部算账。

### 1.1 CPU核心与线程预算：整局统筹

本机只读核验为 **AMD Ryzen 9 5900X，12物理核、24逻辑处理器**。24个逻辑处理器包含SMT资源共享，不是24个独立物理核。执行AI重新核验本机拓扑，用Windows拓扑接口或已有工具取得物理核/SMT兄弟、缓存分组与CPU集合；不假定编号0/1必为某个物理核，也不把固定CPU编号写进发布代码。

先建立全对局线程画像，区分线程存在、实际CPU计算、等待模型/网络、等待引擎同步和GPU/present等待；一个副官HTTP调用线程在等待时不等于占用一核。源码已有副官 `adjutant-sched` 1个池worker、`adjutant-llm` 最多2个池worker及单Agent在途纪律，但BLAS/PyTorch/tokenizer/Ollama内部线程数仍要运行时核验。C#、Godot、Python模型库各自建池可能叠加，不能只给电脑池定上限就宣布核心分配完成。

| 角色 | 初始分配/预算 | 本轮处理 |
|---|---|---|
| 游戏主线程：观察、AI提交、SceneTree、权威模拟 | 保持主线程1个，确保延迟敏感工作有CPU余量 | 减少重复采集/转换和提交尖峰；计量自身CPU与等待，不把Node搬到worker |
| 引擎渲染、物理、导航/RVO worker | 先保留实际默认值，核查共享Godot池和线程优先级 | 测实际并发及主线程同步等待；若成为热点，只对引擎确实支持的线程参数做独立新进程A/B |
| 电脑纯决策计算 | 每局共用1个活跃计算额度；有收益才比较2个 | 普通优先级、有界输入/结果、公平调度；不按玩家/单位开线程，不占GPU推理 |
| 副官Python调度和模型调用 | 保留已有1个调度worker、最多2个调用worker和单Agent在途 | 将实际CPU计算与I/O/GPU等待分开，不把两个角色串行化造成战略阻塞战术 |
| 副官GPU路径的CPU预处理/数学库内部并行 | 先测实际线程及device；只有发生CPU争用时比较1/2个CPU计算线程的候选预算 | 仅在本轮拥有的进程使用受支持的运行参数，保持模型、请求和行为；若回退CPU后延迟恶化则拒绝限制 |
| GPU推理与渲染 | 保留既有在途上限与模型 | 不新增GPU电脑模型，单列显存/带宽和GPU提交等待 |
| 录制/编码、构建、回归、日志整理 | 正式性能采样期间不运行这些本轮辅助工作 | 视频局与性能局分开；给系统、音频、网络和用户其他软件留余量 |

这是待验证的并发预算，不是已将某项绑定到某个物理核心。阶段一先优化已有重复工作与已证实的线程争用；电脑后台迁移仍按后续阶段协议进行。若主要瓶颈是移动/导航而非电脑决策，重新把本轮候选指向对应最小热点或受支持的调度参数，并按原移动合同复验；不要一晚持续改占比很小的电脑计算，也不要无证据扩成整套移动重写。

**核心亲和性单独验证。** 基线为操作系统默认调度；只有线程画像显示后台争抢关键路径，才比较本轮进程的软CPU集合或确属自己的专用线程亲和性。按物理核/SMT和缓存分组生成候选，避免让延迟敏感线程与高负载后台线程共用同一物理核的SMT资源；不硬绑用户进程，不修改系统电源计划。只限制后台线程不代表主线程自动获得专用核心，需在trace里确认效果；.NET公共池线程不得永久设亲和性，也不能修改全局ThreadPool上限影响其他任务。

每轮只改变一种预算或CPU集合，记录默认值、实际值、API支持与恢复方式。默认调度对比受限集合、单并发对比双并发，分别在同场景新进程测量；不能一次同时改核心绑定、线程数、优先级和算法。所有新线程普通优先级；既有导航高优先级是否保留由原始基线及单项实验决定，不一刀切修改所有线程。调度方案支持不同CPU和无法控制时的默认调度回退。

线程画像优先使用本机已有WPR/WPA或等价工具（已只读确认可执行文件存在，未启动trace；工具可执行不等于采样/分析已经成功）。记录主线程、引擎worker、电脑、副官CPU与GPU等待的CPU时间、队列、上下文切换/就绪等待及可得的核心归属。缺失字段写unavailable；不靠整机总占用或温度猜。线程采样自身成本单独测量，正式成绩补无trace样本；只管理本轮会话，不结束他人的采样。

**整局收益为主验收。** 在真实3AI发展/持续交战且副官正常工作时，至少有一个锁定指标（frame p95/p99、超预算长帧率或正常模拟下的容量）可重复改善且超过噪声，同时模拟速度、命令延迟、其他尾帧与副官响应无越界回退。先写baseline和预算再评分；若只有AI分项CPU减少、整局表现尚无变化，报告“局部收益”，不能称用户要求的整局优化已通过。维持1AI小场景与生产VSync/FPS上限复验，不用降低玩法或画质取得成绩。

### 2.1 大部队移动：保守优化优先，鸟群为可选研究

用户最新要求采用保守路线：鸟群（Boids）不一定比现有导航/RVO更好，不是本晚必做或必交付项。阶段一优先在现有算法上减少实测重复查询/转换、路径请求、邻居计算和分配，处理经证明的CPU争用，维持既有指挥与移动行为。取得整局可重复收益即可采用保守候选，不要求加入新算法。

只有群体协调/拥堵被重复测量证实为主要瓶颈、保守候选收益不足且尚有复验时间时，才考虑默认关闭的小规模原型。先50单位同步小样，每次一项，出现安全/订单/到达回归立即拒绝；无收益最多两轮便换回保守热点，不整晚调鸟群权重。不尝试/不采用都可如实交付。完整实验合同见 [整合提示词](G:/AIRTS/AI_RTS/agent/prompts/2026-10-11-match-performance-overnight-integrated.md) 的“可选鸟群研究”节，下文架构仅在选中这个方向时适用。

静态发现：Movement继承NavigationAgent3D并保留RVO/静态精确推出/地表/恢复；FLOW_OFF默认关闭的实验已有邻居空间网格及让行/车道偏置。这不是成熟Boids或全局导航流场；现有网格存有Node引用不能搬到后台。真人由UnitMovementUtils先算逐单位终点并分批提交，C#批量移动会分配环形阵位，电脑通过Gateway接入移动端口；三者组信息和终点合同须追踪，不假定完全等价。

可选原型架构为“原合法命令/阵位 → 兼容的群体路线或走廊 → 轻量分离/对齐/聚合steering → 既有RVO与静态碰撞/到达”。对齐/聚合限同组兼容友军，在墙体/窄口/接近目标时弱化；地面/空中、不同能力/净空分开。路径/索引复用优先同输出的小改动，完整流场与群体架构不作为本晚默认实施。候选必须按导航版本、可达区域、能力和净空合法复用；不取消逐单位安全、不缩半径、不吞掉新指令/攻击/采矿。群体轨迹可变，目的地/最终阵位/碰撞/订单等既有合同不变，新增行为有独立正反门禁。

空间索引减少平均扫描但密集格仍可能接近O(N²)；软队形可有界采样，安全候选不能盲截断。先同步纯数据验证，再按CPU预算批处理；高频移动与低频AI决策不能互相饿死，不每单位开任务，也不新增GPU负担。主线程实时安全检查与权威落地保留。

按50/100/200、容量允许再400逐档，覆盖三种真实命令来源、逆向交叉/窄桥/建筑出口/U形障碍、混合尺寸速度、连续改目标/停止、攻击撤退/采矿/出生、动态障碍/死亡/暂停/换局和联机权威。计量整局尾帧、移动CPU/邻居和路径次数、命令峰值、到达/卡住/碰撞/订单、副官响应，配5 FPS实战回看与必要短事件数据。没有测量不能称鸟群更快，不在一刀里混合改导航、鸟群、线程和RVO。

## 3. 三个验收阶段

阶段内部允许多轮迭代，不把一次插桩、一次移函数或一次编译当作独立交付。先发阶段一提示词；阶段验收后再进入下一阶段。

### 本轮执行安排：整晚多局迭代

用户补充要求：执行AI可以用一整晚反复开对局、迭代优化，以5 FPS录像判断游戏过程。本次提示词仍执行阶段一，但不以做出一个候选或跑通一局作为停止条件。默认按约6–8小时有效工作预算组织，执行时记录实际开始时间与预计截止；用户另给截止时间则以其为准。最后60–90分钟留给最终版本复测、回归、录像审阅与交付，不在最后几分钟加入新优化。

一个候选通过后，在已验证版本上重新测量，再选下一项值得减少的重复工作；一个方向连续三轮无提升就换方向，不把此规则理解成整晚任务自动结束。每个逻辑补丁仍单独开全新Match验证，拒绝失败候选，不批量改完才测试。范围内已无有价值的候选时补齐跨地图、难度、长时及生命周期覆盖，避免为了耗满时间制造改动。

对局以顺序多次开局为主。性能A/B期间仅一个测量实例，不能同时跑多个对局、构建或回归污染数据；不抢用户前台。建议整晚形成12–20局有效的新Match记录，包括短逻辑验证、性能复测与可见实战；实际数量由候选与测量矩阵决定，局数不是成功判据。至少安排1AI/3AI的初始基线与最终版本共4场正常可见对局，各有不少于10分钟有效过程，其中最终版本至少一场延长到30分钟或自然结束；早结束时补足另一场长时稳定性检查。失败、异常和工具阻塞也保留记录，不凑数。

可见实战采用5 FPS连续分段录像（每段60–120秒），配合低开销1–2Hz状态采样和动作/事件时间轴，记录采矿、建造、产兵、侦察、交战、回防、暂停与退局。长时段先粗览，开局、命令、停滞、交战和生命周期关键区间按0.2秒逐帧实际回看；输出视频秒数与对应状态。5 FPS观察玩法过程，不用于证明短于200ms的时序或p95/p99性能。性能成绩来自关闭录制的同场景复测。

### 阶段一：现有电脑更省计算，完整对局可用

**玩家验收：同一地图、同一难度，1 个和 3 个电脑能正常开局、采矿、建造、产兵、侦察、防守和进攻；有可比较的 AI 开销记录，不能只是“感觉更流畅”。**

工作合并为一个阶段：建立整局CPU线程画像和可信测量，选贡献最大的热点做最小优化，形成后续可迁移的数据边界，并反复对局验证。电脑决策先保留同步执行；已有引擎/副官线程预算仅按第1.1节的独立候选实验调整，不同时上线程和大改决策。

1. 在实际调用处作可关闭的低开销聚合计时，分开 Capture/可见性、查询、桥接、各 Controller/编组计算、放置、命令提交、GC，避免父子 inclusive 时间重复相加。记录调用量和新增分配，量出插桩本身的开销。
2. 先验证当前标准权限、经济仲裁、命令顺序和实战行为，再优化一个明确热点。优先减少同一合法观察版本的重复查询/转换和重复统计，或把最贵选择计算提取成同步纯数据函数。没有证据时不得指定某个循环必然是瓶颈。
3. 数据层按玩家、会话、字段、可见状态和相关版本分开；不向电脑暴露原始全知快照。不能把两份存在同帧变更的数据强行合并，不能共用可变 Godot Dictionary 后被某个消费者修改。
4. 保留经济 > 防御 > 进攻的资源仲裁、同档扫描第一个付得起请求的规则，以及即时回执引发的重新评估。不新增“把一拍所有花费都相信旧余额”的缓存。保留已有 AiCadence 和难度配置。
5. 用正常 Match 做完整可见对局、逻辑探针及同场景 A/B；保留版本开关/可复现基线以比较。一次候选失败就撤销自己精确补丁，不在失败候选上叠第二个优化。

阶段一交付：当前电脑性能分解；至少一个收益超过噪声、行为不退化的最小候选，整晚可逐轮积累多个已单独验证的改进；各轮和最终版本相对整晚起始基线的真实对局、性能与回归；已实际回看的5 FPS玩家验收录像；阶段二具体迁移对象。如果没有可重复收益，交付 measured/否证与待复核状态，不强行上线程掩盖问题。

### 阶段二：一部分决策真正跑到后台

**玩家验收：电脑持续发展和交战，决策尖峰更小；暂停/恢复和退局重开正常，电脑不会重复花钱、重复下令或突然停止发展。**

先迁移阶段一证明有价值、状态最清楚的一段纯计算。默认考察经济/生产需求和候选分配；若最贵项是目标评分，可选择目标评分。不能把经济Controller整个函数（包括找合法建造点、发信号、扣款）搬到后台。其余模块继续走旧主线程路径。

实施前先让“同步纯数据规划器”与旧行为对照通过，再用**同一个规划器**运行异步/同步 A/B，区分算法收益与线程收益。

执行器和协议最小合同：

- 每局共享1个计算并发。每玩家最多1个进行中批次和1个待计算最新输入，待处理覆盖旧快照；任务/结果/事件容量明确，统计覆盖、取消与公平调度。未执行的关键资源请求属于现有业务状态，不能随过期任务一起静默丢失。
- 使用轮转/截止期公平调度，不能固定每轮优先玩家1而饿死后面的电脑。每控制器 due/dirty 合并成合适的玩家批次；保留实际业务依赖和时序，不把所有控制器当成互不相干的任务。
- 输入为普通 C# 值数据：稳定玩家/实体ID、合法观察字段、配置值、模拟时间、必要AI状态、版本。没有Node/GodotObject、RID、PackedScene、可变Godot集合、委托捕获节点，也不通过后台调用 WorldQueryRuntime 或当前 WorldQueryService 获取数据。
- worker只读自己的输入，输出命令意图及候选状态；不调用Gateway、不扣款、不创建单位、不发布节点信号、不调用call_deferred。不靠每帧Task.Run排无限任务。后台任务可合作取消，任务异常有回执与计数。
- 输出含 match_generation、ai_epoch、player_id、decision_seq、snapshot_seq/tick、关键依赖版本和有效期。结果只在主线程安全边界消费，不使用Wait/.Result/Join等阻塞式等待。
- **异步结果的snapshot_tick通常落后当前tick，不能因tick不相等全部丢弃。** 按年龄预算及相关依赖判断；目标是否存活、归属、当前可见授权、订单版本、资源/队列容量、施工合法性在提交时复验。新世界帧不等于相关依赖必然失效。
- 每个意图至多执行一次，使用批次/意图序号去重。旧批次、死亡玩家、换局、较新策略/回防订单覆盖过的结果丢弃。当前不可见目标不能靠过去合法观察重新取得当前权限，LastKnown仍只能按原合同使用记忆位置。
- 当主线程接受/拒绝意图后，通过回执推进AI状态与下一拍输入；worker不能先把“请求发出”当成“建造成功”。分配/编组状态的所有者只有一个，不共享两个同时可写版本。
- 同一状态与输入的目标排序、平手选择、随机数使用可复现；线程调度不能决定随机顺序。按稳定ID或原有既定顺序提交，保持经济仲裁。单靠恢复提交顺序不能修复已经改变的输入依赖。
- 暂停不派新任务、不提交结果，后台不自己累加模拟时间；恢复校验epoch/状态并取新观察，避免命令堆积。退局使所有结果失效并取消任务，worker完全停止/释放引用后才回收快照缓冲。
- 降级有单一策略：旧AI模式仅作为明确选择的对照；异步模式过载合并待处理观察、按预算丢弃过期计划并告警。若必须同步回退，一次批次只能选择一个执行者，不能旧、新两套同时下令；必须测回退引起的主线程尖峰。

阶段二必须报告采集、转换、排队、计算、主线程等待、结果校验、提交和GC的总成本。跨帧不阻塞目标不等于排队无限增长，线程CPU与主线程CPU可能重叠，不直接相加成帧时间。

### 阶段三：完整电脑决策整合与长期压力验收

**玩家验收：多电脑、较大部队、持续建设和交战的一整局保持响应，后排电脑不发呆，长时间运行不越来越卡。**

逐模块迁移纯决策：经济/生产 → 侦察/防御 → 进攻与编组（实际优先级按测量调整）。先完成一个模块的相关闭环再迁下一个，不把整个AI重写到最后才开局。真实移动、物理、导航、放置和扣款保持原执行层。

重新测总开销：若主线程采集/合法视野计算成为主因，另建最小候选优化其纯数据筛选或有效索引，并作授权等价对照；不能认为规划器后台化就已经解决快照热点。若移动/避障占主因，记录为独立后续任务，不冒充本AI方案已解决千兵容量。

保留1worker作为基线，只在1worker确有排队瓶颈且线程竞争可控时比较2worker；测与Godot导航/RVO、渲染、其他已有后台任务的竞争。不使用“CPU占用更高”作为通过标准。

完整验证暂停、生产完成、基地受袭、目标死亡/隐藏、工厂销毁、单位归属变化、地图导航版本变化、保存/加载（若支持）、正常退局重开，以及客户端不自行运行权威AI。长时检验快照、邮箱、去重表、情报记忆和任务数的上限与换局归零。

## 4. 统一测量与验收口径

使用真实Godot 4.7.1主工程，采样时不同时跑回归/构建/另一个性能实例。固定机器、地图/种子、难度、阵营、相机、画质、生产帧率/VSync、物理频率和命令序列。1 AI与3 AI各自和自己的旧版比，不能拿不同单位数/模拟速度的对局直接做优化A/B。

| 矩阵 | 目的 |
|---|---|
| 1 AI、3 AI，约50/100/200实际混合实体，闲置/发展、持续移动、持续交火 | 从小场景到压力场景分辨AI计算和执行层开销；实体数包含建筑、资源及出生差异，报告口径 |
| 4个以上AI | 仅选真实出生点数量足够的地图，检验AiCadence外推和公平性；不把多个玩家堆在同一点 |
| PlainAndSimple与实际生成地图 | 检验地图规模与不同既有物理频率，不能降低physics tick比较 |
| 三档难度 | 确认预算没有暗改难度、首波/再派/侦察与发展配置 |
| 独立真实对局至少10分钟，阶段三至少30分钟有效运行或分段等价长测 | 发展、回防、资源/队列与内存/任务长期增长；记录模拟时间与墙钟时间 |

每档先检查出生合法、实际内容与稳定预热，再至少3次同窗口测量或A-B-A。灾难长帧/超时原样记录并提前结束当前压力档；不能删除>500ms的帧。每次独立PID、端口和watchdog，只清理自己的实例。

必需指标：AI主线程CPU时间分解的p50/p95/p99与峰值；总主线程frame p50/p95/p99及长帧；主线程与worker CPU时间；快照次数/实体数、可见性比较次数、查询/转换/排序次数、命令重复/拒绝/有效执行数；快照年龄、任务排队与意图提交延迟；内存/分配/GC；模拟秒/墙钟秒、出生/产出/采矿/伤害；清理状态。无法测的填unavailable，不填0。

建议初始目标（属于待测预算，不是已达成数字）：在3AI压力夹具中，**AI相关主线程p95耗时减少至少30%**且超过重复测试噪声；1AI整体frame p95/p99不出现超过5%且超过噪声的回退；总CPU计算/分配成本没有超过噪声的增加，CPU工作量或重复工作计数有明确降低。若1AI成本已很小，则先约定绝对ms预算，不以微小百分比强称收益。

阶段二新增异步端到端延迟p95建议不超过`min(100ms, 现有决策周期×20%)`；结果就绪后应在下一个可用安全提交边界消费。先测现有延迟并在baseline.md锁定预算，再评分；不能失败后放宽阈值。没有达到目标就写实际数字和否证/未达标，不隐式拉长AiCadence、减少产兵或关闭系统。

现有 `tests/performance/PlayerVsAiPerformanceBaseline.gd` 为headless/fixed-FPS逻辑吞吐，不能替代正常可见性能；不得用`measured_frames/60`当所有模式真实模拟秒。复用工具之前读performance skill的measurement.md：PerfGrid计时单位和长帧过滤、全量runner的forbidden_hits未并入passed等已知问题都要独立核验。

### 4.1 与现有AI副官同时运行

用户明确关注电脑玩家升级后与现有副官共存。电脑规划器采用CPU普通C#计算，不调用Laya/Ollama或另加载神经模型，首版1个计算并发；该选择减少新增GPU负担，但不保证CPU/主线程和显卡资源没有竞争。

本次只读核验：开发配置为 `AIRTS_S1_BACKEND=laya`，`AIRTS_LAYA_DEVICE` 留空，provider说明为自动选择cuda→mps→cpu；真实设备以 `laya_loaded.device` 等运行日志为准。Laya在Python进程内加载，不通过Ollama chat接口。机器当前GPU为RTX 3080 Ti、12GB显存。配置与硬件不能证明模型目前正跑CUDA，更不能证明共存性能已通过。

潜在竞争分别计量：副官的tokenization/图调度/JSON与状态处理仍用CPU；`DebugControlServer._op_tactical` 读取真实单位并处理情报，`AdjutantObservationRuntime` 读节点/权威业务，和电脑查询都会给游戏主线程增加工作。副官推理与游戏渲染共用GPU计算、带宽和显存，Laya回退2B时负载可能变化。不能未经协议和授权等价验证就把两套观察结果合并，或把副官查询直接挪到电脑worker。

阶段一及后续最终候选都增加如下对照，每个条件同时测旧版和候选：

| 副官状态 | 目的 |
|---|---|
| 本轮隔离Match不挂副官 | 电脑本身的成本基线；记录共享服务/模型是否仍驻留 |
| 副官挂接，正常低频观察 | 观察采集、Python调度与游戏主线程的常驻成本 |
| 副官正常执行Laya决策并提交命令 | 实际CPU/GPU推理、命令回执与电脑同时发展/作战 |
| 战斗负载下副官连续工作，覆盖已有超时/回退路径 | 发现排队、显存压力和延迟尖峰；不提高正常调用频率制造虚假压力 |

重点采用3电脑实际交战场景；完整性能矩阵不必全部与每个副官条件相乘。重复测量同条件，记录真实模型/device/端点类型、冷加载与预热、上下文/请求规模、在途量、查询时间、GPU时间/显存、frame p95/p99、副官端到端与命令延迟、timeout/fallback/拒绝率。性能样本关闭录制；补5 FPS共存视频并回看真实命令反馈。冷加载单列，不能夹入一组稳态样本后直接比较。

对照原则为“优化后双方均符合锁定预算”：电脑收益仍成立，副官的响应、任务成功率和正常指挥没有超过噪声/预算的回退，队列不持续增长。不把关闭副官、减少观察字段、拉长副官周期、换小模型或减少产兵作为共存通过办法。现有同一Agent最多一个在途、迟到任务结束才释放的纪律保留，不为压测开第二份Laya推理池。

共存实测使用隔离的本轮Match/runner、独立端口与HUD/日志目录，保持既有模型服务和运行时路径。不得结束用户副官或卸载共享模型来做“关闭组”，不改 `.env.local`、模型或副官协议；也不默认额外启动模型服务、训练或收费云端压测。确有云端战略路径时区分其远程推理与本地调度，响应回放可以验证本地链路，但不能冒充本地GPU真实推理。工具无法完成真实共存时如实写未验证。
