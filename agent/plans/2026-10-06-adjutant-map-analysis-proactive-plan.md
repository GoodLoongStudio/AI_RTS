# AI 副官第三阶段计划：完整地图解析与主动战前提案

状态：DRAFT，供用户审核后交给 DeepSeek。

## 产品目标

战略模式进入后，AI 副官不等待玩家长篇提问，而是先完成一份可核验的地图战前简报：

1. 读取当前选择的具体地图。
2. 解析玩家出生点附近资源、全图资源分布、四个出生点、地图地形/桥梁/水域等可获得事实。
3. 根据单机设置页的槽位配置识别“已占用的其他出生点”和“未知的敌方意图”；不能把空槽位当敌人。
4. 结合玩家选定出生点，主动给出发展路线、战略路线、侦察与防守规划。
5. 玩家主要通过“同意方案”“调整方案”“换一个方案”进行交互；自由文本只是可选补充。

这个阶段仍是封闭测试，不创建 Match、不运行时间、不执行单位命令。先证明“事实被读对、建议基于事实”，再把提案移植到真实对局。

## 先修证据确认的 P0 问题

### P0-1：资源解析器漏读

StrategicMapIntel._parse_resources() 不能按“节点名和 transform 在同一行”解析。应按场景节点 block 解析：

- 从 [node ... parent="Resources" ...] 开始读取，直到下一个节点头；
- 在同一 block 内读取 transform；
- 解析 resource_a 覆盖值；没有覆盖值时读取资源脚本/现有权威默认值，不能默认为 0；
- 类型、坐标、数量、资源 id 都要有来源字段；无法确认的字段写 unknown；
- 用两张真实地图验证源节点数和解析节点数完全一致。

### P0-2：地图情报不能只传资源数量

模型上下文必须包含可引用的事实：

地图身份、尺寸、预览来源
玩家出生点：编号、坐标、朝向
附近资源：id、类型、有效数量、坐标、距玩家出生点的距离、来源
资源簇：按距离/连通区域聚合的摘要
四个出生点：编号、坐标、当前槽位占用状态、来源
地形：水域/桥梁/陡坡/不可通行格；每一项带来源和 confidence
未知：迷雾中的单位、敌方意图、实时采集变化、未能可靠提取的通行性

UI 可以先展示摘要，模型请求中使用紧凑结构化文本；不能只发“资源节点=16个”。

### P0-3：占用出生点必须来自槽位配置

从单机设置页传递地图路径之外，还要传递当前槽位控制器/空位配置，并复用 Play._create_match_settings() 的权威映射规则，得出：

- 玩家选择的出生点；
- 已配置的人类/AI 占用点；
- 空槽位；
- 敌方身份未知但“可能由哪个非玩家槽位占用”的事实。

如果用户改选出生点与已有玩家槽位冲突，UI 要明确提示并允许重新选择；不能静默覆盖或让模型猜测。

## 阶段 3A：确定性地图分析包

新增或扩展只读分析服务，例如 StrategicMapAnalysis.gd。它必须先于模型运行，输出可测试的 analysis_pack：

{
  "status": "ready",
  "map": {"path": "...", "name": "...", "size": [208, 208]},
  "player_spawn": {"index": 1, "x": 40, "z": 28},
  "nearby_resources": [
    {"id": "ResourceA", "type": "A", "amount": 30000, "x": 26.9272, "z": 57.2079, "distance": 32.0, "source": "map_scene"}
  ],
  "all_resources": [],
  "spawn_occupancy": [],
  "terrain_facts": [],
  "unknown_facts": [],
  "source_hash": "..."
}

要求：

- 先做事实抽取，再做推理；模型不能替代解析器。
- 每个事实带 source/confidence，避免模型把推断当事实。
- 距离使用地图世界坐标计算并保留小数，UI 可四舍五入但上下文保留原值。
- 资源数量以资源脚本/场景 override 的有效值为准；不要把未写 override 当成 0。
- 对地形“完整解析”要定义覆盖率：水域、桥梁、陡坡/禁行格、资源和出生点必须给 known 或 unknown 状态；没有可靠导航数据时必须显示缺口，不得让模型假装完整。
- analysis_pack.status != ready 时不能请求提案模型；先显示具体缺失原因和重试。

## 阶段 3B：小模型接线与主动分析

### 服务验证

确认 AdjutantModelService 的端口、模型名和运行时来源唯一；记录 /v1/models、预热、首个实际请求和响应耗时。不能只检查端口能连。

### 请求协议

当前服务有 max_tokens=512 的问题：小模型可能把预算用在 reasoning，正文为空。实现必须：

- 调查本地 runner 对 think=false/reasoning 的实际支持，不凭猜测写参数；
- 给主动简报单独的请求预算，保证输出正文有足够空间；
- 若返回 content 为空而 reasoning 非空，不能当成功，按协议重试一次或报可见错误；
- 正文必须通过结构/长度/地图事实引用校验；不能用“返回了任意字”当成功；
- 失败要区分 warming、timeout、HTTP、empty_content、invalid_proposal；
- 保留原始响应摘要和解析结果用于审计，不能把 reasoning 当 UI 正文直接展示。

### 主动提案请求

玩家选定出生点并且 analysis_pack ready 后，页面自动发起一次内部请求：

请根据以下已验证地图分析包，主动完成战前简报。
输出：
1. 一句话总判断；
2. 推荐发展顺序（最多 3 步）；
3. 推荐战略路线（经济/压制/稳健防守之一，并说明理由）；
4. 侦察与防守重点（最多 3 条）；
5. 需要玩家确认的一个选择。
只能引用分析包事实；推断必须标注；未知敌情必须明说；不要要求玩家先提问。

## 阶段 3C：玩家只确认或调整

右侧副官席改成“提案卡 + 轻交互”：

- 同意推荐方案：只记录测试态 approval，不执行命令；
- 调整方案：展开固定选项，例如“更重视经济”“更重视早期压制”“更重视防守/侦察”；
- 换一个方案：让模型基于同一分析包生成第二套可比较方案；
- 补充条件：折叠的可选短文本，限制长度，不成为主流程；
- 查看地图事实：展开完整资源/出生点/地形事实和来源。

每个方案必须显示：发展目标、战略路线、前三步、主要风险、依赖的地图事实、未知项。玩家看见的是可比较的建议，不是一面要求玩家不断补充情报的空聊天框。

## 阶段 3D：验收矩阵

### 地图事实

1. PlainAndSimple：原始资源节点 16，解析 16；出生点 4；出生点 1 附近资源至少能列出 4 个及其距离。
2. 第二张真实地图：资源数量、坐标、出生点和尺寸随地图变化。
3. 资源 override 与默认数量分别验证；不能把默认有效数量显示成 0。
4. 玩家/AI/空槽位配置变化后，占用出生点和上下文变化。
5. 情报加载失败时不请求模型，不显示“分析完成”。

### 主动提案

1. 选点后无需玩家输入，副官自动出现地图简报和推荐方案。
2. 简报至少引用：玩家出生点、附近两个资源的坐标/距离、一个发展判断；若敌方槽位存在，引用其出生点来源，否则明确未知。
3. 玩家只点击“同意/调整/换方案”即可完成主流程；输入框不是必经步骤。
4. 模型正文为空、只返回 reasoning、超时、乱码或无事实引用时，UI 显示失败并重试，不伪装成功。
5. 同一地图换出生点后，方案必须重新生成，旧方案和旧回复不得污染。

### 闭环证据

必须有静态解析、独立地图审计、可见截图、直接模型请求、页面自动提案、同意/调整/换方案、失败重试、无 Match/无执行证明和独立复核。

## 明确不做

- 不把“地图静态事实”伪装成实时战争迷雾。
- 不让模型自己猜资源点、敌人位置、通行性或数量。
- 不在本阶段接入单位命令、任务卡、租约、计划 JSON、Laya 或真实战斗。
- 不用增加聊天输入量来掩盖地图解析缺陷。
