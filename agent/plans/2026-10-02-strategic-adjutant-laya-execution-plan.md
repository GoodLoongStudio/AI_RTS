# AI 副官战略层 × Laya 执行层：按游戏内阶段验收的实施计划（审核稿 v4）

状态：DRAFT，等待用户审核。本稿按“玩家在游戏里能验收什么”来切分，不按内部类、字段或接口切分。每个阶段内部都允许多轮实现、运行、截图、诊断和优化，阶段通过后才进入下一阶段。

## 一、验收原则

每个阶段都必须形成一个可从正常游戏入口操作的纵向切片：

```text
游戏入口 → 玩家操作 → AI/系统响应 → 游戏内可见结果 → 权威日志/状态 → 回退验证
```

内部数据结构、DCS 协议、模型适配器和测试代码都只能作为该纵向切片的支撑，不能单独作为阶段交付。

任何阶段都要反复循环：

```text
能操作
→ 看截图和真实状态
→ 找出体验/稳定性/性能问题
→ 修复
→ 用同一入口重测
→ 加入异常和回退场景
→ 达到阶段出口
```

## 二、阶段 1：在游戏中和战略层聊天

### 玩家验收目标

启动游戏后，玩家能打开现有副官入口，在游戏内输入一句战略问题或目标，收到战略层回复，并能继续多轮对话。

示例：

```text
玩家：这局先稳住经济，北侧需要侦察吗？
副官：当前建议先派一支轻型小队侦察北侧，同时保留主力守家……
```

这一阶段副官只聊天和解释，不生成可执行战略计划，不向单位下命令，不调用 Laya 实控。

### 需要实现的内容

- 在正常游戏入口打开战略对话面板；优先复用现有 `AdjutantButton` 和副官通信入口。
- 将玩家消息送到现有战略模型/战略角色，而不是战术或 Laya 接口。
- 显示消息发送中、成功、超时、错误和重试状态；不能显示“思考中”但没有真实请求。
- 保留当前对话上下文，并标记当前 `match_id`、玩家身份和暂停/运行状态。
- 支持暂停状态下继续聊天；聊天不能推进游戏时间。
- 模型关闭、超时、空输出、非法输出时，面板要明确显示失败/降级状态，战斗继续不受影响。
- 写入可追踪日志：请求、响应、耗时、模型、match、错误原因；不能把规则 fallback 冒充成模型回复。

### 阶段 1 的多轮优化重点

- 第一轮：打通“按钮 → 输入 → 真实战略模型 → 回复 → 日志”。
- 后续轮次：优化 UI 可读性、消息历史、长文本截断、重复发送、请求取消、超时体验和响应延迟。
- 再后续轮次：在战前和战斗暂停两个入口重复验证，处理切换对局、断线、模型重启和窗口重复打开。
- 每轮都用同一组问题和同一入口重测，并保存截图和日志，直到链路稳定。

### 阶段 1 通过标准

- 玩家可以从正常游戏入口完成至少 5 轮连续战略对话。
- 回复确实来自战略模型；日志能证明请求和返回，不靠假数据或预置文本。
- 正常运行、暂停、模型超时、模型关闭、空输出和非法输出都有清楚结果。
- 聊天期间没有单位命令、资源扣除、任务变化或游戏时间推进。
- UI 截图、运行日志和测试命令齐全；真实失败项列明。

## 三、阶段 2：战略层能看懂当前战局并给出计划草案

### 玩家验收目标

玩家在对话中提出大战略后，副官除了文字回答，还能展示一份“战略计划草案”，包括任务、优先级、约束、风险和需要确认的问题。

示例：

```text
玩家：主力从东侧推进，先拆生产建筑；基地被袭时立刻回防。
副官：我整理成 4 个任务，请确认……
```

草案此时仍不会控制单位。

### 需要实现的内容

- 战略模型读取经过压缩的当前战局事实：地图、己方资源/单位、已知敌情、任务目标、当前暂停/运行状态。
- 返回“自然语言答复 + 结构化草案 + 风险/冲突 + 澄清问题”。
- 游戏内显示任务卡，玩家可以逐项修改、要求解释、重新生成或丢弃草案。
- 校验未知字段、非法任务、冲突目标、重复任务和无法理解的模型输出。
- 草案和已确认计划明确区分；不允许聊天消息直接变成任务。

### 多轮优化重点

- 先用固定假模型验证任务卡和异常 UI，再接真实战略模型。
- 反复优化状态摘要、上下文长度、任务数量、澄清轮次和计划可读性。
- 反复测试模型输出不完整、计划互相冲突、状态过期和玩家连续修改。

### 阶段 2 通过标准

- 玩家能在游戏内看到与当前战局相关的计划草案，而不是泛泛聊天。
- 草案每一项都有可读目标、优先级、前置条件、完成/取消条件和风险。
- 草案不会改变单位和资源；模型异常不会破坏阶段 1 的聊天能力。
- 日志能把玩家原话、战局快照、草案版本和最终展示内容对应起来。

## 四、阶段 3：玩家确认战略，游戏内显示生效计划

### 玩家验收目标

玩家点击确认后，草案变成带版本的生效战略计划；玩家能在战前或暂停时看到当前版本、任务状态、风险和历史版本，并能修改或回滚。

### 需要实现的内容

- 确认、取消、修改单个任务、回滚和版本历史。
- `plan_id/plan_version/source/status` 与任务 ID 在 UI、协调器、DCS/日志中统一。
- 重复确认幂等；旧版本和陈旧模型返回不能覆盖新版本。
- 暂停时确认不推进时间；恢复时重新检查地图、目标、资源和任务有效性。
- 继续保持“计划只展示，不控制单位”的边界，直到下一阶段验收完成。

### 阶段 3 通过标准

- 玩家能在游戏里明确看到“草案”“已确认”“已生效”“已替代”的区别。
- 版本冲突、重复点击、断线、重启和旧结果都有可解释结果。
- 战前确认和暂停修改都能完成；回滚后 UI、日志和计划版本一致。
- 计划生效不会偷偷产生单位命令，阶段 1/2 行为不回归。

## 五、阶段 4：战略任务开始驱动现有执行器（先不让 Laya 决策）

### 玩家验收目标

玩家确认战略后，至少一类任务能够在真实战斗中开始、持续、完成或阻塞，并在游戏内看到进度。此阶段由现有规则/行为树选择具体动作，Laya 仍保持关闭或影子状态。

建议先选择一条最容易验收的任务链，例如“守家防御”或“侦察一个区域”，不要同时接入所有兵种和所有任务类型。

### 需要实现的内容

- 将已确认任务登记到现有 squad/侦察/防守/生产执行域。
- 任务拥有 owner、source、plan_version、generation、TTL、进度、阻塞原因和后继任务。
- 任务租约保护战略意图，规则层只能做安全修正，不能每 tick 无理由改回 baseline。
- 玩家手动接管后释放相关副官租约；任务完成、目标丢失、TTL 到期和计划替代都可结束任务。
- UI 显示任务状态和实际执行结果，日志记录接受、拒绝、替代、完成和失败原因。

### 多轮优化重点

- 先跑单任务短场景，再跑任务被打断、恢复、目标丢失和玩家接管。
- 优化任务粒度、TTL、完成判据、命令 churn、无解释空闲和恢复速度。
- 对照 model=off、模型超时、旧计划替代和 DCS 抖动，确认任务底盘不依赖 Laya。

### 阶段 4 通过标准

- 至少一条任务链在真实 Match 中完成或明确阻塞，玩家能看到原因。
- 有效任务期间没有无理由的策略性覆盖或反复改令。
- 玩家接管不会被副官夺回；模型不可用不造成整段停摆。
- 固定种子短场景和一次较长 Match 都有证据。

## 六、阶段 5：Laya 先影子，再控制一个战术选择

### 玩家验收目标

玩家能看到某个战略任务下 Laya 的局部战术判断，并在经过影子验证后，逐步让 Laya 只控制一个离散选择，例如班组交战姿态。

### 实施顺序

1. **影子模式**：Laya 读取战略任务、局部战况和合法候选，只记录建议，不影响战场。
2. **单项实控**：只开放推进/保持射程/撤退/等待等姿态选择。
3. **后续扩展**：确认单项稳定后，再分别评估目标优先级、目标实例、撤退阈值和支援/集火。

每次只开放一项，不能一次接管全部战术。

### 阶段 5 通过标准

- UI/日志能把战略任务、Laya 选择、实际执行和结果串起来。
- Laya 不能改变战略目标、绕过任务约束或输出坐标。
- Laya 超时、低置信、非法、过期或关闭时回到上一个有效选择/规则 baseline。
- 不出现逐单位抖动、频繁反向、命令 churn 或无解释空闲。
- 影子和实控都有同场景对照数据；没有可重复增益就停止放权并回退。

## 七、阶段 6：事件重规划、暂停恢复和玩家控制权

### 玩家验收目标

基地受袭、主攻目标死亡、路线失效、生产链断裂时，战略层能提出可解释的修订；玩家暂停修改战略、手动接管部队后，副官不会越权夺回。

### 阶段 6 通过标准

- 紧急安全行为先发生，战略重规划异步进行，不阻塞执行。
- 主攻能暂停、回防，威胁解除后恢复或明确结束。
- 旧计划、旧 Laya 返回、旧回执不能跨版本生效。
- 暂停期间确认计划不推进游戏时间；恢复时重新验证陈旧目标和路径。
- 玩家接管和恢复副官都是可见、可追踪的明确动作。

## 八、阶段 7：整体优化和对照验收

只有阶段 1–6 稳定后才做整体优化，不用优化掩盖功能缺陷。

需要持续优化和报告：

- 战略聊天响应时间、上下文长度、澄清轮次和草案冲突率。
- 任务完成率、阻塞时长、命令 churn、无解释空闲、租约替换率。
- Laya p50/p95 延迟、超时率、低置信率、候选拒绝率和有效采纳率。
- 建筑损伤/分钟、战损比、生产接续、撤退后存活和主攻集中度。
- CPU、内存、DCS 往返、观测/写盘开销和单位规模下的帧时间。

固定对照：规则 baseline、固定战略+规则、固定战略+Laya、2B 战略+Laya。所有对照使用相同地图、种子、单位规模和初始资源。

## 九、每个阶段的交付格式

每轮给用户验收时必须提供：

1. 从哪个游戏入口进入、玩家做了什么。
2. 游戏里实际看到了什么。
3. 对应截图和权威日志/状态。
4. 本轮改动和测试命令、rc。
5. 异常、回退和未验证项。
6. 当前阶段是否通过；未通过不得宣布进入下一阶段。

## 十、DeepSeek 提示词发放方式

不按内部字段拆提示词，也不发一份覆盖全部系统的总提示词。按用户可验收阶段发放：

1. 第一份只做 **阶段 1：游戏内战略聊天**。
2. 阶段 1 经过多轮优化并由用户验收后，再发阶段 2。
3. 后续按阶段 3、4、5、6、7 逐份发放。

第一份提示词的出口必须是“用户能在真实游戏中打开副官并和战略层连续聊天”，不是“某个 Python 类测试通过”。

## 十一、请审核的关键点

1. 是否确认阶段 1 就是“进入游戏，与战略层聊天”，而不是先做内部数据模型。
2. 是否接受每个阶段内部进行多轮功能、稳定性、体验和性能迭代。
3. 是否同意阶段 2 先生成计划草案，阶段 3 才允许玩家确认生效。
4. 是否同意阶段 4 先让一种战略任务驱动现有执行器，之后再接 Laya。
5. 是否同意阶段 5 的 Laya 必须先影子、再单项实控。
