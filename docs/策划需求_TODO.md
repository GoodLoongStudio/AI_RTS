# 2. 编辑工具建设总原则

编辑工具的目标不是“看起来像一个专业编辑器”，而是：

> **让策划可以不改代码，独立完成大部分游戏内容。**

所有编辑器尽量满足：

- 数据驱动；
- 可视化；
- 可以实时预览；
- 有错误检查；
- 能复制 / 复用；
- 支持版本控制；
- 运行时和编辑器读取同一份数据；
- 不把核心内容写死在 GDScript 中。

推荐总体结构：

```text
策划编辑器
    ↓
Resource / JSON / 配置数据
    ↓
运行时系统
    ↓
单位 / 技能 / AI / 地图 / 战役
```

# 8. 功能规则文档

每一个系统都应该有一页简洁规则。

例如“镜头锁定英雄”：

```text
单击 F1：选中主英雄
双击 F1：镜头锁定主英雄
再次双击：解除锁定
英雄死亡：自动解除
锁定期间：允许缩放和旋转
锁定期间：禁止边缘滚屏
```

# 20. 程序完成一个功能后，策划验收什么？

每一个程序任务完成后，策划至少进行一次功能验收。

标准流程：

```text
程序完成
↓
策划实际操作
↓
检查是否符合规则
↓
检查异常情况
↓
填写修改意见
↓
确认通过
↓
进入内容生产 / 数值调整
```

## 验收 Checklist

- [ ] 玩家能否理解这个功能
- [ ] 操作是否符合策划规则
- [ ] 有没有明显多余步骤
- [ ] 功能状态是否完整
- [ ] 边界条件是否正常
- [ ] UI 反馈是否足够
- [ ] AI 是否遵守权限
- [ ] 数据是否可以配置
- [ ] 是否需要程序改代码才能加新内容
- [ ] 存档是否正确
- [ ] 是否与其他系统冲突
- [ ] 是否可以进入正式内容生产

# 21. 推荐的程序任务完成标准（Definition of Done）

对于策划依赖的系统，我建议程序任务不能只以“代码能跑”作为完成。

至少应满足：

- [ ] 功能可以运行
- [ ] 没有 Parser Error / Runtime Error
- [ ] 有最小测试场景
- [ ] 核心参数可以配置
- [ ] 策划可以找到配置入口
- [ ] 有 Debug 显示
- [ ] 非法数据能够报警
- [ ] 已写最基本说明
- [ ] 不依赖修改核心代码才能添加同类型内容

例如：

> “技能系统完成”

不应该意味着：

> 程序写好了一个技能。

而应该意味着：

> **策划可以基于技能系统继续创建第二个、第三个技能。**

```text
① 单位数据标准
↓
② 技能数据标准 + 技能编辑方案
↓
③ 地图 / Trigger / Objective 编辑方案
↓
④ 第一战役用上述工具完整制作一遍
↓
⑤ 再决定行为树编辑器需要做到多复杂
↓
⑥ 科技 / 突破编辑器
↓
⑦ AI Agent 权限和战区指挥编辑工具
```

原因：

> **先让第一场完整战役跑通，再根据真实生产需求决定工具复杂度。**

避免一开始花大量时间开发“万能编辑器”，最后却发现策划根本不需要其中大部分功能。

---

# 24. 核心结论

世界观和兵种策划解决的是：

> **我们要做什么。**

而真正支撑程序持续开发和游戏内容生产的策划还必须提供：

> **规则、操作、数据、地图、任务、AI 权限、数值、反馈和验收标准。**

本项目尤其应该优先把：

1. 单位；
2. 技能；
3. 地图；
4. 任务；
5. AI 行为；
6. AI 副官权限；

逐步数据化、工具化。

最终目标是：

> **程序建设系统，策划使用系统持续生产内容。**
