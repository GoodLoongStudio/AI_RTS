## 工具选择规则

静态分析和编辑使用普通文件读取、搜索和补丁工具，结合 godot-bridge 的项目检查和 dsh-godot-skill 的 Godot 4 规则。先读当前工作树和相关 diff，保留其他 AI 的无关改动。

无头验证优先使用 godot-bridge 的 headless/场景运行工具或仓库已有测试 runner。C# 改动先编译，再启动新进程，不能用旧 DLL 的结果判断新源码。

可见实机验证使用 dsh-godot-play 或 godot-bridge 的可见游戏能力：

1. 新开一局单机游戏。
2. 点击建筑按钮，移动蓝图，尝试合法相邻位置和重叠位置。
3. 放置车厂/机场，生产至少三辆矿车或车辆。
4. 观察出生点、建筑边缘、碰撞和单位移动。
5. 截图并实际打开查看，不以“PNG 文件存在”为通过条件。

如果可见游戏插件只能操作编辑器内运行实例，而当前游戏是独立进程，使用仓库 DCS 或 tools/dev/match_instance.py 作为控制通道。先确认实例登记、父 PID 和实际端口，不能猜端口，也不能按映像名批量杀进程。

插件失败时不要停止诊断：headless 可切换到 Godot Mono console，状态可切换到 DCS/MatchGroup，截图可切换到 bridge 视口或客户端 DCS screenshot。不能伪造“已截图”“已开局”或“已验证”。

## 必须执行的闭环

### 1. 基线

修改前保存 git diff 摘要、工作树状态、程序集是否最新、一次启动健康检查、一次真实截图和目标问题的最小复现。

### 2. 最小修改

每轮只修一个根因，并写出：

假设：哪个数据在 local/world/visual/physical 之间错了。
证据：具体文件、运行值、日志或截图区域。
修改：只改与假设相关的文件。
反例：修改后哪种情况必须仍然失败。

禁止通过扩大相邻距离、导航容差或随机出生距离来掩盖问题。

### 3. 双层验证

每次修改后同时执行无头逻辑测试和可见实机测试。两者结论不一致时，停止继续调参，先查运行版本、实例身份、相机位置、地图状态和测试夹具。

### 4. 失败分类

失败必须归类为源码行为、测试夹具、旧程序集/旧场景、导航异步、截图相机或插件基础设施问题。基础设施错误不能标成“功能通过”，功能失败也不能笼统标成“环境噪声”。

## 本任务的强制验收

必须验证：

1. 指挥中心旁的合法位置可以建造普通建筑。
2. 建筑脚印重叠时被拒绝。
3. 建筑旁有己方机动单位时，单位能被安全驱逐。
4. 建筑旁有己方建筑时，不能把建筑当作可驱逐单位。
5. 车厂和机场的视觉模型、CollisionShape3D、MovementObstacle 和逻辑半径能解释彼此差异。
6. 矿车和生产单位不会出生在建筑内部、资源内部、地图外或不可通行地面。
7. 出生失败时不会回退到建筑中心或未经验证的任意位置。
8. 单位实际到达移动目标，并在观察窗口内没有卡住、抖动或穿入建筑。
9. 至少保存并实际查看一张修改前失败截图和一张修改后成功截图。
10. 使用新进程和新编译程序集重复一次，排除旧进程假通过。

## 当前代码特别警告

- MovementObstacle.gd 已有父缩放补偿逻辑；不要只看注释，必须测量 Godot 实际 carve 输入。
- C# CarveRadiusOf、GDScript MovementObstacle 和 SizeAuditProbe 可能采用不同边界公式，必须统一或明确各自职责。
- UnitPlacementUtils.production_spawn_spot 的失败回退必须经过碰撞、地图、导航和边界复验，不能直接发出生成信号。
- UnitRadiusCoverageSmokeTest 只证明部分逻辑 radius，不等于证明物理世界碰撞和导航 carve 正确。
- UI 的 “Something already occupies that spot” 不是足够诊断信息，必须读取 primary issue 和具体重叠对象。
