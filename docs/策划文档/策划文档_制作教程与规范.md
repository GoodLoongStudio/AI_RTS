# AI RTS 策划文档制作教程与规范

> 适用对象：AI RTS 项目内所有策划、新加入成员、跨职能协作者  
> 适用范围：玩法规则、交互、UI、单位、战斗、AI 指挥、关卡等策划文档  
> 核心目标：让不同的人写出来的策划文档可以直接被程序、美术、测试和其他策划理解，并减少“正常流程写清楚了，但边界和异常没有定义”的问题。

---

# 1. 策划文档是做什么的

策划文档不是“介绍想法”，而是把一个玩法或系统变成团队可以共同执行的规则。

一份合格的策划文档至少要让读者回答清楚：

1. 这个系统是什么。
2. 玩家什么时候可以使用它。
3. 玩家具体怎么操作。
4. 正常情况下会发生什么。
5. UI / 战场会给玩家什么反馈。
6. 当前状态如何进入、保持、退出。
7. 条件不满足时怎么办。
8. 多个规则冲突时谁优先。
9. 哪些内容已经确定，哪些内容暂时不属于本文。
10. 哪些内容需要引用其他文档，而不是在本文重复定义。

---

# 2. 当前项目的两份正式范例文档

本项目当前已经有两份可以直接作为新手参考的正式策划文档：

1. 《策划文档_UI交互说明》
2. 《策划文档_基础交互逻辑文档》

两份文档目前都已经进入**正式版 / 冻结**状态。

它们不是“完美模板”，也不是要求以后所有策划文档长得完全一样；它们的作用是展示本项目现在认可的基本写法：

> **先限定范围，再写核心原则；正常规则、状态变化、异常边界、冲突优先级和明确不包含内容都要能够被找到。**

---

## 2.1 《策划文档_UI交互说明》现在实际写了什么

这份文档负责的是**玩家在 HUD 上看到什么，以及控制状态变化时 UI 应该怎么响应**。

文档开头已经明确写出：

- 状态：正式版 / 冻结；
- 本文定义什么；
- 本文不定义什么；
- 前置规则是哪一份文档。

它当前实际覆盖：

- Direct Control；
- Unit AI Command；
- System AI Command；
- 语音输入；
- 同一套 RTS HUD 下的显示、切换、反馈、异常与边界。

它同时明确不负责：

- AI 内部决策算法；
- 单位寻路；
- 伤害公式；
- 语音识别技术实现；
- 程序节点与类结构。

这正是本项目策划文档应该学习的第一件事：

> **UI 策划只定义玩家应该看到和感受到什么，不替程序文档设计代码。**

### 这份文档当前的核心写法

它先给出 UI 总原则：

> Direct / Unit AI / System AI 只改变当前操作层和 HUD 表达，不切换到新的游戏页面。

然后再按具体状态拆开：

### Direct Control

当前正式规则已经明确：

> **选中任意己方单位 / 小队后，默认操作层始终是 Direct Control。**

并继续说明：

- 选择己方对象只改变控制对象；
- 不会自动进入 Unit AI；
- 要进入 Unit AI，玩家必须再次明确按 `Tab`；
- 即使单位已有 AI 行为，Direct Control 也不等于取消 AI 行为。

这说明策划文档不能只写“进入 Direct”，还要说明：

- 什么时候进入；
- 进入以后什么不发生；
- 已存在状态是否被取消。

### Unit AI Command

当前文档明确了：

- 必须存在可控制的己方单位 / 小队；
- 按 `Tab` 进入；
- 当前对象区增加 `UNIT AI`；
- QWER 从普通技能切换成单位 AI 行为；
- 当前生效的 AI 行为必须高亮；
- 再按 `Tab` 回 Direct；
- 退出 Unit AI 操作层不取消已经设置的单位 AI 行为。

这里值得新手学习的是：

> **“操作层状态”和“游戏中正在持续生效的行为状态”必须分开写。**

### System AI Command

当前正式规则已经不是普通 Toggle。

现在明确规定：

- `` ` `` / 反引号只负责进入 System AI；
- 已经在 System AI 时再次按 `` ` `` 不退出；
- 连续按、误触、双击都不能关闭 System AI；
- System AI 的正常退出来自玩家选择任意己方单位 / 小队；
- 选择己方单位后回到该对象的 Direct Control；
- 在 System AI 中查看敌方单位只用于查看，不退出 System AI。

这个例子非常适合新手理解什么叫**异常和防误操作设计必须写进策划**。

如果只写：

> `` ` `` 进入 System AI。

是不够的。

正式规则还要继续回答：

- 再按一次怎么办；
- 连续按怎么办；
- 怎样才算真正退出；
- 看敌人算不算退出；
- 退出后回哪个状态。

### UI 文档已经包含异常与边界

现在这份文档已经正式包含“异常与边界规则”表，例如：

- 无己方对象时按 `Tab`；
- 当前选中敌方对象时按 `Tab`；
- Unit AI 中对象死亡 / 销毁 / 离场；
- System AI 中选择己方对象；
- System AI 中按 `Tab`；
- QWER 指令不可执行；
- 连续快速切换；
- AI 指令执行失败；
- UI 仍指向失效对象。

每一项都同时写：

- 异常情况；
- 游戏怎么处理；
- 玩家得到什么反馈；
- 原状态如何处理。

### UI 文档还包含冲突优先级

当前文档已经明确类似下面的关系：

```text
明确的玩家模式切换
>
当前合法控制对象
>
当前控制层级
>
AI 自动行为显示
>
默认 UI 状态
```

并进一步写清：

- `` ` `` 只进入 System AI，不负责退出；
- 选择己方单位会把控制焦点拉回局部；
- Unit AI 与 System AI 不同时作为当前操作层；
- 语音结果不能擅自改写当前 HUD 模式；
- 指令失败默认保持当前合法状态。

### UI 文档最后明确“不包含什么”

当前明确排除：

- 混合兵种多选时 Unit AI QWER 的最终文案；
- AI 指令完整进度 UI；
- AI 内部失败原因分类；
- 语音识别技术和网络异常；
- 普通战斗 UI 的技能冷却、资源不足等；
- Targeting 的完整规则；
- 具体动画时长、颜色、字号和视觉资源。

这一部分非常重要。

> **“当前不定义”不是文档缺失，而是明确边界。**

## 2.2 《策划文档_基础交互逻辑文档》现在实际写了什么

这份文档是 P0 的**基础输入和控制层规则**。

当前状态同样是：

> **正式版 / 冻结**

它开头已经明确本文只定义：

1. 鼠标；
2. 键盘；
3. Unit AI Command；
4. System AI Command；
5. 语音。

同时明确不定义：

- 复杂组合输入；
- Targeting 完整流程；
- AI 内部决策算法；
- 寻路；
- 战斗数值。

因此它解决的是：

> **玩家输入了什么，在当前控制层和当前对象条件下，游戏应该如何解释。**

而不是解释 AI 内部怎么完成任务。

### 它先写整个输入系统的核心原则

当前正式核心规则是：

> 玩家始终通过传统 RTS 直接输入控制战场；Unit AI 与 System AI 是两个独立的 AI 指挥层级，语音是独立输入通道。

紧接着就冻结了非常重要的己方单位选择规则：

> **选中任意己方单位 / 小队后，默认操作层始终是 Direct Control。**

并说明：

- 选择己方单位不会自动进入 Unit AI；
- 单位即使已有 AI 行为，选中后仍是 Direct；
- 调整 AI 行为需要明确按 `Tab`；
- System AI 中选择己方单位也会回到该对象 Direct；
- Direct 只是当前操作层，不等于取消单位 AI 行为。

这里展示了一个重要标准：

> **基础交互文档应该优先定义“默认状态”和“焦点规则”。**

因为如果默认状态不明确，后面的所有按键规则都会产生歧义。

### 鼠标规则不是只写正常输入

当前文档除了传统 RTS 的：

- 左键选择；
- 右键 Smart Command；
- 框选；
- 小地图；
- 镜头控制；

还单独写了鼠标异常与边界，例如：

- 没有己方可控单位时右键空地；
- 没有己方可控单位时右键敌人；
- 输入后目标失效；
- System AI 中选择己方单位；
- System AI 中查看敌方单位。

因此输入文档不能只是一张“快捷键表”。

### 键盘规则明确状态和防误操作

当前关键规则包括：

- `Tab`：Direct Control 与 Unit AI Command；
- `` ` ``：System AI 的**单向进入键**；
- `V`：按住语音输入。

尤其 System AI 已经明确：

> `` ` `` 不是 Toggle。

也就是说：

```text
不在 System AI
→ 按 `
→ 进入 System AI

已经在 System AI
→ 再按 `
→ 保持 System AI
```

这是一个典型的“重要状态不能被重复输入意外关闭”的规则。

文档同时列出了：

- 无己方对象按 `Tab`；
- 查看敌人时按 `Tab`；
- System AI 中按 `Tab`；
- Unit AI 中按 `` ` ``；
- System AI 中再次按 `` ` ``；
- 空控制组；
- `F1` 没有合法对象；
- A / P 等待目标时按 `Esc`；
- 输入过程中对象失效；
- 连续快速切换模式。

### Unit AI 和 System AI 都分别有自己的边界

基础交互文档没有把所有异常丢进一个大杂烩章节。

而是：

- 鼠标规则旁边有鼠标异常；
- 键盘规则旁边有键盘异常；
- Unit AI 有自己的状态与异常；
- System AI 有自己的异常；
- 语音有自己的作用范围和异常。

这种写法适合复杂系统：

> **异常尽量靠近对应的正常规则写，同时再用通用原则兜底。**

### 语音规则重点解决“作用范围”

当前语音规则已经明确：

```text
明确语义
>
当前选中对象
>
默认上下文
```

并规定：

- 单位级语义不能自动升级成系统级；
- 无法判断对象或范围时不执行；
- 目标失效时不向失效对象执行；
- 明确系统级语义可以按系统范围解释；
- 语音失败不改变当前控制模式。

这体现了本项目 AI 策划的一个核心标准：

> **AI 可以推理，但权限范围不能靠猜。**

### 基础交互文档还有统一冲突原则

当前已经把输入优先关系写成明确顺序，核心方向是：

```text
明确玩家直接输入
>
明确模式切换
>
当前合法控制对象
>
当前控制层级规则
>
AI 自动行为
>
默认行为
```

同时还有通用异常原则：

- 不明确，不扩大；
- 操作失败，不自动切状态；
- 对象失效必须收敛；
- 重复输入必须可预测；
- 玩家明确输入优先；
- 异常必须有最小反馈。

这部分应该成为其他玩法和 AI 文档处理边界问题时的重要参考。

# 3. 从这两份正式文档中总结出的项目标准

这两份文档现在已经不能再描述为“正常流程比较清楚，但异常处理不足”。

**当前正式版本已经把异常、边界、状态回退和冲突优先级纳入正文。**

新手应该从它们实际学习下面这些东西。

## 3.1 先明确“本文负责什么”

两份正式文档都会在最前面说明：

- 状态；
- 本文定义；
- 本文不定义；
- 必要时说明前置文档。

以后新文档也应该优先这样做。

---

## 3.2 先定默认状态，再写操作

例如基础交互不是直接从 `Tab` 开始写，而是先确定：

> 选中任意己方单位 / 小队后，默认操作层始终是 Direct Control。

这类默认规则决定整个系统的基础心智，必须比具体快捷键更早明确。

---

## 3.3 正常规则必须同时考虑“怎么退出”

例如 System AI 不只是定义如何进入。

正式文档同时定义：

- 如何进入；
- 重复输入怎么办；
- 什么操作不会退出；
- 什么操作才真正退出；
- 退出以后回什么状态。

以后所有状态型玩法都应这样写。

---

## 3.4 重要功能必须考虑误操作

System AI 的 `` ` `` 被明确设计成单向进入，而不是再次按下退出，就是典型例子。

原因不是程序实现，而是玩家操作风险：

> 一个重要的全局 AI 状态不应该因为连按、双击或误触被轻易关闭。

因此异常处理不仅包括“非法输入”，也包括：

- 高频误触；
- 连续输入；
- 状态抖动；
- 焦点误切换；
- 用户很可能发生的错误操作。

---

## 3.5 异常必须写结果，而不是只写“无效”

例如不能只写：

> 无单位时 `Tab` 无效。

应该写到类似：

| 异常情况 | 游戏处理 | 玩家反馈 | 原状态 |
|---|---|---|---|
| 无己方可控制对象时按 `Tab` | 不进入 Unit AI | 轻量提示“请先选择单位” | 保持 |

这是当前两份正式文档已经采用的格式。

---

## 3.6 状态、对象、行为要区分

当前正式文档已经明确：

> Direct Control 只是当前玩家操作层，不等于取消单位已经生效的 AI 行为。

因此策划写文档时要区分：

- 当前选中的对象是谁；
- 玩家当前在哪个操作层；
- 单位当前正在执行什么行为；
- AI 当前是否仍在运行。

不能把这些不同概念写成一个“状态”。

---

## 3.7 冲突必须有优先级

如果多个规则可能同时成立，就不能写“系统自行判断”。

应该像当前基础交互和 UI 文档一样，明确：

- 玩家直接输入；
- 模式切换；
- 当前合法对象；
- 当前控制层；
- AI 自动行为；
- 默认行为；

谁先，谁后。

---

## 3.8 “当前不包含”是正式文档的一部分

当前两份文档都明确列出了不属于自己职责的内容。

这样做是为了：

- 防止文档无限扩张；
- 防止两个文档重复定义同一规则；
- 防止程序把“没写”理解成“可以自己决定”；
- 为后续专项文档留下明确接口。

---

# 4. 策划文档必须写什么

## 4.1 文档基本信息

文档开头至少写：

```md
# 策划文档_<系统名称>

> 状态：草案 / 评审中 / 冻结
> 本文定义：
> 本文不定义：
```

如果系统依赖其他规则，再增加：

```md
> 前置文档：
> - 《策划文档_基础交互逻辑文档》
> - 《AI副官_权限与情报规则_P0》
```

目的不是增加形式，而是防止一份文档无限膨胀。

## 4.2 一句话核心规则

每个系统开头必须先用一句话说明核心。

例如：

> 选中任意己方单位 / 小队后，默认操作层始终是 Direct Control；如需进入 Unit AI，玩家必须再次明确按 `Tab`。

如果一句话都说不清楚，说明系统本身还没有设计清楚。

## 4.3 正常流程

正常流程至少写：

```text
触发
↓
进入状态
↓
玩家执行操作
↓
游戏产生结果
↓
给出反馈
↓
保持 / 退出状态
```

不要只写“按键有什么功能”，还要写按完之后：

- 状态是否变化；
- 当前对象是否变化；
- UI 是否变化；
- 原状态是否保留；
- 如何退出。

## 4.4 状态变化

只要系统存在“模式 / 状态”，必须明确：

- 进入条件；
- 当前状态；
- 退出条件；
- 自动退出条件；
- 被其他状态打断后的结果。

推荐写成表格：

| 当前状态 | 操作 | 结果状态 |
|---|---|---|
| Direct Control | `Tab`，且存在可控制己方对象 | Unit AI Command |
| Unit AI Command | `Tab` | Direct Control |
| Direct Control | `` ` `` | System AI Command |
| System AI Command | `` ` `` | 保持 System AI |
| System AI Command | 选择己方单位 / 小队 | 该对象的 Direct Control |

## 4.5 玩家反馈

任何玩家操作都应该至少定义一种反馈。

反馈可以是：

- UI 高亮；
- 状态文字；
- 音效；
- 光标变化；
- 战场标记；
- 临时提示；
- 操作无效提示。

不要只写：

> 玩家无法执行。

应该写：

> 操作不执行，当前状态保持不变，并显示轻量提示“当前没有可控制单位”。

---

# 5. 异常处理统一标准

以后涉及输入、状态、目标、AI、UI 的策划文档，都应该有一个“异常与边界规则”章节。

## 5.1 异常表标准格式

| 异常情况 | 游戏处理 | 玩家反馈 | 原状态 |
|---|---|---|---|
| 无选中单位时按 `Tab` | 不进入 Unit AI | 轻量提示“请先选择单位” | 保持 |
| 当前单位死亡 | 清除当前对象 | 当前对象区切回无选择状态 | 退出当前单位控制状态 |
| 语音无法判断作用范围 | 不执行 | 请求玩家补充对象或范围 | 保持 |
| 当前指令不可执行 | 不执行 | 按钮灰化或短提示原因 | 保持 |

这个表格至少回答四件事：

1. 发生了什么异常；
2. 游戏到底执行不执行；
3. 玩家看到什么；
4. 原来的状态保不保留。

## 5.2 异常处理默认原则

### 原则 A：不明确，不扩大

特别是 AI 指令：

> 无法判断作用范围时，不得自动把局部命令扩大到系统级命令。

### 原则 B：失败不等于切状态

如果一个操作无法执行：

> 默认保持当前模式和当前选择，不因为失败自动跳到其他状态。

### 原则 C：直接输入优先于自动行为

玩家新的明确操作与 AI 当前行为冲突时：

> 玩家明确输入优先。

具体接管后的 AI 是否继续、暂停或恢复，由对应 AI 行为文档定义。

### 原则 D：对象失效必须收敛

如果当前选中单位死亡、销毁、离场或失去控制权：

> 不能继续保持一个指向失效对象的操作状态。

必须定义回退到：

- 无选择状态；
- Direct Control；
- 上一个合法对象；
- 或其他明确状态。

### 原则 E：重复输入必须可预测

例如连续按 `Tab`：

> 每次都按状态机正常切换，不因为动画还没完成就进入第三种未知状态。

### 原则 F：异常必须有玩家可理解的反馈

不能只在后台忽略。

但反馈也不能过度打断：

- 高频小错误：轻提示 / 灰化；
- 需要玩家重新选择：明确提示；
- 高风险 AI 歧义：要求确认；
- 严重阻断：才使用明显弹窗。

---

# 6. 规则冲突怎么写

一个系统只要存在多个输入或多个控制层级，就必须写“优先级”。

推荐格式：

```text
明确玩家直接输入
>
明确模式切换
>
当前合法控制对象
>
当前控制层级规则
>
AI 自动行为
>
默认行为
```

例如语音：

```text
明确语义
>
当前选中对象
>
默认上下文
```

不要只写“系统智能判断”。

“智能判断”不是规则。

如果必须让系统判断，也要写：

- 判断依据；
- 优先顺序；
- 判断失败时怎么办。

# 7. 策划文档不应该写什么

## 7.1 不写程序实现细节

策划可以写：

> Unit AI 状态下，QWER 切换为单位 AI 行为。

不要写：

> 创建一个 UnitAIController 类，然后在 Process 中监听 Tab。

后者属于程序设计。

## 7.2 不把未确认的想法写成正式规则

错误：

> AI 以后应该还能自动建造、生产、外交、科研。

如果当前没有冻结，应写：

> 当前不定义生产、科研等 System AI 行为。

正式文档必须区分：

- 已确定；
- 示例；
- 暂定；
- 待确认；
- 当前不包含。

## 7.3 不使用无法验收的模糊词

尽量避免：

- 合理处理；
- 智能判断；
- 适当提示；
- 必要时；
- 尽量；
- 自动优化；
- 根据情况；
- 友好地显示。

如果一定要使用，后面必须补充规则。

例如不要写：

> AI 根据情况决定是否撤退。

应写：

> 本文只定义“保全优先”是撤离倾向；具体撤退触发条件由《单位战斗行为规则》定义。

## 7.4 不重复定义其他文档已经冻结的规则

如果基础交互已经规定：

> 选中己方单位后默认 Direct Control；`Tab` 用于进入 / 切换 Unit AI；`` ` `` 是 System AI 单向进入键。

其他 UI 文档不要重新创造第二套输入和状态规则。

只写：

> 按照《策划文档_基础交互逻辑文档》的 `Tab` 规则进入 Unit AI Command。

## 7.5 不在一篇文档里解决所有系统

例如 UI 文档不需要同时定义：

- AI 目标选择算法；
- 单位伤害计算；
- 寻路；
- 语音识别技术；
- 网络失败重连。

只写 UI 必须知道的：

> 指令不可执行时，该按钮如何显示、玩家得到什么提示。

# 9. 一个合格规则应该写到什么程度

例如只写：

> 按 `Tab` 进入 Unit AI。

还不够。

推荐写成：

### 正常规则

- 当前存在可控制的己方单位 / 小队时，按 `Tab` 进入 Unit AI Command。
- 当前选择对象保持不变。
- QWER 从普通技能切换为该对象对应的 AI 行为。
- 当前对象区增加 `UNIT AI` 标识。

### 退出

- Unit AI Command 中再次按 `Tab`，返回 Direct Control。
- 已经设定的 AI 行为不因为退出操作层而取消。

### 异常

| 情况 | 处理 |
|---|---|
| 当前没有选中对象 | 不进入 Unit AI，并提示先选择单位 |
| 当前对象在切换过程中失效 | 退出 Unit AI，进入无选择状态 |
| 当前对象不支持 Unit AI | 不切换，显示不可用反馈 |
| 连续快速按 `Tab` | 严格按照当前状态切换，不产生中间状态 |

这样程序、UI、测试看到的是同一套规则。

再例如，System AI 不能只写：

> 按 `` ` `` 进入 System AI。

当前正式文档已经写到：

- 不在 System AI 时，按 `` ` `` 进入；
- 已经在 System AI 时，再按 `` ` `` 不退出；
- 连续按、误触、双击不能关闭；
- 查看敌方单位不退出；
- 选择己方单位 / 小队才退出，并回到该对象 Direct Control。

这就是“规则写完整”的标准：**正常输入、重复输入、误操作、退出条件和退出后的状态都明确。**

# 10. UI 文档专用规则

UI 文档重点写：

- 页面 / HUD 有哪些区域；
- 每个状态显示什么；
- 哪些元素固定；
- 哪些元素替换；
- 哪些元素高亮；
- 状态切换时如何变化；
- 无对象、不可用、失败、等待时显示什么。

UI 文档不负责定义：

- AI 内部怎么决策；
- 寻路怎么算；
- 伤害公式；
- 程序类和节点；
- 数据存储方式。

UI 异常至少考虑：

- 没有选中对象；
- 多选；
- 混合单位选择；
- 对象死亡；
- 功能不可用；
- AI 正在处理；
- AI 指令失败；
- 输入歧义；
- 状态被另一输入打断。

---

# 11. 输入 / 交互文档专用规则

交互文档重点写：

- 输入是什么；
- 输入作用于谁；
- 前置条件；
- 执行结果；
- 状态变化；
- 输入冲突；
- 无效输入；
- 中断和退出。

输入异常至少考虑：

- 没有合法目标；
- 当前对象不可控；
- 同一个键在不同模式下的含义；
- 两个模式是否可以叠加；
- 连续输入；
- 输入发生时对象已经失效；
- 输入与 AI 当前行为冲突；
- 模糊语音 / 模糊目标；
- 操作被其他高优先级输入打断。

---

# 12. 表格、文字和示例怎么用

## 用表格

适合：

- 按键映射；
- 单位类型对照；
- 状态切换；
- 异常处理；
- 优先级；
- UI 区域职责。

## 用短句

适合：

- 核心原则；
- 冻结原则；
- 限制条件；
- 不包含内容。

## 用示例

示例只能帮助理解，不能代替规则。

例如：

> 示例：“全军收缩防线” → System AI。

真正的规则仍然必须写：

> 明确包含“全军、整体、整个战场、战线”等全局语义时，按系统级指令判定。

# 13. 图片怎么配

如果一个交互或 UI 用文字很难直接理解，可以配图。

建议同名：

```text
策划文档_UI交互说明.md
策划文档_UI交互说明.png
```

图片负责：

- 布局；
- 相对位置；
- 视觉层级；
- 状态差异；
- 玩家第一眼应该看到什么。

Markdown 负责：

- 规则；
- 状态；
- 进入退出；
- 异常；
- 优先级。

不要让“图片里看起来是这样”成为唯一规则来源。

# 14. 文档状态标准

| 状态 | 含义 |
|---|---|
| 草案 | 可以大幅修改，不作为正式实现依据 |
| 评审中 | 主方案已形成，等待跨职能确认 |
| 冻结 | 当前版本作为程序 / UI / 测试正式依据 |
| 备用 | 保留参考，但不是当前唯一主规则 |
| 废弃 | 不再使用，应明确指出替代文档 |

如果写“冻结”，就不要同时在正文大量使用“可能、以后也许、应该可以”。

未确定内容应移到“待确认”或“不包含”。

# 15. 新手策划写完后的自检清单

提交评审前逐项检查：

- [ ] 我有没有写清楚本文定义什么？
- [ ] 我有没有写清楚本文不定义什么？
- [ ] 一句话能不能说清系统核心？
- [ ] 正常流程是否完整？
- [ ] 玩家如何进入？
- [ ] 玩家如何退出？
- [ ] 状态是否会自动退出？
- [ ] 玩家操作之后 UI 有什么反馈？
- [ ] 没有合法对象时怎么办？
- [ ] 当前对象失效时怎么办？
- [ ] 操作不可执行时怎么办？
- [ ] 连续输入时怎么办？
- [ ] 两条规则冲突时谁优先？
- [ ] AI 指令范围不明确时怎么办？
- [ ] 有没有使用“合理、适当、智能判断”等模糊词但没有给规则？
- [ ] 有没有写了程序实现细节？
- [ ] 有没有重复定义其他已经冻结的规则？
- [ ] 示例和正式规则有没有混在一起？
- [ ] 已确定和未确定内容有没有明确区分？
- [ ] 程序和测试是否能根据本文直接写验收项？

如果其中有 3 项以上答不上来，文档通常还不适合进入“冻结”状态。

# 16. 本项目策划文档最终原则

策划文档追求的不是字多，而是：

> **正常情况明确，异常情况明确，边界明确，状态明确，责任范围明确。**

推荐所有新文档遵循：

```text
先定义范围
↓
再定义核心规则
↓
写正常流程
↓
写状态变化
↓
补异常与冲突
↓
明确不包含内容
↓
最后冻结
```

一个好的策划文档应该让程序、美术、UI 和测试看到以后，对“这个系统到底应该表现成什么样”得到同一个答案。

如果一条规则需要团队成员自行猜测，说明这条规则还没有写完。
