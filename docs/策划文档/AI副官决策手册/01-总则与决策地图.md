# 01 · 总则与决策地图

> 策略参考；开发、接口和验收统一从 [当前执行入口](../../程序文档/AI副官_当前执行入口.md) 进入。本章的流程是目标设计，不代表全部已实现。

## 1. 当前方案的链路

```
Godot 观测/事件
  → LangGraph 异步协调
  → PydanticAI 调用本机 Ollama / MiniCPM5-2B（**唯一决策模型**）
  → 四列短任务修改（同一模型的快速 / 深度模式）
  → 程序按请求 DecisionFrame 解码并编译为任务
  → 程序权威校验（权限/预算/能力/合法目标）
  → 游戏执行器与单位行为树（含寻路、持续交战、返程）
```

- **只有一个决策模型**。PydanticAI 是结构化调用层，不是第二个指挥官。
- 每局**最多一个实际在途推理**；观测、回执、玩家事件独立处理。取消客户端等待不表示模型已完成，不得立即堆积新请求。
- 模型**超时 ≠ 部队停止**：已接受的任务继续执行（见 [08](08-任务寿命与执行反馈.md)）。

## 2. 三层分工（本手册最重要的概念）

| 层 | 谁负责 | 内容 | 模型可否改变 |
|---|---|---|---|
| **硬约束** | **程序** | 权限（玩家接管优先）、预算与预留、单位能力、合法目标、幂等、代际、TTL | ❌ 不可 |
| **策略偏好** | **模型** | 扩张还是补兵、侦察哪里、抽调哪支队伍、打还是撤、集结还是骚扰 | ✅ 只能在这里选 |
| **持续执行** | **执行器** | 采集往返、到位防守、移动交战、寻路脱困、有限追击、归位 | ❌ 不需要每轮重下 |

**边界铁律**：

- 候选筛选**只做合法性粗筛**，不得"偷偷把所有决策提前做完再让模型复述"。
- 允许**有效的不作为**：`维持现有任务`、`等待资源`、`信息不足先侦察` 都是合法选择。
  **不强迫每轮下新命令**——这本身就是降低 2B 模型出错率的有效手段。
- 持续执行类动作（如"到了就守着"）**每轮重复下发是错的**，会重置任务、丢进度。

## 3. 整局决策地图（可扫描）

**核心：四条线同时推进，不是串行剧本。**

```
                        ┌─────────────── 全局发展阶段（一个，缓慢推进）───────────────┐
                        │  摸底 → 立足 → 扩张 → 施压 → 收束                              │
                        └───────────────────────────────────────────────────────────┘

  经济线(worker)      采集 ──▶ 补工人 ──▶ 换更远/更富矿点 ──▶ 恢复(被打击后)
  建造线(builder)     产能候选 ──▶ 模型选择兵营/车厂/防御等 ──▶ 完工与重建
  侦察线(授权执行者)  开局散点 ──▶ 定向探敌基地 ──▶ 持续更新敌情 ──▶ 情报过期→重探
  军事线(作战单位)    零散 ──▶ 集结(不添油) ──▶ 防守/前压 ──▶ 进攻 ──▶ 撤退 ──▶ 重组再出击

  局部紧急事件（插队，不改变上面四条线的进度）
    基地受袭 / 单位受击 / 资源点被威胁 / 关键单位阵亡 / 路径失败

  玩家层（最高优先，随时插入）
    玩家命令 ──▶ 立即生效，实际受影响对象退出冲突 AI 任务
              ──▶ 明显改变计划时提出意图确认（确认目标/我来指挥/误触交回）
```

**同时性要求（反面清单）**：

- ❌ "侦察完成后才采集" —— 侦察线与经济线必须在**同一轮里并行存在**。
- ❌ "采集完成 4 个工人才开始建兵营" —— 建造线由**余额与建造者空闲**驱动，不由采集线完成驱动。
- ❌ "全军集火 / 全军回防" —— 只对**实际受影响对象**生效（见 [06](06-策略库-玩家介入与故障恢复.md)）。
- ❌ 为所有状态组合建巨大状态机 —— 只维护：**1 个阶段 + N 条小队任务 + 若干紧急事件**。

## 4. 一轮决策的最小结构

```yaml
phase: 立足                 # 程序根据已批准任务和权威进度维护，不自行决定战略
tracks:                     # 四条线的当前任务（可空）
  economy:  gather  | null
  build:    build   | null
  scout:    scout   | null
  military: 集结/防守/进攻/撤退 | null
urgent:                     # 紧急事件摘要；合并与调度按当前技术设计，不限于此示例一条
  - kind: base_under_attack
player:                     # 玩家控制对象（程序保证，模型不得下发）
  controlled: ["Unit_3"]
```

模型**不输出**上面这些元数据字段（`phase`/`tracks` 由程序装配进上下文）。
模型只输出**四列任务修改**，见 [07](07-候选筛选与输出契约.md)；程序不得自行补上模型未选择的扩张、兵种切换或进攻。

## 6. 限制与预期管理

- 限定任务词表、合法目标与输出长度，**有望减少延迟和错误**，
  但**不会提高模型本身的 token/s**；实际收益必须由 [10-评测方案](10-评测方案.md) 同条件测试确认。
- 历史测试曾发现多步政策式提示伴随玩家接管违规等回归，不能据此断言模型没有多步判断能力。
  发展候选应保留合理竞争项与“维持”，程序负责事实和约束，模型负责选择；相关收益须用当前模型、提示词和观测复核。
