# 10 · AI 副官评测方案

> 状态：**Canonical Evaluation Plan / 2026-09-25**
>
> 本章用于回答一个产品问题：**模型是否真的让对局变得更好？**
>
> 旧版只比较“无手册 vs 手册提示词”的 A/B 方案已经不足以覆盖当前 Laya + 2B + 规则混合架构，现改为分层对照。

## 1. 评测原则

必须把以下四件事分开：

1. **模型能否正常输出**；
2. **输出是否通过程序校验**；
3. **订单是否真的执行完成**；
4. **执行后是否改善了对局结果**。

不得用其中任何一项代替另一项。

例如：

- JSON 合法 ≠ 战术正确；
- Accepted ≠ Completed；
- val accuracy 高 ≠ 对局更强；
- 单局胜利 ≠ 模型有贡献；
- 模型调用成功 ≠ 模型订单没有被规则覆盖。

## 2. R0 / R1 / R2 / R3 对照

固定同一批地图种子、电脑难度、初始资源、平衡表和机器环境。

| 组 | 战略层 | 局部战术层 | 目的 |
|---|---|---|---|
| **R0** | 规则 | 规则 | 可玩的确定性基线 |
| **R1** | MiniCPM5-2B | 规则 | 测生成模型的战略增量 |
| **R2** | 固定战略 / 规则战略 | Laya | 测 Laya 的局部战术增量 |
| **R3** | MiniCPM5-2B | Laya | 测完整 AI 副官 |

如果 R0 本身长期不能造成敌方建筑伤害，则停止解释 R1～R3 的训练结果，先修规则基线和玩法 doctrine。

## 3. 固定条件

每组必须记录并固定：

- git commit；
- 地图与 seed；
- 电脑 AI 难度；
- 初始资源；
- balance / assets content version；
- System 1 backend；
- MiniCPM5-2B 模型标签、量化、context；
- Laya checkpoint；
- GPU / CPU；
- 冷启动或热启动；
- 对局最长时间；
- 是否自动接管；
- 规则 feature flags。

不能拿不同地图、不同平衡或不同 bug 修复前后的局直接比较“模型提升”。

## 4. 产品级指标

### 4.1 整局结果

| 指标 | 说明 |
|---|---|
| 胜负 | Victory / Defeat / Timeout |
| 对局完成率 | 是否进入真实 MatchOutcome |
| 完成时间 | 从开局到结算 |
| 首次敌方建筑受损时间 | 反映主动推进是否成立 |
| 敌方建筑伤害 / 分钟 | 比“有没有 attack 命令”更接近真实进攻效果 |
| 我方建筑损失 | 判断防守与扩张风险 |
| 击杀 / 损失 | 战斗交换质量 |
| 战损资源价值 | 不让廉价兵海掩盖实际亏损 |

### 4.2 运营

- 工人空闲时间；
- 资源采集曲线；
- 生产设施空闲时间；
- 第一座兵营 / 车厂 / 扩张完成时间；
- 90 秒 / 180 秒关键兵种数量；
- 资源溢出；
- 不合理双线分兵时长。

### 4.3 小队与命令

- 主攻兵力集中度；
- 小队订单完成率；
- 订单平均寿命；
- 无意义改令率；
- command churn；
- 到达后后继任务延迟；
- path_failed 后重规划延迟；
- 撤退后存活率。

## 5. 模型贡献指标

每个模型订单必须记录 source / owner，并跟踪最终状态。

至少区分：

```text
proposed
accepted
rejected_safety
rejected_stale
expanded
executing
completed
cancelled
replaced_by_player
replaced_by_emergency
replaced_by_rule
expired
```

核心指标：

| 指标 | 意义 |
|---|---|
| 模型订单接受率 | 输出是否具备执行价值 |
| 安全拒绝率 | 模型是否频繁违反硬约束 |
| 规则替换率 | 判断模型是否实际拥有控制权 |
| 完成率 | Accepted 后是否真正执行到底 |
| 结果回报 | 订单执行后 5/10/20 秒的伤害、击杀、损失、目标进展 |
| 空转减少量 | 相比 R0 是否减少闲置 |
| 建筑伤害增量 | 相比对应基线是否提高有效进攻 |

## 6. Laya 训练评测

聚合 accuracy 不再作为主要结论。

至少报告：

- macro-F1；
- 每个 skill 的 precision / recall；
- ATTACK / AMOV / RET / DEFEND 的覆盖率；
- actor / target / stance 分项准确率；
- branch 单独指标；
- 置信度校准；
- 按对局 / 地图 seed 切分 train / val，禁止把同一局相邻帧随机拆到两侧。

训练集必须统计类别分布。

如果 GAT / PROD 等规则多数类占比过高，应下采样；局部战斗样本应包含真实结果标签。

## 7. 2B 评测

除结构合法性外，还要测：

- 战略计划是否被采用；
- 计划在 TTL 内被规则覆盖的比例；
- 同一观测下是否能产生有意义的多小队组合；
- 超时率；
- P50 / P95；
- 冷启动单独统计；
- 重大事件后的异步重规划时间；
- 计划期间旧订单是否持续执行。

2B 不要求高频调用。重点是少量调用是否产生足够大的战略价值。

## 8. 玩家介入验证

构造真实玩家命令：

- 手动移动一个 AI 正在控制的单位；
- 手动接管一整个小队；
- 接管后保持一段时间；
- 显式交还；
- 在模型请求在途时接管；
- 在旧模型结果返回前改变 generation。

必须满足：

- 玩家命令立即优先；
- 只影响实际被接管对象；
- 旧结果不得复活；
- 未交还前 AI 不抢回；
- 交还后 AI 可重新纳入调度。

这类错误属于 P0，即使模型胜率更高也不能接受。

## 9. 规则基线门槛

在比较 AI 模型前，R0 至少需要：

- 经济持续运行；
- 生产不长期空闲；
- 第一支战斗小队主动离家；
- 能侦察到敌方；
- 能对建筑造成非零伤害；
- 受袭后有回防或撤退；
- 一局可进入结算。

如果 R0 失败，必须先说明是：

- 数值 / 兵种问题；
- 目标优先级问题；
- 路径问题；
- 扩张选址问题；
- 规则 bug；
- 执行器 bug。

不能把这些失败记成“模型能力不足”。

## 10. 推荐输出报告

每轮实验输出一张总表：

| Seed | Group | Outcome | Building dmg/min | K/L | First structure dmg | Order complete | Rule replace | Idle time | Notes |
|---|---|---|---:|---:|---:|---:|---:|---:|---|

并保存：

- 原始事件 JSONL；
- 订单生命周期；
- 模型输入 / 输出；
- 模型版本；
- 对局截图 / 关键时间点；
- commit / config；
- 汇总脚本版本。

## 11. 完成定义

AI 副官“更智能”只有在以下条件同时成立时才算有证据：

1. 同条件多 seed；
2. 模型订单确实执行，而不是被规则覆盖；
3. 产品指标相对 R0 / 对应基线有稳定改善；
4. 改善不是来自额外资源作弊、迷雾真值或不同平衡；
5. 权限、generation、TTL、战争迷雾等硬约束不回归。

未满足时只能写“功能已接入 / 模型已运行”，不能写“AI 能力已经提升”。
