# 08 · 任务寿命与执行反馈

> 核心原则：**命令接受回执 ≠ 任务执行结果**。两者必须分开记录。

## 1. 两层状态

| 层 | 来源 | 含义 | 谁写 |
|---|---|---|---|
| **命令回执** | Godot 权威端 | "命令收到了/被拒了" | 游戏 |
| **任务进度** | **观测差分** | "真的到达/打死了/采到了/造出来了" | 协调器 |

```jsonc
// 【设计示例】任务进度上报（与回执分离）
{
  "task_id": "t-1",
  "state": "running",
  "intents": {
    "i-1": {"action": "move", "status": "in_progress", "detail": "向目标推进中",
            "metrics": {"distances": {"Unit_2": 12.4}, "stall_count": 0},
            "updated_tick": 30000}
  },
  "updated_tick": 30000
}
```

## 2. 任务状态（7 + 2）

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `pending` | 已登记未开始 | 意图已接受但尚未观测到进展 |
| `running` | 进行中 | 有可观测进展 |
| `completed` | 完成 | **有成功证据**（见 §3） |
| `failed` | 失败 | 连续无进展 / 单位全灭 / 目标长期不可见 |
| `interrupted` | **可恢复**中断 | 目标脱离视野等（**不并入 failed**） |
| `cancelled` | 被取消 | 玩家命令 / 计划替换 |
| `expired` | 过期 | `expires_tick` 已过 |
| `partially_overridden` | 局部被玩家接管 | 部分对象退出 |
| `waiting_for_player` | 等待玩家确认 | 意图确认挂起 |

**聚合纪律**：只要该任务**还有活跃意图**就保持 `running`，**不得提前闭环**。

## 3. 成功证据（按动作类型，**必须可观测**）

| 动作 | 成功证据 | **反例（不算成功）** |
|---|---|---|
| `move/attack_move/scout/defend/regroup/retreat` | 距离目标 ≤ 到达半径（平面距离，只取 `[x,z]`） | 只是回了 `Accepted` |
| `attack` | 目标 `confirmed_dead` 或 hp 下降到 0 | 目标只是离开了视野（应为 `interrupted`） |
| `gather` | 单位 `carried` 增加；资源点从**完整**观测消失 = 耗尽 | 载量长期不变（应为 stalled） |
| `produce` | **队列项消失 + 观测到新单位** | **队列项消失就判成功** ❌ |
| `build` | 观测到该建筑实体且 `constructed` | 只是下了单 |

> ⚠️ `truncated=true` 时**不得**把"未返回"当成"消失/完成"。

## 4. 进度判定参数（当前实现，可配置）

| 参数 | 值 | 说明 |
|---|---|---|
| `arrive_radius` | 3.0 m | 平面距离 ≤ 该值算到达 |
| `stall_limit` | 3 次观测 | 连续无进展判 stalled |
| `progress_epsilon` | 0.1 m | 判定"有进展"的最小变化 |
| `lost_sight_ticks` | 600（≈10s） | 目标不可见 ≤ 该值只算"暂时" |
| 4×`lost_sight_ticks` | 2400（≈40s） | 超过则判 failed |

## 5. 生命周期分离（关键）

| | 请求接收期限 | 任务执行期限 |
|---|---|---|
| 对象 | 一次模型调用 | 已接受的长期任务（采集/防守） |
| 到期后果 | 本轮降级、不阻塞 tick | **不因一次推理期限结束而中断** |
| 关系 | 模型超时 **≠** 单位停机 | 长期任务自行继续 |

**防复活**：已过时的模型结果**不得**通过续期重新放行。

## 6. 请求身份绑定（程序生成，模型不得填写）

每次模型请求发出时绑定：

| 字段 | 作用 |
|---|---|
| `match_id` | 防止跨对局串味 |
| `snapshot_id` / `based_on_snapshot` | 结果不得用于更旧/更新的快照 |
| 对象控制代际 `generation` | 旧结果不得靠填最新代际复活 |
| 任务版本 `plan_version` / `task_id` | 计划替换后旧任务作废 |
| `expires_tick` | 有限窗口 |

**校验顺序**（保证丢弃原因准确）：
`玩家优先权` → `单位在观测内` → `代际匹配` → `重新接管授权` → `目标合法` →
`批次/活跃/在途去重` → `快照夹紧` → `预算` → `TTL 夹紧` → `批大小截断`。

## 7. 玩家与故障事件的优先级

```
1. 玩家有效命令（最高，立即生效）
2. 对局身份漂移 / 规则版本变化     → 全部拒绝，降级
3. 紧急事件（base_under_attack 等）→ 插队处置，不改变其它任务进度
4. 常规任务推进                     → 四条线并行
5. 模型建议                         → 只是 4 的输入之一
```
