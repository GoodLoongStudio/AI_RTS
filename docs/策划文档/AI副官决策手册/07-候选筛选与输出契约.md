# 07 · 候选筛选与输出契约

## 1. 一轮的完整数据流

```
观测事实（本轮）
  │
  ├─▶ ① 事实提取：把观测变成"可判定事实"（有闲工吗/有敌情吗/能造什么）
  │
  ├─▶ ② 候选生成：枚举"合法且可能有用"的任务方案（**只做合法性粗筛**）
  │        - 能力不匹配、目标非法、预算不足、玩家控管对象 → 直接剔除
  │        - 允许重复/近义方案（如“补工人”与“补士兵”都留）
  │
  ├─▶ ③ 候选裁剪：上限 N 条（建议 3~6），按局势相关性排序
  │
  ├─▶ ④ 模型选择：从候选里选 1~2 条 + 指定单位/目标；**或选"维持现有任务"**
  │
  └─▶ ⑤ 权威校验：能力/预算/代际/TTL/合法目标 → 通过则下发，否则丢弃并留痕
```

**②的铁律**：候选筛选**不得把决策提前做完**。
反例（错误做法）：筛选时就已经决定"派 Unit_2 去打 Enemy_9"，模型只是复述。
正例：给出 `attack`（可选目标列表）/`build barracks`（可选 builder 列表）/`维持`，
让模型决定**做哪个、用谁**。

## 2. 候选项的结构（程序生成，模型只读）

```jsonc
// 【设计示例，非当前接口】—— 程序装配进上下文，模型不需要回填这些字段
{
  "candidate_id": "BLD-01#1",
  "strategy_id": "BLD-01",
  "label": "建造兵营",
  "action": "build",
  "why": "尚无 barracks，且 build_options 提供该组合",
  "options": {
    "builders": ["Unit_2", "Unit_3"],
    "building": "barracks"
  },
  "blocked_by": []            // 有硬约束拦截项时列出（如 ["insufficient_reserve:A"]）
}
```

**注意区分（避免混淆字段）**：

| | 说明 |
|---|---|
| **本节的 JSON** | **新设计示例**，尚未实现 |
| **`DirectiveBatch`** | **当前真实接口**，见 §3 |
| 两者关系 | 候选是"给模型看的菜单"；`DirectiveBatch` 是"模型交回的答案" |

## 3. 模型输出契约（**当前真实接口**）

模型输出 **`DirectiveBatch`**（极简，元数据全部由程序补齐）：

```python
class TacticalDirective:      # directives[] 的元素
    intent_id: str = ""       # 可空，程序补
    action: str               # 12 个动作之一
    units: list[str]          # 只能是 own_units[].name，且不含 player_controlled_units
    target_id: str = ""       # 敌人/资源点 id
    target_pos: list[float]   # [x, z]
    producer: str = ""        # produce/build 的执行单位
    scene: str = ""           # produce: 产品类型 id；build: 建造 id
    task_id: str = ""

class DirectiveBatch:
    directives: list[TacticalDirective]     # 没有可执行动作时给 []
```

**模型严禁输出**：`intent_id / plan_version / based_on_snapshot / issued_tick /
expires_tick / generation` —— 这些由程序按请求上下文填写。

**字段规则**（与 [02 §2](02-事实与硬约束.md) 一致）：

| action | 必填 |
|---|---|
| `attack` | `target_id` ∈ `visible_enemy_ids` |
| `move/attack_move/defend/retreat/scout/regroup` | `target_pos = [x,z]` |
| `gather` | `target_id` ∈ `visible_resources[].entity_id` |
| `produce` | `producer` + `scene`（**整条**取自 `production_options`） |
| `build` | `producer` + `scene`（**整条**取自 `build_options`） |

`DirectiveBatch` 经 `directives_to_intents()` 转成 `IntentBatch` 的 `TacticalIntent`，
**元数据由程序填**，随后进入仲裁（校验/去重/TTL 夹紧/预算/代际）。

## 4. 完整示例：事实 → 候选 → 选择 → 反馈

### 4.1 当前事实（本轮观测摘录）

```jsonc
{
  "server_tick": 30000, "snapshot_id": 42,
  "own_units": [
    {"name":"Unit_0","type":"command_center","can_move":false,"can_produce":true},
    {"name":"Unit_2","type":"worker","can_move":true,"can_gather":true,"can_build":true},
    {"name":"Unit_3","type":"worker","can_move":true,"can_gather":true,"can_build":true}
  ],
  "visible_resources": [{"entity_id":"ResourceA","pos":[7.5,15.6]}],
  "visible_enemy_ids": [],
  "production_options": [{"producer":"Unit_0","product":"worker"}],
  "build_options": [{"builder":"Unit_2","building":"barracks"},
                    {"builder":"Unit_3","building":"barracks"}],
  "player_controlled_units": ["Unit_3"],
  "active_intents": [{"intent_id":"i-1","action":"gather","unit_ids":["Unit_2"]}]
}
```

### 4.2 程序产出候选（已剔除 `Unit_3`：玩家接管）

```yaml
- candidate_id: ECO-01#1
  label: 维持现有采集
  action: gather              # 保持 Unit_2 采集，不下发新命令
- candidate_id: BLD-01#1
  label: 建造兵营
  action: build
  options: { builders: [Unit_2], building: barracks }
  blocked_by: [unit_busy]     # Unit_2 正在采集 → 需先让位，属"可代价"
- candidate_id: ARM-01#1
  label: 补工人
  action: produce
  options: { producer: Unit_0, product: worker }
```

> 注意：`Unit_3` **没有**出现在任何候选里 —— 这是硬约束，不是让模型自己判断。

### 4.3 模型选择（示例输出，**当前接口**）

```json
{"directives": [
  {"action": "produce", "units": ["Unit_0"], "producer": "Unit_0", "scene": "worker"}
]}
```

含义：模型选择"补工人"，`Unit_2` 继续采集（未重复下发，符合"维持"）。

### 4.4 执行反馈（程序侧，非模型输出）

```
① 回执：{accepted: true, status: "Accepted"}            ← 命令接受回执
② 任务进度：active_tasks[t] = running                    ← 观测驱动的真实进度
   - produce：production[] 出现 worker 的 item → in_progress
   - 之后观测到新单位 Unit_7（unit_type=worker）→ **completed**
   - 若队列项消失但无新单位 → **failed**（不得判成功）
```

## 5. 防止"选项太少所以错误率低"

必须同条件检验两件事（见 [10](10-评测方案.md)）：

1. **候选是否漏掉必要行动**：构造"必须建造/必须撤退/必须侦察"的观测，
   检查候选集中**确实包含**该必要动作；若不含 → 候选生成有缺陷。
2. **候选是否已经把答案定死**：把候选数从 3 扩到 6（加入更多合法变体），
   看模型的**选择分布是否真的变化**。若选择不变 → 模型只是在复述，说明候选"过度具体"。

## 6. 输出长度纪律

- 普通轮次输出**尽量短**（目标：`directives` ≤ 3 条，无解释文字）。
- **解释只在必要时产生**（如意图确认场景），不要求模型输出长篇思考。
- 程序负责补齐全部元数据；模型**不复述上下文**。
