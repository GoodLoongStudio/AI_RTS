## 1. 当前运行链路

```text
Godot 权威观测 / 事件
        ↓
agent_runner / graph
        ↓
状态与任务装配
  - 玩家接管 / release
  - generation
  - TTL
  - active intents / routes / production ledger
  - squads / campaign / explore
        ↓
DecisionFrame / 候选
        ↓
Laya System 1（可配置）
        ↓ 不可用 / 超时 / 熔断
MiniCPM5-2B System 2
        ↓ 失败 / 超时
规则 baseline
        ↓
TaskPatch Decode
        ↓
IntentBatch
        ↓
程序校验 / 仲裁
        ↓
Godot 权威命令入口
        ↓
行为树和 RTS 执行器持续执行
        ↓
arrival / path_failed / damage / outcome / production 等反馈
```

当前实现的关键代码入口包括：

- `graph/task_patch.py`：候选、Laya 问题、四列解码、Intent 编译；
- `graph/laya_provider.py`：Laya 加载、预测、健康熔断、数据采集；
- `graph/state.py`：玩家接管、generation、任务状态、持久状态；
- `graph/rules_fallback.py`：无有效模型结果时的规则 baseline；
- `graph/behavior_tree.py`：持续行为与执行层；
- `graph/campaign.py`：副官内部发展主线和决策地图；
- `deploy/agent_runner.py`：协调、模型调用、运行时与日志；
- Godot DCS / NetSync / CommandRuntime：最终权威执行和再次校验。

## 2. 当前三类决策源

### 2.1 Laya System 1

Laya 是判别式选择层：

- 不生成任意文本；
- 从程序提供的候选集合中选技能、执行者、目标和参数；
- 可选取决策地图分支；
- 不可用时必须快速回退；
- 持续不健康时由熔断器停止重复调用。

Laya 的当前价值目标不是复制 GAT / PROD 等规则多数类，而是逐步聚焦：

- 局部交战姿态；
- 主攻目标；
- 集火 / 换靶；
- 撤退 / 等待增援；
- 小队支援关系。

### 2.2 MiniCPM5-2B System 2

2B 通过本地 Ollama 运行。

适合：

- 多目标组合判断；
- 较长周期的经济 / 扩张 / 生产取舍；
- 多小队计划；
- 重大事件后的异步重规划；
- 未来玩家自然语言意图理解。

2B 不进入逐帧同步关键路径；模型在途时继续执行上一份有效任务。

### 2.3 规则 baseline

规则层现在已经具备真实经济、生产、建造、侦察、推进、回防等能力。

它有两个职责：

1. 模型不可用时保证对局继续；
2. 保证无有效模型订单对象不会长期空转。

下一阶段必须避免的行为：有合法、未过期的模型小队订单时，规则层每 tick 再做一次战术重选并覆盖它。

## 3. 硬约束与玩家权限

以下内容必须在模型外保证：

| 项 | 当前机制 |
|---|---|
| 玩家接管 | `mark_player_override()` 使受影响单位 generation 变化并撤销冲突 AI intent |
| 显式交还 | `release_units()` 后才允许 AI 重新接管 |
| 旧结果失效 | generation / plan version / TTL / snapshot 等共同约束 |
| 合法执行者 | 能力匹配、AI lease、玩家控制状态 |
| 合法目标 | 当前规则和观测中的实体、位置、场景和目标域 |
| 幂等 | 重复 intent / command 不能重复扣费或重复执行 |
| 资源安全 | 预算、承诺、队列与资源预留由程序管理 |
| 持续执行 | 模型超时不能自动停止已经接受的任务 |

任何新模型或新训练路线都不能绕过这些边界。

## 4. Task Patch 的当前定位

`task_patch.py` 仍是当前生产落地通道。

它已经支持：

- squad / worker 等 actor；
- ATTACK / AMOV / DEFEND / RETREAT / SCOUT / GATHER / BUILD / PROD 等 skill；
- Laya 的分级候选；
- generation 和 task_version；
- TTL；
- DecisionFrame；
- 解码拒绝原因；
- Laya 决策地图 branch source。

但是从产品角度，**Task Patch 不再是最终交互模型**。

目标结构为：

```text
模型 / Laya
   ↓
SquadOrder（原子小队订单）
   ↓
一次性校验
   ↓
展开为现有 Task Patch / Intent
   ↓
Godot
```

这样可以保留现有稳定的 Intent 和权威链路，同时解决“一支小队动作被拆成多行、逐单位审理”的问题。

## 5. SquadOrder 目标契约

建议至少包含：

```json
{
  "order_id": "ord-...",
  "squad_id": "main",
  "units": ["U1", "U2"],
  "mode": "attack_move",
  "target": {"kind": "enemy_structure", "policy": "production_then_turret"},
  "rally": [62, 41],
  "stance": "aggressive",
  "owner": "laya",
  "generation": 8,
  "ttl": 80,
  "cancel_when": ["target_dead", "base_under_attack"]
}
```

关键语义：

- 一个订单对应一个战术意图，而不是 N 个互不关联的单位行；
- `owner/source` 用来测模型贡献；
- `generation` 继续复用当前控制代际；
- `ttl` 与任务完成条件分离；
- `cancel_when` 只允许预先声明的合法事件；
- 程序仍负责最终展开和硬校验。

## 6. 订单租约

未来仲裁顺序：

```text
紧急安全事件
 > 玩家命令
 > 有效 AI 小队订单
 > 战略计划展开订单
 > 无订单规则 baseline
```

规则层仍可以：

- 修正不可达路径；
- 拒绝非法目标；
- 限制越界；
- 在单位无法执行时退化；
- 处理即时求生。

规则层不应该：

- 仅因为下一 tick 的 baseline 选择不同，就覆盖还在 TTL 内的模型订单；
- 把“安全拒绝”伪装成新的策略命令；
- 在模型订单有效时重新给每个单位独立选另一个战略目标。

## 7. 本地模型服务

游戏侧已经加入本地模型服务拉起 / 预热链。

产品要求：

- 玩家从编辑器或导出 exe 启动，都不应手工先开 Ollama；
- 模型冷启动期间明确显示“预热中”，规则层继续指挥；
- 模型服务端口和 runner 配置必须统一；
- 不允许自对局 runner 覆盖真人玩家 HUD 状态；
- 游戏关闭 / 新局启动时进程生命周期必须可追踪。

## 8. Laya 依赖与打包

旧文档曾断言“副官 Python 环境不需要 torch”。

该结论只对 **MiniCPM5-2B / Ollama-only** 路线成立。

当前若发布包启用 Laya：

- 需要真实安装 Laya 所需依赖；
- torch / transformers 等依赖是否随包必须按实际环境锁定；
- 必须重新测包体、显存、冷启动和兼容性；
- 不可为了保持旧 5.3GB 预算而漏打运行依赖。

因此交付必须区分：

- 2B-only 轻量 AI 模式；
- Laya + 2B 完整 AI 模式。

## 9. 接入新功能时的纪律

新增模型、技能、任务或策略时必须回答：

1. 这是硬约束、策略选择还是执行细节？
2. 模型是否真的需要决定它？
3. 当前规则是否已经能稳定完成它？
4. 如果模型选择成功，规则会不会下一 tick 覆盖？
5. 如何记录 source / owner / outcome？
6. 如何用 R0/R1/R2/R3 验证它产生了增量？

没有这些答案的功能不能直接堆进“AI 更智能”的范围。
