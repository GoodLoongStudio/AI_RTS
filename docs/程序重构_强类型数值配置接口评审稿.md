# 强类型数值配置接口评审稿

> 日期：2026-08-15
>
> 状态：等待项目负责人评审
>
> 对应工作项：`ARCH-012`、`ECO-007`

本文确定经济、单位、建筑、武器、生产和施工数值的权威来源、加载边界及渐进迁移方式。本文不调整平衡数值，不顺带修复导航、Tooltip DPS 或规则 AI 行为，也不制作运行中调参 UI。

## 1. 当前问题

同一个业务数值目前可能存在于多个位置：

| 来源 | 当前内容 | 风险 |
|---|---|---|
| `MatchConstants.gd` | 单位 HP、视野、攻击、成本、工期、采集时间等 | Dictionary 键和值均无编译期约束，场景路径被当作类型 ID |
| `GodotProductionDefinitionRepository.cs` | 再次硬编码生产成本、工作量和生产者资格 | 已与 GDScript 形成重复权威来源 |
| `.tscn` | 导航、选择、目标、障碍等多种 radius | 同名数值语义不同，不能安全合并成单一半径 |
| `Unit.gd` | 根据脚本路径查找 `DEFAULT_PROPERTIES` 并写入运行态 | 重命名或换场景会静默破坏单位定义 |
| HUD 与规则 AI | 直接读取 Legacy Dictionary | UI、Human、规则 AI 和未来大模型入口可能得到不同规则 |
| C# Godot Adapter | 从 Node 动态读取 `attack_damage`、`attack_range`、`radius` 等 | 字段缺失或类型错误只能在运行时暴露 |

因此本项的核心不是把 Dictionary 换成另一个全局对象，而是建立“外部配置 DTO → 完整校验 → 不可变 Catalog → 运行态快照”的单向链路。

## 2. 设计结论（建议）

### 2.1 `UnitTypeId` 覆盖单位和建筑

建议新增稳定 `UnitTypeId`，表示一种可出现在战场上的实体类型。Tank、Worker、CommandCenter、炮塔以及未来移动要塞都使用这一类型；这里的 Unit 是 RTS 的广义单位，不等同于“可以移动的兵种”。

- `UnitId` 继续表示一局内的具体实例；
- `UnitTypeId` 表示跨对局稳定的类型，例如 `tank`、`command_center`；
- 现有 `ProductionDefinitionId` 和 `StructureDefinitionId` 暂不立即删除，由迁移 Adapter 显式映射到相同字符串值；
- 公共领域规则不得从 `.tscn` 路径或文件名推导 ID；
- ID 重命名属于显式数据迁移，不能静默生成新 ID。

建筑和移动单位共用类型身份，但通过可选能力组合区分行为，而不是用互斥的继承树区分：

```text
UnitTypeDefinition
├─ Health / Vision / Spatial
├─ Movement?          可移动
├─ Weapons[]          可攻击
├─ Gatherer?          可采集
├─ Constructor?       可施工
├─ Producer?          可生产
└─ Placement?         可作为建筑蓝图放置
```

这可以自然支持“不能移动但能生产”“能移动且能生产”“建筑可设置战斗姿态”等组合。

### 2.2 JSON 是权威数据格式

建议首轮使用仓库内版本化 JSON，例如：

```text
config/
├─ balance/demo.balance.v1.json
└─ godot/demo.assets.v1.json
```

`demo.balance.v1.json` 只保存引擎无关的数值和稳定 ID；`demo.assets.v1.json` 保存 `UnitTypeId → PackedScene/蓝图/投射物表现` 等 Godot 资源映射。二者分离后，更换模型或场景路径不会改变平衡配置，未来 Python 工具也可以读取同一份数值数据。

不建议用 `.tres` 作为权威平衡格式，因为它会把配置绑定到 Godot 类型系统；不建议继续使用 C# 静态字典，因为非程序成员和外部工具难以编辑及验证。

### 2.3 对局使用不可变配置快照

配置在 Match 装配、任何单位生成之前加载一次。校验通过后构造只读 Catalog，该局始终使用同一版本；运行中修改磁盘文件不会影响已经开始的对局。

开发期重新加载只发生在重新进入对局时。这样可以避免同一局前后数值不一致，也便于回放、缺陷复现和未来网络同步。对局记录至少保存 `schemaVersion`、`contentVersion` 和源文件内容哈希。

### 2.4 数值类型和单位

| 数值 | 类型与单位 | 规则 |
|---|---|---|
| 资源余额、成本、载荷 | `int` | 不允许负数；不因 UI 进度改用浮点数 |
| 生产/施工进度 | `int RequiredWork`、`int WorkPerTick` | 权威进度保持整数；百分比只是派生显示 |
| 攻击与采集间隔 | `int Milliseconds` | 字段名明确单位，避免裸 `float seconds` |
| HP 与伤害 | 首轮保持 `float` | 保留范围伤害、倍率和未来非整数效果；必须有限且非负 |
| 距离、速度、角度 | `float`，字段名标明 Meter/Degrees/Radians | 必须有限，按语义要求正数或非负数 |
| 比例 | `float` | 明确采用 `0..1` 还是可大于 1；友伤默认 `1.0` |

生产当前的 `180/360 RequiredWork` 和施工的 `200 RequiredWork` 是迁移期权威工作量，不把它们误写成秒。调度器如何把 Tick 转为现实时间仍由 Match 固定步进负责。

## 3. 建议的核心契约

以下是接口形状，不是待直接复制的最终实现代码：

```csharp
/// <summary>标识一种跨对局稳定的战场实体类型，包含移动单位和建筑。</summary>
public readonly record struct UnitTypeId(string Value);

/// <summary>描述一份已加载平衡数据的格式版本和内容版本。</summary>
public sealed record BalanceConfigVersion(
    int SchemaVersion,
    string ContentVersion,
    string ContentHash);

/// <summary>提供已经完整校验且在 Match 生命周期内不可变的数值定义。</summary>
public interface IGameBalanceCatalog
{
    BalanceConfigVersion Version { get; }
    UnitTypeDefinition? FindUnitType(UnitTypeId unitTypeId);
    WeaponDefinition? FindWeapon(WeaponDefinitionId weaponId);
    ProductionDefinition? FindProduction(ProductionDefinitionId definitionId);
    StructurePlacementDefinition? FindPlacement(StructureDefinitionId definitionId);
    ResourceDefinition? FindResource(ResourceKind kind);
}
```

`UnitTypeDefinition` 只组合已经验证的领域定义，不保留 JSON 可空字符串或动态 Dictionary。JSON DTO、领域 record 和运行态 Unit 状态必须是三个不同对象：

```text
JSON DTO（允许表达输入错误）
          │ Parse + Validate + Map
          ▼
不可变领域 Definition / Catalog
          │ Match 装配与生成
          ▼
运行态 Unit / Queue / ConstructionSite Snapshot
```

武器定义建议独立于单位定义，通过稳定 `WeaponDefinitionId` 引用。这样同一武器可以被不同单位复用，一个单位也能在以后配置多个武器。首轮只迁移当前主武器，不在本项实现 Beam、地雷或完整多武器调度：

```text
WeaponDefinition
├─ DeliveryKind
├─ BaseDamage
├─ CooldownMilliseconds
├─ RangeMeters
├─ TargetDomains
└─ WarheadDefinitionId

WarheadDefinition
├─ ImpactSelectionMode
├─ RadiusMeters
└─ FriendlyFireDamageMultiplier（当前 1.0）
```

投射物模型、音效和特效属于 Godot asset manifest，不进入领域武器数值。

## 5. 加载与失败语义

加载过程分为四步：

1. Godot Adapter 使用 `FileAccess` 读取仓库内配置；
2. JSON Parser 严格解析 DTO，拒绝未知字段，避免拼写错误被忽略；
3. Validator 一次收集全部可发现问题；
4. 零错误时才映射为不可变 Catalog 并交给 Match 组合根。

建议错误结构：

```csharp
public sealed record BalanceConfigError(
    BalanceConfigErrorCode Code,
    string Path,
    string Message);

public sealed record BalanceConfigLoadResult(
    IGameBalanceCatalog? Catalog,
    IReadOnlyList<BalanceConfigError> Errors);
```

首轮至少校验：

- schema 版本是否受支持，content version 是否非空；
- ID 是否为空、格式非法或重复；
- JSON 是否含未知字段、重复资源项或非法 enum；
- 数值是否为 NaN、Infinity、负数、零值非法或超出约定范围；
- Weapon、Warhead、Producer、Product 和 Placement 引用是否存在；
- 攻击域是否非空，Weapon 与单位能力组合是否自洽；
- 生产/施工成本是否非负，RequiredWork 是否为正整数；
- 当前 Demo 必需的九种单位/建筑、四种产品和五种蓝图是否齐全；
- Godot asset manifest 是否为每个可生成类型提供存在且类型正确的资源。

任何错误都不创建“部分 Catalog”，Match 应在启动前失败并输出全部错误路径。开发构建可显示诊断面板；正式构建进入可理解的加载失败界面。不得悄悄使用零值或硬编码默认值继续运行。

## 6. 与现有系统的兼容边界

### 6.1 Legacy GDScript

迁移期由一个只读 `BalanceConfigGateway` 向 GDScript 暴露按稳定 ID 查询的方法。HUD、Human 和规则 AI 可以逐个改为查询 Gateway；不允许新代码继续直接访问 `PRODUCTION_COSTS`、`CONSTRUCTION_COSTS` 或 `DEFAULT_PROPERTIES`。

在所有消费者迁移前，Legacy Dictionary 暂时保留，并由自动一致性测试比较旧值与新 Catalog。完成迁移后再删除对应 Dictionary，不能让两套数据长期并存。

### 6.2 Godot 场景

每个可命令实体必须显式声明 `unit_type_id`，不能继续由脚本路径推导。生成或加载场景时，Adapter 根据 Catalog 把 HP、视野和当前主武器参数写入 Legacy Node 字段，保证旧 Action 在迁移期继续工作。

场景中的 radius 不能本轮批量合并。导航半径、放置 footprint、可选取半径、可命中半径和视觉圈半径语义不同；迁移前先逐项绑定到命名明确的字段。视觉尺寸不得反向成为领域数值的权威来源。

### 6.3 C# 服务

`GodotProductionDefinitionRepository` 的硬编码目录首先改为从 Catalog 建立；生产和施工服务现有接口可以保持不变。命令校验逐步从 Node 动态字段转为“Catalog 静态能力 + 运行态快照”，但生命、存活、当前姿态、当前订单等可变状态仍属于运行态 Repository，不进入配置。

## 7. 分阶段迁移

建议把 `ECO-007` 拆成四个可独立验证的小步：

| 子项 | 内容 | 完成条件 |
|---|---|---|
| ECO-007A | 配置 DTO、严格 JSON Loader、Validator、不可变 Catalog、错误报告 | 纯 C# 测试覆盖成功和所有主要失败类别；尚不替换运行逻辑 |
| ECO-007B | 迁移资源、生产、施工定义 | C# Repository 不再硬编码；生产/建造人工行为与基线一致 |
| ECO-007C | 迁移单位基础属性与当前主武器 | 场景显式绑定 `UnitTypeId`；HP、视野、攻击值不再按路径读取 |
| ECO-007D | 迁移 HUD 与规则 AI，移除已迁移 Legacy Dictionary | 全仓无旧字典消费者；一致性测试完成使命后删除 |

这一顺序先建立基础设施，再切换低风险的经济闭环，最后处理场景半径和战斗等高耦合数据。每个子项单独提交并更新进度表；任一阶段均不要求同步迁移地图、镜头、输入、导航网格或 AI 操作点配置。

## 8. 测试与验收

自动测试至少包含：

- 基线 JSON 能构造完整 Catalog；
- 未知 schema、未知字段、重复 ID、非法数值和悬空引用均返回稳定错误码及路径；
- 错误配置不产生可用 Catalog；
- 资源成本和工作量保持整数，750 ms 等时间不发生浮点漂移；
- 新 Catalog 与 `2026-08-12` 基线逐项一致；
- 同一配置多次加载得到相同内容哈希和定义；
- Godot asset manifest 的场景均可加载且显式类型 ID 与映射一致。

人工回归沿用现有测试场景，重点确认资源扣款、建造、施工、生产、攻击、视野和 HUD 展示没有非预期变化。Tooltip 当前 `damage * interval` 的疑似 DPS 错误继续登记，不在配置迁移中顺手修复。

## 9. 本次评审需要确认

建议确认以下七项后开始 `ECO-007A`：

1. 接受 `UnitTypeId` 作为移动单位和建筑的统一类型身份，能力采用组合而非互斥继承；
2. 接受版本化 JSON 为权威数值格式，Godot 资源路径使用独立 asset manifest；
3. 接受每局加载一次不可变快照，本阶段不支持对局中热更新；
4. 接受严格加载：存在任一错误时拒绝创建部分 Catalog 和启动 Match；
5. 接受资源/工作量使用整数、时间使用整数毫秒、空间和伤害按语义使用有限浮点数；
6. 接受本轮只迁移基线，不修改平衡数值，也不顺手修复 Tooltip DPS；
7. 接受按 `ECO-007A～D` 分步实施，并在全部消费者迁移后删除对应 Legacy Dictionary。
