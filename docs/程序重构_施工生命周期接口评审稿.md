# 施工生命周期接口评审稿

> 日期：2026-08-15
>
> 工作项：`ECO-004`
>
> 状态：接口已确认，首轮实现完成，待人工验收

## 1. 目标与边界

本项迁移“施工现场已经由 Place 创建”之后的施工生命周期：

- 一个或多个 Worker 接受施工任务；
- Worker 前往现场并贡献施工工作量；
- Stop 暂停 Worker 的完整施工任务，保留目标且不自动恢复；
- Worker、现场和任务中途失效；
- 玩家取消现场并执行已评审的全额退款；
- 施工只完成一次，并发布与同步命令回执分离的权威事件。

建筑放置合法性和首次扣款属于已完成的 `ECO-003`；生产队列属于 `ECO-005`；维修、出售、拆除、占领、渐进支付和施工 UI 重做不在本项实现。

## 2. 当前 Legacy 行为

### 2.1 Worker 任务

`Constructing.gd` 同时负责：

1. 判断 Worker 与 Structure 是否同一玩家；
2. 通过 `MovingToUnit` 前往建筑边缘；
3. 到达后切换到 `ConstructingWhileInRange`；
4. 每帧直接调用 `Structure.construct(delta * speed)`；
5. 建筑完成或目标退出 SceneTree 后销毁 Action。

它没有稳定任务 ID、阶段查询、暂停状态或明确结束原因。Worker 被其他 Action 替换时，施工只会静默停止。

### 2.2 多 Worker

多个 Worker 可以分别创建 `ConstructingWhileInRange`，每个 `_process(delta)` 都直接累加同一浮点进度，因此目前事实上是无上限线性加速。但结果依赖帧序、没有统一聚合点，也无法可靠审计某一 Tick 有哪些 Worker 贡献了多少工作量。

### 2.3 Human 与规则 AI

- Human 放置成功后，`UnitActionsController` 读取“生成瞬间仍被选中”的 Worker 并隐式赋予施工 Action；右键未完成建筑也会直接替换 Action；
- 规则 AI 的 `ConstructionWorksController` 每 0.5 秒随机挑选 Worker 和现场，而且只要任意 Worker 正在施工，就不会再分配第二个 Worker；
- Place、Construct 和 AI 分配没有共享命令回执。

### 2.4 Stop、取消和完成

- `Unit.request_legacy_stop()` 对施工明确返回 `false`，所以现有统一 Stop 无法暂停施工；
- 选中未完成建筑点击通用取消按钮会直接调用 `cancel_construction()`，全额退款并删除节点；
- 完成同时发布局部 `constructed` Signal 和全局 `unit_construction_finished`；没有稳定 SiteId、完成 Tick、定义 ID 或幂等保护；
- Worker/建筑死亡、玩家取消和命令替换没有区分结束原因。

### 2.5 进度与 HP

`Structure.mark_as_under_construction()` 等待 Ready 后把默认满血重设为 1；通用 HP setter 把这次初始化下降误报为真实伤害，产生 `ECO-010` 的“刚建造就播报建筑受击”。后续进度又直接增加 HP，施工进度、可用最大 HP、当前战斗伤害和受击通知没有独立来源。

## 3. 建议分层

```text
Human 右键/放置后建造者  规则 AI 分配  未来 Agent
                    │
                    ▼
       Application ConstructionService
       ├─ Construct / Stop / Cancel 同步回执
       ├─ Worker 订单与现场状态
       ├─ 每个 SimulationTick 聚合工作量
       └─ 完成、取消、摧毁权威事件
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
 IConstructionWorkerPort   IConstructionSitePort
  移动/到位/火花表现       HP/几何/节点生命周期
```

- Domain/Application 不引用 Node、SceneTree、Timer、Signal 或 `delta`；
- Godot Adapter 负责 Worker 导航、施工火花、节点显隐和 Signal 兼容；
- Human、规则 AI 和未来 Agent 只负责选择 Worker/Site，不直接推进进度；
- 对大模型 AI 是否可见的完成信息由未来观察层决定，不能通过不发布权威事件来实现信息限制。

## 4. 稳定身份与整数工作量

施工现场继续使用其建筑 `UnitId` 作为 `ConstructionSiteId`，避免同一节点维护两套身份。建议新增：

```csharp
/// <summary>记录一个施工现场的权威工作量和生命周期。</summary>
public sealed record ConstructionSiteSnapshot(
    UnitId SiteId,
    PlayerId OwnerId,
    StructureDefinitionId DefinitionId,
    int RequiredWork,
    int CompletedWork,
    ConstructionSiteState State,
    long Version);
```

权威进度使用整数：

- `RequiredWork > 0`；
- `CompletedWork` 限制在 `[0, RequiredWork]`；
- UI 浮点进度只由两者相除得到；
- 每个 Worker 定义正整数 `BuildPowerPerTick`；
- 每个物理模拟 Tick 只在一个聚合点把所有实际到位、未暂停的 Worker BuildPower 求和并推进一次。

首轮保持当前约 3.33 秒单 Worker 建成的 Demo 节奏。具体整数可由 Adapter 从现有 `STRUCTURE_CONSTRUCTING_SPEED` 换算，后续迁到 `ECO-007` 强类型配置。

## 5. 现场状态

```csharp
public enum ConstructionSiteState
{
    /// <summary>现场有效，等待或正在接受 Worker 工作量。</summary>
    Active,
    /// <summary>工作量已经达到要求，建筑正式可用。</summary>
    Completed,
    /// <summary>拥有者明确取消，退款最多执行一次。</summary>
    Cancelled,
    /// <summary>施工中 HP 归零或被规则效果摧毁，不退款。</summary>
    Destroyed
}
```

只有 `Active` 可以接受 Construct 和工作量。三个终态不可逆，且每个现场最多发布一次终态事件。

## 6. Construct 命令

```csharp
public sealed record ConstructStructureCommand(
    IReadOnlyList<UnitId> WorkerIds,
    UnitId SiteId);
```

沿用现有批量命令语义，逐 Worker 返回：

- `Accepted`：拥有 Worker、Worker 有施工能力、现场存在且为同一玩家的 Active 现场；
- `WorkerNotFound / WorkerNotOwned / WorkerCannotConstruct`；
- `ConstructionSiteNotFound / ConstructionSiteNotOwned`；
- `ConstructionAlreadyCompleted / ConstructionUnavailable`。

部分 Worker 中途死亡、无移动能力或失效不应让其他 Worker 的订单失败。Accepted 只表示任务建立，不表示 Worker 已到位或建筑完成。

建议增加 `UnitOrderKind.Construct`。阶段仍由订单状态表达：

- Accepted → InProgress：正在前往或已经贡献施工；
- Suspended：Stop 后保留 SiteId，不贡献工作量，不自动恢复；
- Completed：现场完成；
- TargetLost：现场被敌人摧毁；
- Cancelled：玩家取消现场、Worker 收到其他命令，或任务被明确替换；
- UnitLost：Worker 死亡。

移动到现场和实际贡献不拆成两个玩家命令，只作为同一 Construct 订单的内部阶段。

## 7. Stop 与手动继续

沿用此前确认的规则：Stop 暂停完整施工任务，保留 Worker、SiteId 和订单身份，且不会自动继续。

建议玩家再次右键同一 Active 现场时：

- 若 Worker 有指向该 SiteId 的 Suspended Construct 订单，将同一 OrderId 转回 `InProgress`；
- 若目标不同或旧订单已经终止，创建新 Construct 订单并按现有规则替换旧活动订单。

这样“暂停且不自动恢复”不需要额外 Resume 按钮，同时保留连续审计。Worker 在暂停期间可以保持原位；新 Move/Attack/Gather/Construct 命令会取消该 Suspended 订单。

## 8. 多 Worker 聚合

接口从首轮就允许多个 Worker。建议初版采用线性相加：

```text
TickWork = Σ BuildPowerPerTick(实际到位且 InProgress 的 Worker)
```

原因：

- 与当前 Legacy 多 Action 同时调用 `construct()` 的结果一致；
- 最容易验证，没有必要在重构阶段先引入策划尚未确认的递减收益；
- 后续可把聚合策略替换为上限、递减曲线或占位槽，而不改变 Construct 命令。

规则 AI 首轮仍可维持“一次只分配一个 Worker”的策略，避免重构改变 Demo 平衡；接口和 Human 已允许多选 Worker 同时施工。

## 9. Place 后的 Human 兼容行为

Place 不要求存在 Worker，无人施工现场是合法状态。为了维持当前操作习惯，建议 Human Adapter：

1. 进入蓝图模式时捕获当时已选、可施工 Worker 的稳定 IDs；
2. Place 成功后显式提交 `ConstructStructureCommand`，不再读取生成瞬间的 SceneTree 选择组；
3. 未被驱逐的 Worker 立即执行 Construct；
4. 因建筑重叠而被系统驱逐的捕获 Worker，在驱逐到安全位置后再提交 Construct；
5. 若驱逐期间玩家向该 Worker 下达新命令，则取消待提交的 Construct，尊重更新的玩家意图。

未来由指挥中心、建造菜单或 AI 放置且未提供 Worker 时，只创建现场，不自动猜测建造者。规则 AI 通过自己的分配策略另行发 Construct。

## 10. 取消、摧毁与退款

建议拆分：

- `CancelConstructionCommand(SiteId)`：拥有者明确取消 Active 现场；
- 战斗系统把 HP 降到零：现场进入 Destroyed。

按已有评审结论：

- 首轮玩家主动取消允许全额退款；
- 退款使用稳定 TransactionId/SourceId，重复命令不得重复入账；
- 敌人摧毁、友伤摧毁或剧情销毁不退款；
- 取消完成建筑应拒绝；
- 取消现场后相关 Worker Construct 订单进入 Cancelled；摧毁则进入 TargetLost。

GenericMenu 的“取消施工现场”必须调用 CancelConstruction，不应与 Worker Stop 继续共用一个含义模糊的按钮回调。

## 11. 施工进度、HP 与真实伤害

建议首轮将三者分开：

1. `CompletedWork` 只由施工服务推进；
2. 进度增长会按最终 `HpMax` 解锁新的结构 HP，并把本 Tick 新解锁的 HP 加到当前 HP；
3. 已经受到的伤害不会因为后续百分比重新计算而被抹掉；
4. 完成时不强制回满，因此受过攻击的建筑可以带伤完成；
5. 初始化 HP、施工新增 HP 和维修都使用明确的非伤害来源，不发布 `unit_damaged`；
6. 只有战斗/规则伤害造成 HP 下降时发布真实受击事件。

例：最终 100 HP，施工解锁到 40 HP 后受到 15 伤害，当前为 25；继续完成又解锁 60 HP，最终为 85，而不是自动回满 100。

这同时修复 `ECO-010`，又保留“施工速度必须压过敌方伤害，否则现场会被摧毁”的战斗表现。维修属于后续独立接口。

## 12. 权威事件与观察层

建议事件：

```csharp
public sealed record ConstructionCompleted(
    UnitId SiteId,
    PlayerId OwnerId,
    StructureDefinitionId DefinitionId,
    long SimulationTick);

public sealed record ConstructionTerminated(
    UnitId SiteId,
    PlayerId OwnerId,
    StructureDefinitionId DefinitionId,
    ConstructionSiteState State,
    long SimulationTick);
```

- Completed 只发布一次；
- Cancelled/Destroyed 由 Terminated 发布一次；
- 同步 Construct 回执与异步完成事件明确分离；
- 语音控制器只订阅经过玩家身份过滤的完成事件；
- 未来大模型 AI 是否收到、何时收到、是否消耗操作点，由观察/权限层过滤，不修改施工核心事件。

## 13. 自动验证建议

纯 C#：

1. Construct 批量部分成功、去重及所有权校验；
2. Stop 把 Construct 转为 Suspended 且不再贡献；
3. 再次对同一 Site Construct 恢复同一 OrderId；
4. 多 Worker 同 Tick 工作量只聚合一次，线性加速且不超 RequiredWork；
5. Worker 死亡只结束自己的订单，其他 Worker 和现场继续；
6. 完成事件只发布一次，全部关联订单进入 Completed；
7. Cancel 幂等退款，订单进入 Cancelled；Destroyed 不退款并进入 TargetLost；
8. 进度解锁 HP 不触发受击事件，真实伤害保留且完成不回满；
9. 无 Worker 现场可以长期保持 Active。

Godot：

1. 单 Worker 前往现场、显示火花、完成后停止表现；
2. 两个 Worker 比一个 Worker 更快完成；
3. Stop 后 Worker 停止移动/施工，进度保持不变且不自动恢复；
4. 再次右键同一现场继续施工；
5. Worker 中途死亡、现场取消、现场被摧毁均映射正确终态；
6. 放置时捕获的 Worker 使用显式 Construct，选择组随后变化不会改变建造者；
7. 被 Place 驱逐的捕获 Worker 不会在障碍内部施工；
8. 新现场不再误播“建筑正在被攻击”；真实受击仍能播报；
9. 建造完成语音只播放一次。

## 14. 首轮不处理

- 多 Worker 递减收益、最大施工槽位和复杂编队站位；
- 维修、出售、拆除、占领与敌方协助施工；
- 渐进支付、建造队列和资源分配优先级；
- 海上/空中建造者和特殊建造动画；
- 新施工 UI、美术进度表现和策划数值平衡；
- 复杂并发或多线程推进。

## 15. 待确认的接口决策

1. 是否接受权威施工进度使用整数 RequiredWork/CompletedWork，浮点只用于 UI？建议接受。
2. 是否接受 Construct 是批量 Worker 命令，允许部分成功，Accepted 不代表到位或完成？建议接受。
3. 是否接受 Stop 把施工订单转为 Suspended、保留 SiteId 且不自动恢复；再次右键同一现场恢复同一 OrderId？建议接受。
4. 是否接受首轮多 Worker BuildPower 线性相加，不设置递减收益或人数上限？建议接受，策划数值以后替换聚合策略。
5. 是否接受 Place 无需 Worker；Human 只对进入蓝图模式时捕获的 Worker 显式发 Construct，规则 AI 自行选择 Worker？建议接受。
6. 对被 Place 驱逐的捕获 Worker，是否接受驱逐完成后再自动提交 Construct；若期间收到新命令则取消待提交任务？建议接受。
7. 是否接受主动取消全额退款且幂等，现场被摧毁不退款；两者分别使 Worker 订单进入 Cancelled/TargetLost？建议接受。
8. 是否接受施工解锁新增 HP、保留已受伤害、完成不回满，并且非伤害 HP 变化不触发受击事件？建议接受。
9. 是否接受 Completed 与 Cancelled/Destroyed 事件分别发布一次，同步命令回执与异步事件分离？建议接受。
10. 是否接受规则 AI 首轮继续一次只分配一个 Worker，避免本次重构改变平衡，但公共接口支持多 Worker？建议接受。

## 16. 评审结论与首轮实现

2026-08-15，以上 10 项接口决策全部确认。补充确认如下：

- Worker 中途退出施工时，其旧 Construct 订单进入终态并立即删除 Worker→Site 活动索引与 Legacy Action 引用；
- 若其他 Worker 随后完成建筑，仍关联该现场的 InProgress/Suspended 订单统一进入 Completed 并清理；已退出 Worker 不会重新建立关联；
- 订单历史只保留稳定 ID 和状态快照，不持有 Godot Node；Match 退出后由 Match 级服务整体释放；
- 玩家主动取消、未来拆除和被摧毁是三个独立原因。当前只实现主动取消与施工中被摧毁，拆除及其额外效果延期；
- 非伤害 HP 变化不发布受击事件；施工期间真实损伤在完工后保留，维修规则延期评审。

首轮实现采用 `RequiredWork=200`、Worker `BuildPowerPerTick=1`，保持约 3.33 秒的 60 Hz 单 Worker Demo 节奏。具体数值、施工人数限制和非线性加速仍留给后续强类型配置与策划评审。
