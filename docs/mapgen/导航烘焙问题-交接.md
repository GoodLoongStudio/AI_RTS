## 问题 ①：AirNavigation.bake 的 on_thread 烘焙崩溃

- **现象**：`NAVDBG_SKIP_AIR=1` 时进程稳定；不禁用时 0xC0000005（数十秒内）
- **定位实验**（二分）：跳过 `AirNavigation.bake` → 全流程稳定、nav_check.json 可产出
- **缓解（已提交）**：`AirNavigation.gd` 的 `NAVDBG_SKIP_AIR` 环境变量守卫
  - 代价：空中单位无寻路网格（地面导航不受影响）
- **修复方向**：air 烘焙的 Recast on_thread 与 5.6 万 shapes 场景交互 —— 排查
  `bake_navigation_mesh(true)` 的线程安全 / 改用同步烘焙 / 减小 air 导航网格分辨率

## 问题 ②：parse_source_geometry_data 超线性慢

- **现象**：`parse` 对 14,799 体需**分钟-十分钟级**（隔离诊断实测 2h+ 未完成，后被
  异常拖累；Match 上下文实测 ~2h8m 任务时长）
- **根因**：逐 StaticBody 收集 + trimesh 拷贝（大量小物件）
- **缓解**：`nav_check.gd` 烘焙等待上限 900s + 每分钟打印（已提交）
- **修复方向**：
  1. **碰撞合并**（地图侧可行但需覆盖 fbx instance 内部结构，风险中）：
     物件 `collision_layer=0` + 分块（64m）合并 BoxShape 碰撞 → 体数 14,799 → ~800
  2. 或 **fbx 导入设置禁用 physics 生成**（需评估其它地图/单位的共用）
  3. 或 **parse 前过滤**（只收集 blocking 物件的碰撞，decor 跳过）

## 问题 ③：MovementObstacle null-navigation 异常

- **现象**：map-only 环境实例化时每个物件实例 `MovementObstacle.gd:12` 抛
  "Cannot call method 'get_node' on a null value"（数千次）→ 实例化链路 3h44m
- **修复方向**：`MovementObstacle._ready` 对 navigation 未就绪容错（defer/哨兵）
