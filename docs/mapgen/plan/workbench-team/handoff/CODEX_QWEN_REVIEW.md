## 必须返工的工程问题

### 当前工作树实测：普通生成仍有导航失败

本轮在工作台点击普通“生成完整地图”，任务 `099675f81a204026a873c8755015b97f` 在约 137.7 秒后结束，`map_pass=false`。65 个导航目标全部通过，但 51 条路径有 22 条不连通，包括 P0 到其他三家以及自身扩张点。目标投影成功不能代替全图连通。该结果来自当前工作树，考虑下文版本差异，不将责任全部归于原 Qwen 快照；集成版本仍须修复并重新验收。

### F1 / P1：相同两个 Seed 的不同参数地图会覆盖安装结果

`rtsmap/gates/g4_export.py:144` 的 make_map_id 只使用 layout_seed 和 terrain_seed；`rtsmap/workbench/pipeline.py:180` 用其作为安装标识。`install_map` 在同一目录用 copy2 替换场景和高度数据。用户导入/载入参数后更改河湖或高地参数，仍可保留相同两个 Seed，因此两项历史任务会引用同一路径，先前结果无法可靠试运行。

本轮在系统临时目录调用真实 install_map，以 first_config/second_config 模拟两个配置的不同文件；第二次安装后第一份被覆盖。未改动实际游戏地图。复现脚本与 JSON 在 `tmp_logs/codex_review_probe.py`、`tmp_logs/codex_review_evidence.json`。

修复要求：安装标识按任务或完整有效内容隔离，视觉版本和历史重试关系明确。验收需使用相同 Seed、不同河湖参数的两项任务，确认历史截图、包、游戏场景均各自对应。

### F2 / P1：实战通过结论没有足够证据，报告生成器硬编码 pass

`tools/godot/smoke_test.gd:232` 附近以 5 分钟余额大于 30 秒余额作为采集玩家判定；建造消耗可以掩盖真实采集。`stuck` 仅基于最后一分钟位置不变，并未核对单位是否正在执行移动任务。三张报告分别是 mining_players=0、stuck=35/39/37，既不能据此认定四家不采矿，也不能认定这些单位真的卡死。

`tmp_logs/make_handoff.py:222` 的 R12 直接写 status='pass'，没有从采集、移动或错误结果计算。nav_check 只验证导航目标和路径，不驱动单位定向上下坡/过桥，也不测试水域/崖壁错误捷径。现有材料不足以支持“定向运动和四家采集均通过”。

修复要求：用真实采集入账/累计收入事件验证各家采集；定向移动测试记录单位实际轨迹、到达高度与通行结果，覆盖坡、桥和禁止穿越的水/崖壁；报告按断言生成，通过、失败、未测试分别保存。UI 的“地图完成并通过全部验收”（app.js:444）应明确其仅覆盖生成与导航检查，实战状态单列。当前没有可见的 AI 对局操作入口，server.py 也只提供 generate/retry/rebuild_visual 的 POST 路由。

### F3 / P1：选择视觉 profile 在引擎阶段会丢失

`pipeline.py:482` 起的 rebuild_visual 将 profile 放入 g4_params，第一次构建时有效。但 `_build_g4` 未把 profile 写入 g4_scene，`_run_engine` 又从该未保存字段读取 profile，回退默认值并再次调用 build_scene_text。因此非默认样式会在导入后重建场景时被默认样式替换。

修复要求：持久化实际 profile、版本与参数，在所有二次构建中使用同一份值。用明显不同于 default 的 profile 走完整 rebuild_visual→engine→bundle 路径，核对最终场景、计划和图片一致；现有单层视觉测试未覆盖此路径。

### F4 / P2：导出包的依赖清单未覆盖视觉计划，安装不完整也能报完成

`pipeline.py:380` 起的依赖表仅合并 G3 assets_used 和三个固定依赖，未合并 export.json 的 visual_dependencies；但 `_run_engine` 在本机复制资产时专门合并了视觉依赖。GLM 增加 G3 之外的装饰资产后，本机可显示，导出的依赖表可能漏项。

安装脚本依赖硬编码的 G:/AIRTS 源目录；找不到依赖只 Write-Warning 后 continue，最终仍打印安装完成。运行脚本本身也没有随包冻结，而是从目标工程或本机取，历史包可能受到当前脚本变化影响。

修复要求：汇总场景和视觉计划的完整依赖及哈希，包含所需运行脚本或声明可验证的运行时版本；允许外部素材目录，但缺失必须明确失败。用干净目标工程和包声明的素材来源验证安装，不借用开发机未声明缓存。

## 视觉与版本边界

### 视觉口径修正：台地不等于草地

当前 `GeneratedTerrain.gd` 曾按 3.6m 高程阈值混入 `grass_color`，导致台地顶呈绿色。台地只代表高程和战术位置，不需要专门草贴图或绿色生物群系；后续视觉应沿用主地表暖土/砂土材质，用崖壁、坡面受光、边缘阴影和明度差表达高差。

### 视觉口径补充：桥和坡道使用标准素材融合

当前桥面仍由导出器生成的矩形盒和护栏表达，坡道主要由高度场直接生成。最终视觉应优先筛选标准桥/坡道模型，通过权威端点、方向、宽度和高度进行定位与受控缩放，并与地形、岸线、坡脚融合；不能把裸色块或无识别度程序几何当成最终美术。标准模型只负责可见结构，桥下水、桥面碰撞、坡道高度场和导航仍以 Qwen 权威数据为准。候选素材需核对预览、AABB、原点、材质与依赖后再接入。

初选素材包研究见 `handoff/BRIDGE_RAMP_ASSET_RESEARCH.md`。建议先试 4019 战地木桥或 4041 木桥/土坡组合；463 工业桥作为整套同风格备选。4006 单件桥和建筑入口坡道暂不直接采用。

已查看 Qwen 基准 `47-0_oblique.png`：存在大面积单色地面、黑色锯齿岸线、白色岩件和密集散点，尚不能满足最终自然感要求。Qwen 已承认视觉未收尾，但可视几何/材质导入问题应先修成可稳定复现的工程基线，不能简单写成“工程不背锅项”。

当前源码相对交接 file-state 已有 8 个文件哈希变化，包括 g4_export.py、visual.py、engine.py、GeneratedTerrain.gd、游戏 Match.tscn/MatchConstants.gd/Play.gd 等。因此本轮当前代码测试不代表对原 Qwen 快照逐字重放，不能从变更后的表现倒推出全部责任归属。

视觉交接目录目前只有 before 图片，GLM_TO_QWEN 仍是早前未就绪报告；当前 GeneratedTerrain.gd 已有后续视觉改动，需补齐最终文件清单与前后对照后重新核验。参考视频仍未核对。
