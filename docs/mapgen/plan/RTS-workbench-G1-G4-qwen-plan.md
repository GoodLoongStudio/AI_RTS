## 1. 最终目标

**工作台最终覆盖 G1→G2→G3→G4。普通用户选择地图偏好，点击一次生成，得到可以在 AI_RTS 中加载的最终地图，以及真实 Godot 预览、完整地图包和检查结果。**

G2 是最重要的地形设计阶段，当前页面只是完整工作台的基础。完成 G2 调参页面不等于完成本任务。

本文件是完整工作台的主交接计划。[G2-workbench-qwen-finish-plan.md](G2-workbench-qwen-finish-plan.md) 是其中第一部分的详细清单。历史文件中“只做到G2”“不得进入G3/G4”等是当时的执行范围，不是本轮终点。历史文档中的96m地图、固定中央战场、机械防守半圈、旧算法版本不能覆盖当前256m四人地图与用户的最新要求。

产品方向保持：

- 玩家距离、河流、湖泊、水域大小、高地数量、坡口宽窄使用简单选项；工程参数折叠。
- 出生布局自动随机，玩家不手选出生点或布局编号。继续使用现有 G1 生成器与合格布局库，不重写出生算法或改动已有布局。
- 首轮全链路接入可以从现有合格G1库随机取图并重新检查。G1仍是流水线中可追溯的一步；库的扩充如有需要，使用既有生成器输出到新目录，不覆盖64个既有布局，不另造一套G1。
- 逻辑地形由障碍、不同高度的平面和坡道构成；保留3m台地高差、自然轮廓、真实河湖及战略用途。细节材质服务视觉，不把可走地面变成噪声山地。
- 先贯通一张真实地图，再完善随机组合和界面。普通用户不需要手工运行Python、复制资产、打开Godot导入、运行截图脚本或手改游戏地图列表。

## 2. 当前代码实际能做什么

以下由本轮代码核对得出；历史文档中的成功记录仅作为背景，不能当作新版流水线验收。

| 部分 | 现状 | 还缺什么 |
| --- | --- | --- |
| G1 | `g1_starts.py`已有生成和约束检查；`workbench/catalog.py`扫描出30张合格既有布局 | 将随机选择、检查、来源和参数纳入完整任务；仍不显示手选布局 |
| G2 | `7.4.0`；简单选项、预览、真实水域、路线、公平检查已有 | 随机流程联调、大水域失败修复及状态收尾，见G2子计划 |
| G3 | `g3_content.py`，版本`2.2.0`；资源、素材实例化、blocking复检、资源公平已有 | 适配当前G2的台地、坡口、河桥、湖泊；接入独立任务、进度和可复现配置 |
| G4导出 | `g4_export.py`已能复制素材并生成`.tscn` | 当前仍以统一平面、blocking盒和水体蓝板为主；没有读取height生成新版台地顶面与连续坡面 |
| G4验证 | `ortho_capture.gd`、`g4_postprocess.py`、`smoke_test.gd`等工具已有 | 从独立脚本整合为工作台任务，支持任意本次生成地图，完善真实高程和坡道验证 |
| 工作台后端 | `server.py`目前只运行G2并绘制G2审阅图 | 缺少四阶段编排、G3/G4产物、引擎任务状态、错误恢复与完整地图下载 |
| 历史与复现 | 已有任务目录、G2配置、导入导出和历史 | 扩展为各阶段版本/参数/输入输出哈希、资产依赖和G4状态；旧记录保持真实版本 |

需要特别处理的代码事实：

1. G4 `GENERATED_DIR`指向AI_RTS固定目录，文件名只有`seed_<seed>.tscn`。同一G1配不同G2参数会覆盖同名地图，必须改成按任务/地图唯一标识隔离。
2. G4当前出生点、资源位置的Y为0，素材只修正模型原点，不能正确站在新台地上。水体按`terrain==5`导出，需与`water_footprint`、水床及桥面一起对齐。
3. G4 `run_gate`目前只负责复制资产、写场景及`export.json`；导入、Godot截图、后处理、游戏冒烟并没有由该入口完整自动执行。
4. G3 `_inherit_approval`只按阶段和版本继承旧approval，没有核对输入/输出哈希；工作台加入复用或重试前需要修正，避免新地貌继承旧人工认可。
5. `tests/test_g3.py`目前依赖正式`runs/16`，部分测试会直接重新生成正式G3，且会因未放行跳过。改成独立临时输入输出，再用于新流水线验收；不能把整组skip当通过。
6. `tools/make_g4_review.py`硬编码16/35/61及旧输出目录；`g4_postprocess.py`命令入口也默认正式runs，需要参数化。
7. AI_RTS当前导航使用真实静态碰撞几何；`TerrainNavigation.gd`烘焙AABB高度固定为0–5m。真实地形接入应核实范围、碰撞分组、坡度与步高设置，而不是只让场景能打开。
8. 旧冒烟脚本的扩张目标Y固定为0.2，主要测试出生与扩张路线。需新增台地顶、坡道两端、桥头的实际高程目标，防止投影到错误平面后出现假连通。

当前可用Godot路径在`rtsmap/contract.py`的`G4_GODOT_MONO`中：
`G:\AIRTS\godot_mono_471\Godot_v4.7.1-stable_mono_win64\Godot_v4.7.1-stable_mono_win64_console.exe`。
本轮已核实文件存在，AI_RTS的features含4.7和C#。启动时仍应检测配置与实际文件，不能采用旧文档里已经失效的路径。

## 3. 普通用户最终流程

1. 打开“RTS 地图工作台”，设置地图偏好。
2. 点击“生成完整地图”。任务依次进行随机布局、地形、资源与场景布置、游戏地图构建与基础验证，自动显示当前阶段和耗时。
3. 任一阶段未通过时停止依赖它的后续工作，保留可检查的中间结果和具体原因；用户可重试，不能用旧G4冒充本次生成。
4. 成功后默认显示真实Godot最终预览，可切换正交/斜视。G1布局、G2地形、G3资源等中间视图作为辅助查看，不要求用户理解阶段名称才能生成。
5. 可以下载包含场景、必要依赖清单、配置和报告的完整地图包；提供本地打开/试运行入口，接入既有AI_RTS测试能力。
6. 保留“快速预览地形”作为辅助入口，方便调G2。不要把G2快速预览重新设为完整任务的唯一产出。

无需额外开发浏览器3D引擎或把Godot移植到Web。第一版可用Godot生成的真实图片预览，加本地游戏试运行，完成用户目标。

## 4. 执行顺序与完成条件

### 阶段A：G2收尾与完整任务数据结构

- 完成G2子计划里的随机出生、三项失败测试、大水域、参数复现及文案收尾，保留当前已满意的设计。
- 将后端任务抽象为完整地图任务：包含唯一map/job标识、目标阶段、实际G1来源、各阶段完整参数和版本、阶段状态、失败原因、耗时、产物与哈希。
- 正常完整生成目标为G4；G2快速生成沿用同一任务框架。已有G2历史记录可打开，旧配置迁移有明确版本提示。
- 新逻辑可放在`workbench/pipeline.py`等独立模块；`server.py`负责HTTP和任务访问，避免把生成、引擎进程、打包全部塞进单个handler。
- 每个任务独立保存输入副本与输出。Godot导入共享缓存如不能安全并行，则明确串行；前端不阻塞，重复请求不会造成场景相互覆盖。

完成条件：当前G2功能回归通过；完整任务状态能够持久化，并为G3/G4预留实际可调用的阶段接口。

### 阶段B：将G3接入新版G2

- 复用资源与素材放置逻辑，检查其对旧`role/lanes/flank`数据的假设；输入来自本次任务的G2权威数据，不能读取正式runs中的旧同Seed结果。
- G3保留`territory/height/water_footprint`及G2结构语义；只按约定新增overlay并重算blocking/passable，保存`blocking_g2`。改变上游权威数据的操作必须有明确的阶段契约和验证，不能用实例化“修图”隐藏G2失败。
- 湖与主河都不能被岩石填上；桥、坡口、台地可走顶面、出生净空、资源接入路不能被装饰堵住。资源放置同时满足平面落点、真实可达性、净空和公平。
- 补齐阶段进度、资源/物件预览、失败报告、实例预算与版本记录。工作台初版沿用现有资源配额和风格，不新加一排未经验证的经济参数。
- 修正approval继承的哈希判断，使用临时目录测试新旧G2与G3的输入对应关系。

完成条件：从本轮工作台生成的G2直接产生G3；资源公平、净空、结构通行和实例复检通过，且预览与数据一致。

### 阶段C：真正实现G4台地、坡面、桥与水域

这是本次不能按“仅接一个按钮”处理的核心开发项。

- 从G2/G3权威数据构造地面、台地平顶、悬崖、连续坡面和桥面；视觉网格、碰撞、导航使用一致的几何来源。可沿用Godot网格与静态碰撞能力，不做全新地形编辑系统。
- 当前高度定义地面0.6m、台地顶3.6m。G2的坡口2.1m分类值不能直接导出成一块突起台阶；应结合坡口方向、范围和上下端高程生成连续坡面，坡口与两侧平面无缝衔接，符合实际导航坡度与单位运动能力。
- 水床、水面、桥面分开表达。河床连续覆盖桥下，桥面可以通行，普通地面单位不能走进水里；不能用整张平面碰撞提供跨水或穿台地的隐藏捷径。
- 出生点、资源、建筑落点和素材按实际地表/桥面高度放置，不能仍固定Y=0。素材原点修正保留。
- 检查AI_RTS对地面高度、移动贴地、点击目标、导航与建筑放置的现有支持。完成新版地图运行所必需的最小配套修改，独立列清单并保留旧平地图行为，不扩展到战斗规则、网络、账号等无关系统。
- 检查导航只把有效地面与坡面当通行面，悬崖不能爬；检查坡口前后不突跳、单位不会沉地或悬空。不能只凭二维blocking差分宣称三维行为正确。

完成条件：一张当前G2地图转换为真实有3m高差的G4，单位可沿坡道上下、通过桥梁、到达资源，崖壁和水域提供正确阻隔。

### 阶段D：导出、Godot预览与游戏试运行自动化

- 重构G4输出参数：明确输入任务目录、隔离输出目录、游戏项目和Godot路径；不要依赖全局固定路径或`seed_16.tscn`同名覆盖。
- 优先在独立验证项目或任务专属生成目录构建；根据既有游戏依赖打包，登记唯一地图项。只写本任务专属内容，必要的公用游戏兼容修正独立可审阅，不改原始素材包。
- 自动组织素材清单与导入、场景导出、加载检查、正交/斜视截图、导航检查、报告与下载包。场景相对路径及资源引用在目标AI_RTS项目中可解析。
- Godot进程必须有退出码、日志、合理超时与失败状态。引擎或资产缺失时明确报告实际原因；不能返回G2 PNG作为G4效果。后台工具不弹无关窗口。
- 基础场景加载和导航检查纳入普通生成完成条件。较长的4AI对局测试提供独立状态/入口，完成前标为未测试，避免用户以为每次点击都已经跑过5分钟实战。
- 参数化旧截图/审阅脚本，移除固定三张地图假设。包内记录各阶段版本与内容哈希、配置、依赖清单和报告，便于独立复现。

完成条件：用户从页面点击生成即可看到当前任务真实G4预览并下载/试运行地图，过程中不用手动执行引擎命令。

### 阶段E：阶段校验、失败恢复与复现

- 将“当前数据检查通过”与“用户人工认可”分开记录。设计正式、显式的工作台自动流水线执行模式，在验证依赖输入完整、版本/哈希匹配及上游检查通过后继续；不能给所有manifest填`approved=true`来冒充人工认可。
- 保留现有正式CLI审批语义；工作台调用经过校验的共用阶段实现。允许修改产品的执行模型以实现用户授权的一键生成，但不能忽略失败检查或伪造审批记录。
- 上游变化即使Seed相同，也必须使依赖它的旧结果失效。只改G3参数时可以复用同一有效G2；只重拍截图无需随机重做G1/G2。复用依据内容哈希、参数和版本，不能只靠文件时间。
- 失败重试保留已经确定的布局和参数；用户点“重新随机生成”才换成新的地图任务。重试不得在后台悄悄换图，却仍导出旧编号。
- 服务重启后记录恢复；被中断的引擎任务显示中断，不显示成功。部分产物可诊断，但整体只有满足目标阶段完成条件才能显示成功。
- 同配置、同阶段版本与资产版本能重建同一地图结构；截图、引擎导入缓存等受运行环境影响的派生内容不承诺逐字节相同。

完成条件：刷新、重启、重试、历史切换、导入导出不会混淆不同地图或不同阶段结果。

### 阶段F：完整验证与交付

1. 先选一张通过G2的当前版本配置完成G1来源→G2→G3→G4→游戏运行，作为垂直验收样例；再扩大到不同布局与水域组合。7.4大湖成功配置可见G2子计划，但不预设它的G3/G4一定成功。
2. 改造并运行G1/G2/G3及工作台回归；新增G4导出与流水线测试。至少覆盖唯一输出命名、上下游哈希、源数据不变、场景高度和坡面、失败停止、重试与旧配置迁移。
3. 保留G2水域矩阵；全链路至少3张不同出生布局，组合覆盖无水、有河桥、有湖及真实台地。每张完成Godot加载、导航与实际上下坡/过桥检查，再分别做4AI五分钟冒烟，记录四家资源采集与错误日志。
4. 定向检查台地顶与坡脚、桥两岸、出生点与资源的实际目标位置。导航投影不能把高地目标吸附到山脚或地下平面后仍算通过；完整检查端点高度、路径与单位到达。
5. 看真实G4正交与斜视图，确认高低关系、水域连续、坡面衔接、资产贴地与材质；G2和G4的逻辑结构一致。画面与运行验收分开记录。
6. 浏览器验收普通一键生成、进度、各阶段视图、失败、重试、刷新、历史、参数与地图包下载。真实运行验证不能全部mock，测试跳过项与失败项必须单列。
7. 更新启动脚本、使用文档和当前版样例，统一用户入口。提交`docs/plan/RTS-workbench-G1-G4-completion-report.md`，写明源码改动、游戏侧最小改动、真实日志、样例路径、已知限制和逐项完成状态。
