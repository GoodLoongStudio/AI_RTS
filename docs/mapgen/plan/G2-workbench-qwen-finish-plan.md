## 3. 按顺序完成的任务

### P0-A：收尾随机出生流程

涉及 `rtsmap/workbench/static/app.js`、`index.html`、`style.css`、`server.py`、`settings.py`、`catalog.py`。

1. 保留“随机生成地图”作为普通主按钮。请求只传玩家偏好和地形参数，省略 `layout_seed`、`terrain_seed`；后端从对应距离组的合格既有 G1 中随机抽取，再生成地貌编号。
2. 实际布局、地貌编号和完整参数在任务创建时确定并持久化；查询、预览、导出不能再次随机。显式编号请求继续用于高级复现。
3. 删除已无用途的 `layoutSvg`、`updateLayoutSelection`、`renderLayouts`、`shuffleMap` 及布局选择CSS，清掉对已删除DOM的引用。不要误删 `eligibleLayouts` 等仍在使用的逻辑。
4. 主界面不出现手动选出生布局；生成后可以只读显示本图编号。随机允许偶尔抽到相同G1，不要用“相邻两次必须不同”的脆弱测试定义随机，也不要悄悄只保留几张易通过的布局。
5. 验证不限/近/适中/远分组、空库或空分组、无效编号和非法距离的提示。目录发现仍来自真实G1数据，不能硬编码30张白名单。

验收：随机请求能成功创建任务，响应和导出包含实际两个整数编号；带相同编号与参数重放可复现；G1源文件及审批状态不变。

### P0-B：修复大水域组合的实际问题

涉及 `rtsmap/gates/g2_strategy.py` 的 `closed_lakes`、`neutral_plateaus`、`build_geometry`、`acceptance`，以及 `g2_layout.py` 的候选筛选与异常上报。

1. 从上面的失败样例出发，检查真实格网和拒绝记录，区分“候选放置不好”“路线或台地安排造成失败”与“该设置下空间不足”。不能仅按预览PNG判断。
2. 在现有框架内修正放置、避让和候选选择问题：大湖保留战略阻隔作用，同时给可走区域、桥头、有效坡口和中立高地留出空间。避免零碎的不可达地面或没有用途的台地。
3. 建立可复现的小型验证矩阵：河0/1 × 湖0/1/2 × 水域标准/大；无水组合无需重复。总体覆盖近、适中、远三类布局。记录每组实际尝试数、PASS数、无候选数、有产物但未通过数、耗时和失败项，不要求所有布局支持所有组合。
4. 常用组合要有真实成功样例；双湖和河湖同时存在不能只验证“会报错”。如果某个公开组合经过有界尝试仍没有成功样例，报告其约束冲突和证据，作为未解决项，不能标记全部完成。不要用只挑成功Seed的报告代替成功率记录。

6. 修正三项失败测试：用真实适配布局验证成功路径；另设已知失败场景验证明确失败、没有缩小水域、没有伪造PASS。不要简单删除断言、跳过测试，或把所有失败都改成预期结果。
