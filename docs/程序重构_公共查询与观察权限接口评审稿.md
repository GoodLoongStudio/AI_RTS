# 程序重构：公共查询与观察权限接口评审稿

## 1. 评审范围

本轮目标是为玩家交互、传统规则 AI、测试工具和未来大模型 AI 建立同一套只读查询边界。当前只评审契约，不接入操作点、不实现大模型，也不立即迁移所有 Legacy 场景读取。

首个纵向样例建议只提供以下查询：

1. 查询己方单位摘要；
2. 查询指定圆形区域内当前获准观察的实体；
3. 按稳定实体 ID 查询当前获准获知的实体摘要；
4. 查询自己的资源账户摘要；
5. 全知调试查询仅作为测试能力单独授予。

## 2. 当前仓库问题

现有代码大量直接使用 `SceneTree.get_nodes_in_group()`、Node 属性和 `global_position`：

- `SimpleClairvoyantAI` 会遍历全部 `units`，其名称虽然明确表示全知，但这种读取不能成为普通 AI 的默认实现；
- `UnitVisibilityHandler` 通过全局 `Node.visible` 表示当前画面玩家的可见性，这属于表现状态，不能同时代表每个 AI 观察者各自的知识；
- HUD、战役和测试脚本可以直接取得 Node，容易绕过战争迷雾、阵营权限和未来信息时效性；
- 返回 Node 会泄漏未授权字段，也使 Domain/Application 反向依赖 Godot 场景结构。

因此公共查询不得返回 Godot `Node`、节点路径、可变集合或底层仓库引用。

## 3. 建议的分层

### 3.1 Domain

保存纯数据值对象：

- `QuerySessionId`：一次受信任查询会话；
- `ObservationRevision`：快照版本或模拟时刻；
- `EntityObservation`：实体的不可变观察结果；
- `ObservationState`：`Owned`、`VisibleNow`、`LastKnown`、`Unknown`；
- `ObservationField`：位置、类型、阵营关系、生命值、当前任务等字段位掩码；
- `ObserverRelation`：自己、盟友、敌人、中立、未知。

### 3.2 Application

建议公共入口暂命名为 `IWorldQueryService`：

```csharp
QueryResult<IReadOnlyList<EntityObservation>> GetOwnForces(
    QuerySessionId sessionId,
    ObservationField requestedFields);

QueryResult<IReadOnlyList<EntityObservation>> ScanCircle(
    QuerySessionId sessionId,
    CircleObservationRequest request);

QueryResult<EntityObservation> InspectEntity(
    QuerySessionId sessionId,
    EntityId entityId,
    ObservationField requestedFields);

QueryResult<ResourceAccountObservation> GetOwnEconomy(
    QuerySessionId sessionId);
```

这里的 `EntityId` 需要覆盖单位、建筑和资源节点。可以新增统一 ID，也可以在首版使用带种类的联合引用；不建议让调用方猜测一个 GUID 属于哪类实体。

### 3.3 GodotAdapter

Godot 层负责：

- 将稳定 ID 映射为场景 Node；
- 从权威 C# 状态和 Legacy 只读属性组装快照；
- 按观察者计算可见性，不能直接把当前画面的 `Node.visible` 当成所有玩家的权限；
- 保证一次查询使用同一个观察版本，避免结果内部跨帧撕裂。

## 4. 权限模型

### 4.1 调用方不能自报权限

查询请求只携带由组合根签发的 `QuerySessionId`。会话在服务内部绑定：

- 观察者玩家；
- 来源类型（Human、RuleAI、Agent、Debug）；
- 可见性策略；
- 允许字段集合；
- 是否允许全知。

调用方不得在请求中填写 `omniscient=true`、任意玩家 ID 或任意权限级别。否则普通 AI 可以通过修改参数自行升级为全知 AI。

### 4.2 字段授权

调用方可以请求字段，但最终返回字段是：

`RequestedFields ∩ SessionAllowedFields ∩ CurrentObservationAllowedFields`

结果必须携带 `ReturnedFields`，使调用方能够区分“字段值为零”和“字段未获授权”。未来可以用不同会话或受操作点控制的装饰器提供粗略、战术、详细等多粒度观察，而不必复制整套查询服务。

### 4.3 全知调试能力

`OmniscientDebug` 是组合根显式授予的独立策略，只能用于测试、回放诊断或明确命名的全知 AI。普通规则 AI 不得依赖该能力；自动测试需要证明相同请求在普通会话和调试会话中返回不同结果。

## 5. 结果语义

建议 `QueryResult<T>` 至少包含：

- `Status`：`Accepted` 或 `Rejected`；
- `Value`：成功时的不可变快照；
- `ErrorCode`：稳定错误码；
- `ObservationRevision`：结果对应的观察版本；
- `ReturnedFields`：实际返回的字段；
- `Diagnostics`：仅开发构建使用，不向受限 AI 暴露内部原因。

规则建议：

- 合法区域内没有可见实体属于成功的空结果，不是失败；
- “目标不存在”和“目标存在但观察者不知道”对普通受限调用方应使用同一种公开结果，避免通过错误码探测战争迷雾；
- 批量结果按稳定实体 ID 排序，保证测试、回放和规则 AI 行为可重复；
- 查询只返回调用瞬间的快照，不保证下一帧仍然有效；
- 查询不返回命令是否执行，也不替代订单状态事件。

## 6. 战争迷雾与时效性

建议首个实现只权威支持 `Owned` 与 `VisibleNow`：

- 己方实体默认可获得实时基础状态，不受镜头位置限制；
- 敌方与中立实体必须通过该观察者的视野判定；
- 移出视野后首版返回未知，不提供移动单位最后位置；
- 建筑残影和 `LastKnown` 先在契约中预留，等策划确定记忆衰减、建筑摧毁确认和地图情报规则后实现；
- 资源节点是否永久记忆同样留待策划评审。

当前 `UnitVisibilityHandler` 可以继续负责人类玩家画面表现，但查询权限应逐步迁移到按观察者计算的独立 Provider，避免多 AI 共用一个画面玩家的 `visible` 状态。

## 7. 与 AI 操作点的边界

基础查询服务只负责权限和快照，不直接扣操作点。未来由上层 `BudgetedWorldQueryService` 或 Agent Gateway：

1. 根据范围、字段和时效要求计算成本；
2. 原子扣除操作点；
3. 调用相同的权限查询服务；
4. 即使结果为空，也可以视规则消耗操作点；
5. 决定哪些结果与命令反馈可以返回给大模型。

这样玩家 UI 和传统 AI 不必伪装成大模型操作点消费者，同时底层观察权限仍然一致。

## 8. 与传统 AI 外置配置的边界

传统 AI 的阵营、指挥官、地图和玩法配置只能影响“如何使用已获授权的信息”，不能扩大查询权限。普通 AI、剧情 AI 和全知调试 AI 的权限差异由组合根配置的会话策略决定，不能隐藏在战术 JSON 参数中。

## 9. 首个纵向样例建议

接口通过后建议按以下范围实现：

1. 两个玩家、各一个单位，另有一个资源节点；
2. 建立普通玩家会话和全知调试会话；
3. 验证己方单位查询始终可见；
4. 验证敌方进入/离开视野时普通结果变化；
5. 验证调试会话可看到视野外目标；
6. 验证未知 ID 与不可见 ID 对普通会话不可区分；
7. 验证请求未授权的生命值字段不会泄漏；
8. 增加纯 C# 权限测试和一个 Godot 场景适配冒烟测试。

本样例不迁移传统 AI，不实现最后已知位置，不实现操作点，也不提供查询 UI。

## 10. 待接口评审确认

1. 是否接受用组合根签发 `QuerySessionId`，而不是让调用方提交玩家 ID 和权限？
2. 是否接受首版己方单位始终返回实时基础信息？
3. 是否接受合法查询的空结果仍为成功？
4. 是否接受普通调用方无法区分“目标不存在”和“目标当前不可知”？
5. 是否接受首版只实现 `Owned`、`VisibleNow`，`LastKnown` 仅预留？
6. 是否接受请求字段与实际授权字段分离，并返回 `ReturnedFields`？
7. 是否接受操作点位于查询服务之外的 Agent 装饰层？
8. 是否接受全知调试权限只能由组合根授予，传统 AI 配置不能自行开启？
9. 是否接受首个纵向样例只覆盖单位、建筑/资源的基础摘要与己方经济？
