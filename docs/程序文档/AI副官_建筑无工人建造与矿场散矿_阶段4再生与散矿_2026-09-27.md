## 1. 再生规则配置化（提示词 8.2「必须配置化，不能散落在脚本里」）

```json
"resources": [{
  "kind": "A", "collectionDurationMilliseconds": 120,
  "regeneration": { "enabled": true, "delayMilliseconds": 90000, "restoreAmount": 1500 }
}]
```

两份 balance（`demo` / `adjutant-e2e`）都已写入。贯通链与施工字段同一套：
`ResourceRegenerationDto` → `ValidateResources`（启用时延迟与恢复量必须为正整数）
→ `ResourceDefinition(Kind, CollectionDurationMilliseconds, RegenerationEnabled,
RegenerationDelayMilliseconds, RegenerationRestoreAmount)`
→ `BalanceConfigRuntime.GetResourceRegeneration("resource_a")` → GDScript 驱动器。
`enabled=false` 或整块缺失 ⇒ 保持旧的「采空即消失」语义，不改变任何现有对局行为。

**初始取值与依据**：`delayMilliseconds=90000`、`restoreAmount=1500`。依据是当前采集速度
（一车 `carryCapacity=400` × `120ms/单位` = 48 秒装满一车）与对局节奏（实测规则局常见时长
数分钟）：一座采空的扩张矿点在 90 秒后回 1500 矿 ≈ 每 90 秒补 3.75 车，既不至于让远端矿点
变成无限矿，也能让「换点 → 等待 → 回来再采」真的发生。**提示词明确说"用户尚未指定固定秒数"，
这两个数需要在阶段 6 的多种子对局里按实际矿点寿命校准后再定稿。**

## 2. 耗尽不再删实体（阶段 0 断点 F 的前置障碍）

旧实现 `ResourceA.gd:7-10` 是 `resource_a = max(0,value); if 0 → queue_free()`：
实体一消失，**没有任何对象承载这个矿点的身份与再生计时**，再生无处落地。

`ResourceUnit.gd` 现在持有状态机与身份：

| 字段 | 含义 |
|---|---|
| `ore_capacity` | 容量 = `_ready()` 时抓到的开局存量，之后恢复量永不抬高它 |
| `depleted` | 可采 → **耗尽等待** → 再生可采 |
| `regen_remaining_ms` | 距下一次恢复的权威模拟毫秒 |
| `regen_cycles` | 已完成几轮恢复（结果证据 + 幂等自检） |

`apply_regeneration()` 只加**矿点存量**并按 `room` 夹紧（**矿量不超过容量**），
绝不直接给玩家账户加钱 —— 收入仍然必须经过「采集 → 交付」。
`meta "ore_depleted"` 与 `MatchSignals.resource_exhausted` / `resource_replenished` 供表现层与报告订阅。

## 3. 权威驱动器 `Match/ResourceRegeneration.gd`

- **只在权威端跑**，按物理帧 delta 累计**模拟毫秒**；`get_tree().paused` 时直接 return，
  所以**暂停不偷跑**，也不依赖墙钟或客户端定时器。
- 到点结算一次即把矿点翻回 `ready` 并重置计时 ⇒ 再次进入结算分支必须等到它重新被采空，
  **同一周期天然只结算一次**，重复调用不多刷。
- 配置关闭时执行旧语义（`queue_free()`）。
- 测试夹具用 `@export var rule_overrides` 注入「小容量 + 短等待」的确定性周期
  （提示词 8.4 明确要求专用夹具），不影响正常对局。

## 4. 联机与重连同步（提示词 8.2「复用现有权威资源与同步链」）

`NetSync._reconcile_entry_for` 新增 `entry["ore"] = [resource_a, resource_b, depleted,
regen_remaining_ms]`（只给带矿量属性的节点加，不给每个单位条目平白加体积），
客户端在既有镜像入口调用新增的 `ResourceUnit.apply_presentation_ore()` 接受权威数值。
**客户端只接受、不自己推进计时** —— 两端各自刷矿必然分叉。
这一条同时补上了阶段 0 记的「矿量根本不下发、客户端既收不到扣减也收不到回填」。

## 5. 散矿素材（8.1）—— 场景已改，截图验收待做

`ResourceA.tscn` / `ResourceB.tscn` 的 `Geometry` 从**单颗大水晶**
（`rock_crystalsLargeA.glb` 一个实例，偏移 (-2,0,-1.5)）改成**贴地散布的 8 件矿簇**：

| 件 | 网格 | 距原点 | 绕 Y | 缩放 |
|---|---|---|---|---|
| CoreCluster | rock_crystalsLargeA/B | 0.00,0.00 | 0° | 0.52 |
| ChunkEast | rock_crystals | 1.05,0.35 | 37° | 0.62 |
| ChunkSouth | rock_crystalsLargeB/A | -0.72,0.98 | 155° | 0.48 |
| ChunkWest | rock_crystals | -1.18,-0.55 | 210° | 0.40 |
| ChipNorth | rock_crystalsLargeB/A | 0.30,-1.24 | 92° | 0.30 |
| ChipFar | rock_crystals | 1.62,-0.90 | 300° | 0.24 |
| RubbleA / RubbleB | rocks_smallA / rocks_smallB | -0.35,1.55 / 0.85,-0.15 | 18° / 245° | 0.55 / 0.45 |

- **疏密、大小、朝向都有变化**，一片可辨识的散矿而不是一个点。
- 全部是**纯视觉网格，不加 CollisionShape、不加 MovementObstacle** ⇒ 不会形成工人进不去的
  密集障碍，也不增加查询/导航开销（提示词 8.1「视觉矿块不必一块对应一个独立逻辑实体」）。
- 逻辑实体仍是既有矿点；`CollisionShape3D` / `MovementObstacle radius=0.6` /
  `Highlight`/`Selection`/`Targetability` 半径都未动，采集距离与选择区域不变。
- 原来单颗晶体偏移 (-2,-1.5) 使视觉中心与逻辑中心差 2.5m；现在矿簇以原点为中心铺开，
  **选择圈终于落在看得见的矿上**。
- 余量表现：`_refresh_depletion_presentation()` 按 `total_ore()/ore_capacity` 把 `Geometry`
  的 Y 缩放从 1.0 压到 0.35（X/Z 收到 0.85）——**丰富 / 稀疏 / 采空（留地表痕迹，不隐藏）/
  再生后恢复**之间连续可辨，采空后仍能看见并选中这个矿点。
- 复用既有网格与材质（`ResourceA.gd` 的 albedo 替换仍把晶体染成矿 A 的专属材质，
  与装饰石头可区分），未新增外部素材。

**未完成的验收项**：提示词 8.1/8.4 要求「检查真实游戏截图中的整体矿区、工人采集以及

## 6. 顺带修掉的一个真实卡死缺陷（提示词 §D「工人是否被矿场/矿点避让圈卡住」）

`_nearest_ore_stand()` 原来只按**矿点**半径算站位：
`stand = ore + away * (ore.radius + worker.radius + 0.4)`。
但 `OreRefinery.tscn` 的 `MovementObstacle.radius = 6.0`（与它 6.0 的 footprint 同口径），
于是矿点离矿场小于 ~7m 时，报到点落在**矿场自己的避让圈里** ⇒ 工人被每帧推回、原地抖，
实测表现为「指派成功了、也在 Moving，但 150 秒都到不了矿点，矿量与账户纹丝不动」。

现在报到点会沿远离矿场的方向逐步推出到
`refinery.radius + worker.radius + 0.6` 之外（上限 32 次 × 0.5m）。
这条不是为测试放宽断言，是修掉了产品里真实存在的死锁。
