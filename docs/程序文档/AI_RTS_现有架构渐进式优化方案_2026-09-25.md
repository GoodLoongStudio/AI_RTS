# AI_RTS 现有架构渐进式优化方案（2026-09-25）

> 状态：**Canonical / Architecture Optimization Guardrail**
>
> 目标：在**不改变当前重大架构、不推翻已经验证的运行链路、不重新做一套系统**的前提下，对 AI_RTS 的模块边界、职责、接口、配置、运行生命周期、性能、可观测性、测试和交付做持续优化。
>
> 产品与玩法基线：[AI_RTS 当前产品策划基线（2026-09-25）](../策划文档/AI_RTS_当前产品策划基线_2026-09-25.md)
>
> AI 副官当前入口：[AI副官_当前执行入口.md](AI副官_当前执行入口.md)

---

## 1. 为什么现在需要“优化”，而不是“重构”

当前项目已经拥有较完整的基础能力：

- Godot 4.7 Mono / .NET 8；
- C# Domain / Application / GodotAdapter 分层；
- GDScript 场景、HUD、单位行为和游戏表现层；
- CommandRuntime / UnitCommandGateway 等权威命令入口；
- WorldQueryRuntime 等受控查询入口；
- 单机 RTS 基础对局；
- 服务器权威联机 Demo；
- 传统规则 AI；
- AI 副官 Laya + MiniCPM5-2B + 规则 baseline + 行为树；
- 程序化地图工具链；
- 战役胜负 / 结算 / 重开；
- 成长树与跨局成长；
- Windows 导出和本地 AI 运行环境。

因此当前最大的技术风险已经不是“架构能力不足”，而是：

1. 相同事实存在多个来源；
2. 模块边界在多轮快速迭代中逐渐模糊；
3. Python / GDScript / C# 的职责有局部重叠；
4. 配置、端口、模型、日志和运行进程容易漂移；
5. 规则 AI、AI 副官规则 baseline、Laya、2B 的职责容易互相覆盖；
6. 测试很多，但缺少按架构层分级的统一验收；
7. 历史文档容易继续影响当前实现；
8. 为修单点问题而继续增加旁路，会让未来维护成本快速上升。

所以本轮原则是：

> **不重做骨架，只把现在的骨架整理干净。**

## 2. 重大结构冻结区

下面这些属于**当前架构资产**，本优化方案默认不改变。

| 冻结项 | 当前结构 | 优化允许范围 | 禁止 |
|---|---|---|---|
| 游戏引擎 | Godot 4.7 Mono | 优化场景、节点、资源与运行时 | ❌ 换 Unity / Unreal / 其他引擎 |
| 语言组合 | C# + GDScript + Python | 缩小职责重叠、增加清晰适配器 | ❌ 全量改成单一语言 |
| C# 架构 | Domain / Application / GodotAdapter | 整理依赖方向、接口和 DTO | ❌ 重新设计一套 Core |
| 游戏权威 | CommandRuntime / 权威 Match | 增强校验、日志、批处理 | ❌ 模型直接写 Node / HP / 资源 |
| 查询边界 | WorldQueryRuntime / 受控观测 | 压缩 DTO、统一 schema | ❌ AI 直接遍历场景树取真值 |
| 联机 | 服务器权威 + NetSync / NetCommandProxy | 性能、错误诊断、版本校验 | ❌ 改 lockstep / 全重写网络协议 |
| 传统规则 AI | SimpleClairvoyantAI 系列 | 策略质量、参数、行为复用 | ❌ 直接删掉改成全模型 AI |
| AI 副官 | Laya + MiniCPM5-2B + 规则 baseline + 行为树 | 权责、调度、订单、评测 | ❌ 推翻重新做云端 Agent 架构 |
| AI 执行链 | TaskPatch / Intent / Validator / Godot authority | 增加 SquadOrder 上层抽象 | ❌ 绕过现有 Intent/Command 权威链 |
| 程序化地图 | 当前 mapgen 工具和 Godot 接入 | Kit、生成性能、验证 | ❌ 新建第二套地图格式 |
| 战役 | 现有 MatchOutcome / Campaign 入口 | 补 Objective Runtime | ❌ 为每关写完全独立系统 |
| 成长 | GrowthStore + data-driven definitions | 数据结构、UI、效果接入 | ❌ 重新做账户/云存档系统 |
| 打包 | Windows 导出 + 本地 AI runtime | 依赖拆分、启动器、诊断 | ❌ 强制依赖公网服务 |

## 3. 可优化区

重大结构不动，但以下内容应该主动优化。

### 3.1 职责边界

重点解决：

- 谁拥有真实状态；
- 谁能做策略；
- 谁只能做安全校验；
- 谁负责持久状态；
- 谁负责 UI 表达；
- 谁负责日志和回放。

原则：

> **一份事实只能有一个权威来源，其它地方只能缓存或派生。**

例如：

- 单位控制权 → 权威状态 / generation；
- 资源余额 → Match 权威资源系统；
- AI 小队订单 → 副官订单状态；
- 对局结果 → MatchOutcome；
- 成长奖励 → GrowthStore；
- 模型健康 → 模型 runtime；
- HUD 只显示，不自行制造另一套“副官状态”。

## 5. 优化原则

### O1：先包住，再替换

已有稳定能力不直接删除。

如果接口不好：

1. 先增加 adapter；
2. 新调用走 adapter；
3. 验证稳定；
4. 最后清理旧调用。

禁止“大改完成后一起测试”。

### O2：一个权威事实，一个写入口

任何状态只能有一个 writer。

允许多个 reader，不允许多个系统同时“认为自己是权威”。

### O3：策略与安全分离

程序硬约束可以拒绝策略。

程序硬约束不能悄悄做一个新策略，然后把模型策略替换掉却不留记录。

### O4：持续任务不重复下令

采集、守点、攻击移动、建造、生产等任务一旦进入持续执行，不因扫描频率高就每轮重复创建。

### O5：所有跨层对象必须可追踪

订单、Intent、Command、Task 至少应能关联：

- match_id；
- source；
- owner；
- generation；
- task/order id；
- issued_tick；
- expires / TTL；
- final status；
- rejection / cancel reason。

### O6：配置大于隐藏常量

频率、TTL、端口、模型、feature flag、阈值、包路径必须逐步集中管理。

### O7：优化必须可回退

架构优化默认使用 feature flag / adapter / 兼容 DTO。

每一阶段都应该能快速回退到上一稳定状态。

# 6. C# / GDScript 边界优化

## 6.1 保持现有分层

不要求把所有 GDScript 迁入 C#。

推荐边界：

### C# 更适合继续承载

- 权威命令服务；
- 查询服务；
- 经济 / 生产 / 建造的领域规则；
- MatchOutcome；
- 可测试的纯逻辑；
- schema / DTO；
- 跨系统稳定接口。

### GDScript 更适合继续承载

- 场景节点生命周期；
- HUD；
- 输入；
- 镜头；
- 动画和表现；
- Godot Navigation / Node 集成；
- 行为树节点与轻量 glue。

### 优化目标

新功能增加前先判断：

> 这是领域规则，还是 Godot 表现逻辑？

避免同一条业务规则在 C# 和 GDScript 两边各写一次。

# 7. Command / Query 架构优化

## 7.1 命令入口继续统一

Human、传统 AI、AI 副官都继续进入同一权威 Command 链。

不得增加：

- “AI 专用直接执行”；
- “测试模式直接 set position”；
- “模型专用跳过资源校验”；
- “联机和单机两套命令语义”。

## 7.2 增加统一 Command Source

推荐统一：

```text
Human
RuleAI
AdjutantRule
AdjutantLaya
Adjutant2B
System
Test
```

所有日志和结果都保留 source。

这样可以真正统计：

- 谁下的命令；
- 谁的命令被拒；
- 谁完成任务；
- 谁导致 churn。

## 7.3 Query DTO 统一版本

所有 AI 观测逐步统一 schema version：

```text
observation_schema_version
rules_version
balance_version
snapshot_id
server_tick
```

不要让 Python、C#、GDScript 各自猜字段。

# 8. AI 副官架构优化

不改变：

```text
Laya
  ↓ fallback
MiniCPM5-2B
  ↓ fallback
Rules
  ↓
Intent
  ↓
Godot
```

只优化权责。

## 8.1 新增 SquadOrder 上层抽象

现有 TaskPatch / Intent 不删除。

新增：

```text
SquadOrder
  ↓ compiler
TaskPatch / Intent
```

解决：

- 一支队伍被拆成多个单兵命令；
- 多条命令非原子；
- 规则逐个重新判断；
- 模型无法表达完整战术意图。

## 8.2 订单租约

每个有效订单有：

- owner；
- generation；
- priority；
- issued_tick；
- TTL；
- cancel conditions；
- execution status。

规则 baseline 只有在：

- 没有订单；
- 订单失效；
- 安全硬约束触发；
- 紧急事件触发；

时才重新接管策略选择。

## 8.3 Rule baseline 缩小“战略覆盖权”

不删除规则 baseline。

保留：

- 无模型时的完整可玩性；
- 安全；
- 经济底线；
- 防止单位永久 idle。

优化：

- 有有效模型订单时，不重新选战略目标；
- 所有覆盖必须记录 reason；
- 区分：
  - safety rejection；
  - tactical replacement；
  - emergency override。

## 8.4 Laya 不继续扩大到所有决策

Laya 优先用在规则较弱的离散选择：

- 主攻目标；
- 姿态；
- 集火；
- 撤退；
- 支援；
- 等待。

不建议把：

- 普通 gather；
- 基础 produce；
- 固定建造合法性；

作为主要模型价值来源。

## 8.5 2B 保持低频异步

2B 不改成实时单位控制。

优化：

- 更紧凑输入；
- 多小队组合输出；
- 事件触发提前规划；
- 计划 TTL；
- 旧计划持续执行；
- 降低无效调用。

# 9. 传统规则 AI 优化

传统 AI 不重写。

优化目标：

1. 参数统一；

4. 不共用控制状态；

- 威胁评估函数；
- 武器域判断；
- 目标价值表；
- 路径可达判断；
- 战力统计。

不应共用：

- AI 副官玩家 lease；
- 玩家 generation；
- 模型 order；
- 副官 UI 状态。

# 10. 战役 / Objective 优化

不改变现有 MatchOutcome / Campaign 流程。

只补中间一层：

```text
Campaign
  ↓
Objective Runtime
  ↓
MatchOutcome
```

Objective 类型统一：

- Destroy；
- Protect；
- Reach；
- Survive；
- Gather；
- Build；
- Trigger；
- Composite AND / OR。

好处：

- 第一战役不再硬编码全部条件；
- 后续关卡复用；
- AI Benchmark 也可复用 Objective；
- 结算保持现有 MatchOutcome。

# 11. 成长系统优化

GrowthStore 结构保持。

优化：

- effect type 集中注册；
- UI 不自行解释效果；
- MatchReportAdapter 只转换事实；
- GrowthStore 负责持久状态；
- Gameplay modifier 负责应用；
- 避免不同场景自己读取 growth json。

短期不增加大量新树。

先保证已有节点：

- 可保存；
- 可退款；
- 可正确生效；
- 战斗/经济效果有测试。

# 12. 联机架构优化

不改变服务器权威架构。

## 优化点

### 12.1 Snapshot

逐步增加：

- payload 大小统计；
- 单位数与带宽曲线；
- dropped / delayed snapshot 指标；
- 客户端插值质量监控。

只有证据证明全量 snapshot 成为瓶颈，才考虑 delta。

### 12.2 RPC 错误诊断

所有关键 RPC 失败尽量可见：

- version mismatch；
- unknown entity；
- stale generation；
- unauthorized issuer；
- scene mismatch；
- missing spawn。

禁止静默 continue 成为默认错误处理。

### 12.3 单机 / 联机语义一致

Gameplay command 不因联机模式改变业务语义。

只改变：

- transport；
- authority location；
- replication。

# 14. 配置优化

当前多个模块存在 env / json / cfg / export 参数。

优化目标不是“全部塞进一个文件”，而是按作用域统一。

建议：

```text
config/
  game/
  balance/
  ai/
  adjutant/
  network/
  growth/
  mapgen/
```

规则：

- 默认值有一个来源；
- 环境变量只做运行时 override；
- 日志启动时输出最终 resolved config；
- 不在多个文件维护同一个端口 / model / TTL。

# 15. 进程与 Runtime 生命周期优化

当前本地 AI 包含：

- Game；
- Python runner；
- Ollama；
- 可选 Laya 模型。

建议明确状态机：

```text
missing
starting
warming
ready
degraded
stopping
failed
```

统一由一个 Runtime Supervisor 负责“状态观察”，但不要求重写当前启动器。

渐进做法：

1. 先把已有 launcher / model service 状态统一；
2. 加统一 health snapshot；
3. HUD 只读 health；
4. 打包脚本读取同一状态；
5. 最后再考虑封装 supervisor。

# 17. 性能优化原则

不做“先重构再优化”。

必须先测。

## 17.1 Godot

记录：

- frame time；
- physics；
- navigation；
- unit count；
- projectile count；
- snapshot serialize；
- AI controller time。

## 17.2 Python AI

记录：

- observation build；
- Laya inference；
- 2B queue；
- 2B inference；
- decode；
- validation；
- dispatch。

## 17.3 优先处理

1. 重复扫描；
2. 重复序列化；
3. 重复命令；
4. 大对象 deepcopy；
5. 高频日志；
6. 无效模型请求；
7. 每单位重复全局计算。

不先优化“看起来可能慢”的模块。

# 20. 明确禁止的“大改”

没有新的、经过单独批准的架构提案前，不做：

- ❌ 换引擎；
- ❌ 全量 GDScript → C#；
- ❌ 全量 C# → GDScript；
- ❌ 删除现有 Core 重新写 ECS；
- ❌ 将服务器权威改成 lockstep；
- ❌ 将所有 AI 逻辑移进 Python；
- ❌ 将所有 AI 逻辑移进 Godot；
- ❌ 删除规则 AI；

- ❌ 为一个新玩法再建第二套战役 / 成长 / 地图系统；
- ❌ 大规模文件搬迁只为了“目录更漂亮”。

# 21. 推荐分阶段执行

## P0：架构卫生

风险最低，优先执行。

- 权威状态 owner 表；
- source / owner 枚举统一；
- config 重复项审计；
- 端口 / model / TTL 单一来源；
- 日志字段统一；
- 文档状态标记；
- 删除明显失效的 TODO 和假状态；
- 建立架构依赖检查清单。

**出口：** 不改变任何玩家体验，测试无回归。

## P1：接口收敛

- SquadOrder adapter；
- TaskPatch 继续兼容；
- order → intent trace；
- safety reject / strategy replace 分开；
- Query DTO version；
- AI / Human command source 统一。

**出口：** 现有功能保持，日志能完整追一条订单。

## P2：运行时可靠性

- AI runtime health；
- Ollama / Laya / runner 生命周期统一状态；
- 自动启动 / 停止；
- 失败回退；
- 打包模式拆分；
- 错误面板不再依赖 mock 状态。

**出口：** 开游戏即可用；任一模型失败游戏不崩。

## P3：性能与调度

基于 profiling：

- 减重复 query；
- 减重复 command；
- batch；
- 缓存规则静态数据；
- snapshot 指标；
- AI inference 队列；
- 结构化日志采样。

**出口：** 只能以测量数据证明改善。

## P4：产品闭环优化

不加新基础设施：

- Objective Runtime；
- AI 副官真实文本语义；
- R0/R1/R2/R3；
- 对局结果进入训练数据；
- 交付包完整验收。

# 22. 每次架构优化 PR 必须回答

以后任何标记为“架构优化”的 PR，需要在说明里回答：

1. 是否改变重大结构？
2. 是否增加新的权威状态源？
3. 是否增加新的命令旁路？
4. 是否增加新的网络协议？
5. 是否增加新运行进程？
6. 是否破坏旧 DTO / save / replay？
7. 是否可 feature flag 回退？
8. 性能改善有什么数据？
9. 哪些自动测试覆盖？
10. 对产品策划有什么变化？
11. 是否更新 CHANGELOG / 策划变更日志？

只要第 1～5 项出现“是”，默认不属于本方案的“合理优化”，应另开重大架构评审。

# 23. 成功标准

本方案成功不是“代码看起来更漂亮”，而是：

- 新功能接入点更少；
- 状态来源更明确；
- 重复逻辑减少；
- AI 决策贡献可追踪；
- 联机与单机共用相同业务语义；
- 本地 AI 启停更稳定；
- Bug 更容易定位；
- 测试层级更清楚；
- 打包不再依赖开发者机器隐式环境；
- 文档与实际主干保持一致；
- 玩家体验没有因为内部整理而发生不必要变化。

---

## 最终原则

> **保持骨架，整理边界；保留能力，减少重复；先增加可观测性，再做性能优化；先用适配器收敛，再考虑删除旧接口。**

任何优化只要需要“推倒当前大结构才能做”，默认都不属于当前阶段。
