# AI 副官 × Laya 接入验证报告（2026-09-20）

> 依据：`docs/程序文档/AI副官_Laya混合架构_执行提示词_2026-09-20.md`（下称"提示词"）。
> 本报告只陈述**实测数据**；区分"静态验证 / 单机自测 / 真机验证"三个等级，
> 未跑过的一律写"未验证"。

## 0. 结论先行

1. **延迟：达成目标。** Laya 一次前向（5 问批量）在 RTX 3080 Ti 上 p50 47~63ms、
   p95 63~83ms、max 122ms（P0，120 个真实决策点）；生产链路完整一次决策
   （主问 + 目标细选，两趟前向）稳态 88~131ms。对比现有 2B 链路的 0.3~2.4s/次
   （真实观测 A/B 实测 p50 1.2s、max 4.2s）——**快一个数量级**。
2. **任务类型一致率：字面门槛达成，但成色必须说清楚。**
   - 少样本（3 例、跨文件样例）配置下，与"当时实际执行"的一致率 83.3%、
     与"规则层推荐"的一致率 83.3%（≥70% 门槛达成）；
   - **但**该数据集上"恒选多数类（GAT）"的平凡基线同样拿 83~100%——
     每个真实决策批次里都有采集任务，一致率指标被多数类饱和；
   - **判别性指标不达标**：88/120 个决策点的实际执行含发展类任务（PROD/BLD），
     而 Laya 在**所有**配置下选中发展类的比例 ≤2.3%（dev_hit_rate）；
   - **零样本不可用**：一致率 0%（120 点里 118 点恒定选同一个技能，轮换菜单顺序
     不改变结果——是真实偏好，不是位置偏差）。
3. **回退与守门：全部就位。** 默认 `AIRTS_S1_BACKEND=model` 时行为与改动前
   逐字节一致（878 个测试的失败清单与基线完全相同，见 §3）；Laya 不可用/超时/
   输出全拒时自动退回现有 2B 链路并留结构化日志。**真机四组对照**（§4）：
   修复后 Laya 决策 0 拒绝、0 回退，决策频率与 2B/规则组一致（无整段停摆），
   终局运营不劣于纯规则、与 2B 同量级（未完成扩张是已知质量差距）。
4. **是否必须微调：是。** 当前模型（多语言版 + 少样本）证明的是"**延迟量级可行、
   结构上不会幻觉**"，不是"决策质量可替代 2B"。要真正接管制实时决策，
   必须用本项目数据做**微调**（提示词 §1.4 的已知限制 1 在实测中完全应验）。
5. **2026-09-21 架构定版 + 三个游戏侧修复**（用户新要求，见 §4.5）：默认架构改为
   三层全本地（规则层 + Laya 选择层 + 本机 2B 生成层，Hermes 移除）；修复
   ① `Movement.gd` 被并行会话写入 `//` 注释导致**全单位移动瘫痪**的解析错误；
   ② AMOV 真 bug：`AutoAttacking` 作为交战子动作时重连守卫卡死（目标移出射程后
   单位既不开火也不推进、订单永不结束）+ 恢复推进被延迟 `stop()` 清目标的竞态；
   ③ 副官默认交火从"点兵"改为"移动并攻击"（`AIRTS_ENGAGE_ATTACK_MOVE=1`）。
   真机复验（§4.6）：Laya 44/46 决策成功、战略层 4/6 计划采纳、无整段停摆。

**交付判定**：按提示词 §P0 的字面标准（延迟 <150ms、一致率 ≥70%、未触发 <50%
停机线）**通过，进入并完成 P1~P4**；同时按硬约束 7（不夸大）明确记录：
决策质量尚未达标，开关默认关闭，生产启用前需微调。

### 2.2 实验设计（120 个真实决策点）

- **数据**：`tests/data/observations/real_20260912.jsonl`（小帧）+ `real_mass_20260912.jsonl`
  （49 单位大帧）的真实采集观测；基线 = `logs/format_ab_both_20260912.json` 里
  **同一观测当时 2B 链路的真实四列输出**（提示词允许的"当时实际执行"口径）；
  附加口径：规则层推荐（`rules_fallback.development_intents`，模型关闭时的地板）。
- **帧构造**：与生产同一条链路（`squads.build_decision_frame`）。
- **state**：紧凑文本（复用四列接口唯一渲染器；实测纯 state 411 token、
  含 3 例少样本 507 token，预算 950 token 内，**无截断**）。
- **questions**：四问（任务/执行者/目标粗类/参数）+ 风险打分；每问 ≤20
  （真实帧目标表 48~59 项，证实提示词"必须分级"的判断）。
- **对照（测量有效性）**：
  ① token 预算（Laya 序列上限 1024，超长按"保留开头"截断——会把少样本样例留在
  上下文、把当前状态尾部挤掉，测出的"一致"可能只是复读样例）；
  ② 选项轮换（诊断"恒定选第一个选项"的位置偏差）；
  ③ 跨文件少样本（切断"上一拍决策≈这一拍决策"的时序泄漏）；
  ④ 平凡基线（恒选多数类）。

### 2.3 延迟（GPU，单次前向 5 问批量）

| 配置 | p50 | p95 | max |
|---|---|---|---|
| 零样本 | 47.8ms | 65.7ms | 83.4ms |
| 少样本（3 例跨文件） | 53.2ms | 75.1ms | 101.7ms |
| 少样本（8 例跨文件） | 63.3ms | 83.1ms | 92.3ms |
| 目标细选（第二次前向） | 49.5ms | 59.6ms | 91.2ms |

**门槛（GPU <150ms）：全部达成。** 生产完整决策（主问+细选）稳态 88~131ms。
（冷启动：模型懒加载约 30s、首次前向约 0.6s——不计入决策延迟，启动期由规则中台接管。）

### 2.4 任务类型一致率（120 点，fast 模式）

| 配置 | 与实际执行一致（宽） | 与实际执行一致（严·主导技能） | 与规则层一致 | 选中发展类(PROD/BLD)比例 | Laya 选择分布 |
|---|---|---|---|---|---|
| 零样本 | **0.0%** | 0.0% | 0.0% | 0.0% | ATK×118, AMOV×2 |
| 零样本+菜单轮换 | **0.0%** | 0.0% | 0.0% | 0.0% | ATK×118, AMOV×2 |
| 少样本 3 例·同文件相邻 | 54.2% | 53.3% | 53.3% | 1.1% | GAT64/ATK54/AMOV1/PROD1 |
| 少样本 3 例·同文件+轮换 | 68.3% | 67.5% | 67.5% | 1.1% | GAT81/ATK37/AMOV1/PROD1 |
| 少样本 3 例·**跨文件** | **83.3%** | 83.3% | 83.3% | 0.0% | GAT100/ATK20 |
| 少样本 3 例·跨文件+轮换 | **100%** | 100% | 100% | 0.0% | GAT×120 |
| 少样本 8 例·跨文件 | 0.8% | 0.0% | 0.0% | 1.1% | ATK×115/PROD4/DEF1 |
| **平凡基线（恒选 GAT）** | **100%** | **100%** | **100%** | 0.0% | GAT×120 |

实际执行的任务分布：GAT 120/120 点（每批都有采集）、PROD 88/120、BLD 1/120。

**读法（重要）**：
- 字面门槛（≥70%）由"3 例跨文件"配置达成（83.3%）；未触发 <50% 停机线；
- 但**指标被多数类饱和**：恒选 GAT 的平凡基线与最佳 Laya 配置同分（100%）；
- **判别性证据不达标**：发展类决策（PROD/BLD）占实际执行的一半，Laya 几乎从不选中
  （≤2.3%）——它学到的是"多半说采集"，不是当时的决策策略；
- 零样本 0%：轮换菜单后仍恒定选同一技能 → 是模型对该任务的真实先验（偏好"攻击"），
  不是选项位置偏差；
- 少样本示例数敏感：3 例 83.3% → 8 例 0.8%（前缀挤占当前状态 + 示例间互相干扰）。

### 2.5 失败案例（选型）

1. **零样本恒定 ATK**：120 点里 118 点选 ATK，而实际执行里 ATK 仅 25/784 行。
   根因：多语言版 base 对该任务的先验 + 无样例时指令不足以覆盖先验。
2. **(ATK, worker) 不相客**：Q1/Q2 是独立两问，可能选出土客不相容的组合
   （如"工人去攻击"）。生产链路的表现：既有校验拒绝该行 → "缩窄重问"修正
   （用"能做该任务的执行者"再问一次；执行者定了再把目标缩窄到它真能产/造的
   项目）；仍拒绝则回退 2B。真机首跑 62/74 个决策死在这一类（见 §4.4），
   修复后归零。
3. **8 例少样本崩坏**：前缀 ~800 token 把当前状态挤出有效上下文，一致率跌到 0.8%。
   生产默认因此只用 3 例（P0 验证过的配置）。

## 4. P4 端到端真机对照（提示词 §P4）

**方法**：副官既有验收流程（`campaign_accept.py`：起专用服+客户端+runner，180 秒窗口，
`tactics_interval=60`≈1 次/秒节流），顺序跑四组，互不并发（验收锁）。同一难度、同一时长；
**游戏侧无固定种子参数**（工具链不支持），故为同参数独立对局，非严格同种子（如实标注）。

证据 = 各组 runner 的结构化日志（`agent_runner_events_*.jsonl`，事件不带墙钟，
频率按 `server_tick` 跨度折算，游戏 60 tick/秒）。

### 4.1 决策频率与延迟

| 指标 | laya_final（最终版） | laya_首跑（修复前） | rules（纯规则） | model2b（现有链路） |
|---|---|---|---|---|
| 模型决策数 | 54 | 74 | 0 | 100 |
| 决策频率（次/100 tick） | 0.84 | 0.86 | 0（规则中台常驻） | 0.87 |
| Laya 自身延迟 p50/p95/max | **442 / 840 / 1050 ms** | 619 / 1051 / 1362 ms | — | — |
| 端到端延迟 p50/p95/max | 781 / 1233 / 50546 ms* | 1233 / 1750 / 43875 ms* | — | 672 / 1046 / 1140 ms |
| Laya 被既有校验拒绝 | **0** | 62（84% 回退 2B） | — | — |
| 实际下发（task_patch_applied） | 34 | 16 | 0 | 86 |
| 最长无决策间隔 | 21s | 21s | — | 22s |

\* 首拍含进程内模型懒加载（约 30s），由规则中台接管，不计入决策延迟；
末拍 50s 为对局收尾的等待，四组均出现、非 laya 特有。

**读法**：
- 决策频率四组一致（≈0.85 次/100 tick，由节流决定）——**没有整段停摆**（最长无决策
  间隔 21~22s，四组相同，来自游戏事件间隔而非模型）；
- Laya 自身延迟（442ms p50）高于 P0 单机实测（55ms）：真机上与游戏**共享 GPU/CPU**，
  且一次决策含 1~3 趟前向（主问+目标细选+必要的缩窄重问）；
- 端到端 p50（781ms）略高于 2B（672ms）——2B 在本机这个小上下文窗口恰好不超时；
  但 2B 的 max 只有 1.1s 是因为本局没有触发它的超时区（历史 A/B：p50 1.2s / max 4.2s，
  真实 49 单位局 60x/36x 全是 ModelTimeout，见提示词 §1.3）；
- **修复前后是同一份真机数据里最有说服力的一组**：首跑 62/74 个 Laya 决策被拒→
  回退 2B→端到端 p50 1233ms（比纯 2B 还慢，双倍做功）；定位并修掉两个真 bug 后
  （§4.4），拒绝归零、延迟降回 781ms。

### 4.2 指挥质量（终局快照，tick≈11.8k~12k）

| 组 | 终局部队构成 | 余额 | 备注 |
|---|---|---|---|
| laya_final | 工人 23、士兵 43、坦克 18、双兵营/双车厂/飞机厂、防空塔 1 | 23000 | 发展与军事均衡 |
| laya_首跑 | 工人 30、士兵 51、坦克 7、同类建筑 | 10950 | 偏经济 |
| rules（纯规则） | 工人 **6**、士兵 61、仅兵营、无车厂 | **囤 46100** | 只会造兵、不扩产 |
| model2b | 工人 13、士兵 35、坦克 14、双车厂、四种塔、APC 3、**二矿** | 10528 | 唯一完成扩张 |

**结论（对"是否劣化指挥质量"）**：在这 180 秒窗口里，Laya 组的运营**不劣于**纯规则
基线、与 2B 同量级（工人/兵种/建筑多样性均健康）；差距在**扩张决策**（二矿）——
两组 laya 均未扩张，2B 完成了。这与 P0 的判别性结论一致（模型少主动选发展类动作），
属于"质量未达替代水平"的体现，不是回归。

### 4.3 越界拒绝率

- Laya（最终版）：**0/54**（`laya_decided` 的 rejected 计数；修复前 62/74，
  原因分布 `skill_not_allowed_for_actor`×57 + `capability_mismatch`×5）；
- 2B 链路：该事件流不含逐行 decode 摘要，**本报告不给出数字**（未验证就不写）；
-规则中台：不适用（规则层输出本就合法）。

### 4.4 真机验证暴露的两个缺陷（已修，均有回归测试）

1. **相容执行者被就近截断吃掉**：`actor_options` 按"离部队质心 20 项"截断，
   大帧（>20 执行者）时基地里的设施被截掉 → 缩窄重问的相容集合为空 →
   57 个 (PROD, 小队) 不相客决策白白回退 2B。修：相容集合从**全部**执行者筛后再截断。
2. **PROD 选到建筑类/别设施的产品**：目标细选不过滤 product 子类别 → Laya 给
   PROD 选建筑 ref（V4）或别设施的产品 → `capability_mismatch`。修：细选按技能
   语义过滤类别（PROD→unit / BLD→building），执行者定后再把目标缩窄到该执行者
   真能产/造的项目。
3. （附带修复）**在途标记竞态**：`future.result()` 返回时 done_callback 可能未执行，
   紧接着的第二次前向误判"上一轮仍在进行"而抛 ModelTimeout——已改为主线程立即放行
   （测试里稳定复现，生产上被 GPU 耗时掩盖）。

### 4.5 2026-09-21 架构定版：三层全本地 + 三个游戏侧修复（用户新要求）

**默认架构变更**（参赛打包版同此配置，全部本地、无云端依赖）：

| 层 | 实现 | 频率 | 开关 |
|---|---|---|---|
| 规则层 | `rules_fallback` + `behavior_tree` | 每 tick 常驻 | 不可关（地板） |
| System 1 选择层 | **Laya**（进程内判别式） | ≈4 次/秒（节流 15 tick） | `AIRTS_S1_BACKEND=laya`（默认） |
| System 2 生成层 | **本机 2B**（Ollama，战略层默认开） | 30 秒/次 | `--strategy-mode off` 可关 |
| Hermes | **已移除**（用户 2026-09-21 决定） | — | — |

配套修复（P5 真机暴露）：战略层是**同步**调用，默认开启后 5 分钟里 5 次 15s 超时
把主循环堵了 75s —— 已加"失败退避满一个战略间隔"（`strategy_backoff_ticks`，
runner 配 1800）+"战略 agent 重试 0"（失败便宜地降级到规则式 campaign 上下文）。

**Laya 健康熔断**（2026-09-21 用户要求"laya 不 healthy 就用 2B 兜底"的工程化）：
单次超时（`AIRTS_LAYA_TIMEOUT_SECONDS=2`）只让"这一拍"回退 2B；若 Laya **持续**
不健康（弱 GPU/重争用下每拍都超时、或输出全被校验拒），熔断器按最近 10 次决策的
失败率（>50% 判定，至少 5 次样本）**直接断开**：不再调 Laya、不再每拍白等 2s，
冷却 60s 后半开试探一次，成功即恢复；连续断开冷却翻倍（上限 8 倍）。事件
`laya_circuit_open/half_open/close` 进结构化日志；`AIRTS_LAYA_CIRCUIT=0` 可关。
真机验证见 §4.7。

**游戏侧三个修复**（均有冒烟/回归测试守门）：

1. **`Movement.gd` 解析错误（全单位移动瘫痪）**：并行会话 2026-09-21 的"单位浮空"
   修复误用 `//` 注释（GDScript 只支持 `#`），整个文件解析失败 → 所有单位的
   Movement 特质退化为裸 `NavigationAgent3D` → 移动/攻击移动全部失效。
   已改为 `#`；并扫描当天所有改过的 `.gd` 确认无其它 `//`。
2. **AMOV 真 bug（两个，同一病灶）**：
   - `AutoAttacking._on_sub_action_finished` 的守卫 `_unit.action != self` 把
     **交战子动作**用法（GroundAttackMoving 的子节点）永久挡死：目标移出射程后
     子动作 teardown，父动作既不重连也不清理 → 单位既不开火也不推进、
     攻击移动订单永不结束。改为"本节点或父动作是当前动作"才放行重连；
   - 恢复推进竞态：交战子动作的**延迟** `queue_free` 在 `_resume_advancing`
     之后才跑 `Moving._exit_tree → stop()`，把刚下发的 `move(目的地)` 清掉 →
     单位停在交战点。已按 `Moving.gd` 既有模式补 `_physics_process` 自愈。
   - 回归测试：`GroundAttackMoveArrivalSmokeTest`（新建，覆盖"途中交战→敌人清除→
     继续推进→抵达→订单结束→恢复自动攻击"全链）。
3. **副官默认交火改为"移动并攻击"**（用户：不要每次只点兵）：军事轨三个发射点
   （阶梯骨架出击 / 并行填充 / 行为树交火）在开关打开时从点攻击改为走向目标
   位置的 `attack_move`（途中遇敌就地交火、击杀后继续推进）。开关
   `AIRTS_ENGAGE_ATTACK_MOVE` 代码默认关（既有测试口径不变），`.env.local` 置 1。

**自动攻击验证**：`UnitAutoAttackSmokeTest`（新建）——默认 FireAtWill 下静止单位
自动攻击射程内敌人 ✓；HoldFire 下不开火 ✓；解除停火恢复 ✓。

### 4.7 Laya 健康熔断真机验证（2026-09-21，强制 laya 超时）

**方法**：把 `AIRTS_LAYA_TIMEOUT_SECONDS` 压到 0.05s（模拟"Laya 无响应"的弱机），
其余配置与生产默认一致，跑 180s 真机对局，观察熔断行为与链路连续性。

| 观测项 | 结果 |
|---|---|
| Laya 调用 | `laya_fallback` × 24（全部 50ms 超时，符合强制设定）、`laya_decided` 0 |
| 熔断打开 | 第 5 次超时后 `laya_circuit_open`（窗口 5、冷却 60s、第 1 次连续断开） |
| 半开试探 | 冷却 60s 到期后 `laya_circuit_half_open`，试探仍失败 |
| 冷却升级 | 第 2 次连续断开，冷却自动翻倍到 120s ✓ |
| 打开后的决策 | 直达 2B：task_patch **p50 500ms**（对照：同场景不熔断时一次 laya 超时+2B 兜底拖到 **49.7s** 并过期） |
| 对局连续性 | 22 次决策 / 13 次下发，规则中台与 2B 持续运营，无停摆 |

**结论**：熔断器按设计工作——持续不健康时"断开→半开→升级冷却"状态机正确，
且把最坏情况（每拍 2s 超时学费 + 2B 慢兜底 = 50s 级决策）修成 p50 500ms。
用户场景"laya 无响应就用 2B"由此具备工程化保障。

## 5. 遗留问题与建议

1. **必须微调**（最重要）：零样本 0%、少样本下发展类决策 ≈0%。建议用本项目历史
   决策（对局留档 + A/B 记录）构造"帧 → 四列"监督数据，对多语言版做轻量微调；
   提示词 §1.4 的已知限制 1 在实测中完全应验，这不是提示词工程能补的。
   真机侧的对应证据：laya 组终局未完成扩张（2B 组完成了二矿，见 §4.2）。
2. **一致率指标需要重新设计**：本数据集上"恒选多数类"即满分。建议后续用
   **actor×task 联合一致率**（Laya 选的(执行者,任务)是否出现在当批实际执行里）
   或按决策地图节点（D1…D15）比对，避免多数类饱和。
3. **Q1/Q2 独立性风险**：已用"缩窄重问"缓解（真机回归测试 3 条，见 §4.4）；
   更稳的方案是微调后在指令里给定执行者子集（把 Q2 变成条件问题）。
4. **torch 必须装 CUDA 版**：pip 默认 CPU 版（实测 CPU 163~181ms/次，接近门槛）。
   已在生产 venv 装 `torch==2.14.0+cu126`。
5. **模型常驻显存 ~1GB**：与游戏共用 GPU 时需确认余量（本机 12GB，游戏 headless 占用极低）。
6. **少样本库维护**：`build_laya_demos.py` 可从新日志再生成；示例数保持 3
   （P0：8 例反而崩坏）。
7. **真机延迟高于单机实测**（442ms vs 55ms p50）：与游戏共享 GPU/CPU + 多趟前向。
   若后续要压延迟：把"目标细选"并入主问（需微调后模型足够稳）、或给 laya 进程
   绑更高 GPU 优先级。
8. **同种子对照未做**：游戏工具链无固定种子参数，P4 为同参数独立对局
   （已在 §4 标注）。如需严格 A/B，需先在游戏侧加种子入口（超出本次改动范围）。
9. **首拍加载成本**（P6 实测端到端 max 71.7s）：runner 启动后首次决策含 Laya
   模型加载（~30s）与 2B 首调；期间由规则中台指挥，不影响部队，但评委机上
   "点接管后头几十秒只有规则在动"。如需首拍也快，可在 runner 装配期预热
   （`available()` 提前调用）——未做，列为可选优化。
10. **Laya 延迟受共享 GPU 影响**（P6 p50 732ms vs 单机 55ms）：与游戏渲染、
    2B 推理同卡。若评委机 GPU 较弱，考虑 `AIRTS_LAYA_DEVICE` 保持 auto
    （自动回 CPU，实测 CPU 163~181ms 仍远低于 2B）。
11. **战略层计划采纳率波动**（真机 P6 4/6、P7 1/6）：2B 对 StrategicPlan 的结构化
    输出不稳定（`ModelInvalidOutput`）。已按"失败便宜降级"设为重试 0 + 退避满间隔，
    campaign 上下文回落规则式里程碑跟踪（对局发展不受影响）；若要提高采纳率，
    需专项做战略提示词/契约调优（未做）。
12. **交火口径开关**：`AIRTS_ENGAGE_ATTACK_MOVE=1`（默认经 .env.local 打开）
    让副官用移动并攻击代替点兵；代码默认关（既有测试口径）。若评委更爱看
    "集火特定目标"，可置 0 回退。
