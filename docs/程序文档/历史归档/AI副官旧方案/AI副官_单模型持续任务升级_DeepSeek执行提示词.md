## 1. 产品目标与核心改变

项目 `G:\AIRTS\AI_RTS`。玩家要在本机自定义对局看到经济持续发展、多支部队同时侦察、防守与作战，并能随时介入。只有一个真人玩家、一个本地 MiniCPM5-2B 决策模型。保持当前已安装模型，先确认实际模型标签、量化与上下文配置，不静默换模型。

本轮重点不是继续调短轮询、增大批量或增加模型请求并发，而是把主控制接口从“一批立即动作”升级为“少量持续任务与有限目标”。一项任务可以持续覆盖多个单位、多次生产与多个执行步骤；所有任务同时推进，无需模型为每一步批准。模型仍决定发展方向、目标、取舍和优先级，程序负责在这些边界内落实。

例如模型选择“东矿防守”，程序管理授权小队的集结、到位、有限范围交战、目标失效、必要撤离与回到防区；到位只是阶段进度，不是防守任务完成。“补齐一支部队”由程序持续计算已有、在产、损失与缺口，在有限预算和数量内补齐，不是模型每次只生产一个兵。“侦察东侧走廊”包含多个合法观察点和情报刷新，不是走到一个坐标就算探完。

这不是训练模型，也不是做另一个规则指挥官。执行器是正常路径，不应只在模型失败时启用。不得用固定全局规则偷偷替换模型的选择，再把效果全部归功于模型。

## 3. 最小架构

沿用 LangGraph 协调、PydanticAI 结构化调用和本地 Ollama，只保留一个模型决策入口，每局最多一个在途推理。不是“一次战略模型 + 一次战术模型”的串行推理。

链路：游戏事实与任务进度 -> 内存中的手册候选 -> 单模型输出任务增量 -> 权威校验与任务账本 -> 持续执行器 -> 小队与单位底层动作 -> 实际反馈。

模型输出与游戏持续执行必须解耦。慢模型不能阻塞观测、回执、控制权事件或执行器。优先复用现有实现，避免新建通用 HTN/GOAP 引擎、消息中间件、多 Agent 系统或向量库。

Godot 权威端负责单位即时执行、控制权、资源与命令入口；涉及到位警戒、交战边界、目标变化等必须在游戏模型等待期间继续。Python 可负责策略选择、任务进度汇总和非即时工作编排，但不能让脱困、避战等必要即时行为依赖一次慢 runner 循环。明确每种任务只有一个生命周期所有者，另一端只是镜像，不维护两套竞争任务状态。

## 4. 模型表达什么

使用现有决策手册中的稳定策略 ID 和运行时合法目标 ID。任务类型控制在少量可组合模板，例如：采集维护、有限发展计划、有限补兵、防区守卫、区域侦察、集结、攻击推进、撤退重组。名称和拆分由你根据现有代码确定。

模型选择任务模板、授权小队或池、合法目标、优先级、有限规模及风险偏好。预算、风险参数可用有清晰含义的少量预设；程序算术和游戏事实不交模型猜。每个预设必须展示其实际限制，模型可在候选之间权衡，不能只给唯一“正确答案”。

输出只描述变化：创建、调整、取消；未提及的任务继续。空变更合法。明确调整是否保留当前子步骤，避免每轮重建任务。使用稳定 task_id 与版本去重，模型不得生成对局身份、控制代际或请求期限。

示意而非现有接口：

```json
{"changes":[
  {"op":"start","option_id":"offer_east_defense","group_id":"squad_2"},
  {"op":"start","option_id":"offer_ground_reinforcement","group_id":"army_pool"}
]}
```

offer 必须在请求时绑定具体模板、目标、数量/预算上限、可用对象、允许后续步骤和退出条件。组成员动态变化由权威端管理；组 ID 不能成为接管新成员或玩家单位的通行证。现有成员逐对象绑定代际；请求后加入的对象必须通过独立的新授权事件才能参与任务。

如仅 option_id 太限制判断，可提供少量显式参数。实现与现有 DirectiveBatch 的适配，旧协议仍可作为任务产生底层命令的通道；不能把增加几个 JSON 字段当作完成任务执行器。

## 5. 手册必须进入真实决策链

启动时加载并缓存策略定义，用可靠解析器读取规范数据区块。自然语言条件不能直接 eval；映射到一小组可测试的事实判定函数。未知字段和无法执行的模板应显式报错。

按实际局势筛出少量候选，保留不同取舍、延续当前任务和必要的信息获取分支。候选覆盖经济、侦察与军事，不能长期只取最高优先级前三项而使某条职责饥饿。事实变化或任务事件触发重选，另保留低频复查，避免漏事件后永不决策。

模型只读局势摘要、小队摘要、当前任务和相关候选，不读整本目录，不接收全部单位逐个重复的能力表。成本、生产关系和能力来自本局权威规则。可在候选中共享成本定义，不能为了缩短输入删掉资源取舍信息。

默认模型输出目标约 100 至 250 token，复杂更新上限初始 512，具体由实测调整。保留完整 JSON、结构约束与截断检测；验证思考关闭参数是否有效。无需输出长篇思考，玩家意图确认只需必要的简短解释。

## 6. 持续任务必须真正运行

每个任务都要有持有对象、执行状态、子步骤、进度、阻塞原因、退出条件和可恢复方式。可采用 pending/running/blocked/succeeded/cancelled/failed 等简单状态；守卫与采集可长期 running，不能用“Accepted”或“到位”冒充全任务成功。

- 采集维护：空闲授权工人加入、矿点失效后重选允许范围内的矿点，避免反复打断往返。没有实际资源需求时不要为填满任务数强迫采另一资源。
- 有限发展：完成所选建筑/产能目标，使用合法建造位置和工人，维持基本采集；完成、预算不足或条件失效时停止新增支出并报告。不能自行无限扩张。
- 有限补兵：依据目标编成、已有、在产与有效承诺计算缺口，选授权生产建筑，限制队列。新兵进入明确的集结或增援任务，不能出生后长期无事可做。持续补损必须有累计支出或补充数量上限，避免永远填无底洞。
- 守卫：到达后继续警戒，限定追击范围与可攻击类型；敌目标死亡后可选防区内合法目标，威胁解除后回防区，不追到敌基地。
- 侦察：连续覆盖候选区域并记录观察结果与时间，受阻点不算已侦察，未见敌人不等于全图安全。
- 进攻与撤退：沿所选目标和交战约束推进，局部选敌与撤离使用现有底层能力；不得用全图敌我数量机械判断胜负。任务关键前提失效时阻塞或撤离并请求模型调整，不能偷偷换成全局新攻势。

复用已有动作和导航脱困。不要为完成本轮重写寻路，也不能用模型反复发短距离移动来掩盖卡住。不同职责的任务并发推进，模型等待期间照常运行。

## 7. 扩大控制规模但保持简单

新增单位通过权威授权规则加入适合的任务池，生产建筑、工人与作战单位分开统计。不能用“所有己方单位减玩家单位”代替实际授权。池中对象必须能追溯任务或明确等待原因。

小队结构稳定，避免每轮全军重新编组。常规局部任务检查可从 5 至 10Hz、经济检查从 1 至 2Hz 开始评估，这些是调度初值，不是强制每次重发命令，更不是每单位全图扫描。单位运动沿用游戏物理更新。使用事件、缓存和分批预算限制开销。

只有子步骤变化才产生底层命令。移动等合法同类动作可合并，生产/建造不能随意合并为一个订单。批量传输减少往返，权威端逐项处理并返回逐项结果，默认不假定整批原子成功；同一对象冲突、重复扣费仍由统一入口裁决。

待发队列有界、合并旧任务版本、玩家事件优先。不能靠无限队列、无限线程或无限增大 max_batch 解决吞吐。

## 8. 玩家、预算与失效保护

玩家命令进入权威端即收回相关对象、更新代际并撤销冲突子任务；不等待模型。其余单位继续。未确认不自动交回，旧确认按钮不能覆盖新命令。沿用确认目标、亲自指挥、误触交回的产品语义。

固定资源预留与玩家优先不变。任务预算是对玩家预留之外额度的进一步限制；每次实际支出重新检查余额与其他尚未扣款承诺。已扣款不重复算承诺，失效承诺及时释放；任务不能相互借用未授权额度。

模型请求接收期限、任务寿命与允许新增支出的窗口分开。旧响应禁止续期或换新代际；长期防守也不能因模型请求过期反复停止。模型长期离线时维持可行的当前任务与保守自卫，有限建设生产到上限后停止扩张，明确显示等待决策。

规则默认行为只能用于冷启动或明确降级。执行日志区分 model_selected、task_executor、safety_rule、fallback，记录原始任务来源。不要让多个全局规则产者用不统一的动作优先级持续覆盖模型任务。

## 9. 分阶段实现和决定是否有效

先建立固定任务的真实执行，不调用模型，验证单项工作流和多任务并行。然后接手册候选与单模型任务增量，最后接玩家交互和故障恢复。每阶段可运行；不要另建一个演示入口绕开正常副官按钮。

关键验收是“模型安静时任务仍推进”，不只是命令更多：

1. 固定同一地图、种子、单位和预算，对比升级前后。单独做 50/100/200 个授权对象的压力测试，100 为主要目标，200 用于寻找性能边界，不预先承诺通过。
2. 测量有效任务覆盖、可工作对象无任务的时间、新兵入队延迟、事件到首次动作延迟、实际资源收入、建筑完成和单位产出。合法等待单列，不能把全军 hold 计为有效推进来抬高覆盖率。
3. 选定持续任务后，模拟模型延迟或离线 30 至 60 秒，验证采集、有限补兵、守卫和区域侦察在权限及预算内继续；期间注入真实目标死亡、单位损失和局部玩家接管。
4. 同一观测提供至少两组不同可行任务选择，验证改变模型选择会改变任务执行和资源分配；排除“无论模型说什么，规则都做同一件事”。
5. 覆盖任务调整不重置、重复响应不重复支出、成员变更、旧响应、旧按钮、部分批次拒绝、队列不足、路径失败、对局重开和 runner 重启。持久任务恢复前重新核验权威状态。
6. 正常入口连续对局至少 15 分钟，展示经济与多队行动、玩家接管和交回。状态只展示实际进度；提交可复现步骤和证据。

性能：游戏同时运行、模型预热后测至少 100 次真实规模请求，报告首次结构与语义合法率、重试、超时、P50/P95、输入输出 token、显存和游戏帧耗时。延迟目标仍为 P50 <= 1.5s、P95 <= 4s，冷启动单列。记录任务执行器 CPU 时间，禁止用阻塞游戏来让模型测速达标。压缩后不达标要如实报告，不改模型或用规则冒充结果。

## 10. 参考与交付

- [0 A.D. Petra AttackManager](https://github.com/0ad/0ad/blob/master/binaries/data/mods/public/simulation/ai/petra/attackManager.js)：分别管理准备和已启动的进攻计划，各计划持续推进。

- [LLM-PySC2](https://github.com/NKAI-Decision-Team/LLM-PySC2)：可配置小队、动作空间、自动经济管理。本项目只取任务封装思路，不增加模型或多 Agent。
- [Voyager](https://github.com/MineDojo/Voyager)：可复用、持续执行的技能与反馈，属于 Minecraft 研究参考；不照搬 GPT-4、在线生成执行代码或训练流程。
- [python-sc2 命令合并](https://github.com/BurnySc2/python-sc2/blob/develop/sc2/action.py)：区分可合并移动动作与不可简单合并的生产动作。

交付代码、针对性测试、实际运行证据、前后对比、启动方法与剩余问题，同步更新决策手册的实施状态。允许自主调整模块和参数，但必须解释与性能或正确性相关的取舍。没有完成的实机测试明确标注，不能把接口接通、测试数量或短时兵动起来当作整轮完成。
