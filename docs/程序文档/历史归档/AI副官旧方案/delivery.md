## 第一阶段：数据与执行契约

本阶段交付后停在审查节点，暂不接真实双模型，不改线上服务。

1. 记录基线：提交 ID、脏文件清单、规则指纹、测试命令、已知失败。检查工作区说明，沿用现有架构。
2. 导出实际规则和版本，提供足够的战术快照，保留旧 status 使用方式。
3. 增加副官统一提交与回执查询适配，复用权威运行时；落实身份、版本、有效期、幂等和玩家优先权。
4. 实现可独立测试的协调器核心：任务/计划状态、逐条批次、事件合并、单写入及持久化隔离。用确定性假模型验证协议，明确它不是模型实战。
5. 文档化与现有接口的映射、兼容差异和第二阶段待接位置，提交中文审查报告。不要为了测试重写整个网络协议。

必须有证据的场景：

- 新增普通单位/建筑并更改成本，在独立测试配置的新对局中被规则视图发现；不改提示词数值表。生产选择匹配动态生产关系。
- 新对局即使复用 Unit_1 等名称，旧请求/账本也不会生效。
- 双玩家视野与命令权限隔离；未建成/死亡观察者不泄露敌情；失去视野不能当作死亡。
- 两条竞争资源的订单不超支；重复同 ID 不重复扣费或生产，同 ID 不同参数拒绝。
- 玩家手动接管、模型请求乱序返回、过期计划/命令、目标死亡/移出视野均有明确结果。
- PendingAuthority 超时不重复下单，查询终态与原命令 ID 对应；命令接受与任务完成分开。
- 并发输入不覆盖状态/回执文件；事件风暴可合并，断线可通过快照恢复。
- 至少一条真实双进程生产和建造链验证实际状态变化，其他边界优先用确定性测试覆盖。

## 第二阶段：审查后实施

第一阶段经负责人审查后再给具体任务，以下为范围预告：

- 核实服务器 Hermes 集成方式，接入两路配置化 API，宿主调度与降级逻辑。
- 更新战略手册：保留方法和规则引用，删除作为事实来源的硬编码数值、地图尺寸和固定兵种阵容。
- 中文 UI 改为关联事件视图，适配窗口尺寸并做截图验证。
- 实际模型闭环：观测 -> 战略计划 -> 战术意图 -> 权威回执 -> 世界状态 -> 下一轮决策。
- 与旧版单循环对照评估并准备可回退开关。可复用第一阶段旧接口兼容层。

无本机 Hermes 不代表线上没有配置。需要远程时先查实际连接与服务信息，明确读写边界；本次第一阶段不 SSH、不部署、不重启线上服务。缺环境如实记录，不自动安装或迁移线上模型配置。

## 三天内容开发协作

各工具使用独立 worktree/分支；脏工作区不得强制搬移、清理或回滚。不要自动 stash 用户修改。无法隔离时仅修改约定文件并在写入前复读。

内容工具负责平衡配置、场景、模型和新机制；副官工具负责新增适配、协调器、观测、测试和副官界面。共享热点包括 Match.gd、DebugControlServer.gd、NetSync.gd、CommandRuntime、Catalog 与资产映射；保持补丁小，避免同时大改。由负责人在阶段集成时检查差异。

给内容开发工具的约定：稳定 ID 不随显示名更改；数值和生产关系进入现有规则来源；新增能力写明观测字段与命令支持情况；删除/重命名 ID 属不兼容变更，须记录旧新映射及规则版本变化。无需为副官复制第二份平衡数据。

第一阶段定义版本接口，不冻结兵种数值。每次阶段集成记录 commit、dirty diff 指纹和 rules_version；最终验收在最新内容合入后重新执行相关测试。不能拿旧内容测试结果替代新版本验收。

## 测试与汇报纪律

每次运行使用独立 run_id 目录，保留启动参数、版本、事件、回执与快照。不得覆盖失败轮次或汇总各轮最好成绩。PASS/FAIL/SKIP/FLAKY 明确定义；FLAKY 是重试后成功但不稳定，首次失败与重试次数必须保留。

静态检查与项目既有构建/测试按改动范围执行。现存失败逐项与基线对照；没有相关文件改动不能单独证明与本次无关。解析错误、权限串线、重复扣费和玩家控制被覆盖属于阻塞问题。

不要机械跑十轮同一缺陷。先修复确定性问题，再扩展场景和种子；最终模型阶段在固定版本运行连续回归，记录敌袭到回防命令接受的 P50/P95、状态年龄、生产空闲比例、重复/过期命令、API 调用量/费用以及对局结果。超时计入，不能只统计成功请求。无计费数据时仅报 token/调用量，不编造费用。

对照保持地图种子、对手、初始条件、规则版本一致，记录实际模型版本和预算。模型随机性无法完全消除，报告样本量和范围，不用单局胜利证明提升。

只回收本次创建的进程，测试启动前确认连接本地隔离端口，避免误连玩家公网对局。不执行 git commit/push、远程部署或清理其他任务的进程。
