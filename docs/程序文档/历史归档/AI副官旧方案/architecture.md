# [已废弃 / 仅供追溯] 双层副官架构与协议

> Deprecated，2026-09-12 归档。战略/战术两路模型、并行推理和旧参数不再是目标架构。协议历史供排查现有兼容代码，执行请读[当前入口](../../AI副官_当前执行入口.md)。

## 1. 职责与运行方式

- 战略角色：输出阶段目标、任务优先级、兵力分配、资源预留、完成与中止条件；不直接调用游戏命令。
- 战术角色：根据当前计划、局部事件和最新观测提出有限命令批次；不能自行修改资源预留或战略目标。
- 副官协调器：宿主程序调度模型、管理计划和任务、合并事件、校验模型输出、记录决策。模型无需依靠 sleep 工具维持循环。
- 权威执行入口：复用现有游戏运行时完成权限、归属、能力、资源、目标、位置校验。禁止模型绕过入口直接修改游戏状态。
- 游戏既有寻路、自动接战及其他持续行为照常运行。此次不承诺新实现亚秒级智能微操。

优先级：玩家手动命令 > 明确授权的紧急战术任务 > 常规计划任务。紧急任务可中断副官自己的任务，但不得绕过玩家控制、资源硬约束或合法性验证。

同一角色同一对局最多一个活动模型请求；战略与战术可并行。超时请求即使随后返回也必须按请求代际和状态有效性重新校验，不能抢回控制。

战略复盘初始配置 30~60 秒并支持重大事件触发；战术按事件触发并合并重复事件。具体超时、合并窗口、预算和采样频率均配置化，以实测为准，不将此间隔描述成响应时延保证。

## 2. 规则与观测的唯一来源

已有入口：

- source/csharp/Application/Configuration/BalanceCatalogContracts.cs：IGameBalanceCatalog、Version、稳定类型 ID。
- source/csharp/GodotAdapter/Production/GodotProductionDefinitionRepository.cs：生产定义和受信任资产映射。
- source/csharp/GodotAdapter/Input/UnitCommandGateway.cs：既有单位命令入口。
- source/net/DebugControlServer.gd：现有调试观测与命令适配。

从当前 Match 实际使用的 Catalog 导出规则，不能另读磁盘最新配置假装是当前对局规则。Catalog 已约定在对局生命周期内不可变；默认内容变更在新对局生效，本轮不做热更新。

规则视图至少表达：稳定类型 ID、显示名、实际存在的能力、移动与攻击域、成本、生产者与产品关系、已实现的前置条件、施工定义，以及来源指纹。缺失语义标记 unknown/unsupported，不得伪造合理默认值。场景路径由受信任映射解析，不让模型构造任意资源路径。

显示名可能需要从现有本地化或展示资源补充；必须与 Catalog 类型 ID 关联。技能只有在命令执行与观测均支持时才标为可由副官调用。

观测采用公共包头：schema_version、match_id、player_id、rules_version、snapshot_id、server_tick。标识由服务端确定，不能用单位名是否重复来推测换局。

提供三个视图，具体路由命名可按项目现有模式确定：

1. 规则视图：按版本缓存，无需每次传全表。
2. 战略摘要：资源、产能、任务进展、已知敌情及其时间、实际地图边界、合法可用能力。
3. 战术快照：相关我方和当前可见敌方的实体 ID、类型 ID、位置、血量、能力、当前任务，以及相关生产队列、资源点、施工状态。

战术快照必须足以选择 gather/build/attack/move 目标，不能用只有 counts 的 lite 代替；支持范围或实体筛选。截断必须显式报告 truncated 和覆盖范围，并提供续取机制，不能将没返回的单位解释成阵亡。

敌方快照与事件遵守同一玩家视野规则。历史情报带 last_seen_tick，不能更新迷雾中的真实血量、位置或死亡信息。实体失去视野与确认死亡是不同事件。不向模型提供 full_vision。

身份绑定到实际接管的玩家与对局，不得只取第一个 human=true 玩家。控制器不能仅通过自报 as_player 获得其他玩家权限。

## 3. 计划与命令契约

计划必填语义：plan_id、plan_version、match_id、player_id、rules_version、based_on_snapshot、valid_until_tick、阶段目标、任务集合、资源预留、终止条件、面向玩家的简短依据。

任务使用稳定 task_id，指定单位集合或选择约束、优先级、完成条件和允许的动作。战略新计划经协调器采纳后才生效，旧计划输出不能直接覆盖。

命令包必填语义：command_id、request_id、match_id、player_id、rules_version、plan_version、task_id、based_on_snapshot、issued_tick、expires_tick、动作和参数。逻辑时钟以服务器 tick 为准，不比较不同机器的本地墙钟。

权威入口在真正执行前验证：

- 对局、玩家授权、规则和计划版本有效。
- 未过期，相关单位控制代际未被玩家操作或新任务更新。
- 实体存活且归属正确，目标在当前合法可见范围内，能力和目标域匹配。
- 资源和生产/施工条件使用当前权威状态；模型快照只作为决策依据。

版本新不等于所有旧命令均不可用：第一版可保守拒绝旧计划的新提交，但不得自动取消已经接受的生产订单或施工并导致退款/重复扣费。跨版本保留任务须明确迁移。

command_id 幂等作用域为 (match_id, player_id, command_id)。同 ID 同参数重复请求返回原回执，不重复执行；同 ID 不同参数明确拒绝。去重记录与普通展示历史分开，不能因显示历史只留 64 条而失去去重能力。对局内记录有容量上限时应明确背压，不能静默遗忘未完成命令。

回执区分三个概念：传输接收、权威接受、任务完成。保留现有 ok/accepted/status/reason/command_id/result 兼容字段；增加可关联任务与版本的结构化信息。PendingAuthority 的 accepted=false；Accepted 仅代表命令接受，不代表建筑已建成或部队已抵达。任务进度单独报告 running/completed/failed/cancelled/unknown 等状态。

重试先按 ID 查询。超时或查询不到不能直接当失败重新下单；保留 unknown 并复核。执行授权校验同样适用于回执查询，不得泄露其他玩家命令。

## 4. 仲裁与并发

每个对局/玩家一个逻辑写入协调器。模型并行提出意图，协调器按顺序提交权威入口；不同单位的动作可以在世界中并行进行，不要求并发修改 Godot 场景树。

复用现有 CommandRuntime 的实际资源扣除和命令执行。批次明确采用逐条接受并返回逐条回执，不能暗示全批原子成功。同一批前一条花掉资源时，后续条目按剩余资源重新校验。

资源预留是副官花费约束，不是第二套游戏余额；结合已接受的实际支出计算，禁止重复计扣 PendingAuthority。紧急任务若允许动用预留，必须由计划显式授权并记录原因。

玩家手动下令立即更新所选单位控制代际并取消副官对这些单位的控制租约。重新接管需用户显式交回或符合事先选择的自动接管规则，不能下一次模型轮询立刻抢回。

事件带 match_id、player_id、event_id、server_tick；去重、合并和队列均有界。丢事件或消费者断线后，通过新快照恢复，不假设事件永不丢失。

持久化按对局与玩家隔离。现有 last_status.json、last_receipt.json 及固定 .tmp 不可直接被两个会话并发写入。由单一写入者管理，或使用隔离目录、独立临时文件及明确同步机制；仅原子 rename 不解决逻辑覆盖问题。

## 5. 模型与界面边界

两个角色分别配置 provider/model/timeout/输出上限/费用预算，允许暂用同一提供方。凭证仅留服务端配置，不进入客户端、日志、文档或模型上下文。

复用 Hermes 可用的扩展机制，但先核实版本和实际可用接口。不要假设它已有双角色调度 API，也不要直接启动两个互相独立且都能写游戏的 shell 会话。提供方适配与角色职责分离，DGX 后续替换适配器。

模型输出结构化计划或意图，程序校验；失败限次重试并有退避，费用和事件风暴不会造成无限调用。模型不可用时保持既有合法任务与游戏自动行为，界面明确显示降级，不捏造新决策。

UI 消费按 plan_id/task_id/command_id 关联的结构化事件，显示阶段计划、当前动作、可观察依据、执行结果与更新时间。不从不同日志行拼接因果关系；不展示隐藏推理过程，不以 Accepted 文案声称任务完成。
