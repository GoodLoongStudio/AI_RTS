> 追问原因；定位后用户定调："**你要修好这个问题啊，不能让我来操作的，

| 项 | 修前 | 修后 |
|---|---|---|
| 模型服务谁起 | 只有 `build/启动AI_RTS.bat` | **游戏自己**（加载页预热 / 面板接管两条路都保障） |

| runner 连的端口 | `.env.local` 写 11434，.bat 用 11436（不一致） | 游戏钉死 11436 并注入 runner，`.env.local` 已对齐 |
| 预热期间面板文案 | "战略思考这一轮没成功"（像副官坏了） | "本地模型预热中（首次约 1~2 分钟），先用规则指挥" |

## 2. 那条 HUD 到底是什么（先答用户的问题）

`为什么：战略思考这一轮没成功，先用规则顶住` 来自 `agent_runner.py` 的
`DEGRADE_CN["strategy_model_"]`，含义是**战略层模型（System 2，`minicpm5-adj-16k`）
本轮调用失败，按设计回落到规则层**。日志里的真因（今天累计）：

| 层 | 异常 | 次数 | 原因 |
|---|---|---|---|
| strategy | `ModelUnavailable` | **154** | `模型调用失败：Connection error.` |
| strategy | `ModelTimeout` | 16 | 15s 超时 |
| strategy | `ModelInvalidOutput` | 4 | 输出不合法 |
| tactics | `ModelUnavailable` | 7 | Connection error |

`Connection error` 是 **TCP 层就连不上**，不是模型答得不好。实测：11434 与 11436
**都没有 LISTENING**，也没有 `ollama.exe` 进程。服务根本没起。

## 3. 根因：保障动作写在了启动器里，而不是游戏里

`build/启动AI_RTS.bat` 才会 `start ollama.exe serve`（端口 11436）并设好三个
`*_BASE_URL`。玩家只要不是用那个 .bat 启动游戏——从 Godot 编辑器/DEBUG 跑、
直接双击 exe——模型服务必然不在。而 runner 只从 `.env.local` 读端点，
那份文件写的又是 **11434**（与 .bat 的 11436 不一致），于是连"连不上哪儿"
都看不出来：面板只说"没成功"。

## 4. 修复

### 4.1 新增 `source/ui/AdjointModelService.gd`（模型服务自动保障）

状态机 `""/starting/warming/ready/timeout/missing/failed`，每个状态都有一句
玩家能看懂的中文文案（`status_text_for()` 拆成纯函数以便无副作用单测）。
流程：**已在听 → 直接预热**；没在听 → 定位运行时 → 拉起 → 等端口（≤45s）→
发一个 1-token 的预热请求把 2.6GB 权重载进去（≤180s）→ `ready`。
**全程非阻塞**（冷模型首次推理实测 ~71s，阻塞启动不可接受）。

运行时定位覆盖两种布局：分发布局 `<exe 同级>/adjutant_runtime/`、
仓库布局 `<工程>/build/adjutant_runtime/`。

### 4.2 为什么要"脱离父进程"拉起（否则每次开游戏都重付 70 秒）

`OS.create_process` 的子进程在 Windows 上被父进程的**作业对象**管着，父进程一退
全部被杀——实测 Godot 退出后，连同 `cmd /c start` 拉的子孙一起死。服务活得比游戏久
才有意义。所以改为经 **WMI（`Win32_Process.Create`）** 拉起：那种进程不在我们的
作业对象里，能活过游戏退出。

`ollama serve` 只认 `OLLAMA_HOST` / `OLLAMA_MODELS` 两个环境变量（没有对应命令行
参数），而 WMI 的 Create 不能传环境变量 → 承一层 `.cmd`（由游戏写文件，不进任何
shell 解析），再用 `.ps1` 调 WMI（同样写文件，避开嵌套引号地狱）。
脱离失败则退回普通子进程（只活本次会话，仍然满足"不用手动起"）。

### 4.3 接进两条 runner 启动路径

| 位置 | 改动 |
|---|---|
| `main-menu/Main.gd`（**主菜单**） | 开过接管的玩家一进主菜单就开始起服务 + 预热，把菜单停留时间用起来 |
| `Loading._prewarm_adjutant()`（加载页） | 起 runner **之前**先 `ensure_started(self)`，预热与地图加载并行 |
| `AdjutantButton._start_local_runner()`（面板"接管"按钮） | 同上 |
| `AdjutantRunnerLauncher.start()` | 同上，并新增 `parent` 参数往下传 |

主菜单这一处有两个护栏，避免替玩家决定/拖累无关玩家：只对**开过副官接管**的玩家
预热（`auto_takeover`，没开过的不替他决定）；专用服实例不预热（服务端起它是浪费 2.6GB）。

### 4.4 端点钉死 + `.env.local` 对齐

runner 引导文件里注入（`env_file.py` 只填"尚未存在"的变量，所以这里必胜）：

```python
os.environ["LLM_BASE_URL"] = "http://127.0.0.1:11436/v1"
os.environ["TACTICS_BASE_URL"] = "http://127.0.0.1:11436/v1"
os.environ["STRATEGY_BASE_URL"] = "http://127.0.0.1:11436/v1"
```

实测子进程里三个键都拿到了正确值。同时把两份 `.env.local`
（`source/adjutant_coordinator/` 与 `build/adjutant_runtime/`）的 11434 改成 11436，
消掉"两处口径不一致"这个坑。

### 4.5 预热期间面板说真话

`_apply_hud_status()` 在 `AdjutantModelService.is_warming()` 时，把"为什么"换成
"本地模型预热中（首次约 1~2 分钟），先用规则指挥"。玩家看到旧文案只会以为副官坏了，
实际只是冷模型还没载入。预热完成后让位给 runner 自己的结论。

## 5. 顺带修掉：自对局在覆盖玩家的面板状态

诊断时发现 `hud_status.json`（游戏面板读的那份）被**我的自对局训练局**每秒覆写。
真因是导入顺序：`selfplay_match.py` 先 `from runner_ctl import ...`（模块级就把
HUD 目录焊死成 `%APPDATA%\...\adjutant_logs`），**之后**才设隔离环境变量——
隔离写了等于没写。已把 `runner_ctl.hud_dir()` 改成调用时解析，`selfplay_match.py`
在起 runner 前把 `AIRTS_RUNNER_HUD` 指到本局 `state_<tag>/`。已停掉当时那局并确认
文件停止刷新。

## 7. 对后续测量的影响（必须知道）

**从本轮起，自对局的战略层可能是活的。** 第 1~9 轮所有 `--backend off` 的对局，
战略层其实每轮都在 `Connection error`（服务没起）——那些局实际是"纯规则层"在打。
现在模型服务会自己起来，`backend=off` 只关 System 1（Laya），System 2 仍然在跑。
**所以本轮之后的对局数据不能直接和第 1~9 轮比**，要重新建基线。
