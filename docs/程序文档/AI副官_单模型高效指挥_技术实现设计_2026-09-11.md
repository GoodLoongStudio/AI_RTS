# 单模型高效指挥：技术实现设计

日期：2026-09-11。

配套入口：[执行计划与提示词](AI副官_单模型高效指挥_计划与DeepSeek执行提示词_2026-09-11.md)。本文确定关键实现方法，不是已完成的开发报告。只修改文档；以下代码、训练和验收工作交由 DeepSeekV4.1FLASH 执行。

## 1. 技术判断与已核实的问题

可以实现的是：一个本地模型选择具体任务，由游戏同时执行多个小队的任务，覆盖经济与战斗，并响应玩家接管。尚未证明的是：当前 MiniCPM5 在真实输入、游戏 GPU 负载和事件排队下，持续达到快速模式约 1 秒和深度模式 1-3 秒的响应，以及足够好的整局判断。不能把这两类结论混为一谈。

本次只读核查得到以下证据：

- 当前 Ollama `/api/ps` 显示 `minicpm5-adj-16k:latest`，2.5B、Q8_0、上下文窗口 16384，全部模型数据驻留 GPU。显卡为 RTX 3080 Ti 12GB。窗口大小不等于实际输入长度，不能仅凭 16K 判定耗时原因。
- 日志 `C:\Users\Administrator\AppData\Roaming\Godot\app_userdata\Open RTS\adjutant_logs\agent_runner_20260911_230604_2a2012f7.jsonl` 中，抽取时最近 10 个 tick 记录均走 `strategic`，单轮耗时 12.789-13.210 秒，合计约 129.7 秒；全部记录战略输出校验失败、重试耗尽，累计 `sent` 均为 198。它证明这段运行里战略失败持续占用协调循环，没有新增下发；不代表已找到每一个失败 JSON 的具体原因。
- `graph/pydantic_agents.py` 当前战略输出上限为 1280 token，战术为 512，`retries=2`，通过 `run_sync` 和 `future.result` 等待。最大输出设置不是实际输出量，但复杂输出及多次重试确实允许一次调用占用较长时间。
- `graph/interrupts.py` 在没有计划时优先选择战略；失败路径不建立计划。`nodes.py:_on_model_failure` 用状态中的 tick 记录失败时刻；若该 tick 停留在推理开始时，而推理耗时已经超过冷却长度，下一轮可能立即重新尝试。该时间基准问题必须用失败注入验证，不能只把冷却数字调大。
- `graph/runtime.py:_dispatch` 逐条同步提交；`_refresh_observation_clock` 会把已经到期的命令期限延到当前时刻之后。后者不能作为解决慢推理的方法，必须区分结果过期与任务持续时间。
- 已核对 [官方权重](https://huggingface.co/openbmb/MiniCPM5-2B) 与 [配置](https://huggingface.co/openbmb/MiniCPM5-2B/blob/main/config.json)：提供 safetensors，Apache-2.0，`LlamaForCausalLM`。微调及标准工具接入有现实技术路径，但本机训练、导出及收益尚未验证。

这些证据支持先修调用与执行链路，不能支持“换个框架或做 2000 条训练就一定质变”的承诺。

## 2. 核心方案：模型修改小队任务表

2026-09-12 修订：以下按[混合架构纠偏提示词](AI副官_混合架构纠偏提示词_2026-09-12.md)实施。规则中台常驻运行默认/有效策略，智能体负责观测摘要、候选、任务记忆和异步反馈；模型仅低频修改策略和任务。模型关闭或等待时，默认规则独立运营。

```text
Godot：控制权 + 小队成员 + 持续任务 + 执行反馈
  -> 本机观测适配：全局摘要、相关小队、目标表、任务与参数菜单
  -> 规则中台按独立节拍生成基础候选，保留有效任务
  -> 非阻塞收取 MiniCPM5 的短任务修改；无结果时沿用有效策略
  -> 程序解码与统一仲裁：绑定真实对象、原请求快照、代际、策略/任务版本
  -> Godot 权威校验并修改任务表
  -> 各小队执行器持续驱动已有单位行为树
```

关键变化不是把模型叫得更频繁，而是同时消除三个浪费：生成大量协议字段、反复输出未变化任务、等待模型后才执行下一批单位动作。模型仍决定具体战术，不退化为只选一个笼统阶段目标。

200 个单位可以组成约 10-16 个稳定作战小队及独立经济执行者。一次模型结果修改几个小队，其余小队继续已有任务，所以受控单位数不等于本轮输出条数。不存在“只有本轮被重新点名的单位才行动”的限制。

### 2.1 固定四列输出

模型输出使用 JSON，先固定一个轻量结构：

```json
{"u":[["S2","ATK","E3","P1"],["S5","DEF","B1","P0"],["F1","PROD","U1","Q4"]]}
```

每行严格为 `[actor_ref, skill_ref, target_ref, params_ref]`：

| 字段 | 含义 | 示例解释 |
|---|---|---|
| actor_ref | 授权小队、工人组或生产执行者 | S2 是作战小队；F1 是可用生产建筑 |
| skill_ref | 从手册编译的任务模板 | ATK 攻击、DEF 防守、PROD 按目标生产 |
| target_ref | 请求目标表中的合法引用 | E3 可见敌人；B1 基地；U1 合法产品 |
| params_ref | 本轮提供的参数档 | P1 绑定路线、阵型、节奏；Q4 表示本次批准的数量 4 |

以上仅是结构示例，不是给模型的固定答案。S2/E3/P1 等由本轮输入表解释，不能把日志里的旧短编号用于下一次请求。后台日志同时保存可读的完整解码结果。

- PydanticAI 结构层使用对象中的字符串二维数组，约束每行 4 项；程序再按列做类型、能力、目标、参数相容性验证。避免为整个战场构造庞大的动态 JSON Schema，也避免依赖未验证的复杂 tuple schema 支持。
- `{"u":[]}` 表示不修改任务。阶段目标可用可选 `g` 字段引用阶段 ID，不要求每轮重复。快速模式最多 4 行、深度最多 8 行是初始容量，实际 token 与截断率决定能否使用该容量。
- 首先采用短语义 ID，保留 ATK/DEF 等可辨别任务含义，不直接把所有语义压成无说明整数。若实测数组方式比简短对象方式判断更差，改回对象并比较相同场景；不能只追求少 token。
- `P0` 明确定义为维持当前参数；新建任务时采用模板中公开的默认参数。其他参数档写明路线、阵型、节奏、追击范围等。模型选择参数档就是选择这些行为，执行器不能自行把它换成另一个战术。
- 需要新的路线或数量选择时，先生成合法参数档供模型选择；不要求模型计算路径点、猜坐标或填写资源账本。所有表只包含玩家可见信息与明确允许的历史记忆。

### 2.2 程序展开与旧接口接入

引入内部 `DecisionFrame` 和 `TaskPatchBatch`。前者是不可变的请求视图，保存引用表、对局 ID、规则版本、快照、逐对象代际、小队成员版本、任务版本及本地接收期限；后者是模型输出解码后的完整任务修改。

元数据只能取自发起请求时的 `DecisionFrame`，不能在结果到达时换成最新代际。目标权限和有效性仍在权威端按当前状态复核。

旧 `StrategicPlan` 不再是模型必须先生成成功才能下令的前置条件。若已有协调器仍依赖它，程序将默认策略或模型选中的任务模板展开为内部兼容计划；任务 ID、completion、allowed_actions 等来自模板，身份和版本来自程序。不得额外调用战略模型补齐。默认策略可以独立发展、生产和扩张，须标记规则来源；不得把程序补出的任务记作模型选择，或推翻玩家约束与有效模型策略。

任务按小队 / 执行者分别维护版本。相同任务重复返回只确认现状；有变化时只替换相关任务。不能每轮创建一个全新全局计划，导致所有仍有效任务一起重置。

批量入口保留逐项权威校验与回执。冲突、拒绝和部分执行明确反馈，不能把非原子批次伪装成全部成功。模型失效、接口失败和执行失败分别记录。

## 3. 单模型异步调度的具体做法

### 3.1 单写入者与一个推理工作槽

- Python 使用一个 `asyncio` 事件循环。观测读取、回执读取和模型请求为独立异步任务；只有状态归并器可以提交对局状态变化。模型工作任务只读 `DecisionFrame`，返回结果事件，不直接修改共享状态。
- LangGraph 处理已收到事件、构建决策请求及接收结果；不能用等待模型的图执行锁住观测入口。使用 PydanticAI 的异步调用，不再在协调线程上执行 `future.result`。
- 调度唤醒初始为 100ms，观测摘要最多 10Hz；这是调度频率，不是每秒调用模型 10 次。模型空闲且存在需处理事件才发请求。
- 每局一个实际在途推理。结果、异常、退出和取消都走统一完成入口；取消等待不等于 Ollama 已结束。未确认完成时不释放工作槽并不断追加新请求。
- 网络超时、推理总期限、退避使用 `time.monotonic()`。控制代际和游戏任务仍使用权威状态。失败退避从失败完成时开始计算，不使用推理前的旧 tick。

### 3.2 待处理事件与优先级

玩家接管和交回在 Godot 权威端立即生效，Python 只镜像状态。其他待处理事件按小队 / 经济执行者合并，更新内容但保留最早未处理时间。

默认优先级为：基地或授权部队正在遭受重大威胁；任务失效或需要换目标；空闲单位及经济生产更新。使用同级轮转；等待超过 2 秒提升一级，再等待超过 4 秒提升至最高队列的队尾，避免反复出现的新事件永久压住旧事件。预算重新检查和任务反馈持续运行，不依赖排到模型。

普通更新不取消在途推理；返回时按对象校验。控制权改变、对局切换或任务被明确替换时，丢弃相关旧结果。全局模式切换先使旧模式工作失效，再在工作槽实际释放后采用新模式，HUD 显示切换中的真实状态。

### 3.3 两种模式与物理限制

两种模式使用同一个常驻模型、同一 4096 上下文配置，避免切模式就重新加载不同模型。快速模式限制关注范围、候选数量和输出；深度模式提供更完整的相关小队、预算及后续条件。初期都验证关闭长思考，深度模式质量提升需要评测，不能仅凭名称声称更聪明。

约 160 token/s 的历史生成速度意味着 96 个输出 token 仅生成部分就约需 0.6 秒，256 个约 1.6 秒；还要增加输入处理、排队和游戏提交。这只是量级估算，不是当前实测延迟。

单工作槽存在不可消除的等待：若当前请求尚需 0.8 秒，新的紧急请求自身又要 0.8 秒，新事件响应至少约 1.6 秒。LangGraph 的 interrupt 不能自动抢占 GPU 已开始的计算。方案追求通常约 1 秒的快速响应，不承诺所有同时发生的事件都在 1 秒内得到新的模型决定。

因此必须同时采用短输出、事件合并、持续执行和已批准的局部安全行为。超过响应目标如实记为超标；不能用规则动作冒充模型响应，也不能通过丢弃慢样本制造达标结果。若真实工作负载下目标仍不能满足，先缩减请求中的重复信息和输出，再依据测量说明单模型能力差距。

## 4. Godot 中持续执行和编队的实现

### 4.1 权威任务表

每个小队 / 经济执行者保存一条当前任务，至少包括模板、目标、参数、成员、任务版本、控制代际与状态。状态为 pending、running、blocked、completed、failed、cancelled。工作流可包含模板预先定义且已经被模型选择的步骤，不允许执行器临时编造新战略。

玩家接管更新实际对象代际、移出相关 AI 任务；小队剩余成员继续执行。任务表独立于 Python 进程存在，runner 断开时保留有效任务及权限，恢复时从权威端读取，不能拿旧 checkpoint 反向覆盖。

- ATK：沿批准路线接敌，驱动现有攻击行为；目标死亡、丢失和越出追击范围按模板结束或报告，不自行开始另一次战略进攻。
- DEF：到达防区后持续警戒和有限范围交战，不能到达位置就 completed。RET：按批准撤退目标持续脱离、到位再结束。SCT：按探索点和观察条件推进，失败需回报。
- GATHER：驱动现有采集循环。BUILD：预检、资源承诺、实际施工、建筑完成。PROD：模型批准有限数量或补充目标，执行器按队列空位和预算逐项提交，达到数量后完成。
- 建造、生产不通过选中单位猜执行者；实际工人和生产建筑必须进入权限校验。每个生产建筑默认最多一个尚未开始的 AI 排队项，玩家订单优先；已支付支出按游戏原有规则处理。

### 4.2 编队与寻路

已确认项目使用 `NavigationAgent3D` 和 `NavigationServer3D`。保留底层导航，不新建全地图寻路系统，不引入每个单位每帧一次的大范围路径搜索。

1. 模型选择路线意图和参数档。程序用当前导航网格提供直接路线、经友方集结点路线、几何侧翼航路等有限可达候选；报告长度和可见威胁，不声称掌握战争迷雾后的安全情况。
2. 小队计算共享中心路径，将拐点作为阶段航路点。在阶段航路点分配横队、纵队或疏散阵位，经导航投影检查；单位仍用已有移动能力到达阵位。
3. 不每帧移动所有单位的目标点。只有航路点推进、阵型变化、目标显著位移或障碍变化时更新目标；行进中主要通过速度协调和已有避让保持队形。
4. 小队正常基准速度取未脱队成员的最低正常移动速度，领先成员减速；不靠不断反向下移动命令把成员拉回。窄口临时转纵队，通过后恢复模型选定队形。
5. 初始受阻策略：约 2 秒没有路径进展时触发一次局部重寻路；累计约 5 秒仍无进展时标记该成员脱队恢复，主队不继续等它。重新接近队伍后归队；正常到位或被玩家停止不能误判为卡住。阈值集中配置并实测。
6. 小队状态约 5Hz 错峰更新，邻域检查使用空间分桶并限制邻居数量；路径更新设置每帧预算，超过预算顺延。复用现有避让，不叠加第二套全员两两碰撞处理。

这能以较小改动建立可用编队，但不能预先保证所有地图和 300 单位都流畅。验收要同时报告原游戏导航耗时和新增编队耗时，分清已有瓶颈与新增开销。

## 5. 决策手册如何变成可执行能力

手册目录保留；每个任务模板增加对应结构化条目：稳定 ID、所需能力、目标类型、参数定义、执行器、完成条件、可中止条件和候选生成条件。使用普通 JSON / YAML 及已有解析工具，不执行文档中的任意代码。

运行时先按规则与权限排除非法选项，再提供多种合理选择。输入保留小队数量、兵种组成、健康分布、当前任务、关键威胁、生产与预算摘要；不能只给“敌人数量更多”这种单一统计。模型决定选什么、给谁、打谁及采用哪个参数档。

策略库可以定义复用工作流，例如“建成兵营后按已批准数量生产士兵并到指定地点集结”。模型选择此工作流后，程序推进已批准步骤；遇到预算变化、工人被接管、产线不可用等关键条件则反馈并等待新决定。这样的复用减少重新描述与重复推理，同时保留模型的任务选择权。

## 6. 微调的具体起点及边界

先验证短输出决策接口，再收集真实失败样本训练，不把微调放在修复阻塞和执行能力之前。

- 对照当前运行模型与官方 release 权重来源、聊天模板和特殊 token；不能静默换成 Base 或 SFT-only 检查点。
- 本地 QLoRA 技术样机使用 4-bit 基座、LoRA rank 8、序列长度 1024、batch size 1、梯度累积 16、梯度检查点；优先在标准 Llama 的 q/k/v/o 投影上训练。以实测显存决定是否可用，不能由“12GB”直接推断一定能训练。
- 先用约 32 条样本验证加载、训练、合并、GGUF 转换、Ollama 加载和输出一致性，只作工具链测试。之后再构建至少 2000 条正式样本，并按对局 / 场景家族隔离训练与测试。
- 正式训练起始学习率 1e-4，最多先做 2 个 epoch；保留验证集最佳版本。依据错误类型调整数据与训练参数，不通过反复训练测试集提高分数。
- 样本训练“战场事实 + 候选菜单 -> 短任务编码”，附程序验证和实际任务结果。训练必须包含不改令、部分玩家接管、资源不够、多解与不确定敌情，避免只学固定开局。
- 本机真实收益通过独立回放及整局比较确认。2000 条是首批规模，不是能力保证；如果动作选择能力没有改善，不能因为结构输出更漂亮就替换默认模型。

## 7. DeepSeek 必须按此顺序验证

### A. 先证明短决策接口可用

取至少 50 个不同的真实观测或标注回放，覆盖战斗、经济、撤退、侦察和玩家介入。用当前模型比较旧格式和四列格式，报告实际输入 / 输出 token、首次结构合法率、语义合法率及耗时。另检查模型能否同时输出多个不同小队任务，而不只复述一条固定候选。

此阶段隔离模型接口，不把回放结果当成真实游戏端到端结果。若短格式在 96 token 内仍频繁截断或判断更差，先修接口与输入；不得先铺开整局改造再寄希望于微调。

### B. 独立证明游戏执行能力

通过同一权威入口注入固定任务，在真实游戏先让四个小队分别进攻、防守、侦察、撤退，同时运行采集和一个建造 / 生产工作流。验证持续执行、玩家局部接管、伤害、资源和产出。这是执行器测试，明确标记为固定任务，不计作模型效果。

### C. 合并闭环并消除已经观察到的阻塞

接入真实异步模型。注入持续失败和慢响应，确保观测、任务反馈与其他有效任务继续推进；战略失败不得成为下令的前置障碍。用单调时钟验证失败退避，用过期结果验证不得续期。

之后扩大到 100、200 单位，记录短输出覆盖范围、紧急事件响应、排队时间和每个小队实际进展；300 单位作压力测试。只有瓶颈明确后才调整频率、批次和输入容量。

### D. 专用训练与完整验收

在稳定接口上开展工具链样机与正式训练，再完成主计划中的两种模式各 100 个请求、两场各 15 分钟真实对局及全部协作 / 故障验收。A/B/C 是必要的技术验证，不是缩减交付范围或只交演示的理由。

每轮记录“观察到的问题 -> 具体机制 -> 一项主要修改 -> 固定条件对照结果”。未通过前置验证时继续针对该失败迭代，不盲目扩大改造；确有外部阻塞时说明证据和未达目标。最终判断看真实游戏里的发展、协作和模型响应，不能只看框架名字、测试数量或原始生成速度。

## 8. 全网案例核验后的借鉴决策（2026-09-11）

本节是外部实现核验结果，不把论文摘要、演示视频或一次胜负当作已验证性能。下列项目按“公开代码 / 论文实际写明的机制”区分可借鉴部分与不可照搬部分。

### 8.1 SwarmBrain：慢战略与快反射必须分层

- 论文 `SwarmBrain: Embodied agent for real-time strategy game StarCraft II via large language models` 明确把 LLM 的 Overmind Intelligence Matrix 用于宏观资源、扩张和多路进攻，把 Swarm ReflexNet 做成条件—响应状态机处理基础战术；原因是 LLM 推理延迟不适合快节奏操作（论文第 3 节）。
- 公开仓库 `ramsayxiaoshao/SwarmBrain` 的 README 进一步说明：早期先生成约 20 条命令以覆盖首次推理等待；仓库实现与论文并不完全一致，而且明确声明 Tactical Retrospect / Self-verification 更新模块未随代码发布，面对更难对手会受 LLM 能力限制。
- 本项目借鉴：单一 MiniCPM5-2B 只做低频、短输出的任务修改；行军、避障、正常自卫、队形恢复和已批准撤退条件由本地状态机 / 行为树立即执行；模型慢或失败时已有任务继续运行。不得把 SwarmBrain 的双模块名称直接复制成第二个战略模型，也不得把其对电脑玩家的胜负宣称为本项目能力证据。

### 8.2 Vimy：把模型意图编译成可验证规则

- Vimy 的公开设计明确写出“LLM never directly controls the game”：模型输出攻击性、经济、兵种构成、进攻时机等 doctrine 权重，再由模板化条件编译为规则；数值经过边界约束和验证，同一状态下规则可确定地触发。LLM 在 goroutine 中异步生成 doctrine，游戏使用种子规则立即运行。
- 本项目借鉴：保留模型选择战术方案和参数的权力，但将方案编译为版本化、可校验的 `DirectiveBatch` / 工作流参数；权威端只执行通过权限、能力、预算、视野、目标和代际检查的结果。模型不可直接逐帧控制单位，也不能返回任意脚本。
- Vimy 是 OpenRA 的个人项目，不是经过同行评审的 MiniCPM / Godot 证据；它的权重 doctrine 不能替代本项目的多小队任务编码和执行回执。

### 8.3 OpenRA-RL：异步接口与观测性比“让模型每帧下令”更重要

- OpenRA-RL 的公开架构是约 25 Hz 的 C# 引擎、gRPC 桥和 Python wrapper；通过有界 `DropOldest` 通道容忍 40 ms 脚本 AI 与约 2 s LLM 并存，并提供 50 个 MCP 动作、回放和逐局记录。作者报告的 Qwen3 32B 基线在 5 局中经济分数约 0.58–0.80、战斗为 0.0，并明确称其是诚实基线而非能力证明。
- 本项目借鉴：模型请求使用单一在途限制、有界队列、旧普通快照可丢弃、紧急事件优先；记录排队、推理、校验、权威提交和实际生效时间，保存逐请求观测—结果—回执—回放关联。不得把 50 个细粒度工具全部暴露给 2B 模型；首期保持小队 / 方案级紧凑动作。
- OpenRA-RL 是 2026 年社区平台，技术文章不是本项目 Godot 端到端验收；其 2 s 推理容忍机制不能被误写成一秒响应达标。

### 8.4 TextStarCraft / LLM-PySC2：压缩观测、显式动作空间和指标

- TextStarCraft II（NeurIPS 2024）提供 Protoss-vs-Zerg 文本环境、动作抽取和 L1/L2 摘要；论文提出 Chain of Summarization 以减少长上下文负担，并公开 `action_info.py`、`action_extractor.py`、状态到文本和文本到动作适配器。其仓库列出 PBR、RUR、APU、TR 等宏观指标。
- LLM-PySC2 公开仓库将 PySC2 包成 LLM 环境，支持文本 / 图像观测、可配置 UnitTeam、动作空间、动作识别器、多智能体实验和数据记录；README 明确 MainAgent 负责环境调度，SubAgent 才查询 LLM。
- 本项目借鉴：把观测分成稳定 ID、变化摘要、候选动作、反馈和可见敌情，使用可测 tokenizer 的短摘要；模型输出只包含版本、squad / executor、方案、目标和必要参数，由动作适配器转换；把宏观发展、任务覆盖、实际执行进展和延迟分开统计。不能直接照搬 TextStarCraft 的单 PvZ、文本回合设定，也不能把 LLM-PySC2 的多个 SubAgent 变成多个指挥模型。

### 8.5 Voyager：可检索、可验证的技能 / 策略库

- Voyager 公开代码 `voyager/agents/skill.py` 使用向量库按任务检索技能代码，并把代码与描述持久化；`voyager/agents/action.py` 将上一轮代码、执行错误、事件和当前观测一并提供给模型。README 说明其依靠 GPT-4、Minecraft 控制原语和迭代环境反馈，不是实时 RTS。
- 本项目借鉴：决策地图和已验证工作流应有稳定 ID、前置条件、参数范围、完成 / 退出条件、失败原因和版本；根据当前候选与失败反馈检索少量相关条目，成功执行后才写入可复用案例。禁止把模型未经程序验证的答案写进训练集或运行时技能库，禁止把 JavaScript 技能代码注入 Godot 权威端。

### 8.6 0 A.D. Petra：任务生命周期与单位归属的成熟参照

- Petra 的 `attackManager.js` 维护不同类型的 upcoming / started attack 计划并处理盟友请求、完成和清理；`attackPlan.js` 的注释和代码覆盖目标选择、集结点、路径可达性、运输需求、单位组成、生产队列和状态推进。
- 本项目借鉴：每个 AI 小队工作流必须有稳定归属、目标、集结 / 路径意图、准备、执行、完成、失败、退出和补员状态；生产 / 建造需求只能进入统一权威队列；目标死亡、路径失败和不可达必须产生可追踪回执。模型只选择候选计划和可调参数，不能绕过这些生命周期。

### 8.7 反例与证据等级

- AlphaStar、DI-star 等强 RTS 结果主要依赖大规模模仿学习 / 强化学习和专用神经网络，公开资料不能转化成“给 MiniCPM 加提示词就能达到同等微操”。它们可作为状态表示、动作分解和离线回放评测的研究背景，不能作为本方案的直接实现来源。
- SIMA 使用视觉输入和键鼠输出，目标是跨 3D 游戏的短技能；它没有证明多小队 RTS 的经济与战术闭环，因此只可参考“短技能数据与人类指令对齐”，不应替换本项目的权威 API。
- `When Agents Rule` 是小规模、非同行评审的浏览器 RTS harness；其 compact JSON、独立 `plan` 工具、逐调用反馈和 JSONL transcript 对接口 / 回放设计有启发，但 README 自己警告单局不能证明模型能力，不得引用其胜负作为验收。

### 8.8 对本项目方案的强制改动

1. 保留“一个决策模型”，但采用 **低频模型决策 + 高频确定性执行器**；删除任何让模型每帧直接控制单位或通过第二 LLM 复核来补救的设计。
2. 将 `DirectiveBatch` 升级为可编译、可回执、可过期的任务修改；候选方案、规则约束、技能库和动作适配器均有版本号。
3. 将队列实现为有界、可取消、单一在途推理：普通观测可合并 / 丢弃，紧急事件抢占；旧结果只能被拒绝，不能续期或刷新代际。
4. 增加技能 / 决策案例库的检索命中、程序合法性、实际完成和失败原因字段；只有真实执行成功且可复现的案例才允许进入库或训练集。
5. 验收增加外部案例对应项：模型延迟与队列分解、任务生命周期、实际状态变化、部分玩家接管、经济指标、回放可重放、失败降级。文档中的性能数字继续作为目标，不能改写成外部项目已经替本项目证明的结果。

### 8.9 HIMA / Society of Mind：层级职责可借鉴，模型数量不可照搬

- 可借鉴的是“高层目标、专长执行器、独立评测”的职责边界，以及把不同对局 / 兵种 / 难度隔离成可比较的测试集；不能把三模型层级、外部 FastAPI 模型服务或其胜率直接搬进本项目，因为本项目明确要求一个本地 MiniCPM5-2B 和 Godot 权威端。
- AI_RTS 的折中实现：同一个模型输出小队级任务修改；行为树、导航、生产队列和状态机作为确定性专长执行器；快速 / 深度只是同一模型的输入范围与输出预算，不是额外模型。

### 8.10 AlphaStar / 模块化 SC2 AI：说明“动作分解”有依据，但不属于 LLM 方案

- AlphaStar 及公开的模块化 SC2 研究把观测、战略、战术 / 动作和价值估计拆成模块，并用大规模人类回放与强化学习训练；代码、训练资源和硬件规模与本项目不同。
- 本项目只吸收“按时间尺度和动作粒度分解、分别测量模块”的工程原则，不借用其网络结构、训练规模或胜率作为 MiniCPM 证据；所有可执行结果仍须经过本地权威校验和实际回执。
