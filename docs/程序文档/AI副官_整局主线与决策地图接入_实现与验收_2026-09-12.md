## 3. 关键设计（为什么这么切）

### 3.1 只有一条权威链、只有一份实现

- 决策地图**不产出命令**：它只产出「可选路线 + 前置条件」与「分支偏好」
  （`order_override` / `produce_first` / `expand_probe`），实际命令仍由
  `rules_fallback` / `behavior_tree` / 模型候选汇入同一套仲裁与下发（`arbitrate → dispatch`）。
- 里程碑的"完成"**只认权威证据**：观测事实（`op=tactical`）+ 权威回执（Accepted/Completed）。
  生成 plan、生成 task、写日志都不算（这正是纠偏点名的病根）。
- 观测解析与"在途状态"口径收敛为**全仓唯一实现**：
  `observation_view.normalized_units`（含 `movement`）与 `graph.state.INTENT_LIVE_STATES`
  被 `rules_fallback` / `campaign` 直接引用，不再手抄（见 §6）。

### 3.2 `campaign_state` 字段（都在 `graph/campaign.py::default_campaign`）

```
mainline_id / mainline_version   这一局按哪张主线跑 + 定义版本
phase                            摸底 → 立足 → 扩张 → 施压 → 收束（+ phase_history）
milestones{M01..M07}             status/attempts/done_tick/frontier_since/blocked_reason/
                                 rejections/last_evidence（前置条件与成功证据在 MILESTONES 表）
tracks{economy,build,scout,military}  status / current{动作,执行者}/ suspended_objects
next_frontier + frontier_kind    当前最值得推进的**一个**节点
blocked_milestones               已被阻塞的节点（完成即移出）
expansion_candidates / expansion_probe   分基地候选落点 / 扩张前探点
interrupt_stack                  紧急事件栈（含 resume 恢复点）
suspended_objects                玩家局部接管的对象（只挂起，不清空主线）
decision_available / decision_locked / decision_context  决策地图检索结果
transitions                     有界的变迁历史（阶段/前沿/里程碑/分支）
```

里程碑（默认主线）：

| id | 名称 | 阶段 | 权威成功证据 |
|---|---|---|---|
| M01 | 工人开采 | 摸底 | 采集命令被权威接受 + 观测到工人 |
| M02 | 产能建筑 | 立足 | 观测到**已完工**的兵营/车厂/机场 |
| M03 | 首支作战队 | 立足 | 观测到作战单位达到阈值 |
| M04 | 扩张选址 | 扩张 | 程序算出合法的分基地落点（视野内、离主基地 ≥30m） |
| M05 | 分基地/分矿 | 扩张 | 观测到**第二座已完工**指挥中心 |
| M06 | 持续施压 | 施压 | 出击被接受 **且** 敌方出现死亡/掉血 |
| M07 | 收束 | 收束 | 已侦察到的敌方单位全部确认死亡或对局结算 |

### 3.3 图拓扑（LangGraph 与内置执行器同构）

```
ingest_observation → update_campaign_state → classify_event
   ├─ player_interrupt → reconcile_plan
   ├─ strategic / tactical / emergency → …
   └─ wait
 → arbitrate_intent → dispatch_to_godot → observe_receipt → advance_milestones → persist_checkpoint
```

- `update_campaign_state` 在路由与微操**之前**：阶梯顺序、里程碑证据、中断栈都由它决定；
- `advance_milestones` 在回执结算**之后**：本轮下发产生的回执证据当轮生效，
  已处理完的中断同轮弹出并恢复原主线与四条 track；
- 两个节点调用同一实现且**按 tick 幂等**，重复调用不会重复计数。

### 3.4 规则中台如何"沿主线"跑（4 个由前沿驱动的开关）

| 开关 | 取值 | 作用 |
|---|---|---|
| `build_order` | 前沿节点声明 | 建造优先级：立足=兵营→车厂→机场；扩张=指挥中心优先；施压=防御塔优先 |
| `produce_first` | M03/M06/M07 | **先补兵再扩建**（否则"永远还有下一座建筑"会把生产级饿死，见 §6.2） |
| `allow_attack` | 施压/收束 | 规则阶梯主动出击只在施压之后（手册：集结→前压→进攻，禁止添油） |
| `expand_probe` | 前沿=M04 且无候选 | 派**机动**单位前探远端矿点方向（SCT-01/SCT-02），补上"有矿点→有合法落点"之间缺的一环 |

### 3.5 模型如何参与（低频、有界、可校验）

模型输出仍是四列 `{"u":[[执行者,任务,目标,参数]], "g":"D3"}`：

- `u` 是对 baseline 候选表的**稀疏 patch**（原有语义不变）；
- `g` 是**主线分支选择**：只能取上下文「可选路线」里的 ref（如 `D3`/`BLD-01`），
  程序校验前置条件后才采纳；不满足/未知/留空 → **沿用当前主线**，不清空任何东西；
- 提示词每轮带上「主线」与「可选路线」两行（含前置条件），模型不需要重新发明整局计划。

## 6. 本轮修掉的七个**结构性**根因（不是当场打补丁）

> 6.1–6.4 是"同一类问题换皮复发"（口径分叉 / 判据缺维度），6.5–6.6 是**真机跑出来的致命缺陷**
> （一个让 runner 自杀、一个让 runner 静默退出）。
> 每一个都配了类级守门用例（§5），并已在代码注释里写明不变式。

### 6.1 观测解析存在第二份副本（`movement` 只在其中一份）

`rules_fallback._normalized_units` 曾是 `observation_view.normalized_units` 的**手抄副本**，
新增 `movement` 只加在后者 → 扩张前探挑中**不会动的炮塔**，`move` 被权威端连续 `Rejected`（6 条），
扩张选址被误判成"命令连续失败"而阻塞。
**治本**：副本改为转调唯一实现，并在 `batch_from_rules` 里也删掉第三份手写解析；
补"两份视图逐字段一致"的守门用例。

### 6.2 生产级被"永远还有下一座建筑"饿死（整局只出 1 个兵）

阶梯是"逐级 return"结构：建造序列（兵营→车厂→机场→两座塔→第二座基地）**永远**还有下一项，
于是生产级一次都轮不到。真机 5 分钟实测：建筑全建完、**作战单位 0 个**、M03 卡 12000 tick 被超时阻塞。
**治本**：由前沿节点决定"先补兵还是先扩建"（M03/M06/M07 → `produce_first`），
并让建造线在前沿切换后自然恢复（`build_order` 每 tick 重算）。修后 M03 从 15045 tick 提前到 **5031**。

### 6.3 终结态的生产意图永久占住设施（整局只出 1 个兵）

`producing_units` 只看 `action == produce`，而 `active_intents` 是**追加式历史**（永不清理）：
第一次生产结束后那条 `completed` 意图仍在表里 → 该设施**永久**被判成"正在生产"。
**治本**：按 `graph.state.INTENT_LIVE_STATES`（唯一事实来源）过滤存活状态；
同时把这个状态元组从三处手抄收敛成一处引用。

### 6.4 几何类拒绝被算进"里程碑重试预算"

`_note_rejections` 原先统计**所有**被拒命令。真机 `--model on` 实测：6 条
`build/Rejected`（落点那一刻不在己方视野内 = 几何类）就把 M05「分基地/分矿」整条判成
blocked。按本仓库既有纪律，几何类拒绝是"换个点就行"（由 `RejectionLedger` 按点拉黑处理），
不该升级成"这条主线走不通"。
**治本**：里程碑重试预算只统计**内容类**拒绝（`placement.classify_rejection` ∈
contract/capability）；几何类仍由落点账本自愈。

### 6.5 `_decide()` 参数撞名 → 整个 tick 抛异常 → runner 自杀

```python
_decide(state, "campaign_interrupt_resolved", **item)   # item 自带 "kind"
# TypeError: _decide() got multiple values for argument 'kind'
```
异常发生在**调用时**（函数体来不及执行），所以无法在 `_decide` 内部兜住；
连续 20 轮异常后 runner 按 `--bad-tick-limit` 退出。
**治本**：把 `kind` 改成**位置专用参数**（`def _decide(state, kind, /, **payload)`，
`AdjutantGraphState.decide` 同步），同类数据从"致命错误"退化为"无害字段"；
调用点同时把中断类型改名成 `interrupt_kind` 保持日志可读。
**验收侧同步加固**：`campaign_accept.py` 现在会检查 `runner.out` 里有没有 `fatal`
（`runner_alive_at_end`），避免"runner 已死、采样还在跑"被误读成"发展慢"。

### 6.6 串台响应被当成"对局结束" → runner 静默退出

`match_active(port)` 原先只看 `bool(status["match"])`。DCS 是"裸 TCP + 一行 JSON"，
同机并发查询时可能收到**串台载荷**（实测收到战术视图那种没有 `match` 键的响应）：
runner 连续 6 次判 False → 以 `no_active_match` **正常退出**（不是报错，看着像"对局结束了"），
而同一对局几十秒后仍然 `match=True`。验收脚本因此在两轮里只看到"M01/M02 完成"，
**差点被当成规则退化**。
**治本**：把"异常响应"与"事实"分开 —— 只有"确实像 status 响应（含 `players`/`is_server`
等 status 独有字段）且没有 `match`"才判对局结束；串台/非 dict 载荷一律保持常驻，下一轮再判。
配套：验收脚本新增 `runner_alive_at_end` / `runner_tick_errors` / `runner_fatal` 完整性字段。

### 6.7 事件类型 ≠ 紧急事件（附带说明）

`campaign.EMERGENCY_KINDS` 取手册 §3 的五类（基地受袭/发现敌军/编队损失/路径失败/关键单位阵亡），
比 `interrupts.EMERGENCY_EVENT_KINDS`（只两类）更宽 —— 这是刻意的：
手册把"路径失败"也列为局部紧急事件，压栈后**只暂停受影响对象**。
真机上正是 `path_failed` 这类事件触发了中断栈，从而暴露了 §6.5 的崩溃。
