# 阶段 6 前置：固定地图 / 固定种子对局入口 + 逐局结果仪表（2026-09-27）

对应提示词 `AI副官_建筑无工人建造与矿场散矿计划核查修复提示词_2026-09-27.md`
第六节「逐局报告」与第七节完成判据。阶段 0 核查报告把**「今天没有固定种子对局入口」**
记为硬断点：没有可重复的采集入口，§6 要求的「5 个筛选种子 + 10 局回归」就只能是
一堆互不可比的样本，任何"已实施"的结论都站不住。本轮把这个入口补上，并把它自己
能不能被证明先证明一遍。

## 一、这一轮真正改了什么（按链路层次）

### 1. 权威进程：让 `match_seed` 不是安慰剂

- `source/net/NetSession.gd`
  - `var match_seed := 0`（0 = 不干预，行为与加字段之前逐字一致）。
  - `_consume_cmdline_fixed_match_args()`：把 `--map/--seed` 的解析收进**唯一**实现，
    由 `try_start_from_cmdline()`（专用服）与 `_launch_match()`（唯一开局收敛点）
    共同调用。原来那段解析被埋在 `--server` 分支里，**本机 listen server 跑自对局时
    根本不会执行**——那样的 `--seed` 就是纯装饰。
  - `_apply_match_seed()`：`match_seed > 0` 时调用 Godot 全局 `seed()`。
  - `_launch_match()` 的开局日志现在同时打印**地图与种子**，报告的凭据来自权威端自己
    说了什么，而不是调用方传了什么。

### 2. 拒绝假凭据的两条硬规则

- **非法地图直接退出**，不再"回退默认地图继续跑"。旧 `validated_map_path()` 的静默
  兜底对普通玩家是对的，对回归是致命的：跑 10 局会得到 10 行写着 A 图、实际是 B 图
  的证据。实测（headless 专用服）：
  - `--map res://source/match/maps/Bogus.tscn` → `ERROR: --map 非法或未登记` +
    `固定地图回归拒绝在替代地图上开局，进程退出（不产出假凭据）`，**进程退出码 1**。
  - `--map …/PlainAndSimple.tscn` → 正常启动，无错误。
- **`op=start` 的 `map/seed` 只在服务器进程接受**。客户端设种子什么也不会改变
  （全局 RNG 只在权威模拟一侧决定结果），静默接受等于发假凭据，所以返回
  `FixedMatchOnServerOnly` 明确拒绝。

### 3. 四类"§6 要报但一个都没埋"的仪表（`source/net/DebugControlServer.gd`）

| 指标 | 埋点位置 | 说明 |
| --- | --- | --- |
| Worker 施工占用累计秒数 | `_fast_diff_units` 按 10Hz 采样累加 `_construction_worker_seconds`，`op=tactical` header 导出 | 本次改造的**核心反证指标**，目标 0 |
| 施工中 Worker 数 | 每个单位实体新增 `constructing`（action 脚本名以 `Constructing.gd` 结尾） | 与上一行互为交叉验证 |
| 矿场放置 / 首次接管 / 首次交付 | 10Hz 差分发 `construction_started` / `refinery_takeover` / `refinery_delivery`；实体带 `refinery` 统计 | "完工"与"交付"必须是两个不同事实 |
| 矿点存量与再生状态 | resource 实体带 `ore_remaining` / `ore_capacity` / `ore_depleted` / `regen_remaining_ms` | 阶段 0 时只能看到"有没有矿" |

### 4. 采集与分析层

- `selfplay_match.py`：`--map/--seed` **同时传给专用服与客户端**（服务器才是权威那侧）；
  `--refinery-at <秒>` 到点发一条**不带坐标**的 `op=build OreRefinery`，让权威端用
  既有 `auto=resource` 模式在远端矿堆附近自己找落点；`_economy()` 把三张经济账
  透传进 `detail_log`；结果 JSON 记录 `map/seed/refinery_receipt`。
- **`op=tactical` 显式 `limit=4096`**。游戏侧实体窗口默认 **128 条**，200×200 图上
  矿点+单位会超窗口，默认口径下的"全图矿量"只是前 128 个实体的部分和——
  把**截断当耗尽**是这次最容易无意中造出假证据的一条路。`truncated` 现在原样进样本，
  分析层据此判定这一局的矿量账可不可信。
- `match_metrics.py`：`BUILDING_TYPES` 补登记 `ore_refinery`（漏登记会让分析层完全
  看不见矿场，"没有矿场"与"没统计到矿场"就分不开）；新增 `_economy_metrics()`，
  **缺项一律 None，不补 0**。
- 新增 `run_fixed_seed_regression.py`：`--map --seeds --seconds --backend --tag`，
  逐局跑 + 逐局分析，产出 `sweep_<tag>.json` 与 §6 的 Markdown 表；
  结果目录从 `selfplay_match.OUT` **导入**而不是硬编码副本（路径漂移的表征是
  "跑完 10 局、表里 10 行 no result json"，看起来像回归失败，其实是找错地方）。

## 二、实测证据（不是计划，是跑出来的）

### 1. 种子机制是真的（探针实测，随后删除探针）

`seed(12345)` 后连续 8 次 `randf()`，再次 `seed(12345)` 重放：

```
PROBE repeat_equal=true different_seed_equal=false
PROBE first[0]=0.30768033862114 other[0]=0.93421822786331
```

同种子逐位复现、不同种子给出不同序列 ⇒ `_apply_match_seed()` 灌的是游戏里
`randf()/randi()` 真正读取的那个 RNG（单位出生散布、增强卡抽取、随机挑选目标）。

### 2. 一局真实对局里，权威端自己承认了图与种子

`tmp_logs/dcs/selfplay_server.out`（固定图 `PlainAndSimple` + `--seed 424242`）：

```
[FIXEDSEED] 全局 RNG 种子已设为 424242
联机: 开局，人类 1，槽位 [0]，配置 [1, 2, 0, 0]，地图 res://source/match/maps/PlainAndSimple.tscn 种子 424242
```

### 3. §6 逐局表的第一行（真实对局，150 秒，`--backend off`）

| 局标 | 地图 | 种子 | 权威结算 | Worker 施工占用(s) | 施工中 Worker 峰值 | 首座兵营建成(s) | 矿场放置 | 矿点数 | 开局全图矿量 | 终局全图矿量 | 耗尽矿点数 | 窗口截断 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| fs_probe_424242 | PlainAndSimple | 424242 | timeout | **0.0** | **0** | **48.6** | None | 16 | 361928 | 340916 | 1 | 否 |

- `Worker 施工占用 = 0.0` 且 `施工中 Worker 峰值 = 0`，同时**兵营在 48.6 秒真的完工了**
  （判据取实体首次以 hp>0 出现在观测里，不是下单时刻、不是 `Accepted` 回执）。
  这就是需求①「建筑施工默认不占用 Worker」在真实对局里的直接证据，
  不再只有冒烟测试那一条。
- 全图矿量在 210 秒里从 361928 掉到 340916（−21012），16 个矿点里有 1 个真的见底。
  `truncated=否` 说明这是**全图口径**，不是窗口部分和。
- 矿场三列是 `None`：这一局纯规则副官在 150 秒内没走到 M08。`None` 的含义是
  "这局没采到"，**不是**"矿场功能坏了"——后者由阶段 2/3 的专项证据支撑。

### 4. 回归没有变坏

- `dotnet build OpenRTS.csproj`：0 警告 0 错误。
- C# 核心测试：`Construction service 10/0`、`Structure placement 6/0`（阶段 1 的两块
  全绿）。总失败数 **19**，与本轮开工前同一批：`Production 3` + `Balance config 16`。
  逐条核对失败名（Tank 成本 A×500 基线、Resource B 采集时间、skills 校验若干、
  生产队列 3 项），**没有一条涉及本轮新增的 `constructionProgressSource` /
  `oreRefinery` / `regeneration` 字段**——是并行改动的口径漂移，不属于本任务，
  没有去"顺手改绿"。
  其中 `MissingSkillsCollectionRejectsWholeCatalog` 抛的是
  `ArgumentOutOfRangeException: length ('-1')`，看着像校验代码自身的缺陷，已记下待
  该模块的作者处理，不在这里代改。
- 三个专项冒烟测试在仪表改造后重跑，全部 0 失败：
  `AutomaticConstruction 0` / `OreRefinery 0`（日志照旧给出真实的
  `收到交付 worker=Unit_3 amount=400（累计 1 次 / 400 矿）`，两座矿场各 2/2 容量、
  互不抢工人）/ `OreRegeneration 0`。
- headless 冷启动无 `Parse Error` / `SCRIPT ERROR`，确认两个 autoload 脚本改动可用。

2. **真实对局里的矿场闭环**：已加 `--refinery-at`，第一局带脚本矿场的实测结果

3. **`balance_first/last/grew` 三列**：本轮才发现旧 `peak_balance` 读的是
   `op=match_forces` 里**从来不存在的** `balance` 字段，所以恒为 0——"资源增长"这条
   判据此前无法从逐局表证明。已改从 `op=tactical` header 的 `resources` 取
   `balance_a`，并用旧结果验证了缺失时确实返回 `None` 而不是 0。
   **注意**：改完之后必须重新跑局才有数，旧 result 里没有这个字段。
4. **10Hz 事件流（`construction_started` / `refinery_takeover` / `refinery_delivery`）
   目前没有被分析层消费**：`fast_scan.py` 会把它们收进 runner 的事件缓冲并写进
   `runner.out`，但 `match_metrics` 只解析 `receipt`/`movement_gate` 两类行。
   逐局表现在用 1 秒采样口径（首次时刻精度 ±1s）。要更准的时刻需要再写一段
   `runner.out` 事件解析，本轮没做，也没有声称做了。
5. **逐帧可复现 ≠ 固定种子**。种子管住的是游戏侧随机量；帧调度与网络时序带来的
   非确定不在其覆盖范围。§6 的表头读表须知里已明确写了这句限定，避免"固定种子"
   被读成"整局逐位复现"。
6. **§8.1 / §8.4 的散矿视觉验收**（散矿素材、富矿/采空/再生三态截图）仍未取证。
   本轮没有截取画面，也没有用"资源文件在"代替"眼睛看到"。
