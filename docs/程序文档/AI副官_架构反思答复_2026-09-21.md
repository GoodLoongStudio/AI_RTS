# AI 副官架构反思报告答复

> 针对《AI副官_架构反思与问题清单_2026-09-21.md》的独立评估。
> 结论按当前代码、训练记录和四局实测整理；没有把未跑过的实验写成已验证结果。

## 先给结论

当前失败的首要原因不是 MiniCPM5-2B 或 Laya 的容量不够，而是控制权、动作粒度和训练标签都放错了位置：

1. 规则中台每 tick 继续给每个单位生成 baseline，模型只能稀疏覆盖；模型即使选对，也可能在下一轮被规则重新改写。
2. Laya 学到的是“最终下发链”，其中 95% 是 GAT/PROD，且 ATTACK 为 0 条。因此 84.7% 是多数类模仿分数，不是战术能力。
3. 四列接口把一个小队动作拆成单行、逐单位、逐次审理，无法表达“这六个单位作为一个班一起推进并集火”。
4. 微操行为树完全不读取模型的战术偏好，模型没有机会学习集火、风筝、换靶和撤退时机。
5. 这四局还暴露了两个比模型更优先的问题：副官命令的托管权被双 runner 收回，以及安全闸门用“已进接触圈的单位”逐个计兵力。两者修复后才真正测到了战斗链。
6. 修复后仍然 0 建筑损伤，已经更像“战斗 doctrine 和兵种/发展配置不成立”，不是继续提高 Laya 训练准确率能解决的问题。

因此不建议推翻为“模型每帧控制单位”，也不建议把规则层删掉。应改成：

```text
2B：异步战役计划和班组编组（秒级到十几秒级，允许过期）
Laya：5~10 Hz 的班组/局部交战选择（集火、姿态、风筝、撤退、换靶）
规则与行为树：硬安全、路径、射程、CD、动画和每帧执行；没有有效模型订单时才提供基线
```

最重要的改变是“订单租约”：模型或战略层下达的小队订单在 TTL 内拥有战术优先权，规则层只检查安全和可执行性，不得每 tick 把它改回采集、散点推进或单兵撤退。

## 对第 8 节问题的逐项回答

### 1. 三层分工是不是本末倒置

是。问题不是三层这个数量，而是权威顺序：现在规则层既负责生产 baseline，又负责班组选择，还通过闸门拥有最后的战术否决；Laya 在做规则已经会做的多数类选择；2B 只在 30 秒边界上改变一个分支位。真正有信息价值的选择没有稳定的控制通道。

规则层不应收缩成“只剩几条 if”。它应保留三类权威：

- 不变量：权限、合法目标、路径存在、地图边界、友军/敌军关系、技能 CD、资源扣除、单位不能同时执行冲突动作。
- 执行器：寻路、射程保持、开火、动画、队形跟随、到达确认和受击后的即时求生。
- 无订单时的基线：经济、生产、守家等保底行为。

它不应继续拥有“有有效班组订单时，每 tick 重选班组目标”的权力。将“安全拒绝”和“战术替换”分开：前者可以拒绝，后者只能在订单过期、目标消失或明确触发紧急事件时发生。

### 2. Laya 最佳粒度是什么

不是全军粗选，也不是每个单位分别问一次，而是“局部交战班组批量问答”。建议一个班组 4~12 个同质或相近单位，问题控制在 8~16 个：

- 交战姿态：推进、保持射程、风筝、集火、撤退、守点；
- 目标类别和目标实例：生产建筑、炮塔、指挥中心、敌方高威胁单位；
- 交战阈值：优势不足时保持/后撤，优势成立时压上；
- 队形和支援：跟随、集结、分两组、等待增援；
- 目标切换和集火上限。

Laya 不要输出每帧坐标。它选择的是行为模式和目标，行为树负责把模式变成每帧移动与开火。这正是 47~63ms 的 p50 延迟可以承担的工作；是否能稳定 10Hz，仍需看 p95、CPU/GPU 并发和最坏情况下的队列长度，不能只看 p50。

如果要对位 Jev 式微操，训练样本必须以“局部交战片段”为单位，而不是全军每 tick 的最终下发链。每条样本至少包含：交战前状态、候选动作、选中的姿态/目标、5/10/20 秒后的伤害、击杀、损失、阵型散度、是否成功脱离。X 页面当前无法抓取（返回 403），所以这里不对视频内容作未经核实的具体断言；上述设计针对报告描述的集火、风筝、撤退类微操能力。

### 3. 2B 应放在哪里，四列接口要不要废掉

2B 适合生成多个班组的组合计划、解释原因和处理不确定的长期取舍。它不适合放进 1~5 秒的同步关键路径，除非实测最坏延迟、超时和积压都满足要求。建议：

- 战役计划仍保留 20~40 秒的低频版本；
- 发生基地受袭、侦察发现重兵、主攻目标死亡、生产链断裂等事件时，异步提前重规划；
- 输出 3~8 个班组订单，允许带优先级、集合点、目标类别、目标优先级、姿态、TTL 和取消条件；
- 计划生成期间继续执行上一个有效订单，绝不阻塞实时战斗。

四列接口不必立即删除，但应降级为“内部落地格式”，不能再作为模型的主要表达能力。建议增加一个原子的小队订单接口，例如：

```json
{"orders":[
  {"squad":"main","units":["U1","U2"],"mode":"attack_move",
   "rally":[62,41],"target_policy":"production_then_turret",
   "stance":"aggressive","ttl":80}
]}
```

系统再把小队订单展开成四列行，并一次性校验。这样既保留现有命令协议，也不再让模型承担逐单位填表的吞吐成本。

### 4. 训练目标应该是什么

当前“模仿实际下发链”不能作为主目标，因为它把规则的重复输出重新学了一遍。建议分三阶段：

1. **交付前监督学习**：使用经过筛选的强教师轨迹。教师可以是修好的规则基线、人工操作片段、2B 审核后的班组计划，或者明确赢下来的局部交战。对 GAT/PROD 做下采样，对 ATTACK/AMOV/RET/目标选择做过采样；按比赛局或地图种子切分 train/val，不能随机切同一局的相邻帧。
2. **结果加权**：每个订单挂接 5/10/20 秒结果，使用伤害、击杀、己方损失、建筑损伤、阵型保持和任务完成度组成短期回报。先做胜局/高回报样本加权和失败样本降权，不要在样本还不足时直接上离线 RL。
3. **数据足够后再做偏好/离线 RL**：对同一状态下“赢得更多、损失更少、完成目标更快”的两个候选动作做 pairwise preference。模型必须看到真实候选差异和结果，不能用自己的预测给自己当教师。

branch 标签可以保留，但它只代表战役主线选择，不能替代战术标签。`mainline_node` 修复后能保证标签可采纳，却不代表这个节点一定是好决策；它还需要结果回报验证。

### 5. 规则层应该保留 baseline 吗

保留，但变成“无有效订单时的地板”，并加入订单仲裁器：

```text
紧急安全事件 > 有效的模型班组订单 > 战略计划展开的订单 > 规则 baseline
```

订单必须有 owner、generation、TTL、取消条件和执行状态。规则层每 tick 可以修正路径和安全参数，但不能把一个仍在 TTL 内的 attack-move 订单改成另一个目标。所有被拒绝的订单必须记录“安全拒绝”还是“策略替换”，否则无法知道模型是否真的失效。

### 6. 微操是否需要模型

需要，但模型只负责规则明显不擅长的离散选择。射程、碰撞、寻路、开火 CD、动画状态和“当前这一帧如何移动”继续由确定性执行器完成。模型适合负责：

- 多个敌人之间的集火与换靶；
- 远程单位保持射程还是追击；
- 看到援军时压上还是等待；
- 受伤单位是否退出，其他单位是否继续压制；
- 目标建筑的优先级。

这比把三年积累的行为树全部换成神经网络可靠，也能让 Laya 对战局产生可测的增量。用班组批量问答而不是单兵串行调用，10Hz 才有现实可能；需要实际测 p95、超时率、批大小和状态 token 长度。

### 7. 怎样干净测出模型贡献

先固定已经修好的运行条件：单 runner、同一地图种子、同一电脑难度、同一生产平衡和同一初始资源。至少做以下顺序对照，每个条件跑多个不同种子：

| 组别 | 战略计划 | 班组战术 | 目的 |
|---|---|---|---|
| R0 | 规则 | 规则 | 可赢的确定性基线 |
| R1 | 2B/固定计划 | 规则 | 测战略是否有贡献 |
| R2 | 固定计划 | Laya | 测 Laya 的战术/微操贡献 |
| R3 | 2B | Laya | 测完整组合 |

不要只报 val accuracy。每局至少报：胜率、首次建筑受损时间、建筑损伤/分钟、击杀/损失比、90 秒前坦克数、主攻兵力集中度、攻击订单完成率、模型订单接受率、规则替换率、命令 churn、闸门安全拒绝率、单位空转时间和撤退后存活率。模型贡献应按“同一状态下模型订单被执行后的结果”和对应基线比较，而不是按整局胜负猜功劳。

### 8. 最大盲区

当前最大盲区有四个：

1. **控制权没有定义清楚**：双 runner 事故说明“谁拥有单位”比模型准确率更基础；以后必须把 owner、source、lease 写入每条命令并做不变量测试。
2. **没有最小可行战斗 doctrine**：纯步兵打 16m 反地炮塔、240 秒不出坦克、扩张贴敌并两线分兵时，任何模型都会输。先证明规则基线能在 EASY 上拆掉至少一座建筑。
3. **没有时间抽象和订单持续性**：一行一单位、每轮重规划会让队伍永远在改方向；这比“模型选错一次”更能摧毁战斗效果。
4. **状态和标签是下游结果的混合物**：过滤器可能把真正困难的选择提前删掉，标签又来自过滤后的规则链，最终得到一个高分但没有战场责任的模型。

另一个统计盲区是随机切分导致的泄漏：同一局相邻帧高度相似，训练/验证分开后仍能记住 D9/D12 和 GAT/PROD 的常量。必须按 match_id/seed/时间段做拆分，并报告每类和每种局面的指标。

### 9. 如果从头设计

我会把系统设计成“计划、战术、执行”三层，而不是“规则全量先下发、模型稀疏覆盖”：

1. **观测层**：把地图、可见性、单位、资源、威胁、路径和订单状态压成结构化 state；保留观测时间和置信度。
2. **战役层（2B）**：异步生成经济/生产/扩张/主攻方向，以及 3~8 个班组订单。输出受 schema 约束，计划有版本、TTL 和完成条件。
3. **战术层（Laya）**：按班组或局部战区 5~10Hz 批量回答姿态、集火、目标优先级、撤退/风筝和支援问题。问题选项来自真实候选，不能把所有坏选项过滤掉后再宣称模型做了选择。
4. **执行层（规则/行为树）**：把班组订单展开为单位动作，处理路径、射程、CD、碰撞、编队、受击和到达确认；只在安全不变量或订单失效时拒绝/降级。
5. **结果层**：每个订单记录接受、执行、替换、完成、取消及 5/10/20 秒结果，直接生成训练和评估数据。

交付前不需要实现完整强化学习。优先完成一条可观测闭环：

```text
固定生产与主攻 doctrine → 小队订单 → Laya 局部选择 → 行为树执行
→ 订单结果 → 胜率/建筑损伤/战损指标
```

## 10 月 1 日前的建议顺序

### 阶段 A：先让规则基线赢（最高优先级）

- 固定一条 EASY doctrine：早车厂、明确坦克配额、主力只打一条线；扩张延后到主攻条件满足或改到安全位置。
- 目标优先级先写成可审计规则：能打到的生产建筑/反地炮塔优先，其次指挥中心；先验证射程、伤害、路径和目标可达性。
- 跑 `backend=off` 的同种子局，确认至少能造成建筑损伤并有明确的胜负上升趋势；否则暂停模型架构重构。

### 阶段 B：把模型从“追认”改成“拥有订单”

- 实现班组 ID、订单 TTL、owner/source/generation 和原子订单展开。
- 规则层保留安全否决，取消有效订单期间的策略性覆盖。
- 先让 Laya 只控制 3 个离散决策：主攻目标、交战姿态、撤退/等待；不马上接管全部动作。

### 阶段 C：重做数据和评估

- 新数据只采集修复后的局；按局/种子切分；下采样 GAT/PROD，补齐 ATTACK/AMOV/RET、目标和建筑伤害结果。
- 训练报告改为 macro-F1、每类召回、选择覆盖率、校准误差和局级指标。
- 按 R0/R1/R2/R3 顺序做可重复对照，先看建筑损伤和胜率，再看模型准确率。

### 暂时不要做的事

- 不要把 2B 放到 1~5 秒同步关键路径。
- 不要让 Laya 每个单位每帧输出坐标。
- 不要在没有足够结果样本时直接上离线 RL。
- 不要继续用“最终下发链”作为唯一教师标签。
- 不要用 84.7% 聚合 val 作为架构成功标准。

## 最终判断

报告的 A-1 至 A-6 怀疑大体正确，但优先级应调整为：

```text
P1-4 战斗 doctrine/射程/发展基线
→ 订单权威与时间抽象
→ Laya 班组战术
→ 结果标签与对照评估
→ 再考虑离线 RL 和更高难度
```

在“规则基线不能稳定拆建筑、模型订单没有租约、标签主要是规则多数类”这三个条件未解决前，继续训练 Laya 只会让 84.7% 变成更高的数字，不会带来预期的对局质变。
