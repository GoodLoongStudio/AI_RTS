## 0. 一句话摘要

`PlainAndSimple.tscn` 的地面平面 `center_offset` 在地图从 100×100 放大到 208×208 时没跟着改，
导致**地面只铺满逻辑地图的 50.3%**；出生点被静默吸附到悬崖边、12/16 个矿点落在空区，
AI 副官因此完全无法建造与采矿。修复后 AI 建造支出从 0 次恢复到 4 次/局。

## 2. 先排除的假设（避免后来者重复走）

**假设：工作区未提交的 `MatchConstants.Navmesh.CELL_SIZE` 0.8/0.6 → 0.3/0.4 会导致烘焙失败。**
（紧邻的旧注释正是"2048m 图 cell 过小会让 Recast 栅格超限 → Baking interrupted → polygons=0"）

**排除依据**：`AirNavigation._safety_checks()` / `TerrainNavigation._safety_checks()` 会 assert
场景里烘好的 navmesh 参数必须等于 `MatchConstants` 常量，而 `Match.tscn:117-138` 的两个
`NavigationMesh` 子资源**已同步**为 `cell_size = 0.3 / cell_height = 0.4 / agent_radius = 2.3(空) 2.8(地)`，
assert 不会炸；实测也烘出了网格（`NAVDBG polygons=58`、`NAVDBG air polygons=2`）。
另外 `Navigation.should_skip_runtime_navigation()` 对 `map.size >= 256` 与逻辑地形图本来就整段跳过烘焙，
208 图不受该阈值影响。

> 遗留观感问题（非本次故障因）：`MatchConstants.gd:104-105 / 117-118` 的注释仍在解释
> "0.3 → 0.6 是为了把栅格从 6800² 降到 3400²"，而常量值已被改回 0.3/0.4，**注释与值矛盾**，建议同步。

## 3. 真因①：地图地面偏移（已修，AI 副官故障的直接原因）

### 3.1 缺陷

`source/match/maps/PlainAndSimple.tscn` 修复前：

```
[sub_resource type="PlaneMesh" id="PlaneMesh_frqq2"]
size = Vector2(208, 208)
center_offset = Vector3(50, 0, 50)      ← 漏改

[node name="Map" instance=ExtResource("1_sqrvi")]
size = Vector2(208, 208)
```

`Terrain` 是 `Map.tscn` 下无 transform 偏移的 `MeshInstance3D`，所以平面在世界里铺
`x/z ∈ [50-104, 50+104] = [-54, 154]`，而逻辑地图是 `[0, 208]`。
烘焙侧 `TerrainNavigation.bake()` 又设了 `filter_baking_aabb = AABB(ZERO, (map.size.x, 40, map.size.y))`
（从 0 裁起），叠加 `agent_radius = 2.8` 的边缘侵蚀，最终可行走/可建区 = **`[3.0, 151.2]²`**。

**历史约定**（从 git 历史反推，BigArena / 旧 PlainAndSimple 均符合）：
平面 `size` = 地图 size + 4（每边 2m 外扩），`center_offset` = 地图 size / 2。
- 旧 PlainAndSimple：地图 100 → 平面 104 / offset 50 → 铺 `[-2, 102]` ✅
- BigArena：地图 100 → 平面 104 / offset 50 ✅
- 09-27 放大后：地图 208 → 平面 208（少 4）/ offset **仍是 50**（应为 104） ❌

引入提交：`8956c1d「小更新」`（2026-09-27 18:39，尺寸统一那批改动的一部分）。

### 3.3 为什么故障是"静默"的（重要机制，排查时别只看配置）

`MovementObstacle._align_unit_position_to_navigation()`（`source/match/units/traits/MovementObstacle.gd:96-115`）
会把单位的 XZ **吸附到 navmesh 最近点**（Y 取真实地表，2026-09-21 修"单位浮空"时引入）。
所以基地明明配在 (160,28) 的空区，运行时却被无声挪到 (151.2,28)，日志里不报错——
只表现为后续所有放置请求 `SurfaceNotBuildable`。

连带影响：`PlainAndSimple.tscn` 的 16 个 `ResourceA` 里有 **12 个落在空区**
（x≈152-170 / z≈156-172 的四簇，含 AI 家旁边那簇），修前 AI 既不能建也采不到矿。

### 3.4 修复

```diff
-size = Vector2(208, 208)
-center_offset = Vector3(50, 0, 50)
+size = Vector2(212, 212)
+center_offset = Vector3(104, 0, 104)
```

（按历史约定：平面 = 地图 + 4m 外扩、offset = 地图一半 → 铺 `[-2, 210]`，完整覆盖 `[0,208]`。）

> ✅ 这条同时**关闭了** `docs/程序文档/地图与单位尺寸联动核查清单_2026-09-27.md:49-50` 的待办：

## 4. 真因②：放置门槛随 footprint 一起放大（已按用户选择放宽视野部分）

### 4.1 三重门槛（`source/csharp/GodotAdapter/Construction/GodotStructurePlacementWorldPort.cs`）

| 判定 | 位置 | 口径 |
|---|---|---|
| `Navigable()` | :188 | footprint **圆周 16 采样点 + 圆心**全部落在地表 navmesh 上，容差 0.05m（256+ 生成图改走 `SurfaceBuildable()` 高度/坡度判定） |
| `FullyVisible()` | :143 | 采样点需"当前可见（己方 revealer 视野 + `SightCompensation` 2.0m）**或**已探明（`FogOfWar.is_explored`）" |
| `WaterBlocked()` / `Occupied` | :165 / :96,:102 | 整环水面校验；单位/资源重叠判定（仅在全环可见时才查，避免泄漏占用信息） |

尺寸统一后的 footprint 半径（`config/balance/demo.balance.v1.json` → `constructions[].footprintRadiusMeters`）：

| 建筑 | 半径 m | 建筑 | 半径 m |
|---|---|---|---|
| 机枪塔 / 对空炮 | 2.0 | 车厂 | **6.65** |
| 对地炮 | 2.2 | 基地 | 7.0 |
| 兵营 | 6.25 | 机场 | 8.0 |
| | | 矿场 | **9.8** |

视野（balance `sightRangeMeters`）：基地 10 / 矿场 10 / 无人机 10 / 车厂 8 / 矿车(原工人) 5。

### 4.2 实测：全图可建比例（8m 网格 × 圆周 16 点口径，`tmp_logs/diag_play/bsp.out.log`）

| footprint 半径 | 可建比例 | 失败点到网格中位距离 |
|---|---|---|
| 2.0（机枪塔） | **47.0%** | 30.8m |
| 6.65（车厂） | **40.7%** | 27.5m |
| 9.8（矿场） | **34.8%** | 30.6m |

（注：这组数字含真因①的空区，修地图后整体会上升；比例差反映的是"半径越大越难放"的趋势。）

### 4.3 建筑会把自己啃成洞，洞被 agent_radius 放大

建筑完工后 `MovementObstacle._affect_navigation_if_needed()`（:118）把自己加入
`terrain_navigation_input` 组并 `MatchSignals.schedule_navigation_rebake`，重烘后建筑位置成为空洞，
**洞半径 = 自身碰撞半径 + `agent_radius`**（`MatchConstants.Terrain.Navmesh.MAX_AGENT_RADIUS`，09-27 由 0.9 → **2.8**）。

实测基地径向剖面（8 方向对称，到 navmesh 的平面距离）：

```
方向  0°: 2m=2.4  4m=0.4  6m=0.0  8m=0.0 ...  → 洞半径 ≈ 4~5m
方向 90°: 2m=2.4  4m=0.4  6m=0.0 ... 14m=0.2 16m=1.3 → 14~16m 处是矿点啃的洞
方向270°: ... 26m=1.0 28m=3.0 30m=5.0        → 地图边界侵蚀
```

基地脚下最近网格点在 **4.02m** 外 → 车厂（6.65m）圆心必须离基地 **≥ ~11.5m** 才能整环落在网格上。

### 4.4 已做的改动（用户拍板选项：放宽视野门槛）

```diff
+    /// <summary>可见性采样环半径占 footprint 半径的比例（见 FullyVisible 注释）。</summary>
+    private const float VisibilityProbeRadiusScale = 0.5f;
...
-        foreach (var point in SampleCircle(center, radius))
+        foreach (var point in SampleCircle(center, radius * VisibilityProbeRadiusScale))
```

- 只动 `FullyVisible()`；`Navigable()` / `WaterBlocked()` / `SurfaceBuildable()` 的整环地形校验**保持严格不变**。
- `SampleCircle()` 本身已含圆心，所以"圆心 + 半半径环"共 17 点。
- 效果（`PostRefactorPlayabilityTest` 93 个候选点的问题分布）：

| | 修地图后 | + 放宽视野 |
|---|---|---|
| `NotVisible` | 55 | **44** |
| `SurfaceNotBuildable` | 36 | 36 |
| `Occupied` | 1 | **12**（更多候选走到了后续判定，即放宽生效） |

## 5. 真因③：开局链路（**另一会话在飞，我没动**）

2026-09-28 的"红警2 口径"改动（未提交）：

- `Match._spawn_player_units()`：开局**不再送 2 个工人**，只有基地 + 1 架无人机；
- balance：`worker.allowedProducerUnitTypeIds = ["vehicle_factory"]` → 矿车（内部 id 仍是 `worker`）只能由车厂生产；
- 矿场完工赠送一辆矿车（`RefineryFreeMinerSmokeTest` 覆盖）；
- 建筑 `constructionProgressSource: "automatic"` → 自动施工，不需要建造者；
- `Ra3Sidebar`：建筑页第一格改成矿场；`CommandCenterMenu` 的生产矿车按钮已移除，挪到 `VehicleFactoryMenu`；
- 规则 AI 三个控制器已摘掉"必须先有 Worker"的前置（`DefenseController` / `OffenseController` / `EconomyController`，
  `EconomyController._try_produce_worker` 的生产者由 `command_center` 改为 `vehicle_factory`）。

**由此产生的约束冲突**（这是"造不了建筑"的第二半原因）：

```
车厂圆心需 ≥ ~11.5m（navmesh 洞，§4.3）
基地视野只有 10 + 2 = 12m，无人机 10 + 2 = 12m
→ 半半径环（3.3m）需探到 ~15m，整环口径需探到 ~18m
⇒ 开局不先派无人机出去开图，大建筑无任何合法落点
```

小 footprint 建筑（炮塔 2.0/2.2m）仍可贴基地建造，所以症状表现为"炮塔能放、车厂/矿场全红"。

## 7. 遗留问题与建议（需要拍板，我未实施）

### 7.1 设计约束：开局必须先开图才能造大建筑

若认为"这符合经典 RTS 侦察语义、可接受"，则无需改动（当前状态）。
若认为"玩家实报为故障，需要降低门槛"，三个候选（按侵入性排序）：

| 方案 | 改动点 | 代价 |
|---|---|---|
| A. 恢复开局送 1 辆矿车 | `Match._spawn_player_units()` | 与"红警2 口径：开局不送工人"直接冲突，需用户先推翻该设定 |
| B. 提高基地/开局视野 | balance `command_center.sightRangeMeters` 10 → 16~18 | 影响迷雾平衡与 AI 索敌口径（`DefenseController` 注释里"基地 10m / 工人 5m"两档理由要重写） |
| C. 解耦"建筑挖洞"的 agent_radius | 建筑重烘用独立（更小）的 agent_radius，寻路仍用 2.8 | 需要两套 navmesh 参数，`_safety_checks()` 的 assert 与 `copy_navmesh_settings()` 都要跟着改；收益是建筑间距回到放大前手感 |

> 我的倾向：**C > B > A**。C 修的是"洞被无谓放大 1.9m"这个纯技术副作用，不动玩法设定；
> A 会推翻用户自己定的红警2 口径。

### 7.2 一条既有红（**非本次改动引入**，已做归因）

`tests/automated/StructurePlacementSmokeTest.tscn` → 1 failure：

```
被覆盖的友军应移动到建筑 footprint 外并待命（实测 4.08 m，需要 > 4.20 m，action=WaitingForTargets()）
```

`4.20 = tank.radius + turret.radius`，坦克 3 秒内被驱逐到 4.08m 就转入待命，差 12cm。

**归因方法**（可复现）：把 `VisibilityProbeRadiusScale` 调回 `1.0f` → `dotnet build` → 重跑，
失败签名**逐字相同**（`tmp_logs/diag_play/sps.out.log` vs `sps_base.out.log`）⇒ 与可见性改动无关。

**怀疑方向**：`Movement.gd` 09-27 把脱困接受半径改成了随半径放大
（`_give_up_commitment()`：`maxf(RECOVERY_ACCEPT_RADIUS_M, radius * 2.0 + 0.5)`），
驱逐位移可能在"够近即接受"的判据下提前收敛；或 `DisplacementMargin = 0.35f` 未随尺寸放大同调
（`地图与单位尺寸联动核查清单_2026-09-27.md:42-43` 已把"建造间距判定"列为待同调项）。

### 7.3 注释与常量矛盾（观感/维护风险）

`MatchConstants.gd:104-105 / 117-118` 的注释仍在解释"0.3 → 0.6 是为了避开 Recast 栅格超限"，
而值已是 0.3/0.4。若后续要上 2048m 生成图，`should_skip_runtime_navigation()`（≥256 跳过）会挡住，
但注释应同步，否则下一个人会以为常量写错了而"修回去"。
