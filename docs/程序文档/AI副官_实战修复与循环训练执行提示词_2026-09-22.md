# AI 副官实战修复与循环训练执行提示词

你负责把 `G:\AIRTS\AI_RTS` 中的 AI 副官修复到接近设计预期的 RTS 指挥效果。

本任务不是只改提示词、只修单元测试或只增加训练轮数。必须形成并执行完整闭环：

```text
固定场景复现
  → 找到实际断点
  → 最小一致修复
  → 自对局采集
  → 样本与标签审计
  → 训练/微调
  → 固定种子评测
  → 与基线对照
  → 根据失败样本继续修复和训练
```

每一轮都必须留下输入版本、代码版本、模型版本、数据集版本、随机种子、日志位置和结论。没有实际对局证据，不得声称“达到预期”。

## 2. 目标行为

最终目标是让副官在真实对局中稳定表现出：

- 采集、建造和生产能持续推进；
- 兵力达到条件后能组成小队并主动出击；
- 小队能找到合法路线、进入有效射程并持续产生伤害；
- 能够攻击敌方建筑，而不是只有“发出 attack 命令”；
- 劣势时局部撤退，优势时继续压制；
- 基地受袭只召回必要的局部兵力，其他战线不被无理由清空；
- 任务持续到完成、失败或明确中断，不因每次扫描自动换令；
- 玩家接管、归还、模型超时、空输出和迟到结果都不会破坏执行链；
- Laya 和 2B 的选择能够在合法范围内改变实际战术，并且这种影响可以从日志和对照实验中证明。

## 3. 必须先建立证据链

对每个关键决策建立可关联链路：

```text
观测
→ 候选动作
→ 模型选择
→ 解码结果
→ 规则/行为树合并
→ 仲裁结果
→ 权威回执
→ 实际位置、生产、开火、命中、伤害或摧毁结果
```

每条链至少带上：`match_id`、`tick`、`snapshot_id`、`request_id`、`intent_id`、单位或小队、目标、来源、当前任务、覆盖原因、拒绝原因和结果时间。

严格区分：

- 模型提出的动作；
- 程序保留或替换后的动作；
- 权威接受的订单；
- 单位实际执行的动作；
- 最终战果。

`Accepted` 不是成功。移动不是进攻成功，`attack` 不是造成伤害，模型输出合法也不是决策正确。

## 4. 第一阶段：关闭模型，修好确定性执行层

先用规则层和行为树跑固定场景，暂时关闭 Laya/2B，证明执行地板本身可靠。至少覆盖：

1. 工人采集 → 建造兵营 → 生产作战单位；
2. 持续生产不会被重复建造、扩张或错误回防长期抢占；
3. 作战单位离开基地并组成小队；
4. 小队接敌、进入射程、开火并产生可观测伤害；
5. 小队能够攻击敌方建筑并最终摧毁目标；
6. 敌多我少时局部撤退；
7. 基地受袭时局部回防，威胁解除后恢复原任务；
8. 玩家接管和归还只影响相关单位。

针对“建筑不掉血”，必须逐项排查：

- 是否发现了合法建筑目标；
- 目标 ID、实体类型和可攻击性是否一致；
- 是否存在武器域、射程、碰撞、占地或路径问题；
- 单位到位后是否真的开火；
- 命中事件是否产生伤害事件；
- 是否被下一轮扫描、回防、撤退或集结立即改令；
- 当前兵种、数量、资源和攻击力是否足够摧毁建筑；
- 当前运行使用的平衡配置是否与测试假设一致。

每修一个确定性缺陷，都要补一个能复现该缺陷的回归场景。

## 5. 第二阶段：修复控制权和任务持续性

明确三层职责：

- 战略层：阶段目标、经济倾向、主攻方向和何时转换阶段；
- 战术层：小队任务、局部目标、进攻/回防/撤退取舍；
- 执行层：移动、攻击、队形、路径、射程和安全约束。

不能让规则、行为树和模型同时反复替同一单位决定目标。建立明确的任务 owner、优先级、租约或完成条件。

有效任务只有在以下情况才允许被中断或改派：

- 目标死亡、失效或不可达；
- 玩家接管；
- 真实紧急威胁；
- 路径失败或明确无进展；
- 更高优先级且通过规则校验的新任务。

检查模型合并规则：

- 模型没有指定的单位继续执行原任务或规则 baseline；
- 模型不能覆盖撤退、安全边界和玩家控制；
- 规则不能无理由覆盖模型明确选择的合法小队任务；
- 高优先级动作必须按单位冲突逐个判定；
- 一条线的威胁不得升级为全军回防；
- 同一单位不能同时保留互相冲突的 attack、move、retreat、gather 等任务。

## 6. 第三阶段：审计并修复训练数据

先审计，不要直接继续训练。

对 `teacher_dataset`、`laya_dataset_v*` 和新采集数据统计：

- 任务类别分布；
- 分支分布；
- actor、目标和兵种分布；
- 标签来自 Laya、2B、规则、行为树还是人工；
- 标签是否属于当时可选候选；
- 标签是否通过最终仲裁；
- 订单是否被权威接受；
- 是否有执行与结果证据；
- 是否存在重复、空标签、错帧、错误回声或类别严重失衡。

特别检查：状态里出现 `ATK/AMOV`，不代表标签就应该是攻击；但如果军事场景长期只记录 `GAT`，必须解释其来源。模型自述、规则 fallback 和最终实际行为不得混写成“教师答案”。

建议每条样本至少包含：

```json
{
  "observation": {},
  "candidate_actions": [],
  "model_choice": {},
  "final_action": {},
  "accepted": true,
  "executed": true,
  "outcome": {
    "damage": 0,
    "production_progress": 0,
    "target_destroyed": false,
    "survived": true
  },
  "teacher_source": "rule|behavior_tree|laya|2b|human|verified_outcome",
  "label_quality": "verified|accepted_only|unverified|invalid",
  "next_observation_tick": 0
}
```

不可信样本必须保留原始记录并标记隔离，不得直接混入高质量教师集。不要靠简单复制攻击样本解决问题，先修正候选空间、标签来源和结果判定。

## 7. 强制执行循环训练

训练不是一次性步骤，而是每轮都必须完成的闭环。每一轮按下面顺序执行：

### 7.1 生成自对局

固定版本的地图、平衡配置、敌方策略、运行时长和种子集合。至少包含：

- 正常发展；
- 小队主动进攻；
- 建筑攻坚；
- 敌袭回防；
- 劣势撤退；
- 双线作战；
- 玩家介入；
- 模型超时、空输出、非法输出和迟到结果。

先用少量种子快速筛查，再用固定评测种子做正式比较。采集完整日志，不只保存模型输出。

### 7.2 自动审计样本

每轮训练前生成数据审计报告，至少列出：

- 总样本数和有效样本数；
- 各任务/分支/兵种/目标比例；
- 无法关联到最终执行结果的比例；
- 被仲裁替换、拒绝、过期和重复的比例；
- 攻击、回防、撤退、生产和建筑攻坚样本数量；
- 每类样本的结果分布；
- 本轮相对上一轮新增的失败模式。

如果标签仍然几乎只有采集，或者大多数样本没有执行结果，停止训练，先修采集和标签链。

### 7.3 训练或微调

只使用通过质量门槛的样本作为主训练集；低质量样本可以用于错误分析或单独的拒答/安全训练，但不能当作优秀示范。

保持独立的训练集、验证集和固定评测集。不得用固定评测对局反复训练。记录模型权重、训练参数、数据版本和随机种子。

训练目标必须分别评估：

- 结构合法率；
- 候选选择准确率；
- 任务持续性；
- 战斗结果；
- 建筑伤害和摧毁；
- 生产连续性；
- 误回防、误撤退和无理由改令。

不要用一个总分掩盖某类能力退化。

### 7.4 固定评测并与基线对照

同一批固定种子至少比较：

1. 规则/行为树 baseline；
2. baseline + Laya；
3. baseline + Laya + 2B 战略层；
4. 本轮训练模型。

只改变被测模型或训练版本，不偷偷改变敌人、资源、视野、平衡和地图。输出逐局结果与汇总统计。

### 7.5 根据失败样本继续修复

每轮结束后把失败按根因分类：

- 观测错误；
- 候选缺失；
- 标签错误；
- 模型选择错误；
- 合并/仲裁覆盖错误；
- 权威拒绝；
- 路径/射程/伤害执行错误；
- 任务过早中断；
- 生产或资源不足；
- 评测或日志关联错误。

下一轮只针对明确根因增加数据、修代码或调整训练。不要同时随机改很多项，否则无法知道哪项有效。

### 7.6 版本晋级与回滚

只有当新版本在固定评测集上没有关键回归，并且至少一项目标行为有可重复提升时，才允许晋级为下一轮基线。

若建筑攻坚、生产连续性、玩家接管或安全约束退化，立即回滚到上一稳定版本，并把退化样本加入错误集。不要因为总体平均分上升就保留关键能力回归。

## 8. 验收指标

至少记录以下指标：

- 首次有效出击时间；
- 首次建筑伤害时间；
- 首次建筑摧毁时间；
- 生产空闲比例；
- 资源积压和兵种组成；
- 小队任务持续时间；
- 无理由改令次数；
- 有效伤害、损失和存活率；
- 敌袭到实际响应的延迟；
- 模型选择被采用、被替换、被拒绝和无效的比例；
- 模型开启相对 baseline 的收益或退化；
- 每个固定种子的胜负和关键失败原因。

规则层能赢，只能说明执行基础可用。还必须证明模型在需要取舍的场景中改变了合法战术，并且这种改变带来稳定收益，才能认定混合架构达到设计方向。

## 9. 每轮必须交付的报告

每轮写一份简短报告，至少包含：

1. 本轮代码、模型、数据和配置版本；
2. 复现的失败场景和证据路径；
3. 已确认根因与排除的错误判断；
4. 实际修改及职责变化；
5. 样本审计结果；
6. 训练参数和训练集/评测集划分；
7. baseline 与新版本逐种子对照；
8. 仍未解决的问题；
9. 下一轮只准备验证的假设；
10. 若环境、模型服务或运行时长导致未验证，明确写“尚未验证”，并给出复现命令。

## 10. 完成标准

每个缺陷必须遵循：

```text
失败复现
→ 最小一致修复
→ 针对性回归
→ 固定场景实战
→ 自对局采集
→ 标签审计
→ 训练/微调
→ 固定种子对照
→ 根据失败进入下一轮
```

不能用架构图、提示词长度、命令数量、`Accepted` 数量或单元测试通过率替代真实对局证据。没有完成至少一轮“采集—审计—训练—评测—修正”的循环，不得宣称训练有效；没有完成固定场景和多种子对照，不得宣称已经接近设计预期。
