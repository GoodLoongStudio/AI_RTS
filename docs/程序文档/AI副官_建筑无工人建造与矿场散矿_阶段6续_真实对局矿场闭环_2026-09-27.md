## 一、这一轮最重要的一条：找到了"玩家/副官入口"与"权威端"语义不一致的真断点

阶段 6 把脚本化矿场触发做出来以后，真实对局里矿场三列一直是 `None`，而日志里只有一句
`NoValidSite` 和客户端的 `PendingAuthority`。这一轮把它钉死了：

```
[CMD][服务器] place_structure 拒绝: runtime/参数缺失
```

- 断点位置：`source/net/NetSync.gd` 服务器侧 `place_structure` 处理段，
  判据 `placement_runtime == null or units.is_empty() or extra_clean.is_empty()`。
- 为什么它是断点：阶段 1 之后，客户端 `_op_build` 对 `automatic` 建筑**不再要求带建造者**
  （零工人施工的语义），于是转发命令里的 `units` 是空的；而这条转发入口还按旧口径把
  `units.is_empty()` 当拒绝条件。结果：
  - 权威端直执行路径（单机、专用服自执行）没有这个限制 ⇒ 冒烟测试全绿；
  - **联机/副官/脚本走的转发路径被静默拒收** ⇒ 用户在真实对局里永远看不到矿场。
- 这正是提示词 §7 完成标准第 2 条要求的一致性问题（"权威端、规则 AI、副官和玩家入口语义一致"），
  也是 §C「`Construct` 是否只是旧兼容路径」那一问的实际答案：**转发入口才是没改的那一个**。

修复（`NetSync.gd`）：

```gdscript
var progress_source := _construction_progress_source_for(parts[0])
if placement_runtime == null or extra_clean.is_empty() \
        or (progress_source == "worker" and units.is_empty()):
    print("[CMD][服务器] place_structure 拒绝: runtime/参数缺失（进度源=%s，units=%d）" % ...)
    return
```

`_construction_progress_source_for()` 与 `DebugControlServer._construction_progress_source`
同一口径（查 `BalanceConfigRuntime.GetConstructionProgressSource`），**查不到配置按 `worker` 保守回退**，
不在配置缺失时悄悄放开零工人施工。

## 三、下一个真实断点：矿场在真实对局里留不住工人

fs_ref10 的时间线（同图同种子，权威观测）：

```
t+112  矿场建成（Unit_96，constructed=true，服务半径 30m，圈内确有矿）
t+112  assigned=2   ← 接管发生过
t+130 起 assigned=0 且 delivered=0，一直到 t+322（约 190 秒）再没接管过任何人
```

也就是提示词 §D 预判的那一条：**"只有空闲 Worker 才能被接管，是否导致矿场永远抢不到人"**。
当前 `_is_claimable()` 只认 `action == null` 或 `AutoGatheringResources.gd`；
而真实对局里玩家方的工人由规则副官持续下**权威采集订单**，`_supervise_assigned()`
一看 `_has_authoritative_order()` 为真就立刻释放名额，之后这些工人的 action 是
`CollectingResourcesSequentially.gd`（采集子动作），按现行判据**不具被接管资格**。

这一轮先把**断点分布仪表**补齐（只做诊断，不改任何判定），两种可能各自要打印得出来：

```
[REFINERY-CLAIM] … 无可接管工人：工人=6 已被占用=0 忙={'CollectingResourcesSequentially.gd': 6}
[REFINERY-CLAIM] … 候选人=3 但报到点为空：stand=null 服务半径内矿=true
```

前一种成立 ⇒ 要改的是资格判据（经济类订单应当可被矿场改派，玩家显式/军事/施工订单仍然优先）；
后一种成立 ⇒ 要改的是报到点计算（避让圈外推那一段）。**在拿到这行日志之前不动判定逻辑**，
不重犯第一节那三个"按推测改代码"的错。

## 五、采集入口自己的两个硬伤（会让所有真实对局结论失真）

### 5.1 端口段用错了：检查 24589，实际起在 24569

`selfplay_match.py` 的 import 顺序是 `import restart_local` 在前、算 `BASE` 在后，
而 `restart_local` 在 **import 那一刻**就按 `AIRTS_TEST_BASE` 的默认值把
`GAME_PORT/CLIENT_PORT/SERVER_PORT` 固化成 24569/24570/24572。于是：

- 打印出来的是"验收端口 24589 在专用段 24589-24592 内"（凭据是假的）；
- 游戏实际起在 **24569 面板默认段**，而 `kill_our_game()` 又按端口匹配进程；
- 同机另一路会话正好在用这一段（实测看到它的 `--port 24569 --debugport 24572`），
  两边走的正是 `dev_ports` 顶部 2026-09-13 血案注释描述的互相杀。

后果直接体现在证据上：5 个筛查种子里 3 局 `rc=2`，还有一局"客户端 4 秒就绪、
52 秒后连接被拒"——`op=tactical` 拿到的是**别人那一局**的服务器，
于是"可见远端矿点=False 可动单位=None"，看起来像地图/视野坏了。

修法（三处）：

1. `BASE` 与环境变量在 `import restart_local` **之前**定好；
2. 加端口自检：`GAME/CLIENT/SERVER != BASE/BASE+1/BASE+3` 就直接 `SystemExit`，
   以后谁改回 import 顺序会当场响，而不是安静地连到别人的局；
3. 长链全部显式 `export AIRTS_TEST_BASE=24609`（第二段），与另一路会话完全隔离。

**判别性验证**：同一粒种子 33，之前 `可见远端矿点=False`、52 秒断连；
换到 24609 段后同一种子 4 秒就绪、侦察单位正常出发、矿场建成。
⇒ 那 3 个 rc=2 与"地图没散矿/矿场建不起来"无关，纯粹是采集入口串了台。

### 5.2 `takeover_count` 声明了却从没自增

仪表里 `assigned=2` 而 `takeovers=0`，说明 §6 要的"首次矿场接管 Worker 时间"
这条指标**永远不会落账**（`op=commands`/`refinery_takeover` 都靠它）。已在 `_assign()` 补自增。

### 5.3 上一节"客户端 move 没生效"的结论作废

坐标口径修正后同一局看得很清楚：真人链路（客户端转发）的 `op=move` **就是生效的**，
单位 100 秒内走了 ~170 米、12.1 米抵达目标矿点，回执写的还是 `PendingAuthority`。
所以那条"改走权威端直执行"的兜底只是保险，**不是**修复；真正的 `PendingAuthority`
之谜是 §一 那个转发入口拒绝，跟 move 无关。

## 五又二分之一、又抓到一条会让 §8.2 整条不成立的缺陷：矿量镜像从来没发出去过

`fs_screen_44` 的服务器日志里 8365 条同一句错误，栈顶全部指向同一行：

```
SCRIPT ERROR: Invalid call. Nonexistent 'bool' constructor.
   [0] _reconcile_entry_for (res://source/net/NetSync.gd:245)
   [1] _recompute_client_visibility (res://source/net/NetSync.gd:635)   ← 8361 条
   [2] _broadcast_snapshot (res://source/net/NetSync.gd:584)
```

那一行是阶段 4 加的矿量/再生状态镜像：

```gdscript
entry["ore"] = [int(...), int(...), 1 if bool(unit.get("depleted")) else 0, int(...)]
```

`bool(<Variant>)` 在这个引擎调用里非法 ⇒ **整条赋值语句执行失败** ⇒
`entry` 里根本没有 `ore` 键 ⇒ 客户端与重连者**一个矿量数字都没收到**，
更谈不上"耗尽等待"标记与剩余再生毫秒。

直接后果：

- 阶段 4 报告第 4 节写的"矿量下发已补上、客户端只接受不自己推进计时"在当前构建上**不成立**，
  本报告予以更正；`§8.2` 要求的"单机、联机及已有存档/重连路径保持资源量与再生时刻一致"
  此前实际是断的。
- 为什么一直没被发现：判绿口径只看 `expected_marker` + 返回码，**不校验 SCRIPT ERROR**
  （这条坑在仓库记忆里就有，今天又在自家测试上验证了一次）。

修法（三处，全部去掉 `bool()` 转换）：

| 位置 | 原写法 | 现写法 |
|---|---|---|
| `NetSync._reconcile_entry_for` | `1 if bool(unit.get("depleted")) else 0` | 先取 `var depleted_flag = unit.get("depleted")`，再 `1 if depleted_flag else 0` |
| `ResourceUnit.apply_presentation_ore` | `depleted = bool(int(report[2]))` | `depleted = int(report[2]) != 0` |
| `ResourceRegeneration._rule_for` 判据 | `if not bool(rule.get("enabled", false))` | `if not rule.get("enabled", false)` |

本轮新增到 `OreRegenerationSmokeTest` 的那条断言（`_reconcile_entry_for` 必须下发
`[a, b, depleted, regen_remaining_ms]` 四元组）**正好能抓住这个缺陷**——旧代码下
`entry` 里没有 `ore` 键，断言直接红。修复与断言的对照结果以扫局与定向回归的日志为准。

## 六、矿场"留不住人"断点：仪表给出的答案与改判

隔离端口段重跑同一粒种子（fs_diag2），第一次拿到完整、干净的断点分布：

```
[REFINERY] Unit_104 完工，接管计时器已启动（间隔 2.0s，容量 4，服务半径 30.0m）
[REFINERY-CLAIM] Unit_104 在册=0/4 无可接管工人：工人=6 已被占用=0
                 忙={ "CollectingResourcesSequentially.gd": 6 }
```

三件事同时成立：**计时器是好的、半径内确实有矿、6 个工人全在采集**。
旧 `_is_claimable()` 只认 `action == null` 或 `AutoGatheringResources.gd`，
把"正在顺序采集"当成"有显式订单、不能碰"，于是矿场在真实对局里一个人都接不到 ——
提示词 §D 预判的"只有空闲 Worker 才能被接管是否导致矿场永远抢不到人"成立。

改判（`OreRefinery.gd`）：按**任务类别**而不是"有没有订单"决定资格。

- `GATHERING_ACTIONS = [AutoGatheringResources, CollectingResourcesSequentially,
  CollectingResourcesWhileInRange]` 可被接管：矿场只是把他的采矿区改到服务半径内、
  交货点改到本矿场，**任务类别没变**；
- 移动 / 施工 / 交战这类**改变任务类别**的订单一律不碰；在册工人一旦被这类订单拿走，
  `_supervise_assigned()` 立刻释放名额（玩家与军事优先，§6"玩家接管"行仍由冒烟测试钉住）；
- `_supervise_assigned` 原来只把 `AutoGatheringResources` 留在册，工人一进
  `CollectingResourcesSequentially` 就被释放 —— 这是 fs_ref10 里
  `assigned` 从 2 掉回 0、之后 190 秒零接管的真正原因，同一处一起修掉。

### 6.1 改判后的真实对局闭环（fs_verify1，同图同种子 33，只改判据）

| 时刻 | 权威观测事实 |
|---|---|
| t+130 | 矿场已放置、施工中（零工人，自动推进） |
| t+140 | `constructed=true`，`takeovers=6`，`assigned=1` |
| t+171 | **首次交付：delivered=1 / 400 矿** |
| t+201 | `delivered=2 / 800 矿`，`assigned=4`（达到容量上限） |

§7 完成标准第 3 条（"矿场不只是存在资产或类，而是能完工、接管工人、采矿、
回矿场交付并产生资源"）第一次在**真实对局**里有数，而不再只有冒烟夹具。

### 6.2 但暴露出双控乒乓，已加冷却

同一局里 `takeovers` 60 秒内从 6 涨到 25，而 `delivered` 只涨 2 ——
说明规则中台也在给同一批工人下采集令，两边互相顶：矿场派过去 → 规则令顶掉 →
名额释放 → 下一 tick 又派。提示词 §8.3 明确禁止"反复重下相同采集订单"。

修法：`reclaim_cooldown_s = 20`，释放名额时给工人盖冷却戳
（`_release_worker()`），冷却内不再重新接管同一个工人；仪表新增 `冷却=` 计数。
效果由随后 `fs_precheck` / 扫局各局的 `takeovers` 增速复核，不在此预测。

### 6.3 冷却之后仍然振荡，仪表把真凶指出来（并暴露我另一处自埋 bug）

加冷却后的 `fs_precheck`（同种子 33，220 秒）：`assigned` 在 0/2/0/3/0 之间跳，
`takeovers` 60 秒涨到 18，**交付 0**。光看计数分不清是"规则层抢人"还是"工人半路阵亡"，
所以给每次释放打了原因行 `[REFINERY-RELEASE] … 原因=…`。

顺着这条日志复查 `_supervise_assigned()` 时，发现我上一轮改判据时把局部变量
`var action = worker.get("action")` 删掉了，而函数里还留着 `if action == null:` ——
GDScript 不报错，`action` 解析到**矿场自己**继承自 Unit 的 `action` 属性（建筑恒为 null），
于是那个分支永远走不到，非经济任务的工人一直挂在册。这就是振荡的另一半原因。
修法：显式 `var action: Node = worker.get("action")`。
