## 1. 使用原则

本项目的共同执行层不是鼠标、HUD或某个AI脚本，而是C# Application公共接口：

```text
Human输入 ─┐
传统规则AI ├─→ 固定身份Adapter → Application命令/查询 → Godot执行端
未来LLM  ──┘
```

必须遵守：

- `AI_RTS.Domain`与`AI_RTS.Application`禁止引用Godot；
- 调用者不能提交Godot Node作为领域身份，跨边界使用稳定ID和DTO；
- 写操作使用Command并返回结构化结果；
- 长时间行为使用Order状态和事件表达，`Accepted`不等于最终完成；
- 读取使用QuerySession和不可变观察结果，不遍历场景树绕过视野；
- UI、语音和动画消费结果或事件，不决定权威规则；
- Python、LLM和数据库只能经未来Infrastructure/Adapter接入。

接口详细决策依据可查《程序重构_公共接口最终评审稿.md》及各专项接口评审稿。

## 2. 稳定身份与坐标

`source/csharp/Domain/Common/`定义以下常用身份：

- `MatchId`、`PlayerId`；
- `UnitId`与`BattlefieldEntityId`；
- `ResourceNodeId`；
- `CommandId`、`UnitOrderId`；
- `UnitTypeId`、`WeaponDefinitionId`、`StructureDefinitionId`、`ProductionDefinitionId`等配置ID；
- `QuerySessionId`；
- `WorldPosition`。

Godot Node与稳定ID的映射由`GodotStableIdentity`及每局Registry维护。不要使用Node实例ID、NodePath、场景路径或节点名称替代领域身份。`Vector3`只在GodotAdapter边界转换为`WorldPosition`。

## 3. 命令上下文、批量结果与订单

### 3.1 CommandContext

每次权威命令包含：

```csharp
CommandContext(CommandId, MatchId, IssuerPlayerId, SimulationTick)
```

发出者身份必须由可信组合根绑定。外部文本、网络请求或GDScript参数不能自行指定任意`IssuerPlayerId`。

### 3.2 CommandResult

`CommandResult.Status`只有：

- `Accepted`：全部成员在下令时接受；
- `PartiallyAccepted`：至少一个接受且至少一个拒绝；
- `Rejected`：全部拒绝或命令结构无效。

`UnitResults`逐单位返回`Accepted`、稳定`CommandErrorCode`和可空`OrderId`。批量选择中单位死亡、失效、无移动能力或不属于发出者时，不回滚其他有效单位。

不要把`PartiallyAccepted`转换成简单`false`，也不要只显示第一条失败原因。

### 3.3 异步订单

订单类型见`UnitOrderKind`，状态见`UnitOrderState`：`Accepted`、`InProgress`、`Suspended`、`Arrived`、`Completed`、`Unreachable`、`TargetLost`、`Cancelled`和`UnitLost`。

桥梁坍塌、地形变化、单位速度不同和目标移动不会妨碍同步回执；它们通过后续订单状态变化表示。需要语音提示“到达”“建造完成”时，应监听相应事件或终态，而不是在命令返回`Accepted`时播放完成语音。

## 4. 单位命令接口

权威接口：`AI_RTS.Application.Commands.IUnitCommandService`；实现：`UnitCommandService`；Human组合入口：`UnitCommandGateway`/`CommandRuntime`；传统AI入口：`RuleAiCommandGateway`。

| 方法/命令 | 当前语义 |
|---|---|
| `Move` / `MoveUnitsCommand` | 普通移动；可移动射击能力由单位配置和Legacy执行端决定 |
| `ApproachEntity` | 靠近实体footprint；用于把敌方建筑或资源当位置目标 |
| `FollowEntity` | 持续跟随单位/建筑，直到停止、替换或目标失效 |
| `ForceMove` | 玩家明确的位置意图；可点击实体表面取得位置 |
| `GroundAttackMove` | 向地面推进并按交战姿态处理沿途敌人 |
| `EntityAttackMove` | 以可见敌方实体为最终目标推进并沿途交战 |
| `TacticalWithdraw` | 有倒车能力者沿路径倒车；其他可移动单位退化为移动 |
| `HaltMovement` | 只停止移动，保留任务并转为不自动恢复的暂停状态 |
| `Stop` | 统一停止当前活动订单，并取消显式ForceAttack；之后允许自主索敌重新开始 |
| `SetEngagementStance` | 设置`Aggressive`、`Guard`或`HoldGround`等持续姿态 |
| `SetFirePolicy` | 独立设置正常开火/停火，不改变姿态 |
| `Attack` | 普通敌方实体攻击，受停火限制 |
| `ForceAttack` | 实体或地面显式攻击，临时覆盖停火，直到停止或目标失效 |
| `CancelForceAttack` | 只取消显式强制攻击 |
| `GatherResources` | Worker围绕指定资源节点执行采集—返程—交付循环 |

新增单位命令时：

1. 在`Application/Commands/Units`定义强类型Command；
2. 在`IUnitCommandService`加入用例，并在`UnitCommandService`完成权限和逐单位校验；
3. 如需引擎动作，在`Application/Units`定义最小端口；
4. 在GodotAdapter实现端口，Legacy Action只能从这里启动；
5. 更新订单类型/状态（如需要）；
6. 为Human、规则AI或未来Agent增加各自Adapter，不复制规则；
7. 先补纯C#测试，再补Godot场景与人工验收。

## 5. 查询和观察接口

权威只读接口：`IWorldQueryService`。当前查询包括：

- `GetOwnForces`：己方单位与建筑准确信息；
- `ScanCircle`：按圆形范围和字段粒度查询受视野限制的实体；
- `InspectOwnEntity`：只允许稳定ID查询己方实体；
- `GetOwnEconomy`：己方准确资源账户；
- `GetBattlefieldBounds`：公共可玩矩形边界，不代表每一点都可导航。

`QueryResult<T>`始终包含状态、值、公开错误码和观察版本。成功但没有实体时必须返回`Accepted`及空集合，不能返回null、缺键或无响应。

### 5.1 QuerySession权限

会话由`WorldQueryRuntime`在Match组合根中签发，固定：观察者、来源、己方字段、可见敌方字段和是否全知。当前来源包括Human、RuleAI、Agent预留和OmniscientDebug。

普通调用者不能创建、修改或交换会话。传统AI获得固定到自身玩家的标准会话；攻击网关仍会再次校验敌方目标当前可见，隐藏和不存在统一返回`TargetUnavailable`，避免错误差异泄漏情报。

### 5.2 LastKnown

当前只为离开视野的敌方建筑保留LastKnown。重新侦察发现建筑不存在时残影清除；敌方可移动单位暂不保留残影。表现层可以调整残影明暗，但不得改变观察状态。

### 5.3 大模型操作点边界

`IBudgetedWorldQueryService`已经预留，但本轮没有实现扣点算法。未来Agent只能访问它，不能直接取得`IWorldQueryService`或`WorldQueryRuntime`。实现必须在调用底层查询前原子扣点，即使查询成功返回空集合或产生无效观察也不得退款。

## 6. 经济、放置、施工、生产与集结

| 系统 | 公共接口 | 关键规则 |
|---|---|---|
| 资源账户 | `IResourceAccountService` | 多资源交易原子应用；不允许负余额；交易ID防重复入账 |
| 放置评估 | `IStructurePlacementService` | 只读评估与真正放置分离；检查环境、视野、地图、建筑/敌军阻挡 |
| 施工 | `IConstructionService` | 放置和Worker施工分离；多Worker可扩展；主动取消退款、被摧毁不退款 |
| 生产 | `IProductionService` | 每建筑独立队列；当前全额预扣；主动取消全额退款；生产者丢失不退款 |
| 集结 | `IRallyPointService` | 位置、友军单位或资源目标；目标失效回建筑默认出口 |
| 控制组 | `IControlGroupService` | 玩家本地稳定ID集合；空选择清组，空组召回清选择，失效成员自动过滤 |
| 胜负 | `IMatchOutcomeService` | 当前Demo使用最后存活参战方规则；玩法扩展应替换Rule而非HUD判断 |

经济奖励、定时产出建筑和未来渐进支付应通过资源账户交易接入，不能把经济系统绑定为“只有Worker交付才能增长”。

## 7. 强类型数值与Godot素材映射

权威数值文件：`config/balance/demo.balance.v1.json`；Godot资源映射：`config/godot/demo.assets.v1.json`。

`BalanceConfigLoader`进行全量校验并生成不可变`IGameBalanceCatalog`。`BalanceConfigRuntime`在Match进入场景树时加载Catalog，再加载`GodotAssetManifest`；任一错误都会阻止对局启动。

配置约束：

- ID使用小写稳定字符串，不以`.tscn`路径作为ID；
- 时间明确使用毫秒，距离/速度明确使用米制含义；
- 金额、工作量和Tick使用整数；
- 当前Legacy执行器每单位只支持一件主武器，配置多武器会明确失败；
- 平衡定义与PackedScene映射必须一一对应；
- 修改Schema时增加版本和迁移/校验，不静默容忍未知结构。

## 8. 新增单位流程

新增单位不是只复制一个`.tscn`。推荐顺序：

1. **确定稳定ID和能力**：在平衡JSON的`unitTypes`增加类型，声明HP、视野、可空Movement、武器、采集/施工/生产能力；
2. **定义武器/弹头**：需要新武器时先增加`warheads`、`weapons`，明确交付类型、目标域、范围和友伤；
3. **建立场景**：在`source/match/units/`创建场景和必要脚本，能力节点必须与配置一致，例如声明Movement就必须有`Movement`节点；
4. **满足视觉契约**：挂载`UnitVisualBindings`，绑定`VisualRoot`、`CollisionRoot`、`SelectionAnchor`、`HealthBarAnchor`、`GroundFootprint`和`PrimaryMuzzle`；动画根可选；
5. **登记素材映射**：在`demo.assets.v1.json`把`unitTypeId`映射到单位场景；建筑还要登记蓝图场景；
6. **登记生产或施工**：可生产单位增加`productions`并列出允许生产者；建筑增加`constructions`、费用、工作量、环境和footprint；
7. **接入菜单/AI策略**：HUD只提交稳定类型ID；传统AI是否生产该单位由策略配置决定，不能写入核心单位规则；
8. **生成并提交UID**：用Godot打开项目，提交新脚本对应`.uid`，不提交`.godot`缓存；
9. **测试**：配置Loader测试、场景实例化、命令能力、生产/施工、死亡清理和相关人工视觉测试。

替换模型时优先只修改`VisualRoot`下内容和语义挂点，不改单位根、稳定类型ID或核心能力节点。炮塔旋转根、炮口和碰撞尺寸应通过绑定/场景适配表达，不能让业务代码依赖导入GLB的内部层级。

## 9. 新增按键或按钮动作流程

当前默认Action集中在`Application/Input/DefaultInputBindings.cs`，运行时为`InputBindingRuntime`，玩家覆盖文件为`user://controls.cfg`。

步骤：

1. 定义稳定Action ID，例如`unit.patrol`，不要把物理键名当Action ID；
2. 选择`InputContextId`；同一键可在不同上下文复用，不能在同一上下文冲突；
3. 需要玩家键位时使用`Bind`增加默认单键或一个Shift/Ctrl/Alt加普通键；
4. 只允许按钮/系统调用的功能使用`ButtonOnly`，正式版本不会因此自动获得快捷键；
5. 在相应GodotAdapter/HUD订阅`ActionPressed`，转换为公共命令或本地表现；
6. 增加输入服务测试：默认值、组合键优先、上下文屏蔽、覆盖冲突和恢复默认；
7. 修改配置结构时提升`ControlsSchemaVersion`并明确旧配置策略。

首版只支持一个修饰键加一个普通键。组合键按精确匹配处理，`Ctrl+1`不会同时触发`1`。三键组合和Shift/Ctrl/Alt彼此优先级尚未评审，不得先行加入隐式规则。

## 10. 新增机制流程

新增机制先判断它属于哪一层：

- 纯规则、状态、错误码、数值类型：Domain；
- 用例、校验、状态转换、端口：Application；
- Node/RID/Navigation/Animation/Audio/文件系统：GodotAdapter；
- 鼠标、HUD、模型和特效：Godot场景/GDScript表现层；
- Python、HTTP、数据库：未来Infrastructure。

标准垂直切片：

1. 编写接口评审文档和明确非目标；
2. 定义稳定ID、Command/Query/Result/Event；
3. 在Core实现并编写纯C#测试；
4. 定义最小端口，不让Godot类型进入Core；
5. 实现GodotAdapter和组合根装配；
6. 接入Human及适用的规则AI；
7. 增加Godot自动场景、手动验收和缺陷记录；
8. 更新Legacy允许清单、结构/接口文档和变更日志；
9. 执行完整回归。

## 11. 导航专项从哪里接入

导航规则的Application边界是`IUnitMovementPort`；当前Godot实现是`GodotAdapter/Navigation/LegacyMovementPort.cs`，实际NavigationAgent与路径执行仍位于：

- `source/match/Navigation.gd`；
- `source/match/TerrainNavigation.gd`与`AirNavigation.gd`；
- `source/match/units/traits/Movement.gd`；
- `source/match/units/traits/MovementObstacle.gd`；
- `source/match/units/actions/`中的移动/撤退/移动攻击执行端；
- 单位与障碍场景中的碰撞、半径和导航域配置。

后续修复狭缝振荡或做多单位优化时：

1. 保持`UnitCommandService`的权限、批量结果和订单语义不变；
2. 在`IUnitMovementPort`扩展确实需要的最小结果，如`Blocked/Unreachable`，不要让Application轮询NavigationAgent；
3. 在GodotAdapter/Legacy执行端处理NavMesh、RVO、路径转弯和局部避障；
4. footprint必须同时核对视觉、碰撞、NavMesh、RVO和放置净空；
5. 复杂并发、多线程、共享走廊或Flow Field实施前先提交性能证据和方案评审；
6. 建立独立缺陷分支及障碍复现场景，不夹带命令语义改动。

## 12. 传统规则AI从哪里细化

当前策略脚本位于`source/match/players/simple-clairvoyant-ai/`。它们通过：

- `WorldQueryRuntime`取得固定玩家的标准权限会话；
- `RuleAiCommandGateway`按稳定ID执行Move、Halt、Attack、Gather、Construct、PlaceStructure和EnqueueProduction。

细化传统AI时可以修改策略选择、外置配置、阵营/指挥官/地图/玩法差异，但不得：

- 使用`get_nodes_in_group("units")`获得全图敌军；
- 直接设置`unit.action`、HP、资源、施工或生产队列；
- 把Godot Node作为长期策略身份；
- 根据错误差异探测隐藏单位；
- 为AI复制一套经济或建造规则。

推荐把AI人格、优先级、阈值和可生产类型放入版本化外置配置，由策略层消费；地图专用AI应通过显式配置选择，而不是在通用控制器中硬编码地图名称。

## 13. 大模型AI和跨语言测试从哪里接入

当前仓库没有真实LLM、Python服务或数据库实现。未来推荐链路：

```text
Python/LLM服务
  → 版本化DTO/IPC客户端
  → Agent身份网关
  → IBudgetedWorldQueryService（先扣操作点）
  → 结构化Intent校验
  → 与Human/RuleAI相同的Application命令
```

接入要求：

- 第一个实现应是确定性Mock，不直接连接真实模型；
- DTO必须包含协议版本、请求ID、Agent/玩家身份、超时与取消；
- 操作点由游戏进程内可信服务强制扣除，模型返回内容不能修改余额；
- 查询范围和字段粒度决定成本；空结果仍是成功且消耗已经发生；
- 大模型不能取得Debug会话、Godot Node、数据库直连或隐藏战场快照；
- 命令同步回执和后续事件还要经过Agent反馈策略过滤，不默认全部返回模型；
- 外部调用必须具备超时、取消、重试上限、限流、日志和安全降级；
- HTTP、WebSocket、stdio或其他IPC需根据部署方案另写ADR。

测试接入点优先使用Core接口的内存实现和确定性观察仓库；需要Godot集成时，在新的Agent Gateway测试场景中由组合根签发专用`QuerySourceKind.Agent`会话，不得调用`GetDebugSessionForTests`。

## 14. Debug与Release构建差异

### Debug

- 允许自动测试取得标准会话和全知测试会话；
- 允许测试把己方Node转换为稳定实体引用；
- 可启用God Mode、诊断UI及测试探针；
- 这些能力只能用于开发与测试。

### Release

- `GetStandardSessionForTests`和`GetDebugSessionForTests`返回空字符串；
- `GetOwnEntityReferenceForTests`返回空字典；
- 不创建`OmniscientDebug`授权；
- 正式Human、RuleAI、Agent必须通过组合根的正式身份装配。

任何依赖测试API才能工作的功能都不满足交付条件。每个涉及查询、安全边界或条件编译的修改必须单独执行Release构建。

## 15. 测试与提交检查清单

最低要求：

1. C#类型、功能方法、枚举项和重要字段具有中文XML注释；
2. `if/for/foreach/while`等控制语句始终使用大括号；
3. `dotnet build OpenRTS.csproj --configuration Debug`；
4. 相关Core测试及Godot场景通过；
5. `tools/audit_core_engine_boundary.ps1`；
6. `tools/audit_legacy_gdscript_authority.ps1`；
7. `git diff --check`；
8. 修改场景时检查Node名、组、Signal、C#导出属性名及UID；
9. 高风险或交付前运行`tools/run_full_regression.ps1`；
10. 更新需求/缺陷、接口、测试和验收文档。

完整手动功能入口见《程序重构_手动功能验收清单.md》，完整自动套件说明见《程序重构_完整功能回归套件.md》。
