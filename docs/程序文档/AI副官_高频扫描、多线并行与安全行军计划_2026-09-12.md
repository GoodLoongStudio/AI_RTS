## 2. 目标和不可变约束

必须同时满足：

1. 紧凑状态与新增事件的实时扫描约 10Hz；
2. 五条线路采用随规模和负载调整的协调与控制节拍：常规以约 2Hz 为参考，大规模战场允许约 2 秒一轮（0.5Hz），包括常规协调和变化意图的批量下发，不强制内部协调仍达到 2Hz。验收以多线并发、部队持续执行、生产及时接续和关键事件响应为主；只发变化意图，不要求每个单位每轮收到新命令。轻量扫描与游戏侧任务执行保持独立，紧急事件应能提前唤醒协调，不能为了固定频率重复下令或拖垮权威端。（用户于 2026-09-13 明确调整，覆盖旧频率硬指标。）
3. MiniCPM5-2B 仍是唯一在途决策模型。模型低频做战略分支、目标、优先级和参数，不能阻塞实时扫描、规则地板、行为树或已有任务；
4. 规则中台常驻运行，模型关闭、超时、空输出、非法输出或冷却时，采集、建造、生产、防御、侦察和已批准战斗任务仍继续；
5. 所有候选都进入同一个仲裁和 Godot 权威入口，区分 `origin=baseline|model|behavior_tree`；
6. 主力移动必须有侦察确认、有效导航路径和安全中继点；没有这些证据时只能集结、守卫、回基地或等待；
7. “5 万初始经济快速发展”只是压力场景，用来观察并发和衔接是否真实提升，不得把它当成只调生产规则的目标；
8. 任何完成结论都必须区分代码推断、日志证据、截图证据和真实游戏结果。

禁止：增加第二个模型、让扫描线程直接写 LangGraph 状态、10Hz 重拉完整 tactical 视图、重复发送仍在执行的任务、用 `attack_move` 掩盖没有路线验证、用 `Accepted` 或“生成了计划”代替实际完成。

## 3. 三个节拍和线程边界

### 3.1 实时扫描层：10Hz

每 100ms 读取缓存型快速状态和事件增量，至少包含：

```json
{
  "server_tick": 0,
  "sampled_at": 0.0,
  "snapshot_id": 0,
  "event_seq": 0,
  "map_bounds": [0, 0],
  "nav_revision": 0,
  "units": [],
  "visible_enemies": [],
  "production": [],
  "receipt_deltas": [],
  "task_deltas": []
}
```

Godot 游戏循环维护缓存；查询直接复制最近快照和自上次 `event_seq` 之后的增量，不在每次请求里遍历并序列化完整场景。快照必须带真实游戏 tick 和采样时间。runner 只在扫描线程更新一个有界、可丢弃旧值的快照队列；事件按序号去重，不能因旧事件阻塞新事件。

扫描层可以更新任务进度、路径状态、到达/受击/生产回执和行为树执行输入，但不能调用模型、读取完整战略视图或直接写 LangGraph checkpoint。

### 3.2 协调层：常规约 2Hz，大规模允许约 2 秒一轮

由单一协调写入者按当前选定节拍消费最新快照和事件：常规约 500ms，大规模可放宽到约 2 秒一轮。记录选定周期、实际周期、单位规模和调整原因。轻量扫描持续缓存新增事件，游戏侧已有任务持续执行；关键事件可提前唤醒协调，不等待下一次常规周期。每轮各线路都获得处理机会，只下发变化意图，按顺序执行：

```text
observe_fast_delta
-> update_task_progress
-> advance_campaign_and_decision_map
-> run_baseline_policy
-> keep_active_tasks
-> collect_model_patch_if_ready
-> reconcile_and_arbitrate
-> batch_dispatch_changed_intents
-> checkpoint_and_metrics
```

规则地板和已有任务不以模型结果为门控。每条线路每周期至少获得一次处理机会；紧急线可抢占当前提交，但要有老化上限和轮转，不能永久饿死经济、建造或侦察。完整规则/战略视图只在协调层按需读取，不进入 10Hz 路径。

LangGraph 状态采用单写者原则。模型线程只能把带请求 ID、快照 ID、代代号、策略版本和 TTL 的结果放入线程安全结果队列；协调层校验新鲜度、权限和冲突后才合并。

### 3.3 模型层：低频、单一在途

沿用 `ThreadPoolExecutor(max_workers=1)` 或等价单飞行调度器。模型只输出四列稀疏 patch：未提及的单位和战略线继续沿用规则或有效任务；空批次、超时、非法、过期、关闭和冷却都不能清空 baseline。模型请求不能因为取消客户端等待就无限积压。

## 4. 快速状态和增量事件接口

优先新增或复用 `op=adjutant_fast_state`。接口应返回上一节的最小字段，并支持 `since_event_seq`；若暂时无法实现所有事件，先保证命令回执、生产变化、受击、路径失败、单位到达和任务状态有递增序号，缺失项明确标记为未知。

Godot 端要求：

- 在权威游戏循环维护快照缓存，不在 TCP 请求回调里重复扫描完整场景；
- `snapshot_id` 随状态采样递增，`event_seq` 对事件全局递增；
- `map_bounds` 和 `nav_revision` 来自权威端；无效值不得被 Python 猜测替代；
- 回执至少能区分 `Accepted`、`Rejected`、`Expired`、`PathFailed`、`Effective`、`Completed`、`Blocked`；
- 任务事件携带 `task_id/unit_id/request_id/decision_generation`，完成和失败必须有证据字段；
- 保留已有完整 `rules/strategic/tactical` 接口供低频诊断和回放使用。

## 5. 五条独立线路和批量仲裁

协调器建立以下独立队列和统计：

```text
economy  采集、工人数、资源均衡
build    工地派人、建筑依赖、扩张落点
scout    侦察、可见性、路径探路
military 集结、护送、作战、撤退
urgent   受袭、路径失败、玩家接管等紧急事件
```

每条线路维护当前任务、下次到期、重试退避、最后处理 tick 和饿死时间。统一仲裁执行权限、代际、预留、TTL、玩家接管、资源承诺和目标冲突检查。只提交与上次权威状态相比发生变化的意图；仍处于 `Running/Effective` 的任务不得重发。

优先使用现有批量意图接口一次提交多个线路的变化命令。批量传输不等于批量成功：权威端必须逐项回执，日志保留每项 `accepted/rejected/effective/completed/failed` 及原因。生产和建造的资源扣除继续走原子权威逻辑，不能因为批量请求合并而重复扣款。

## 6. 长期主线和决策地图

保留并扩展已有 `campaign_state`、`active_plan`、`PlanStore` 和 checkpoint，不新建平行战略系统。每局开局由程序根据地图、资源、建筑能力和决策地图建立默认主线：

```text
摸底 -> 立足 -> 扩张 -> 施压 -> 收束
```

主线至少包含主基地稳定、产能建筑、首支作战队、扩张候选/第二基地或分矿、持续防守/施压里程碑；每个里程碑有前置、成功证据、失败原因、重试退避和退出条件。`economy/build/scout/military` 四条线绑定当前主线，紧急事件压入 `interrupt_stack`，处理后回到原恢复点。模型只选择或修改候选分支，不负责每轮重新发明整局计划。

## 7. 安全移动硬闸门

禁止继续以“基地坐标 + 罗盘方向 + 半径”作为主力移动依据。固定流程：

```text
侦察单位探路
-> 权威导航查询得到路径
-> 评估威胁和地图边界
-> 生成安全中继点
-> 侦察确认
-> 主力按小队推进
-> 到达由观测确认
-> 重新观测并规划下一跳
```

优先调用项目已有 `NavigationServer3D`、`Navigation.gd`、`TerrainNavigation.gd` 和现有移动接口；必要时增加只读路径查询，不在 Python 伪造“安全路线”。以下任一条件不满足，主力不得野外移动：

- `map_bounds` 缺失、非法或坐标系未确认；
- 没有权威导航路径或路径版本已过期；
- 没有安全中继点或侦察确认；
- 单位属于工人、建造者、基地或其他重要保护对象；
- 敌情出现、路径失败或侦察确认丢失后尚未重规划。

主力使用稳定小队和中继点，不让单位各自散开。每个移动任务记录 `route_id/nav_revision/waypoints/route_length/threat_score/scout_confirmation/retreat_point/last_replan_tick`。遇敌、受阻或路径失败立即停止当前推进并把事件送入 `urgent`；不得用 `attack_move` 绕过检查。到达只表示移动段完成，不自动表示侦察、防守或攻击任务完成。

## 8. 实施阶段和完成条件

按以下顺序实施，每一阶段通过后自动进入下一阶段：

### P0：快速链路和埋点

- 实现 `adjutant_fast_state` 缓存/增量接口；
- runner 拆出约 10Hz 轻量扫描和自适应协调（常规约 2Hz，大规模允许约 2 秒一轮）；
- 补快照年龄、扫描/协调频率、事件延迟和三级命令时间戳；
- 本地测试覆盖无模型、模型超时、空输出和非法输出时规则仍运行。

完成条件：扫描平均频率接近 10Hz；协调周期符合记录的规模与负载策略，大规模约 2 秒一轮可以通过，不因低于 2Hz 单独判失败。必须用真实行为证明多线并发、生产接续、模型等待期间任务不断线和关键事件及时处理；无完整场景 10Hz 重序列化。

### P1：多线调度和批量权威闭环

- 五条线路独立队列、轮转和饿死保护；
- `_dispatch` 使用批量意图入口，逐项保留权威回执；
- 只提交变化命令，清理重复发送和 `LedgerFull` 型无效重试；
- 生命周期双侧记录和 checkpoint。

完成条件：五条线路在有任务时均有处理机会；Accepted、Rejected、Effective、Completed 可追踪到同一任务；模型异常不清空 baseline。

### P2：安全移动

- 接入权威导航路径和 `nav_revision`；
- 实现侦察先行、安全中继点、小队推进、到达后重观测；
- 对无边界、无路径、无中继点、重要单位和敌情变化加硬拒绝；
- 保留 `attack_move` 仅作为已验证路径上的执行动作。

完成条件：没有有效路径的主力移动数为 0；侦察先行覆盖率、遇敌停止/重规划延迟和地图越界次数可统计。

### P3：主线与决策地图

- 开局创建可执行 campaign；
- 规则地板在模型关闭时推进产能、兵力和扩张候选；
- 紧急任务完成后恢复主线和各线路未完成任务。

完成条件：无模型对局出现产能建筑、兵力增长和扩张候选；满足前置后实际完成第二基地/分矿或给出权威阻塞证据。

## 9. 短局自循环验证协议

DeepSeek 每次改动都必须自行循环，不等待用户再次说“继续”，也不能开一局后静置十分钟：

1. 先做静态检查和针对性自动测试；
2. 启动独立 `run_id` 的 30 秒短局；
3. 在 0、5、15、30 秒保存截图，同时读取快速状态、增量回执、任务进度和错误日志；
4. 发现异常立即停当前短局，定位根因，修改后重新开 30 秒；
5. 连续三次短局达到门槛后再跑 90 秒；
6. 最后才跑 3～5 分钟集成局；
7. 每局记录代码版本、地图、种子、端口、参数、控制器、模型模式和起止时间；
8. 发展期不开电脑 AI 敌人；战斗使用固定脚本波次并单独标记证据类型。

每一轮报告至少包含：快照频率和年龄 `p50/p95/max`、协调频率/耗时、各线路处理次数、多线同时活跃数、真实 Accepted/s、任务完成率、Rejected 原因、批量提交效果、地图越界数、无路径移动数、侦察先行覆盖率、遇敌停止/重规划延迟，以及截图和真实游戏行为。明确标注“代码推断 / 日志证据 / 截图证据 / 真实游戏结果 / 尚未验证”。

大规模验收额外记录单位与编队数量、选定与实际控制周期、各线最长未处理时间、生产设施满足资源/人口/依赖条件时的空转时间、生产完成到下一项入队的延迟，以及多个编队和生产设施同时工作的时间线。生产空闲须区分无资源、无人口、依赖未满足、策略主动保留与调度漏处理；持续执行的长任务无需反复下令。Accepted/s 和任务计数只作诊断，不能代替这些行为证据。
