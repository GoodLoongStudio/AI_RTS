## 2. 推荐最终目录

以下是迁移目标，不是要求马上整体改名。AI_RTS 原路径保留，减少编辑器、脚本和会话失效。

```text
G:/AIRTS/
├─ AI_RTS/               唯一游戏源码仓库
├─ runtime/              固定版本引擎、按用途隔离的 Python 环境、开发推理运行时
├─ asset-library/        商用源包、音频原件、素材授权、转换源文件
├─ artifacts/            所有生成结果，按用途分区
│  ├─ runs/              日期/任务/run_id：日志、截图、指标
│  ├─ mapgen/            地图生成中间结果
│  ├─ datasets/          审核后的训练数据及来源清单
│  ├─ models/            模型版本、checkpoint、评估结果
│  └─ scratch/           可过期删除的临时输出
├─ releases/             版本化发布包与校验清单
│  ├─ v0.4/
│  └─ v0.3/              暂保留一个可用回滚版本
├─ archive/              唯一旧改动、旧仓库、历史设计、参考工程
└─ skill.md              极短工作区导航，指向主仓库当前规范
```

编辑器要求固定位置的 .vscode/.codebuddy/.cursor/.workbuddy 等隐藏配置继续保留，不为“目录数量少”强行搬走。服务器信息.md 不并入公开仓库或发布包；本次只确认其位置，没有读取内容。

引擎从 godot_mono_471 迁到 runtime/engine 前必须先改配置；第一阶段可以保留原路径，因此目标结构需要分阶段达到。虚拟环境不能仅剪切后假定可用，应从依赖清单重建并验证。

主仓库保持 Godot 约定文件在根目录：project.godot、csproj/sln、global.json、export_presets.cfg、图标及其导入元数据、README、LICENSE 等。第一轮不移动 source 下的场景和脚本，避免引入大量 res:// 路径和 UID 变化。

## 3. 具体合并与清理

### 3.1 发布目录：六套收敛到当前版、回滚版、共享运行包

- 将六个 release_* 入口统一到 releases/版本，发布注记与完整分卷同目录。
- v2、三套 release_assets 及临时文件夹/release_assets 合计约 24.68 GiB，是主要退役候选，不代表可无条件删除。
- 暂保留 v4 与 v3；核实游戏包、模型、运行环境的兼容关系和离线启动后，再退役旧版。
- 先检查完整压缩包可解压、各分卷齐全、SHA-256、版本说明和远端备份可恢复性。不得按分卷名称单独删除一卷。
- 游戏包与大型运行时按独立版本发布；相同运行时只留一个物理副本，由 manifest 指定依赖，不因每个游戏版本重新保存全部模型。
- 已发现 tools/release/pack.ps1 固定写到 release_v4，upload.py 默认使用 release_assets_gpu，update_body.py 指向临时文件夹/release_assets。三个脚本先统一参数与 manifest，再迁目录。仅移动文件夹会让下次打包重新生成旧目录。

重要：release_v2/AI_RTS_Demo 和 release_v3/AI_RTS_Demo 都是指向 G:/AIRTS/AI_RTS/build 的 Junction。它们不是两份旧版本的解压快照，也不能拿来验证 v2/v3 的真实内容。计算空间不能加两次，任何清理工具都必须跳过链接目标。

### 3.2 地图工具：代码收敛到 AI_RTS/tools/mapgen

逐文件内容比较（排除 Python 缓存）结果：

| 区域 | 旧工具文件数 | 主仓库文件数 | 同名且内容相同 | 同名但不同 |
|---|---:|---:|---:|---:|
| rtsmap | 51 | 55 | 30 | 21 |
| tools | 119 | 126 | 91 | 27 |
| tests | 12 | 14 | 8 | 4 |
| docs 对比主仓库 docs/mapgen | 85 | 85 | 84 | 0 |

文档两边各有一个仅在本侧出现的文件；旧工具 tools 的唯一额外项是 check_ai_rts_nav.log。因此合并基础已经很充分，但内容不同的文件不能直接覆盖，且 RTS_Map_Tool 当前还有未提交改动。

做法：保存旧工具 Git 状态和工作树差异，逐项判定主仓库是否已包含其有效逻辑；保留旧仓库唯一改动的可恢复快照；以主仓库版本为入口验证地图工作台、生成、导出、游戏加载后，再归档/退役旧工作目录。

优先处理 RTS_Map_Tool/review 的 10.36 GiB，其中 G4 约 10.09 GiB，多份 map.tscn 单个 0.47–0.72 GiB。保留最终通过版本、关键失败样本、生成参数、种子、代码版本和截图。其他中间地图只有确认可复现后才能清除。不能以“有种子”替代可复现验证，旧生成代码和素材也可能已变化。

### 3.3 tmp_logs、output、review：按内容合并，不按目录名删除

- 普通运行日志、截图、JSON 指标统一到 artifacts/runs/日期/任务/run_id。
- tmp_wb_matrix_out、tmp_wb_probe_out、tmp_wb_smoke_out 归 mapgen 产物。
- ui_design 的有效设计归主仓库 docs 的相应主题；大图、渲染图归 artifacts；重复草稿归历史。
- 根 docs 的两份记录和根散落对局报告归主仓库历史文档，保留日期与来源。
- output 下的 deploy-seed、snapshot-verify、bare 仓库、bundle 先查唯一提交/未提交文件；有价值的保留恢复包，不能当图像输出一并丢弃。

明确保留的非垃圾：
- tmp_logs/selfplay/ft_v1、ft_v2 含两份各约 1.20 GiB 的模型权重；
- tmp_logs/langgraph_recon 含约 1.45 GiB 的 GGUF；
- tmp_logs/dcs 中有实际使用的控制脚本；
- logs 中可能有待审核训练样本、失败复现证据及唯一备份。

训练资产要独立登记：数据版本、teacher_source、标签质量、规则版本、地图/种子、基础模型、checkpoint、评估指标。先保留当前最佳 checkpoint、上一最佳 checkpoint、代表失败样本及数据来源，再制定其他轮次的保留策略；原始垃圾日志与训练数据不能混删。

### 3.4 临时文件夹：拆分后取消这个总入口

- 96套（3.31 GiB）、初选素材包（2.77 GiB）：进入 asset-library，源包和授权资料保留。已导入游戏的精简运行素材继续在 AI_RTS/assets。
- archify、Kitbash_Command、openyrweb-reference、godot-ai-repo：按是否有独立开发价值归 archive/reference 或保留独立工程，不把它们源代码混入游戏。
- airts_agent_venv（4.42 GiB）、airts_laya_venv（4.40 GiB）、laya_venv 与 laya_probe_venv（各约 0.79 GiB）：比较 Python 版本、依赖及 CUDA/Torch 兼容性，再重建必要环境。建议保留训练、推理、地图生成所需的最少集合；不能强行共用一个环境。

### 3.5 AI_RTS_verify：损坏的旧 worktree 指针，先救唯一文件

它约 0.033 GiB，.git 指向 AI_RTS/.git/worktrees/AI_RTS_verify，但 git status 报该位置不是仓库；主仓库 worktree list 也只列出当前主目录。不能靠 git status 无输出误判它干净。

逐文件比较并保留未迁移内容后才退役。Git bundle 只能保存可达 Git 对象，不能单独保存这里的未提交/未跟踪文件。若属于应用托管 worktree，执行时使用应用归档流程；不能仅因名称带 verify 就递归删除。

### 3.6 主仓库内部：去生成物，保留测试能力

确认 Git 当前跟踪了：
- 58 个 .log 文件；
- 16 个 tests/perfgrid/.regress_state 标记；
- 201 个 source/adjutant_coordinator/logs 下的文件；
- 1273 个 tools/mapgen/review、tmp_logs、workbench_output 下的文件。
这些数字存在分类重叠，不能相加当总数；其中有些可能是正式夹具，要逐项识别。

把正式回归夹具移到明确 fixtures；历史证据移归档；可再生结果退出 Git 跟踪并补忽略规则。只修改 .gitignore 不会取消已跟踪文件。

工具建议按用途集中：
- tools/release：构建、打包与发布；
- tools/mapgen：地图工作台；
- tools/qa：诊断、截图和回归编排；
- tools/assets：素材处理脚本；
- tools/training：训练入口与数据审计编排。
dev 与根 tools 的有效脚本按用途归入上述位置；Python 包内部必须的模块留原包，不为目录好看破坏 import。临时 run_chain/finish/recapture 等脚本逐项归纳成有参数的统一入口，不把不同语义脚本简单拼接。

仓库根的验收截图归媒体/证据目录；临时 gd/tscn 成对保留有用诊断或退役。关联 .uid/.import 必须一起核查，不可批量把它们当缓存删。

music 下原始音频与 assets/music/user 的运行副本用途不同：代码注释已明确原件/运行副本关系。可将原件归 asset-library，保留来源映射；不要因文件名不同就留两套混乱入口，也不要删掉唯一原始文件。

Godot/app_userdata 可能是用户设置、成长与对局记录，不等同 shader cache；.godot 的 imported/mono 可以重建，但先保存需保留的编辑器状态，并在引擎关闭后操作。.git 尤其 LFS 对象不能手动删；本轮不建议改写历史或清空 LFS。根 Godot 扫描未发现普通文件，不应误认成第二套占空间的引擎。

## 4. 文档合并：按主题维护现状，按日期保留证据

当前主仓库 docs 有 293 个文件，程序文档 69、plan 87、mapgen 85。建议保留中文策划/程序文档主分类，并在分类下组织主题；现有统一规范规定了目录布局，执行时同步更新规范与索引，不能只搬文件。

每个活跃主题只保留三个当前入口：
1. 当前设计：目标、规则、职责及确定的决策。
2. 当前任务：未完成项、优先级、具体验收。
3. 当前进度：已验证内容、运行版本、证据地址。

历史提示词、阶段报告和交接稿放该主题历史目录，保留日期与原始证据，不揉成一篇超长“最终版”。现存旧入口应保留跳转并明确被哪个文档替代。工作区 skill.md 目前混有冻结副官、旧分支等陈旧信息，应缩成导航，避免继续复制规则。

## 5. 预计收益与执行顺序

可以争取释放约 25–40 GiB，但这是“旧版退役 + 地图中间产物筛选 + 环境去重”的条件估算，不是已经确认可删除空间。日志/模型/素材/当前 build 不计为一键可删。

分批执行：
1. 清单：源路径、拟处置、目标、大小、引用、Git 状态、链接目标、是否运行中、保留理由、校验值。
2. 低风险去重：哈希完全相同的发布文件；完整分卷作为整体处理，先保留一套可用包。
3. 文档和普通产物归位：先改输出入口，再迁旧文件，避免重新生成旧目录。
4. 地图工具差异合并：测试生成/导出/游戏加载后，收掉旧工具工程。
5. 环境收敛：记录依赖并重建；把有效训练数据、模型从日志区迁出来。
6. 主仓库跟踪清理：区分正式 fixtures 与生成物，完成构建、相关测试和发布启动验证。
7. 稳定观察期后处理可删除项，核实实际释放空间及没有新增散落目录。

当前有 Godot、Ollama 和 llama-server 正在运行，后两者使用 AI_RTS/build/adjutant_runtime；主仓库与地图仓库都有未提交改动。正式迁移应选相关任务结束的时间窗口，保留当时工作状态；不得通过按进程名批量杀进程、git clean/reset、递归追随 Junction 来实现清理。

建议未来写入规则：源文件只进主仓库，原素材只进素材库，模型/训练数据只进专用区，生成结果必须带任务与 run_id，发布只进版本目录。清理入口先输出 dry-run 清单，执行后保留迁移映射和回退记录。这样这次整理后才能持续保持整洁。
