# AI RTS 完整检查与下一步优化建议（2026-09-27）

## 结论

当前项目已进入可运行原型阶段，但还没有达到设计预期的可交付状态。无工人自动施工、散矿几何、耗尽后周期再生、矿场交付和空间网格索敌都已进入代码；问题是这些功能尚未全部形成稳定的真实对局闭环。最优先的阻塞点是单位缩放后的几何契约不一致、混战帧时仍超预算、规则 AI 建筑选址被拒绝，以及副官 UI 与真实运行状态不一致。

## 已确认有效的部分

- config/balance/demo.balance.v1.json:559-664 的建筑配置支持 constructionProgressSource=automatic 和 automaticWorkPerTick=1；Ra3Sidebar.gd:795-808 按配置决定是否需要工人。
- ResourceUnit.gd:75-110 保留矿点实体和容量；ResourceRegeneration.gd:37-82 只在权威物理帧推进。当前配置为 90 秒后恢复 1500，恢复进入矿点，不直接加玩家账户。
- ResourceA.tscn/ResourceB.tscn 已使用核心、碎块和小石块组成散矿表现。
- 最新 recheck2_ore-refinery.out 显示 0 failure，记录了 3 次、合计 1200 矿的交付。这证明受控链路成立，但还不能证明普通地图的完整经济闭环。
- TargetAcquisitionGrid.gd:125-151、WaitingForTargets.gd:114-129 和 GroundAttackMoving.gd:102-124 已接入空间候选索敌，并保留了对照开关。

## 当前阻塞问题

### 1. 单位缩放后的几何契约未收口（P0）

MatchConstants.gd:110-123 的地面/空中 MAX_AGENT_RADIUS 仍为 0.9，注释却承认运输车等单位半径已达到 2.8m。部分场景的根半径、Movement/MovementObstacle 半径、导航网格和 footprint 也不是同一份数据。

证据：

- clipcheck_battle.out 在 204 单位混战中反复出现 Unit radius exceeds the established limit。
- MovementScaleSmokeTest 当前记录 8 个失败：n=50 到达率 0.840；n=100 到达率 0.700；n=200 到达率 0.245、112 个假 Unreachable。
- rule-ai-battlegroup、rule-ai-offense-logistics 和结构放置回归仍触发 navmesh agent_radius 断言。

这会同时破坏寻路、编队间距、建筑选址和性能数据。应建立单位空间规格单一来源，统一视觉包围盒、根 radius、Movement/NavigationAgent3D、MovementObstacle、放置判定、navmesh agent 半径和建筑 footprint。不要只把 navmesh 常量盲目改成 2.8，应先决定最大单位烘焙、分层导航还是局部避让，并重新测量烘焙预算。

### 2. 混战性能仍未达标（P0）

最新 G:/AIRTS/tmp_logs/clipcheck/clipcheck_battle.json：

- 204 个单位，平均 FPS 16.03，1% low 4.15；
- P50 48.83ms，P95 165.88ms，P99 227.86ms；
- attack-move 末帧仍有 24 个，平均 stuck ratio 0.875，unreachable 24；
- 网格索敌为 1852 次查询、46039 个候选、97ms 累计，索引维护 30ms。

g4battle200 矩阵各版本平均 FPS 约 11.8–15.8，1% low 约 2.4–3.2；g4idle400 约 37.5 FPS，说明待机索敌改善有效，混战主瓶颈已转移到移动/避障/导航/攻击结算/观察同步。Godot 官方建议按帧时和函数占比定位真正瓶颈，而不是继续优化已经下降的局部计数（https://docs.godotengine.org/en/stable/tutorials/performance/cpu_optimization.html）。

下一轮先对 Movement/Navigation、局部避让、攻击与投射物、Fog of War、观察快照分别计时；固定 204 单位，无副官与无渲染截图做 CPU 基线，再一次只改一个区。建议目标先定为 P95 <33ms、P99 <50ms。

### 3. 经济闭环缺普通对局证据（P1）

90 秒/1500 的再生可能让玩家很难感知“散矿可再生”。普通地图需要显示矿点余量、耗尽/再生中/可采状态、倒计时、矿场占用工人数和工人状态。应补固定种子 10 分钟真实局：两个矿场、三名以上工人、一次耗尽和一次再生，验证账户收入、矿点库存、再分配和守恒。受控 smoke 不能代替这条验收。

### 4. 规则 AI 和副官有“能说、不能执行”的断层（P1）

recheck3_rule-ai-offense-logistics.out 仍有两项失败：生产建筑放置被 NotVisible/SurfaceNotBuildable 或 Occupied 拒绝。recheck3_adjutant-command-protocol.out 的 build 因 Occupied 被拒绝并伴随 AccessViolation。rule-ai-expansion 虽报告 0 failure，日志仍有放置拒绝，不能只看 marker。

回归 results.json 混有 3 个 fresh fail、33 个 fail_cached、65 个 skipped_done，不能当作干净全量结论。规则 AI 和副官应采用“接受、状态变化、最终完成”三段证据；建筑命令必须使用权威选址器返回的合法点。build/produce/move/attack 各跑 20 次，目标接受率 ≥95%，零 AccessViolation。

AICommandHUD.gd:490-530 仍有本地关键词解析和固定回答作为兜底。应在 UI 明确区分本地规则模式和外部副官模式，避免标题显示外部进程运行而状态卡显示副官尚未启动。

### 5. UI 影响可读性和操作判断（P1）

clipcheck_battle_shot1.png 与 g4battle200_A_r3_20260927_shot2.png 显示：

- 左上副官区、底部对话区和右侧生产栏占据大量屏幕；
- 棕色迷雾/地形压低战区对比度，单位关系不易读；
- Ra3Sidebar.gd 多处局部字号为 10–13px，绕过 SystemUIStyle 的 16px 通用字号；
- Ra3Sidebar.gd:694 仍写“点击后由工人前往建造”，与自动施工配置矛盾；
- 副官标题、状态卡、聊天和小地图没有统一说明当前是否需要确认。

优先修正自动/工人施工文案、关键文字字号（至少 14px，重要数值 18px）、颜色之外的图标/形状提示，并把副官面板改成可收起的窄状态条。

## 下一轮顺序

1. 收口半径、footprint、navmesh、避让的一致性，先让 MovementScale、UnitRadius、AI placement、Battlegroup 连续三次通过。
2. 做混战分区计时，先修 24 个 unreachable 和 stuck ratio 0.875。
3. 用固定种子真实局验证自动施工、矿场交付、耗尽、等待、再生、重新采集。
4. 修规则 AI 权威选址和副官命令闭环，清掉 AccessViolation。
5. 收口 HUD 语义、字号、状态一致性和遮挡。
6. 最后才做模型训练和循环迭代：每轮只改变一个策略变量，记录 snapshot、command_id、完成率、失败原因、资源效率、战损和响应延迟。规则地板必须常驻，不能变成模型失败后的 fallback。

## 建议交付门槛

- 200 单位真实混战 P95 ≤33ms、P99 ≤50ms，unreachable ≤2%，连续 3 次；
- 100/200 单位移动到达率 ≥95%，假 Unreachable ≤2%；
- 5 类建筑各 3 次零工人自动施工全部完成；
- 两个矿场、三名工人、一次耗尽和一次再生，账户与矿点库存守恒；
- 副官 build/produce/move/attack 各 20 次，接受率 ≥95%，零 AccessViolation；
- 关键 UI 文本 ≥14px，自动施工文案与配置一致；
- 清除回归缓存后再报告 fresh failures 与历史 failures。
