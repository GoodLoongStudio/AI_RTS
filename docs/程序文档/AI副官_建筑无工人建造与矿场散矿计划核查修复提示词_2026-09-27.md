你负责核查并修复 `G:\AIRTS\AI_RTS` 中一个新的结构性问题：

1. 产品设计曾要求建筑放置/建造不依赖工人持续施工；

## 二、不要混淆四个概念

必须把下列概念拆开验收：

1. **建筑放置**：找到合法位置、扣款并生成施工现场；
2. **建筑施工进度**：施工现场如何从 0 增加到完成；
3. **矿场运营**：矿场完成后如何管理附近矿点、工人、服务半径和交货点；
4. **散矿地图布局**：地图上是否存在多个可达、分布合理、具有经济价值的远端矿点。

“矿场自动指派工人”只能说明第 3 项的一部分；“第二基地建成”只能说明第 1、2 项的一部分；任何一项都不能替代另外三项。

## 四、确定并实现目标语义

当前用户需求按以下优先级解释，除非历史证据证明范围不同：

### 1. 建筑施工默认不占用 Worker

建筑放置成功后，建筑施工进度应由权威施工系统自动推进，不再要求 Worker 作为施工进度来源，也不应把采矿 Worker 拉去工地。

必须保留：

- 玩家权限、预算、落点、视野、建筑能力、重复放置和取消退款校验；
- 建筑施工阶段、完工事件、半透明表现、导航障碍和生产解锁；
- 施工失败、被摧毁、取消和断线的权威状态；
- 玩家对工人的正常采集与手动控制。

不要简单地把 `RequiredWork` 设为 0 或把建筑直接标记完成。应明确一个可配置的 `construction_progress_source`，例如：

- `automatic`: 放置后按模拟 Tick 自动施工；
- `worker`: 旧兼容建筑仍由 Worker 施工；
- `hybrid`: 建筑自动施工，Worker 只能提供加速，而不是硬前置。

若当前产品范围要求“所有建筑都不需要 Worker”，就以 `automatic` 为默认，并把旧 Worker 施工降级为兼容接口；若只有部分建筑适用，必须在平衡/资产配置中逐类声明，不能按名称硬编码。

### 2. 矿场是独立经济建筑

矿场本身的建造应遵循上面的建筑施工规则，不应为了建矿场抢走采矿 Worker。矿场完工后才进入运营阶段：

- 选择服务半径内可达且有剩余资源的矿点；
- 维护矿场容量和 Worker 占用账；
- 只接管没有玩家订单、没有施工、没有高优先级军事任务的 Worker；
- Worker 到位后自动采集并回矿场交货；
- 矿点耗尽、矿场被摧毁、路径失败或玩家接管后有明确恢复分支；
- 多座矿场之间不能重复占用同一个 Worker；
- 矿场运行指标必须有实际收入、交付和资源点消耗证据。

### 3. “散矿”必须是地图与运行时的联合计划

不能只在地图文件里放几个 Resource 节点，也不能只在规则层写“去远端矿点”。需要同时验证：

- 主基地附近基础矿；
- 远端扩张矿；
- 侧翼/共享矿；
- 中央或高风险矿；
- 各资源点之间的路径距离、可达性、容量和竞争关系；
- 矿场服务半径与矿点布局相匹配；
- 远端矿被发现后能触发矿场候选，而不是只触发第二基地；
- 没有远端矿或不可达时能给出明确阻塞证据，不在基地旁反复建假矿场。

## 五、实施顺序

按下面顺序推进，不能一口气重写经济、地图和副官：

### 阶段 0：只读核查

交付设计血缘表、代码调用图和断点证据。确认哪些内容“有计划未实现”、哪些内容“已有实现但未接入”、哪些内容“设计冲突”。

### 阶段 1：确定性施工闭环

关闭模型和副官高层选择，使用固定地图和固定平衡配置验证：

1. 不分配 Worker，放置一座兵营；
2. 施工进度自动增长；
3. 建筑完工并解锁生产；
4. 采矿 Worker 不被施工占用；
5. 玩家手动取消获得正确退款；
6. 建筑被摧毁、断线、重载和联机同步不出现幽灵施工现场。

如果产品设计实际要求混合模式，额外验证 Worker 加速只改变速度，不改变能否开工。

### 阶段 2：矿场闭环

在远端矿点旁放置矿场，不分配施工 Worker，等待其自动完工。随后验证：

1. 矿场只接管合资格空闲 Worker；
2. Worker 到达服务半径内矿点；
3. Worker 实际采集；
4. 资源实际回到矿场账户；
5. 同一矿场不超过容量；
6. 两座矿场不重复抢同一 Worker；
7. 显式订单、玩家接管和施工任务优先；
8. 矿点耗尽后能换点或结束任务；
9. 矿场被摧毁后 Worker 能恢复到合法默认任务。

### 阶段 3：主线接入

把矿场纳入 `campaign` 和主线：

- M04 扩张选址要区分“远端矿点可用”和“第二基地候选”；
- M05 不得只以第二座指挥中心作为“分基地/分矿”完成证据；
- 应新增可独立完成的矿场里程碑，例如“矿场完工 + 至少一名 Worker 实际交付”；
- `BUILD_LADDER`、模型候选、自动降级和恢复都必须能到达矿场分支；
- `produce_first`、施工串行和主攻门槛不能把矿场分支永久挡死；
- 没有合法远端矿时不发矿场命令，并记录具体原因。

### 阶段 4：散矿地图闭环

选至少 3 个固定地图/种子，检查资源布局、路径和矿场服务半径。记录每家的主矿、扩张矿、侧翼矿、中央矿数量、距离和可达性。地图布局失败时不要用规则阈值掩盖。

本阶段同时完成第八节的散矿素材替换和周期再生，在正常游戏入口验证“采集 → 耗尽 → 等待 → 再生 → 重新采集 → 交付”。

### 阶段 5：模型与循环训练

在确定性施工和矿场闭环通过后，才重新打开 Laya/2B。训练循环必须遵循：

```text
固定地图/配置/种子
→ 自对局采集
→ 审计建筑施工、矿场、散矿标签和结果
→ 隔离没有结果证据的样本
→ 训练/微调
→ 固定评测集对照
→ 分析失败样本
→ 只改一个主要假设
→ 再采集、再训练、再评测
```

每条样本至少区分：

- 模型建议的建筑或矿场动作；
- 规则中台自动产生的动作；
- 权威接受的放置/施工/采矿命令；
- 实际完工、采集、交付、换点和资源增长结果；
- `teacher_source`、`label_quality` 和失败原因。

不要把“第二基地建成”自动标记成“矿场计划成功”，也不要把 `Accepted` 自动标记成“建筑已完成”或“矿场有效运营”。

## 六、必须新增的验收场景

至少新增并保留以下自动或半自动测试：

| 场景 | 必须证明 |
|---|---|
| 零工人建兵营 | 放置接受、施工自动推进、建成、无 Worker 被占用 |
| 零工人建车厂/炮塔 | 不依赖 Worker，生产或防御能力正常解锁 |
| 施工取消/退款 | 未完成建筑取消后状态、资源和占位正确 |
| 远端矿场 | 矿场在远端矿旁完工，不贴主基地假扩张 |
| 矿场自动运营 | Worker 实际到矿、采集、回矿场交付、资源增加 |
| 多矿场 | 工人不重复占用，容量受限，服务半径正确 |
| 矿点耗尽 | 停止无效采集并换点或结束 |
| 散矿素材 | 正常镜头下呈现贴地散布的矿块/矿簇，可辨识、可选中，采集路径不被装饰碰撞堵住 |
| 矿石再生 | 采空后按配置等待游戏时间再生，资源不超容量，暂停期间不偷跑 |
| 再生后恢复采集 | 矿场重新发现可采矿点并派合资格工人，实际交付增加；不抢玩家订单 |
| 再生同步与恢复 | 单机、联机及已有存档/重连路径保持资源量与再生时刻一致，不重复刷矿 |
| 玩家接管 | 矿场不抢玩家控制或显式高优先任务 |
| 分基地/分矿 | 第二基地、矿场和实际增收分别有证据 |
| 模型关闭/超时 | 施工和矿场基础链继续运行 |
| 模型开启 | 模型只改变合法策略，不破坏确定性闭环 |

真实对局至少使用固定 5 个筛查种子，并在候选修复版本上使用固定 10 局回归。报告逐局给出：

- 首座建筑放置、完工时间；
- Worker 被施工占用时长，目标应为 0（混合加速模式另报）；
- 首座矿场放置、完工时间；
- 首次矿场接管 Worker 时间；
- 首次矿场交付时间和资源增量；
- 每座矿场实际服务的矿点与 Worker 数；
- 矿点耗尽与再生时刻、再生数量、重新采集和交付的证据；
- 分基地是否完工；
- 建筑、矿场和 Worker 的失败/拒绝/中断原因；
- 模型开启相对关闭的差异。

## 七、完成标准

只有同时满足以下条件才能写“计划已实施”：

1. 能指出历史计划、后续覆盖和当前权威口径；
2. 建筑施工不再错误依赖 Worker，且权威端、规则 AI、副官和玩家入口语义一致；
3. 矿场不只是存在资产或类，而是能完工、接管工人、采矿、回矿场交付并产生资源；
4. 散矿在地图布局、路径可达性、矿场服务半径和运行时任务中形成完整链路；
5. 分基地和分矿的里程碑不再互相冒充；
6. 固定场景和多种子真实对局均有结果证据；
7. 完成至少一轮“采集—审计—训练/微调—评测—失败归因—再迭代”；
8. 关键能力没有因修复而退化：玩家控制、预算、权限、取消退款、战争迷雾、生产队列和战斗执行必须保持正确。
9. 散矿素材已在真实场景替换并完成可见检查，至少连续两次“耗尽—再生—重新采集—交付”闭环通过；矿量、画面和权威状态一致。

最终报告必须说明：

- 哪些计划真实存在；
- 哪些计划曾被其他口径覆盖；
- 哪些已经部分实现但没有接入主线；
- 哪个代码断点导致用户看不到效果；
- 修复前后同条件对照；
- 训练循环中每轮的数据和评测证据；
- 尚未验证或仍受环境限制的部分。

禁止用“有 `OreRefinery.gd`”“`BUILD_LADDER` 包含 `ore_refinery`”“命令 `Accepted`”“单元测试通过”替代真实的完工、采集、交付和资源增长证据。

## 八、补充必做：散矿素材与周期再生

### 8.1 矿石素材替换

“散矿”既指资源布局，也指矿石本身的视觉形态。将现有不符合设计的矿石模型改为贴地散布的小矿块、矿簇或矿带：同一片矿区有疏密、大小和朝向变化，从正常 RTS 镜头高度能看出是一片可采资源。

- 先盘点现有素材，优先复用合适矿石网格和材质，必要时制作变体；交付实际接入的模型、材质、资源场景和导入文件。
- 保持项目美术风格，资源与普通装饰石头要可区分；不要只换图标或生成一张概念图就算完成。
- 视觉矿块不必一块对应一个独立逻辑实体。可复用既有矿点作为逻辑单位，以多个网格表现一片散矿，避免无谓增加查询、碰撞和导航开销。
- 校准地形贴合、尺寸、选择区域、采集距离和碰撞。装饰矿块不能形成工人无法进入的密集障碍，也不能埋地或浮空。
- 表现要反映余量：丰富、稀疏、采空、再生后恢复之间有清楚区别。采空时可保留地表痕迹，但不能显示仍有大量可采矿石。
- 覆盖实际使用的手摆地图和生成地图入口。检查真实游戏截图中的整体矿区、工人采集以及采空/再生前后状态。

### 8.2 再生规则与权威结算

默认目标是：某矿点采空后进入等待期，经过可配置的游戏时间恢复一定矿量，并能再次被采集。再生间隔、每次恢复量、最大容量和是否启用再生必须配置化，不能散落在脚本里。具体数值依据当前采集速度和对局节奏选取初始值，在报告中注明并实测校准；用户尚未指定固定秒数。

- 以权威模拟 Tick/游戏时间计算再生，暂停时停止计时；不能依赖客户端计时器或墙钟时间各自刷矿。
- 维护“可采 → 耗尽等待 → 再生可采”的明确状态。耗尽后保留矿点身份及再生记录，不能删除实体后永久丢失再生位置和计时。
- 同一再生周期只能结算一次，矿量不超过容量；再生增加矿点存量，不直接给玩家账户加钱。收入仍须经过实际采集与交付。
- 再生更新走现有权威资源与同步链，复用现有生命周期；兼容已有存档、读档和重连能力，不因重新加载或重复事件多刷一次。
- 再生不得把建筑、单位挤走或生成阻路碰撞；矿区占地与建筑放置须有一致规则，不能允许建筑覆盖后又长出穿模矿块。
- 只向玩家和 AI 提供其视野权限内的最新矿量与状态。迷雾中的再生不能成为实时情报泄漏。

### 8.3 与矿场、副官和训练的衔接

- 耗尽时停止无效采集，释放或调整矿点占用，允许工人转到其他合法矿点；不要求工人在空矿旁罚站等待。
- 再生后刷新合法资源候选和矿场分配。已永久拉黑“空矿”的缓存必须按资源状态变化失效，否则矿长回来了仍不会有人采。
- 矿场在权限和容量范围内为再生矿安排合资格工人，不打断玩家命令或已有高优先级任务，不反复重下相同采集订单。
- 将耗尽、等待、再生、重新采集和交付记入结果链与样本审计。模型学习基于可见矿量和经济需求选择换矿、等待、扩矿，不能把等待再生一概标成失败。
- 循环训练对照双方使用相同素材、地图、采集与再生配置。先固定新经济规则的基线，再比较训练版本，不能把额外再生收入当成模型能力提升。

### 8.4 实际验收

使用小容量、短等待的专用夹具验证至少两个完整再生周期，并在正常容量、正常等待配置的真实对局中验证一次完整周期。另测暂停恢复、多工人同时采空、重复更新、已有重连/存档恢复路径，以及再生后的视野与派工行为。

提交矿区改造前后及“丰富—耗尽—再生”的实际截图、资源存量时间线、权威再生事件、工人订单和交付记录。视觉检查、逻辑测试、真实收入证据都完成后，才可将此项标记为完成。
