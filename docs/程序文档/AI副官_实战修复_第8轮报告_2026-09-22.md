## 3. 根因（用户截图那个问题的真因）

逐单位追单（det_55）：Unit_32 的订单序列里 **`bt-defend`（优先级 92，"基地受袭：
基地附近的作战单位回防"，目标就是基地）反复压过 `rule-probe-expansion`
（优先级 2）**；EASY 反复搔扰我家 → 回防圈内**所有**单位都被这条摁住 →
56 个作战单位 50 个堆在离家 15m 内、敌军 30 个没人去打。单位本身几乎不挪动
（Unit_32 用 260 秒只挪了 10 米）。

即：不是航点算错、不是订单被拒（484 条 Accepted）、不是闸门拦（放行率 89%）——
是**回防分支的覆盖面**把大军锁死了。

## 4. 修复（D17 回防配额）

- `_should_defend_home` 从"回防圈内全部回防"改为"**只在配额名单内**才回防"；
- 配额 = `clamp(来犯之敌数 + 2, 3, 10)`，按离基地近远取前 N 个
  （`_defend_quota_names`，新常量 `DEFEND_QUOTA_MARGIN/MIN/MAX`）；
- 配额外的单位**落回交火/前压分支**：既清来犯之敌，又把战线往外推。
- 语义：防守力量与来犯规模匹配——既不"一个兵回防送死"，也不"全军回防放弃进攻"。

测试：3 个新用例钉住"不全军蹲守"（回防数 ≤ 配额且必须有人交战）、
"配额随来犯增长"、"远处单位永不回防"。既有 `test_far_line_keeps_task_...`
（振荡回归）原样通过。

单压它而没有替代 = 放弃探索；前沿格以基地为锚，作战单位沿它走反而更不出门。
