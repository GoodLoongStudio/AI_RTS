# 程序重构：最小命令与单位视觉接口评审稿

> 文档状态：本轮接口评审通过，尚未编码
>
> 评审范围：Tank Move/HaltMovement 纵向样例所需最小接口

> 2026-08-12 命名修订：结合后续传统 RTS 命令评审，本稿中的 `Move` / `MoveUnitsCommand` 实现名称统一调整为 `ForceMove` / `ForceMoveUnitsCommand`；原有逐单位校验、部分成功和订单状态语义不变。
>
> 根命名空间：`AI_RTS`

## 1. 本轮目标

只建立足以验证下列链路的接口：

```text
Human input
  → selection snapshot
  → Move/HaltMovement command
  → ownership and state validation
  → deterministic command result
  → Godot Navigation adapter
  → Tank movement/stop
```

本轮不包含攻击、编组持久化、AI 副官、规则 AI 迁移、生产、数据库或 Python。

## 2. 稳定标识

建议使用强类型 ID，避免裸 `string`、NodePath 和 Godot InstanceId 在层间传递：

```csharp
namespace AI_RTS.Domain.Common;

public readonly record struct MatchId(Guid Value);
public readonly record struct PlayerId(Guid Value);
public readonly record struct UnitId(Guid Value);
public readonly record struct CommandId(Guid Value);
public readonly record struct UnitOrderId(Guid Value);
```

初期可由 Godot Adapter 在单位创建时分配并维护 `UnitId ↔ Node` 注册表。ID 生成策略在存档/回放设计前可先使用注入的 `IIdGenerator`。

`CommandId` 标识一次批量调用；每个被接受的单位获得独立 `UnitOrderId`。这样多个速度不同的单位可以分别报告到达、受阻或取消，同时仍能追溯到同一个 CommandId。

## 3. 坐标值

领域/Application 接口不直接公开 `Godot.Vector3`：

```csharp
namespace AI_RTS.Domain.Common;

public readonly record struct WorldPosition(float X, float Y, float Z);
```

Godot Adapter 负责与 `Vector3` 转换。第一版保留 Y，地面移动校验器可以将目标投影到地面导航域。

## 4. 命令上下文

```csharp
namespace AI_RTS.Application.Commands;

public sealed record CommandContext(
    CommandId CommandId,
    MatchId MatchId,
    PlayerId IssuerPlayerId,
    long SimulationTick);
```

第一版调用者身份等同于玩家。未来加入 Human、RuleAI、Agent、Replay 等来源时，可新增 `ControllerId/CommandSource` 作为审计字段，但不以来源决定游戏权限。

## 5. 命令类型

```csharp
namespace AI_RTS.Application.Commands.Units;

public sealed record MoveUnitsCommand(
    IReadOnlyList<UnitId> UnitIds,
    WorldPosition Destination);

public sealed record HaltMovementCommand(
    IReadOnlyList<UnitId> UnitIds);
```

第一版约束：

- `UnitIds` 不允许为空；
- Dispatcher 在执行前去重，并使用稳定顺序处理；
- Move 是到位置，不包含攻击移动、队形或寻路策略；
- `HaltMovement` 仍是只停止当前导航/位移的底层能力；玩家统一 `Stop` 是独立上层意图，按订单类型暂停移动/工作任务、取消当前普通 Attack 与显式 ForceAttack，但不改变持续战斗策略，也不等同于禁火；
- 攻击由独立的开火策略控制，后续以 `SetFirePolicy(HoldFire/ReturnFire/FireAtWill)` 等明确命令评审；
- 采集和施工属于工作任务，不因 HaltMovement 自动取消；取消工作需使用独立命令；
- 命令 DTO 不持有 Node、SceneTree、NavigationAgent 或回调。

### 5.1 移动、工作与开火必须分离

当前 GDScript 将采集/施工实现为包含移动子动作的组合 Action。直接把 `unit.action` 清空会连同工作任务一起取消；只把移动速度清零而保留组合 Action，状态机又可能在下一帧重新请求移动。因此迁移后的单位状态至少分为：

```text
Unit task/order       Gather / Construct / Attack / None
Navigation request   Moving / Halted / Arrived / Blocked
Fire policy          HoldFire / ReturnFire / FireAtWill
```

第一阶段只迁移 Tank，不把 HaltMovement 暴露给尚未完成任务/导航解耦的工人单位。已确认的后续语义：

- 工人在目标旁采集或施工时，HaltMovement 不产生实际影响，工作继续；
- 工人在前往工作目标途中收到 HaltMovement，工作任务保留但进入 `Suspended`，不会自动恢复移动，否则玩家会感觉停止命令失效；
- 再次下达同一工作命令或显式 Resume 后恢复；下达新的 Move 则替换当前工作任务；
- 攻击与自动索敌不受 HaltMovement 控制，禁火由 FirePolicy 负责。

`Suspended`/Resume 是后续工人命令评审建议，不属于 Tank 纵向样例的已批准接口。

## 6. 返回结果

建议支持多单位部分成功，避免一个无效单位导致整组选中单位完全不响应：

```csharp
namespace AI_RTS.Application.Commands;

public enum CommandStatus
{
    Accepted,
    PartiallyAccepted,
    Rejected
}

public enum CommandErrorCode
{
    None,
    EmptyUnitSet,
    UnitNotFound,
    UnitNotOwned,
    UnitCannotMove,
    InvalidDestination,
    NavigationUnavailable,
    MatchNotRunning
}

public sealed record UnitCommandResult(
    UnitId UnitId,
    bool Accepted,
    CommandErrorCode ErrorCode,
    UnitOrderId? OrderId);

public sealed record CommandResult(
    CommandId CommandId,
    CommandStatus Status,
    IReadOnlyList<UnitCommandResult> UnitResults);
```

错误码是稳定程序契约；显示文本由 Presentation 根据错误码本地化，领域层不返回面向玩家的中文字符串。

### 6.1 原子性建议

Move/HaltMovement 使用“逐单位校验、部分接受”：

- 全部成功：Accepted；
- 部分成功：PartiallyAccepted；
- 全部失败或命令结构非法：Rejected。

资源扣除、建筑放置等未来命令可能需要整体原子性，不能把本规则机械套用到所有命令。

### 6.2 “部分成功”的准确含义

“部分成功”只用于一个批量命令中，各单位能够独立校验和执行的情况。例如选择 A、B、C 后下达 Move：

| 单位 | 校验结果 | 单位结果 |
|---|---|---|
| A | 属于玩家且可移动 | Accepted |
| B | 属于玩家但为不可移动对象 | UnitCannotMove |
| C | 已死亡、引用过期或不存在 | UnitNotFound |

此时 A 接收移动，B/C 不执行，命令汇总为 `PartiallyAccepted`。它不表示某一个单位“移动了一半”，也不表示异步行动已经完成。

执行规则：

- 先完成命令结构校验；空集合、非法坐标、比赛未运行等使整个命令 Rejected；
- 再按稳定顺序校验所有单位，形成接受集合与拒绝原因；
- 最后只对接受集合产生效果，返回每个 UnitId 的结果；
- Move/HaltMovement 可采用此策略，因为单位间相互独立；
- 建筑放置、资源扣除、编队保持等涉及共享事务或整体约束的命令，默认不得部分执行，必须单独定义原子性。

展示层可把结果汇总为“3 个单位中 1 个已接收命令”，但不得直接暴露会泄漏战争迷雾信息的内部错误原因。

### 6.3 接受之后发生变化

命令被接受时，只能证明该 Tick 中单位可控、目标和导航请求初步合法，不能保证未来一定到达。动态地形、目标被摧毁、单位死亡、堵塞和后续命令都可能改变结果。

每个 `UnitOrderId` 独立维护后续状态：

```csharp
public enum UnitOrderState
{
    Accepted,
    InProgress,
    Suspended,
    Arrived,
    Unreachable,
    TargetLost,
    Cancelled,
    UnitLost
}
```

- `Arrived`、`Unreachable`、`TargetLost`、`Cancelled`、`UnitLost` 是终态；
- 单位速度和路径长度不同，只会让各 OrderId 在不同 Tick 到达，不影响最初的批量 CommandResult；
- 单位中途死亡时，其订单进入 UnitLost，不能让批量进度永久等待；
- 桥梁炸毁或剧情改变地形时，导航层先请求重新寻路；存在替代路径则继续 InProgress，不存在路径才进入 Unreachable；
- “移动到坐标”中的目标坐标不会因附近对象被摧毁而消失；Attack/Follow/Interact 等以实体为目标的命令，在目标消失时进入 TargetLost；
- 玩家下达新命令导致旧订单被替换时，旧订单进入 Cancelled，并记录替换它的新 CommandId（若有）。

导航地图更新可能晚于场景几何变化，因此不能在桥梁销毁的同一帧武断报告 Unreachable。Godot Adapter 应在导航变更生效并完成一次重新寻路后，再产生稳定结果。具体的阻塞判定时间和到达容差属于导航策略配置，不进入领域命令 DTO。

批量进度可以由 Application 根据 CommandId 聚合，例如“5 个到达、1 个不可达、1 个已损失”；它是查询/展示模型，不回写或篡改最初的 CommandResult。语音是否提示“部队已到达”由 Presentation 的聚合策略决定。

## 7. 调度接口

评审建议：第一阶段使用明确重载，避免过早引入反射式泛型总线。

```csharp
namespace AI_RTS.Application.Commands;

public interface IUnitCommandService
{
    CommandResult Move(CommandContext context, MoveUnitsCommand command);
    CommandResult HaltMovement(CommandContext context, HaltMovementCommand command);
}
```

优点：接口简单、易发现、易调试。等命令数量增加并出现统一中间件需求后，再评审 `IGameCommandDispatcher.Dispatch<TCommand>`。

命令调用保持同步且快速；实际移动会跨多个 Tick 进行，`Accepted` 只表示订单已合法接收，不表示单位已经到达。到达、失败、被打断等通过后续领域事件/订单状态查询表达。

这里需要区分两类返回：

- `CommandResult`：立即产生的权威执行回执，说明命令是否被系统接收以及内部拒绝原因；
- `DomainEvent`：稍后发生的游戏事实，例如到达、建造完成、采集被打断。

“建造完成”的语音提示来自 `StructureConstructionCompleted` 一类异步事件，而不是最初建造命令的同步返回。两者都应进入内部日志和测试链路，但某个控制者能否看到、何时看到、看到多少，由观察与反馈策略决定。

### 7.1 权威结果不等于可观察反馈

底层命令必须产生完整结果，以支持一致性、日志、回放和测试；Human、规则 AI、大模型 AI 不应被默认授予同样的反馈：

```text
Command execution → Internal CommandResult / DomainEvent
                  → Feedback & observation policy
                  → Human UI/voice, Rule AI, or LLM observation
```

Presentation 只能显示经过策略过滤的 `ObservableFeedback`。尤其是大模型控制器，不直接订阅原始 CommandResult 或全部领域事件，避免用错误码、完成事件和隐藏目标状态绕过战争迷雾与信息成本。格式错误、身份失败、点数不足等协议级结果可以立即返回；世界内效果是否发生则可只通过付费观察获得。

## 8. 查询与选择边界

Human Adapter 通过本地 Selection Service 获取 ID，而不是让命令服务查询 `selected_units` 组：

```csharp
namespace AI_RTS.Application.Players;

public interface ISelectionService
{
    IReadOnlyList<UnitId> GetSelectedUnits(PlayerId playerId);
    void ReplaceSelection(PlayerId playerId, IReadOnlyList<UnitId> unitIds);
    void ClearSelection(PlayerId playerId);
}
```

选择是本地应用状态，不改变单位领域归属。规则 AI 和未来 Agent 可以直接提交其查询得到的 UnitId，不需要伪造选择。

最小只读查询：

```csharp
public interface IUnitQueryService
{
    UnitSnapshot? GetVisibleUnit(PlayerId viewerId, UnitId unitId);
    IReadOnlyList<UnitSnapshot> GetControllableUnits(PlayerId playerId);
}
```

`UnitSnapshot` 的完整字段在后续查询接口评审中定义；本样例至少需要 ID、OwnerId、Position、CanMove、OrderState。

## 9. Godot 导航端口

Application 不直接访问 `NavigationAgent3D`：

```csharp
namespace AI_RTS.Application.Units;

public interface IUnitMovementPort
{
    MovementPortResult RequestMove(UnitId unitId, WorldPosition destination);
    MovementPortResult RequestHalt(UnitId unitId);
}
```

Godot Adapter 负责：

- 根据 UnitId 找 Node；
- 判断 Movement trait/NavigationAgent 是否存在；
- 将目标交给现有 GDScript Action 或新 C# 节点；
- 把引擎错误转换成稳定错误码；
- 不把 Node 返回给 Application。

Tank 纵向样例阶段允许 Adapter 暂时桥接现有 `Moving.gd/Movement.gd`，以验证公共接口，不要求同一切片重写全部导航。

## 10. 单位视觉契约

### 10.1 目标节点结构

```text
UnitRoot
├─ VisualRoot
├─ CollisionRoot
├─ SelectionAnchor
├─ HealthBarAnchor
├─ GroundFootprint
├─ MuzzleAnchors
│  └─ Primary
└─ OptionalAnimationRoot
```

### 10.2 C# 适配组件

```csharp
namespace AI_RTS.GodotAdapter.Units.Visuals;

public partial class UnitVisualBindings : Node
{
    [Export] public Node3D? VisualRoot { get; set; }
    [Export] public Node3D? CollisionRoot { get; set; }
    [Export] public Marker3D? SelectionAnchor { get; set; }
    [Export] public Marker3D? HealthBarAnchor { get; set; }
    [Export] public Marker3D? GroundFootprint { get; set; }
    [Export] public Godot.Collections.Dictionary<StringName, Marker3D> MuzzleAnchors { get; set; } = new();
    [Export] public Node3D? OptionalAnimationRoot { get; set; }
}
```

上面是评审示意，Godot 是否支持对 `Marker3D` Dictionary 的理想 Inspector 编辑体验需在样例中验证；若不适合，可改为独立 `UnitSocket` 子节点数组。

### 10.3 替换模型规则

- 领域和 Application 不读取 VisualBindings；
- 战斗适配器只通过语义挂点名请求炮口；
- 外部 GLB 可以整体替换，内部节点层级不成为业务契约；
- 碰撞、选择半径、导航半径和模型包围盒分别配置，不从视觉缩放隐式推导；
- Visual Adapter 启动时验证必需挂点，错误应带 UnitTypeId 和场景路径；
- Tank 样例只要求 VisualRoot、CollisionRoot、SelectionAnchor、HealthBarAnchor、GroundFootprint 和 Primary Muzzle。

## 11. 纵向样例验收

接口获批并实现后，Tank 样例需要证明：

1. Human 右键地面不再直接给 Unit 写 Action，而是产生 MoveUnitsCommand；
2. 非所属单位被拒绝并返回 UnitNotOwned；
3. 不可移动单位返回 UnitCannotMove，其他所选单位仍可移动；
4. HaltMovement 能终止已接收的移动，且不具有取消攻击/工作任务的隐含语义；
5. 命令和结果不包含 Godot Node；
6. 现有 TestOneUnit 场景的 Tank 可以通过桥接层移动；
7. 无 Godot UI 的 Application 测试覆盖接受、部分接受和拒绝；
8. Tank 模型更换只需修改 VisualBindings/场景资源，不修改 Move/HaltMovement 代码。

## 12. 评审结论

已确认：

1. 命令需要结构化返回；完成状态使用后续事件/查询表达；是否向大模型公开由观察策略决定；
2. 第一阶段使用 `IUnitCommandService` 明确方法；
3. Unit ID 第一阶段使用进程内 Guid；
4. 接受 VisualBindings 语义挂点契约；
5. Move/HaltMovement 对互相独立的多单位采用“部分成功”，详细边界见 6.2；
6. 保留底层 `HaltMovement`，新增统一 `Stop`：移动及工作任务暂停且不自动恢复，当前普通 Attack 与显式 ForceAttack 取消；持续攻击意愿仍由交战姿态和禁火/开火策略控制；
7. 工人在途中 Halt 后保留任务、进入 Suspended 且不自动恢复；
8. 动态地形、单位死亡和不同到达时间通过独立 UnitOrderId 的异步状态表达，不改变初始 CommandResult。

可以开始只包含 Tank Move/HaltMovement、Guid、UnitOrderId 与 VisualBindings 的纵向样例。工人、攻击和完整导航失败策略仍按后续功能分批编码，不借本次通过提前扩大实现范围。
