## 1. 本轮结果

施工不再由多个 GDScript `_process(delta)` 直接修改建筑浮点进度。Human、规则 AI 和未来 Agent 均通过同一 Application 入口提交 `ConstructStructureCommand`；Match 级 `ConstructionService` 统一持有现场、订单、整数工作量、退款和终态。

已实现：

- `ConstructionSiteSnapshot` 与 `Active / Completed / Cancelled / Destroyed`；
- 批量 Construct 的逐 Worker 校验和部分成功；
- `RequiredWork=200`、Worker 每物理 Tick 贡献 1 点的首轮线性聚合；
- Stop 暂停整个施工任务，再次指定同一现场恢复同一 `OrderId`；
- Worker 新订单、死亡、现场完成/取消/摧毁时的统一终态清理；
- 玩家主动取消全额退款且不重复入账；施工中被摧毁不退款；
- Human 在进入蓝图模式时捕获 Worker，Place 后显式提交 Construct；被建筑驱逐的 Worker 到位后再施工，新命令可取消等待；
- 规则 AI 继续一次只选择一个 Worker，但使用同一公共施工入口；
- 施工初始化与新增 HP 使用非伤害写入，不再误报 `unit_damaged`；施工期间真实损伤保留至完工。

## 2. Worker 无残留保证

运行时只允许 `ConstructionService` 的活动分配表保存 Worker→Site 关系，Godot Adapter 只保存弱引用。以下情况都会使 Construct 订单进入终态，并在订单事件回调中删除活动分配和 Legacy Action：

| 原因 | Worker 订单终态 | 现场状态 | 退款 |
|---|---|---|---|
| Worker 收到其他命令 | Cancelled | Active | 无 |
| Worker 死亡 | UnitLost | Active | 无 |
| 其他 Worker 完成现场 | Completed | Completed | 无 |
| 玩家主动取消现场 | Cancelled | Cancelled | 全额、一次 |
| 施工中现场被摧毁 | TargetLost | Destroyed | 无 |

Suspended Worker 只在活动分配中保留稳定 SiteId/OrderId，不保留 Godot Node 强引用；如果其他 Worker 完工，它同样进入 Completed 并被清理。纯 C# 回归已明确验证“一个 Worker 退出、另一个完成”后活动引用数量为 0，退出者也无法再被暂停。

## 3. HP 规则

施工进度只增加“本次新解锁”的结构 HP，而不是按当前百分比覆盖当前 HP。例如最终 100 HP，解锁到 40 后受到 15 点伤害，再完成剩余施工只新增 60，最终为 85。完工不自动维修。

初始化与施工新增 HP 会刷新血条，但不会发布受击事件；普通伤害仍通过原 HP setter 发布 `unit_damaged`。维修、出售、拆除和带来源的完整 `DamageApplied` 事件属于后续工作。
