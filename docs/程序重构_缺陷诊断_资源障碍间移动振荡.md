# 缺陷诊断：资源障碍间移动振荡

日期：2026-08-13

状态：已定位主要诱因，尚未实施修复。经 2026-08-13 评审，该缺陷紧急程度较低，不进入当前重构关键路径；重构阶段只保持导航端口与算法实现解耦，重构完成后建立独立缺陷分支修复并优化导航寻路。

## 现象

Tank 位于 `PlainAndSimple` 场景三块相邻 `ResourceA` 之间时，向右上方资源附近下达移动命令，可能无法离开狭窄区域，并在两侧反复移动。

2026-08-14 补充复现：对敌方建筑下达 ForceMove 后，Tank 能正确接近目标，但在贴紧不可进入的建筑 footprint 后来回踱步；同一目标下 Helicopter 可正常停在建筑上方。该现象说明输入分派已正确，地面单位在不可达终点附近仍缺少稳定的 `Blocked/Unreachable` 收敛规则。本项与资源狭缝振荡一并留到重构完成后的导航缺陷/优化分支处理。

## 静态配置与几何测量

- 地形 `NavigationMesh`：`cell_size = 0.3`、`cell_height = 0.3`、`agent_radius = 0.9`；
- Tank：物理碰撞半径 `0.8`，`NavigationAgent3D.radius = 0.9`，因此导航直径为 `1.8`；
- `ResourceA`：`NavigationObstacle3D.radius = 0.6`，同时还配置了静态 `vertices`；
- 三块资源中心距离约为 `1.80`、`1.98`、`2.20`；扣除两侧障碍半径后，局部净间距仅约为 `0.60`、`0.78`、`1.00`，均小于 Tank 的导航直径 `1.8`。

因此，Tank 所处位置对当前导航与避障半径而言不是有效通道。主要问题不是 `cell_size` 过大，而是场景部署位置与单位通行净空契约不一致。

## 振荡原因

1. Tank 从不可通行或导航网格边缘区域开始移动，路径查询只能把起点吸附到最近的合法导航位置；
2. `Movement.gd` 检测到移动不足后，会连续若干帧强制选择目标方向左侧或右侧的横向速度；
3. 狭缝没有足够净空，局部避障又会修正该速度，下一轮脱困可能改选另一侧；
4. 最终形成左右反复移动，而不是稳定脱困或明确报告不可达。

`path_max_distance = 0.51` 小于 Tank 导航半径，在狭窄网格边缘也可能增加重新寻路频率，但是否为本场景的直接放大因素仍需运行时路径日志确认。

## 当前导航实现

项目使用 Godot 原生 3D 导航组件：`NavigationServer3D`、`NavigationRegion3D`、`NavigationMesh`、`NavigationAgent3D` 与 `NavigationObstacle3D`。项目代码在其上增加了运行时烘焙、路径跟随、局部脱困、编队目标分配与命令系统。

当前多单位移动不是共享路径或 Flow Field：每个单位拥有独立 `NavigationAgent3D`，分别请求路径并参与 RVO 局部避障。Godot 原生导航服务器会统一管理导航图和避障计算，但项目层尚未实现路径查询错峰、共享走廊、分层编队或大规模单位专用优化。

## 建议修复顺序

1. 建立确定性复现场景和运行时诊断，记录路径点、路径索引、目标点吸附结果、期望/安全速度、重新寻路与脱困触发次数；
2. 增加部署净空校验，禁止单位生成或重定位到不满足其导航半径的位置；
3. 将盲目的左右横移脱困改为有稳定方向、重试上限和明确 `Blocked/Unreachable` 结果的恢复流程；
4. 统一资源障碍的视觉、物理碰撞、导航烘焙和局部避障 footprint，避免静态 `vertices` 与动态 `radius` 无意叠加；
5. 完成单单位正确性后，再为多单位测试路径查询错峰、邻居数量、编队通道宽度与性能基线。复杂并发或多线程优化不在本缺陷的首轮范围内。

## 本轮边界

本轮仅执行诊断和记录，没有修改寻路参数、场景部署或移动算法。

后续修复不得把 Godot `NavigationMesh`、RVO 参数或具体脱困算法写入 Domain 命令契约。当前重构只通过导航端口表达“请求移动、取消移动、查询状态和返回不可达结果”等稳定能力，使专项分支可以替换寻路实现而不修改上层玩家、规则 AI 或未来 Agent 的命令入口。
