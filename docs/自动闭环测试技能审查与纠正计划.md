# 自动闭环测试技能审查与纠正计划

日期：2026-09-30。范围：当前代码、项目技能和用户提供的两张截图。此轮是源码与技能审查，没有完成新单机对局的截图复现，不得声称游戏已经修好。

## 结论与证据

现有工具具备启动、发命令和保存截图的能力，但通过标准不足以证明用户目标完成。技能中的“迭代到全绿”依赖探针的断言；断言漏掉视觉效果、真实输入和最终结果时，重复执行也会一直假绿。不能仅凭这些文件判断另一个模型本身不具备能力，也不能证明它实际加载过该技能。

### 1. 截图存在被当成画面通过

`tools/dev/match_instance.py` 的 `_cmd_selftest` 使用 `os.path.exists(shot)` 检查截图。技能的 `scripts/probe_template.py` 也只有文件存在检查。没有强制查看截图、确认目标可见、检查模型比例、出生点或穿模。

纠正：截图写入成功只表示证据已采集。执行 AI 必须实际打开图片，逐项给出通过、失败或无法判断。黑屏、目标在画外、被 UI 遮挡都属于证据不合格，不能判绿。

### 2. 测试入口与玩家入口不一致

技能默认 `launch_server` + `launch_client`，`wait_match` 和行为检查读取独立服务端。玩家要求单机，但技能没有要求最终用单机入口复现。底层命令也可能绕过 HUD、蓝图和鼠标拾取链路。

纠正：保留该 selftest 作为测试通道自检，明确它不代表玩法验收。新增或使用有实例登记和所有权清理的单机启动路径；最终必须通过玩家单机入口、建筑按钮、蓝图放置、生产按钮完成回归。不能简单删掉 launch_server 后假装现有 MatchGroup 就支持单机，wait_match 当前仍读取 server。

### 3. 移动了一点不代表完成任务

selftest 选择任意带 movement 的单位，并以 XZ 曼哈顿位移超过 2 为通过。它没有验证选择的是矿车、是否到达目标、是否绕开建筑或是否卡住。模板继承相同逻辑。

纠正：按 unit_type_id 选择目标；断言生产完成、实际出生位置、路径可达、最终到达和一定观察期内不穿模。为断言设置明确超时。

### 4. 技能存在过期和冲突的指引

`airts-auto-loop-testing/SKILL.md` 的反向案例仍要求未探索区域返回 NotVisible，与当前无迷雾建造限制规则冲突。关联的 `airts-godot-control-channel/SKILL.md` 写“没有相机 op”，但当前 `DebugControlServer.gd` 已有 camera 和 `_op_camera`。文件同时保留动态端口和历史固定端口说明，增加照抄旧路径的风险。

纠正：移除过期验收案例；关联技能以当前源码 API 为准；旧流程放入明确的历史区。测试生命周期继续保留动态端口、实例登记和仅清理本轮 PID 树的机制。

### 5. 日志报错仍可能返回成功

`tools/run_targeted_godot_tests.py` 的 passed 只要求 marker 出现且退出码为 0。forbidden_hits 单独记录，没有参与最终失败列表。因此有 SCRIPT ERROR 的运行仍可能以退出码 0 结束。

纠正：分开报告行为断言和日志诊断，但总验收必须同时满足。致命脚本错误、解析失败、崩溃和超时必须失败。已知非致命告警必须逐条有依据地豁免，禁止统一称为环境噪声。

### 6. 探针删除与证据覆盖妨碍复现

技能要求一次性脚本跑完即删，模板使用固定证据目录；定向 runner 默认覆盖相同测试日志和 summary。其他会话可能同时写同名结果。

纠正：有效复现脚本纳入版本管理。每轮保存唯一 run_id、代码版本及脏文件哈希、程序集哈希、地图、种子、进程身份、启动方式、命令、状态、截图和结果。记录修复前失败与修复后通过，避免混用不同版本的证据。

## 当前游戏代码的风险

1. `UnitPlacementUtils.gd:production_spawn_spot` 搜索返回 INF 后，仍直接计算前方位置并返回，没有对回退位置做合法性复验。它可能落进其他建筑、资源、水域或地图外。这包含上一轮本助手引入的回退，应纠正：失败保持待部署并重试，不消耗或丢弃已完成生产项，不在中心或任意前方强制生成。
2. 出生算法遍历生产建筑所有 GeometryInstance3D，需确认是否把高亮、选择圈、特效等非实体几何计入边界。起点当前又加入 agent_radius，候选验证还要求单位外围九点都在导航面内。导航网格本身已经按代理尺寸收缩时，可能再次增加出生距离。必须测量，不能继续叠加 buffer。
3. `MovementObstacle.gd` 已新增逆父缩放；VehicleFactory 场景也明确写入 1/3。其注释声称 carve 使用 radius，而 C# CarveRadiusOf 使用 vertices 世界外缘，SizeAuditProbe 又使用 obstacle.radius。三个定义不一致。必须检查实际烘焙输入及引擎配置，用单障碍场景测出真实边界；不要把任何一段注释当证明。
4. `SizeAuditProbe.gd` 直接把 CylinderShape3D.radius 当作世界值，未计入 CollisionShape3D 的 global_transform。当前车厂碰撞节点继承根 scale=3，审计因此低报。必须打印 shape 原值、碰撞节点完整世界变换以及实际物理查询结果。
5. 两张用户截图显示建筑相对车辆的视觉比例悬殊，但仅凭静态图片无法确定车辆是否卡住、出生时是否重叠、比例是否符合用户期望。Worker 场景包含 root scale=2 与模型局部 scale=0.22；车厂包含 root scale=3 与模型局部 scale=0.2，原始模型大小还不同。必须测量实际加载模型的世界尺寸和屏幕包围框，不能仅比较 scale 数字。

## 给实施 AI 的任务

先修验收标准，再依靠同一复现场景修游戏。不要再次把所有建筑和单位按统一倍数盲目缩放。

1. 建立用户截图对应的单机复现：基地旁建车厂，再建机场；从车厂连续生产三辆矿车，记录出生当帧、1 秒后、5 秒后，指挥车辆穿过建筑旁通道。
2. 保存固定镜头截图和世界状态：模型实体边界、碰撞世界边界、逻辑脚印、导航边界、出生位置、单位最终位置。截图必须实际打开检查。
3. 复查真实玩家蓝图与最终建筑的比例、位置是否相同；核对车辆是否可辨识和正常选中。没有确认的目标比例标为待确认，不自行创造设计规格。
4. 对出生失败保留待部署状态，修正不经验证的回退；用四周被围、邻接资源、地图边缘作为反例。
5. 统一尺寸数据的意义和转换位置，用物理查询、导航查询和视觉观察互相核对；不要强求矩形建筑、圆形代理和视觉装饰具有相同边界，但差异必须明确并符合玩法。
6. 修改技能的默认入口、过期规则和验收门槛，保留安全的实例管理。保留正式复现探针，修复测试 runner 的错误退出码。
7. 修复后在新进程重复相同场景，并至少换一个出生位置验证。发现失败则记录失败项、修改和重测结果；遇到可重复的基建阻塞要报告证据，不将它改判通过。

## 完成条件

- 单机 UI 操作能相邻建造，重叠建造被拒，蓝图与成品一致。
- 矿车出生不重叠、不越界、不进入不可通行地面；被围堵时等待部署。
- 车辆确实走到目标且没有持续卡住，而非仅有少量位移。
- 图片已被执行 AI 查看，每项视觉目标有明确结论。
- 本轮致命日志错误为零，测试返回码与验收结论一致。
- 报告带独立证据目录和可重复执行的探针；没有实机验证的项目明确写未验证。

本文件修正上一份尺寸指南中证据不足的固定 carve 结论和不经验证的出生回退建议。上一轮同帧测试最近导航点相距约 7 至 10 米，只能证明候选不在当时的导航面上，不能单凭这一点断言只是导航尚未初始化。
