## 1. 已确认实施约束

- 主技术栈：Godot 4.7 Mono + C#；GDScript 允许作为迁移期薄适配器。
- 根命名空间：`AI_RTS`，子命名空间按架构层和功能域组织。
- 目录按架构层级与类型分类，不按开发者或临时任务分类。
- 大模型/Python 不属于本次重构实现范围；后续由其他成员通过公开端口接入。
- 当前重构分支只做本地提交，重构完成前不推送、不合并 main。
- 公共接口先提交文档/签名评审稿，由项目负责人批准后编码。
- 初版性能目标为可接受运行和无明显退化；可以采样，但不提前实施复杂多线程、并发或并行模拟。
- 引入多线程、并发、Job 化或跨进程复杂调度前，必须单独说明瓶颈证据、线程所有权、确定性、Godot 主线程约束和测试方案并评审。
- 视觉运行基线由团队共享文档和项目负责人手动验证；程序侧负责构建、脚本错误、接口、状态和自动化测试。
- 旧缺陷允许随迁移暂时存在，但必须登记；迁移回归不得被旧缺陷名义掩盖。

## 3. 跨语言边界原则

未来 Python Agent 不直接加载或修改 Godot Node。推荐边界为版本化 DTO 和进程/网络协议：

```text
Python Agent
  ↔ versioned observation / intent DTO
C# Infrastructure.Interop
  ↔ IAgentIntentInterpreter / standard commands
C# Application + Domain
```

协议应具备：版本、请求 ID、操作者 ID、超时、取消、错误码和可观测日志。具体采用 HTTP、WebSocket、stdio 或其他 IPC，等待实际部署需求后形成 ADR。

## 6. 测试和性能策略

### 6.1 测试层级

- Domain 单元测试：无 Godot 场景，覆盖命令规则和结果；
- Application 测试：使用假查询/仓储/时钟，覆盖权限和调度；
- Godot 集成测试：场景、Navigation、Signal 桥接和生命周期；
- 无头短时场景测试：捕获脚本错误、崩溃和刷错；
- 人工视觉测试：由项目负责人验证模型、UI、镜头观感和操作体验；
- 完成阶段端到端测试：Human、规则 AI、任务和胜负闭环。

### 6.2 性能

初版只记录简单、可重复的基线：单位数量、平均/低分位帧时间、导航或命令耗时、内存趋势。只有出现可复现瓶颈且简单优化不足时，才讨论多线程或并发方案。

性能优化不得破坏：

- 命令顺序和结果确定性；
- Godot 主线程对象访问约束；
- 测试可重复性；
- 取消、退出和资源清理；
- 调试与错误定位能力。
