# 玩家资源账户接口评审稿

> 状态：2026-08-14 部分通过，`SourceId` 空值语义待确认
>
> 对应工作项：`ECO-001`
>
> 本稿只确定玩家资源账户、交易和迁移边界；不迁移资源点存量、Worker 载荷、建筑放置、施工生命周期、生产队列或具体数值配置。

## 1. 当前实现与风险

当前 `Player.gd` 同时保存 `resource_a/resource_b`，并提供 `add_resources`、`has_resources`、`subtract_resources`。各调用方的行为如下：

| 调用方 | 当前行为 | 主要风险 |
|---|---|---|
| Worker 交付 | 直接执行 `player.resource_a += ...` 和 `resource_b += ...` | 绕过统一交易入口，难以记录来源和防止重复入账 |
| Human 建筑放置 | 先检查余额，放置时再扣款 | 检查与扣款分离，未来异步或多控制器操作时可能竞态 |
| 规则 AI 建造 | 各 Controller 分别检查和扣款 | 规则重复，无法形成统一失败原因 |
| 生产队列 | 入队时扣款，取消时全额退款 | 缺少稳定交易身份和可审计的扣款—退款关联 |
| 取消施工 | 当前全额退还建筑成本 | 退款来源未记录，重复调用时缺少幂等保护 |
| HUD、测试 | 直接读取 `Player.resource_a/resource_b` | 迁移时容易与 C# 权威余额形成双写和显示分叉 |
| 测试开关 | `allow_resources_deficit_spending` 让 `has_resources` 恒为真 | 规则位于 GDScript FeatureFlag，无法由权威账户保证一致性 |

资源账户不能只服务 Gather。任务奖励、固定资源建筑、退款和脚本调整都必须经过相同边界，但控制器能否立即观察交易结果仍由反馈/观察策略决定。

## 2. 建议的职责划分

```text
Human / 规则 AI / 战役脚本 / Worker / 建造与生产
                         │
                         ▼
             Application ResourceAccountService
              ├─ 原子校验并应用交易
              ├─ 幂等与稳定失败原因
              └─ 发布权威余额变化事件
                         │
                         ▼
              Domain ResourceAccount / Store
                         │
                         ▼
       Godot EconomyRuntime + Player.gd 兼容门面 + HUD
```

- Domain 保存余额规则和值对象，不引用 Godot Node、场景路径或 GDScript 字典。
- Application 接受交易、进行原子校验并返回权威结果。
- Godot Adapter 负责 `PlayerId` 与 Player Node 的映射、初始余额导入、Legacy 字典转换和 UI 信号。
- Human、规则 AI 和未来大模型 AI 不直接修改余额字段。
- 反馈层决定某个控制器是否看到完整结果；内部服务始终产生可测试的权威回执与事件。

## 3. Domain 类型

沿用现有 `ResourceKind.A/B`，建议新增：

```csharp
namespace AI_RTS.Domain.Economy;

/// <summary>表示一种资源的有符号变化量；正数入账，负数扣款。</summary>
/// <param name="Kind">资源种类。</param>
/// <param name="Amount">变化数量；交易内不得为零。</param>
public readonly record struct ResourceDelta(ResourceKind Kind, int Amount);

/// <summary>表示某个玩家资源账户的只读权威快照。</summary>
/// <param name="PlayerId">账户所属玩家。</param>
/// <param name="Balances">按资源种类保存的非空余额集合。</param>
/// <param name="Version">每次成功交易后递增的账户版本。</param>
public sealed record ResourceAccountSnapshot(
    PlayerId PlayerId,
    IReadOnlyDictionary<ResourceKind, int> Balances,
    long Version);
```

约束：

- 同一交易中每种 `ResourceKind` 最多出现一次；Adapter 在提交前合并 Legacy 字典。
- 资源数量使用 32 位 `int`，运算使用 `checked`；溢出必须拒绝，不能截断或回绕。当前对局规模不需要 `long`，未来还可能设置经济存量上限。
- 正式规则默认不允许余额小于零。
- 快照必须复制为只读数据，调用者不能持有账户内部可变字典。
- 资源种类未来可以扩展；服务和 HUD 不应假定永远只有 A/B 两项。

## 4. 交易身份、来源与原因

建议在 `Identifiers.cs` 增加 `ResourceTransactionId`，并定义强类型原因：

```csharp
/// <summary>标识一笔资源交易，用于审计和幂等处理。</summary>
/// <param name="Value">当前对局内唯一的 Guid 值。</param>
public readonly record struct ResourceTransactionId(Guid Value);

/// <summary>说明资源变化发生的业务原因。</summary>
public enum ResourceChangeReason
{
    /// <summary>建立账户时导入初始资源。</summary>
    InitialBalance,
    /// <summary>Worker 抵达有效交付点后交付载荷。</summary>
    WorkerDelivery,
    /// <summary>开始放置或建造建筑时支付成本。</summary>
    ConstructionCost,
    /// <summary>取消建筑时退还资源。</summary>
    ConstructionRefund,
    /// <summary>单位进入生产队列时支付成本。</summary>
    ProductionCost,
    /// <summary>取消生产时退还资源。</summary>
    ProductionRefund,
    /// <summary>战役或任务目标完成后的奖励。</summary>
    MissionReward,
    /// <summary>资源建筑按模拟时间产生的收入。</summary>
    PassiveIncome,
    /// <summary>关卡脚本、调试工具或兼容代码产生的明确调整。</summary>
    ScriptedAdjustment
}
```

交易还应携带可选 `SourceId`。首版使用 `Guid?`，由 `Reason` 决定它表示 Worker、建筑、生产队列项或任务；未来相应稳定 ID 建立后直接填入，避免现在用场景路径或自由字符串形成长期契约。

## 5. Application 契约

```csharp
/// <summary>请求以一笔原子交易改变指定玩家的资源余额。</summary>
public sealed record ApplyResourceTransaction(
    ResourceTransactionId TransactionId,
    MatchId MatchId,
    PlayerId PlayerId,
    IReadOnlyList<ResourceDelta> Deltas,
    ResourceChangeReason Reason,
    Guid? SourceId,
    long SimulationTick);

/// <summary>表示资源交易的权威处理状态。</summary>
public enum ResourceTransactionStatus
{
    /// <summary>交易已完整应用。</summary>
    Applied,
    /// <summary>相同交易已经应用，本次没有再次修改余额。</summary>
    AlreadyApplied,
    /// <summary>账户不存在。</summary>
    AccountNotFound,
    /// <summary>交易结构、数量或来源不合法。</summary>
    InvalidTransaction,
    /// <summary>至少一种资源不足，整笔交易没有应用。</summary>
    InsufficientResources,
    /// <summary>交易会造成数值溢出，整笔交易没有应用。</summary>
    Overflow,
    /// <summary>相同 TransactionId 被用于不同内容。</summary>
    TransactionConflict
}

/// <summary>记录资源交易结果及处理后的权威账户快照。</summary>
public sealed record ResourceTransactionResult(
    ResourceTransactionId TransactionId,
    ResourceTransactionStatus Status,
    ResourceAccountSnapshot? Snapshot);

/// <summary>提供 Match 范围内统一的资源账户查询与交易入口。</summary>
public interface IResourceAccountService
{
    /// <summary>查询玩家当前资源快照；账户不存在时返回 null。</summary>
    ResourceAccountSnapshot? Find(PlayerId playerId);

    /// <summary>原子校验并应用一笔资源交易。</summary>
    ResourceTransactionResult Apply(ApplyResourceTransaction transaction);
}
```

`Apply` 的原子性是指：A/B 成本必须一起成功或一起失败，不能只扣除其中一种。`AlreadyApplied` 返回第一次成功后的快照，不重复发出余额变化事件。相同 ID 但内容不同必须返回 `TransactionConflict`。

“是否买得起”可以由快照用于 UI 预览，但真正执行时必须再次调用 `Apply`；不得用 `CanAfford` 后再无条件扣款的两阶段流程。

## 6. 权威事件

每次 `Applied` 发布一次 `ResourceBalanceChanged`，至少包含：

- `TransactionId`、`MatchId`、`PlayerId`；
- `Reason`、`SourceId`、`SimulationTick`；
- 本次全部 `Deltas`；
- 交易后的账户版本与余额快照。

该事件供 HUD、测试、战役目标和存档系统消费。它是内部事实，不代表未来大模型 AI 可以无成本获得余额变化；对外观察仍需经过视野、信息时效和操作点策略。

## 7. 负余额与测试策略

评审确认任何对局都不允许负余额。贷款上限只会把“资源不足”的边界向后移动，不能解决无上限下单导致的经济规则失效，因此首轮不建立贷款或负余额机制。

- 任何导致任一余额小于零的交易整体返回 `InsufficientResources`；
- UI 预览和最终扣款读取同一规则，不能再让 `has_resources` 单独绕过校验；
- 现有 `allow_resources_deficit_spending` 不进入新账户契约，迁移完成后应删除；
- 需要无成本验证建造/生产的测试场景应显式设置足够的初始资源，或通过带 `ScriptedAdjustment` 原因的调试交易注入资源，不能制造负余额。

## 8. Godot 迁移兼容方案

首轮新增 Match 子节点 `EconomyRuntime`，在一个对局内持有唯一账户服务。`Player.gd` 暂时保留导出的 `resource_a/resource_b`，但角色变为兼容门面：

1. Player 注册时，把场景导出的 A/B 数值作为 `InitialBalance` 导入一次；
2. 初始化完成后，C# 账户是唯一权威来源；
3. `Player.gd.add_resources/subtract_resources/has_resources` 暂时保留签名，内部改为调用 `EconomyRuntime`；
4. `resource_a/resource_b` 只镜像最新快照，供现有 HUD、场景和自动测试读取；业务代码不得再直接写入；
5. `changed` 由权威 `ResourceBalanceChanged` 驱动，每笔成功交易只发出一次；
6. `GodotUnitRegistry` 当前拥有 Player Metadata ID 创建逻辑。实施时应提取共享玩家身份组件，确保命令与经济系统对同一 Player Node 使用同一 `PlayerId`，不能各自生成 ID。

迁移期允许兼容门面存在，但禁止 C# 余额和 GDScript 字段双向同步。双向同步无法可靠判断哪一侧是权威，也容易把一次 Worker 交付重复入账。

## 9. 首轮调用点迁移

`ECO-001` 建议迁移以下现有余额写入，但不改变它们的玩法规则：

| 调用点 | 交易原因 | 首轮保持的行为 |
|---|---|---|
| Worker 抵达 CommandCenter | `WorkerDelivery` | 抵达后一次入账；途中死亡不入账 |
| Human/规则 AI 放置建筑 | `ConstructionCost` | 放置成立时原子扣款 |
| 取消未完成建筑 | `ConstructionRefund` | 暂时保持当前全额退款 |
| 单位进入生产队列 | `ProductionCost` | 入队时原子扣款 |
| 取消生产项 | `ProductionRefund` | 暂时保持当前全额退款 |
| 场景初始余额 | `InitialBalance` | 每个 Player 每场对局只导入一次 |

任务奖励和被动资源建筑本轮只预留 `Reason`，不实现生产逻辑。建筑放置合法性、施工暂停、生产队列稳定 ID 和具体退款比例仍分别属于 `ECO-003`、`ECO-004`、`ECO-005`。

## 10. 未来渐进支付与资源分配边界

传统 RTS 可能允许玩家在余额不足时先把建筑或单位加入列表，随后把每次资源收入分配给多个未完成项目；项目只根据累计获得的资源推进。这能减少玩家长期处于低存量时无法下单的问题，也可以由未来 AI 副官或资源分配 UI 辅助管理。

首轮仍按评审决定采用简单规则：只有 A/B 等全部成本均足够时，才以一笔原子交易一次性扣款并开始建造或生产。未来的渐进支付另列 `ECO-009`，账户接口不得假定一次 `ConstructionCost` 或 `ProductionCost` 必须支付项目全部成本。

渐进支付也不需要把权威资源余额改成浮点数：

- 玩家余额、项目总成本和累计已支付量都使用整数；
- 每次实际分配多少资源，就提交多少整数扣款；
- 项目的最大可推进比例由“各类资源累计已支付量 / 各类资源总成本”的最小值决定；
- 模拟层可用定点余数处理单 Tick 不足一个资源单位的分配，表现层可用浮点数显示进度条；
- 完成时以累计整数校验总支付量，避免浮点舍入造成免费进度、重复扣款或无法精确退款。

“平均分配、轮流分配、玩家优先级或 AI 副官分配”属于调度策略，不进入资源账户本身。账户只负责每一笔分配交易的原子扣款、幂等和审计。

## 11. 自动验证建议

纯 C# 测试至少覆盖：

1. A/B 同时扣款成功，版本只增加一次；
2. 任一资源不足时整笔失败，两种余额都不改变；
3. 收入、退款、任务奖励和被动收入使用同一交易入口；
4. 相同交易 ID 重放返回 `AlreadyApplied` 且不重复入账/发事件；
5. 相同 ID 不同内容返回 `TransactionConflict`；
6. 重复种类、零变化、空交易及溢出被拒绝；
7. 所有对局均禁止负余额，测试资源必须由初始余额或显式调试交易提供；
8. 快照不可修改内部余额。

Godot Smoke Test 至少覆盖：

1. 场景初始 A/B 数值只导入一次；
2. Worker 交付后 C# 快照、Legacy 字段和 HUD 一致；
3. 建造/生产扣款及取消退款各只发生一次；
4. 余额不足时不生成建筑、不加入生产队列，余额不发生部分扣除；
5. Human 与 SimpleClairvoyantAI 使用同一账户服务和规则；
6. 既有 Worker 返程死亡丢失载荷测试保持通过。

## 12. 首轮不处理的内容

- 资源节点存量和 Worker 载荷的完整 C# 迁移；
- 交易数据库持久化、跨局经济或云端同步；
- 多线程与并发优化；当前按主模拟线程顺序处理交易；
- 渐进支付与资源分配调度、资源预占、贷款、市场交换、资源上限和逐步退款；
- 大模型 AI 的资源观察权限与反馈频率；
- 新经济来源的实际玩法逻辑。

## 13. 接口评审结果

2026-08-14 已确认：

1. 首轮一笔交易可以包含多种 `ResourceDelta`，并保证全成功或全失败；当前只有全部成本足够才开始建造或生产；
2. 接受 `ResourceTransactionId` 幂等语义，必须防止重复入账和重复扣款；
3. 资源数量使用 32 位整数；权威余额不使用浮点数。未来渐进支付采用整数累计支付与定点余数，浮点数只用于进度显示；
4. 所有对局均不允许负余额；现有赤字测试开关不进入新架构；
5. 首轮保留 `resource_a/resource_b` 作为只读兼容镜像；
6. 取消施工和取消生产暂时保持当前全额退款，以独立退款交易记录；受到攻击后的部分退款等复杂规则以后评审。

尚待确认：`SourceId` 首版是否允许为空。建议允许：已有 Worker/Unit 可以填写稳定 ID，任务与生产队列项尚未建立稳定 ID 时先为空；等对应切片建立身份后再补齐，不使用自由字符串代替。

该项确认后即可进入代码实现，并在进度表中将 `ECO-001` 从“接口评审中”改为“进行中”。
