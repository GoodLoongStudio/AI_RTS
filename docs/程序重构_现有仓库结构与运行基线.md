## 1. 文档目的

本文回答三个问题：

1. 当前仓库由哪些模块组成，各模块如何协作；
2. 当前代码实际实现了什么，而不是策划文档计划了什么；
3. 为什么本轮重构不能只把 GDScript 一行行翻译成 C#。

手动运行步骤和逐项验收标准见《程序重构_手动功能验收清单.md》；目标架构、迁移阶段和 AI 副官冻结边界见《程序重构_总体方案与AI副官冻结策略.md》。

## 2. 结论摘要

当前仓库不是从零开发的项目框架，而是一个较完整的 Godot RTS 模板，加上团队近期实现的单人战役灰盒、单英雄开局、AI 指令 HUD、镜头设置和 Godot MCP 支持。

模板部分已经形成可玩的 RTS 闭环：玩家配置、地图加载、单位选择与编组、移动、资源采集、建筑放置、生产队列、战斗、战争迷雾、小地图、胜负判定，以及一个掌握全图信息的规则 AI。

团队新增的“AI 副官”目前仍是本地模拟：通过中文关键词把文本映射为 `MOVE / ATTACK / DEFEND / SCOUT / RETREAT / STOP`，并根据任务脚本返回预设建议。仓库中没有实际的大模型 API、Python 服务、数据库或持久化对话系统。因此重构时应保留“玩家意图 → 可验证命令 → RTS 执行层”的产品方向，但不能把当前关键词解析器当作未来 AI 架构。

现有代码适合快速演示，不适合作为长期复杂项目的核心边界。主要问题是：以场景路径充当类型 ID、用 `Dictionary` 充当接口、依赖节点名称和 `find_child/find_parent`、大量全局自动加载、弱类型属性、UI 与业务状态混合，以及测试不能可靠地令 CI 失败。C# 重构应优先建立稳定领域接口和可测试的纯逻辑层，再逐步替换 Godot 表现层。

## 3. 仓库规模与目录

审计时 `source/` 中约有：

- 124 个 `.gd` 脚本；
- 87 个 `.tscn` 场景；
- 8 个 `.tres` 资源；
- 8 个 `.gdshader` 着色器；
- 132 个 Godot `.uid` 文件。

核心目录如下：

│  ├─ Constants.gd            聚合各类常量
│  ├─ Signals.gd              通用全局信号

## 4. 启动与场景组合流程

主流程为：

```text
project.godot
  → source/Main.tscn
  → Logo 展示结束
  → source/main-menu/Main.tscn
      ├─ 单人战役 → CampaignMenu → Loading → Map + Match + CampaignController
      ├─ 自定义对局 → Play → Loading → Map + Match
      ├─ 设置 → Options
      ├─ 制作人员 → Credits
      └─ 退出
```

`Loading.gd` 动态加载地图场景和 `Match.tscn`。`Match.gd` 接收 `MatchSettings`、地图实例和可选的 `campaign_data`，然后：

1. 把地图挂入 Match；
2. 按玩家配置实例化 Human 或规则 AI；
3. 在地图出生点创建初始单位；
4. 建立玩家、单位和敌我分组；
5. 初始化导航、战争迷雾、小地图和镜头边界；
6. 若存在战役数据，额外创建英雄身份、AI 指令 HUD 和 CampaignController。

## 5. 当前模块职责

### 5.1 全局配置与数据模型

`Globals.gd` 负责窗口/鼠标设置、独立的 `user://camera.cfg`、God Mode 和全局缓存。`Constants.gd` 聚合比赛常量和玩家常量。`MatchSettings.gd` 与 `PlayerSettings.gd` 以 Godot `Resource` 表示一局比赛的玩家、可见性、可观察玩家及控制器类型。

当前优点是使用简单；缺点是配置读写、迁移、运行态缓存和调试状态集中在同一个全局对象中，且大量系统直接访问它。

### 5.2 Match 组合根

`Match.gd` 是当前主要 composition root，但也直接处理出生、单位分组、镜头定位、战争迷雾显隐、战役英雄注册等业务。它同时承担装配器和业务协调器职责。

`MatchSignals.gd` 是全局事件总线，包含选中、目标、伤害、死亡、生产、建造、资源不足、导航重烘焙和胜负等事件。事件可以降低显式引用数量，但当前缺少清晰的发布者/订阅者所有权文档。

### 5.3 单位、建筑与行为

`Unit.gd` 继承 `Area3D`，包含生命、攻击、视野、玩家归属和当前 `action`。具体数值主要由场景路径在 `MatchConstants.DEFAULT_PROPERTIES` 中查表注入。

单位场景共九种：

- 移动单位：Worker、Tank、Helicopter、Drone；
- 生产建筑：CommandCenter、VehicleFactory、AircraftFactory；
- 防御建筑：AntiGroundTurret、AntiAirTurret。

行为通过运行时添加到单位下的 Node 表达，现有行为包括移动、追踪、攻击、自动索敌、采集、建造和等待目标。Movement 使用 `NavigationAgent3D`，包含避障、卡住侧移和旋转平滑。

这种“行为即 Node”能直观看到场景树状态，但业务状态依赖节点生命周期、节点组和场景树查找，单元测试和无 Godot 环境复用比较困难。

### 5.4 Human 操作层

Human 本身几乎只是 Player 的场景组合；输入行为主要由子控制器承担：

- 左键单选、框选、Shift 增减选择、双击同类选择；
- `Ctrl+1..9` 保存编组，`1..9` 召回编组；
- 右键地面移动或设置建筑集结点；
- 右键单位决定攻击、采集、建造、跟随或将其设为集结目标；
- Worker 选择后可放置五类建筑，并检查地图边界、碰撞和资源；
- 生产建筑通过 HUD 菜单加入生产队列；
- 单位选择与命令有声音反馈，关键事件有语音播报。

### 5.5 规则 AI

`SimpleClairvoyantAI` 意为“简单、全知 AI”，不是大模型 AI。它通过五个组件工作：

- EconomyController：基地/工人数量、资源采集与重定向；
- ConstructionWorksController：安排工人完成未完工建筑；
- DefenseController：建造对地/对空炮塔；
- OffenseController：建造工厂、生产坦克/直升机、组成进攻编队；
- IntelligenceController：控制无人机在已知单位之间侦察。

根 AI 维护按优先级排列的资源请求，并向各控制器分配资源。它直接读取场景树中的所有单位，因此“Clairvoyant”是准确描述；它不受正常战争迷雾情报边界约束。

### 5.6 HUD、战争迷雾与小地图

HUD 提供资源条、上下文单位菜单、生产队列、暂停菜单、小地图和可选 AICommandHUD。

小地图显示单位与相机视野框；左键点击/拖动移动相机，右键向当前选择单位发出移动命令。UnitVisibilityHandler 根据可见玩家和视野处理单位显隐，并为离开视野的建筑保留假体。FogOfWar 及 Minimap 各自依赖地图尺寸和可见玩家设置。

### 5.7 单人战役与 AI 指令 HUD

目前只有一个可进入任务：`回声撤离`，地图为 `EchoExtractionGreybox.tscn`，尺寸 600×450。玩家以单个 Tank 场景作为“先锋指挥单元”英雄开局，敌方仍使用规则 AI。任务通过到达 SignalGate、PerimeterCamp、AbandonedConvoy、EmergencyExtraction 等标记和一次原地警戒/停止命令推进，最后点击撤离显示结果页。

AICommandHUD 支持：

- 单英雄或三小队显示模式；
- F1 选择英雄，双击 F1 锁定/解除镜头跟随；
- Q/W/E/R/D/F 映射移动、攻击、警戒、侦察、撤退、停止；
- 文本关键词解析同类命令；
- 询问下一步、风险或状态时返回任务脚本提供的预设答复；
- 攻击必须再次右键确认敌方单位，移动类命令必须再次右键确认地图位置。

其中没有网络调用、模型推理或工具调用。`_mock_agent_busy`、`_ask_mock_agent`、固定 0.22/0.28 秒等待和预设字符串明确说明这是交互原型。

## 7. 自动化验证的真实状态

仓库只有一个自动化场景 `CampaignSmokeTest.tscn`。2026-08-11 的重构前运行结果为：

- 它确实创建了 600×450 战役地图、单个玩家英雄、敌方单位、战役控制器、AI HUD、镜头和暂停菜单；
- 输出中出现断言失败：`单人战役界面缺少设置入口`；
- 随后仍打印 `CAMPAIGN_SMOKE_TEST_OK` 并以退出码 0 结束；
- 退出时报告 Navigation RID 泄漏。

断言失败原因是 CampaignMenu 动态创建了设置按钮，但没有把节点名设为测试要求的 `SettingsButton`。更重要的是，当前测试框架会把失败吞掉并继续报告成功，所以它不能作为可靠 CI 门禁。本文不把本次结果记为“测试通过”，而记为“核心场景可实例化，但自动化基线失败且存在假阳性”。

2026-08-12 已在重构分支修复测试基础设施：设置按钮获得稳定节点名，所有测试条件通过统一失败收集器记录；正常路径返回 0，环境变量强制失败探针返回 1。Navigation RID 泄漏仍存在并单独保留为旧缺陷。

第一次在受限沙箱内直接启动 Godot 还发生了引擎原生 signal 11；允许访问 Godot 的 AppData 后才可运行。这是执行环境约束，不等同于项目业务崩溃。

## 8. 已确认缺陷与风险

### 8.1 当前可见缺陷

1. 测试结束报告 NavigationAgent/NavigationObstacle/NavigationMap RID 泄漏。
2. 战斗朝向逻辑在攻击者与目标水平位置重合时持续调用无效 `looking_at` 并刷错，可能造成卡住表现。
3. 初次导入会产生大量 `.godot/imported` 缓存；这些文件应保持忽略，不应提交。

### 8.2 架构风险

1. **字符串/路径充当类型系统**：单位默认属性以 `.tscn` 路径查表，重命名资源可能改变业务行为。
2. **Dictionary 充当契约**：战役数据、资源费用、AI 元数据缺乏编译期约束和版本迁移能力。
3. **场景树即依赖注入容器**：大量 `find_child`、`find_parent`、固定 NodePath、节点组和 duck typing；场景改名容易造成运行时故障。
4. **全局自动加载过多**：Constants、Globals、Signals、MatchSignals、Utils 等成为隐式依赖。
5. **表现与业务混合**：CampaignController 和 AICommandHUD 在代码中动态创建 UI，同时推进目标、解析命令和控制单位。
6. **Action 生命周期耦合 Node**：行为逻辑难以脱离 Godot 主线程做快速单元测试或服务器模拟。
7. **常量集中且巨大**：数值、地图清单、场景路径与导航参数混在同一脚本，后续平衡、Mod、存档兼容困难。
8. **缺少正式接口**：没有 `class_name`，也没有可替换的时间、随机数、模型客户端、数据库、存档或命令总线接口。
9. **错误传播弱**：动态加载、节点查找和信号调用大多到运行时才暴露问题。
10. **测试覆盖不足**：五个手动场景加一个不可靠冒烟测试，无法支撑大规模跨语言迁移。

## 9. C# 重构边界建议

重构不应一次性删除全部 GDScript。推荐采用“C# 领域核心 + Godot 适配层 + 可替换外部服务”的渐进式结构：

```text
Game.Domain (纯 C#，尽量不依赖 Godot)
  ├─ Units / Combat / Economy / Production
  ├─ Commands / Orders / Validation
  ├─ MatchState / Objectives / Visibility contracts
  └─ 数值类型、ID、事件、结果类型

Game.Application (C# 用例与编排)
  ├─ Match orchestration
  ├─ Campaign mission runner
  ├─ AI intent → validated command pipeline
  └─ Save/load and telemetry ports

Game.Infrastructure (C# 外部实现)
  ├─ Godot resource/config adapters
  ├─ LLM HTTP client / Python process or service bridge
  ├─ Database repositories
  └─ Logging, serialization, migrations

Game.Godot (C# Godot 节点/场景适配)
  ├─ 输入、相机、NavigationAgent、Animation、Audio
  ├─ HUD/ViewModel binding
  └─ Scene spawning and node lifetime
```

迁移优先级建议：

1. 先建立测试运行器、错误退出约定和重构前验收基线；
2. 建立强类型 ID、数值配置、Match/Player/Unit 快照和命令结果；
3. 抽出资源、生产、战斗、目标流程等纯逻辑；
4. 建立 `IAgentService`、`IIntentInterpreter`、`ICommandValidator`、`IGameQuery` 等接口，把 Mock 和真实 LLM 放在接口外侧；
5. 将规则 AI 控制器改为读取受约束的游戏查询接口，明确是否允许全知；
6. 最后迁移高度依赖 Godot 的镜头、导航、选择框、动画和 UI 节点。

GDScript 可在过渡期保留为薄适配器。只要领域规则、接口、配置和测试已经进入 C#，无需为了“脚本数量归零”提前重写稳定的视觉节点脚本。

## 10. 协作与接口纪律

为减少多人冲突，建议后续每个迁移任务遵守以下规则：

- 每个 PR 只迁移一个可独立验收的垂直切片；
- 新 C# 类型进入独立目录和命名空间，不在同一 PR 大规模移动美术资源；
- 场景 NodePath、节点组、信号名、输入动作名在替换前形成兼容清单；
- 新旧实现短期并存时由 Feature Flag 或明确 composition root 选择，禁止双写状态；
- 所有外部系统通过接口进入，密钥和环境地址不写入场景或仓库；
- 每个切片更新结构文档、接口文档、测试结果和变更日志；
- 合并前以本文件和手动验收清单核对行为差异，并记录“保持、改变、删除”的理由。
