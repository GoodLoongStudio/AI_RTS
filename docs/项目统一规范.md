# AI_RTS 项目统一开发与交付规范

> 文档状态：**Canonical / 项目统一规范**  
> 适用范围：策划、程序、美术、AI、测试以及自动化 Agent 参与的所有正式项目工作。  
> 权威级别：本文件高于 `docs/程序文档/` 中的历史重构记录、阶段性评审稿和旧版本环境记录；若发生冲突，以本文件和项目负责人最新明确要求为准。

---

# 1. 核心原则

1. `main` 是项目唯一正式交付基线和权威代码状态。
2. 正式功能必须做到：**需求明确、代码/内容落地、可运行、可验证、文档同步**。
3. 不允许以“代码写完”“能编译”代替游戏功能验收。
4. 不允许为了通过 CI 删除测试、放宽错误检测、隐藏失败或绕开权威接口。
5. 新系统优先数据驱动和可复用；如果策划新增第二个同类内容仍必须改核心代码，则该系统原则上还没有完成工具化。
6. AI、Human、传统规则 AI 都必须通过统一的游戏权威接口工作，不建立第二套游戏规则。

---

# 2. 固定开发环境

## 2.1 Godot

项目统一使用：

**Godot Engine Mono 4.7.1 Stable**

要求：

- 必须使用 Mono / .NET 版本，不使用标准非 Mono 编辑器作为正式开发和验收环境；
- 本地编辑器、C# Godot SDK、CI Godot 版本必须保持在 4.7.1；
- 不允许个人擅自升级或降级 Godot 主/次/补丁版本；
- 如确需升级，必须同时更新 C# SDK、CI、相关文档并完成完整回归；
- `project.godot` 中的 `4.7` feature 标记属于 Godot 的兼容特性标记，不代表允许使用其他 4.7.x 版本进行正式验收。

## 2.2 .NET

当前统一使用仓库 `global.json` 指定的：

- .NET SDK：`8.0.423`
- Target Framework：`net8.0`
- 禁止使用 Preview SDK 作为正式构建环境。

`global.json` 是团队 .NET SDK 的权威来源。需要升级时必须作为独立环境变更处理。

## 2.3 基础检查

开始正式工作前至少确认：

```text
Godot --version  → 4.7.1 stable mono
dotnet --version → 与 global.json 一致
```

环境不一致时，不得用本机结果宣布正式验收通过。

# 4. Git 与 main 规范

## 4.1 权威分支

- `main` 是唯一正式交付分支；
- 默认正式修复和交付直接进入 `main`；
- 未经项目负责人明确要求，不创建长期功能分支、备份分支或重复交付分支；
- 如因多人协作临时使用分支，验收后必须合并回 `main` 并清理无用分支；
- 不允许对 `main` 做无授权的 force push、rebase 改写历史或回退他人提交。

## 4.2 开始工作前

- 以最新 `main` 为基线；
- 先检查目标文件是否刚被其他人修改；
- 不用旧 SHA 覆盖较新的文件；
- 同一个文件连续修改时必须基于最新内容继续。

## 4.3 Commit 规范

一个 commit 尽量只包含一个清晰主题。

推荐中文提交信息：

```text
功能: 增加单位模式切换基础能力
修复: 修复英雄镜头锁定状态不同步
重构: 统一单位命令入口
文档: 整理策划与程序文档目录
美术: 更新玄甲坦克模型与材质
测试: 增加技能系统回归场景
```

禁止：

- `update`、`fix`、`改一下` 等无法理解改动内容的提交信息；
- 把完全无关的大量功能塞入一个提交；
- 提交 `.godot/`、`bin/`、`obj/`、本地测试输出、临时缓存；
- 提交 API Key、Token、密码、证书私钥等秘密信息。

# 5. 程序架构强制规则

## 5.1 C# 分层

继续遵守现有结构：

```text
Human / Rule AI / Future LLM
            ↓
GodotAdapter / Gateway
            ↓
Application
            ↓
Domain
```

强制要求：

- `Domain` / `Application` 不引用 Godot Node、SceneTree、PackedScene 等引擎对象；
- 领域身份使用稳定 ID，不使用 NodePath、实例 ID、场景路径代替业务 ID；
- 写操作通过 Command；
- 读取通过受权限控制的 Query / Observation；
- `Accepted` 只表示命令被接收，不等于跨 Tick 行为已经完成；
- UI、动画、语音不拥有权威游戏规则；
- 不新增未登记的 Legacy GDScript 权威写入旁路。

## 5.2 数据驱动

新增单位、武器、技能、科技、任务等内容应优先进入版本化配置和稳定 ID 系统。

禁止为了添加每一个新兵种重复硬编码整套逻辑。

通用系统的完成标准应包含：

> 在不修改核心运行时代码的情况下，可以配置至少第二个同类型内容。

# 6. AI 开发强制边界

1. LLM 不得直接操作 Godot Node、SceneTree 或内部状态对象；
2. LLM 输出必须先转成结构化 Intent / Command Candidate，再经过权威 Validator；
3. AI 不得绕过战争迷雾和权限读取隐藏敌军信息；
4. 内部 `WorldQuery` 与未来 LLM `Perception Gateway` 必须保持边界；
5. AI 的幻觉、非法目标、超时、模型不可用不能破坏权威游戏状态；
6. 模型失败时游戏必须能够安全降级到玩家手动控制或传统规则 AI；
7. AI 训练/评测数据必须记录输入观察、输出意图、结构化命令、执行结果和最终战斗结果，不能只保存聊天文本；
8. 任何外部模型 API Key 只能放在本机安全配置/环境变量中，禁止提交仓库。

# 7. 编译与自动化验收

正式提交涉及程序代码时，至少要求：

## 7.1 C# 构建

```text
AI_RTS.Core.csproj 构建通过
OpenRTS.csproj 构建通过
Release 构建无阻断错误
```

新增 Domain/Application 逻辑必须优先补纯 C# 测试。

## 7.2 Godot 验收

至少检查：

- Godot 4.7.1 Mono 可以正常导入项目；
- 无 Parse Error；
- 无 `Failed to load script`；
- 无 `Failed loading resource`；
- 主场景能够启动；
- 修改涉及战役时，必须跑战役相关 smoke / regression；
- 修改涉及单位、技能、导航、生产、建造等系统时，必须跑对应自动或人工场景。

## 7.3 CI

- 正式交付以 `main` 上的 CI 结果为准；
- CI 失败时不得宣布“已完成验收”；
- 不允许通过删除测试、忽略错误码、降低检查等级来“修复 CI”；
- CI 与本地结果冲突时，必须定位环境或行为差异，而不是选择性忽略。

---

# 8. 人工功能验收

自动测试通过不等于玩法完成。

功能提交必须根据改动范围检查：

## 8.1 基础功能

- 正常路径可用；
- 连续重复操作不会进入异常状态；
- 单位死亡、目标失效、切换场景等边界情况合理；
- 玩家手动控制优先级正确；
- AI 和玩家不会争抢权威状态。

## 8.2 RTS 规则

- 命令是否合法；
- 多单位部分成功语义是否正确；
- 战争迷雾是否泄露信息；
- 资源、生产、建造是否出现重复扣款/退款；
- 订单完成与同步 Accepted 不混淆。

## 8.3 UI

- 1280×720 基线可正常使用；
- 关键控件没有互相遮挡；
- 快捷键与输入焦点不冲突；
- 状态变化有可理解反馈；
- 不能只因为“按钮能点击”就算 UI 验收通过。

---

# 9. 美术资产验收

新增或替换美术资产必须检查：

- 来源和授权可追溯；
- 单位比例与 RTS 战场尺度一致；
- Pivot / 朝向 / 坐标轴正确；
- 材质和贴图引用完整；
- 不出现丢材质、紫色/黑色异常、错误透明；
- 碰撞、选择范围和视觉模型不要互相当作同一权威尺寸；
- 炮口、选择锚点、血条锚点等语义挂点正确；
- 资源替换不应因为模型内部节点改名而破坏核心业务逻辑；
- 外部素材必须记录许可证和必要署名信息。

重大单位应至少在实际 RTS 摄像机距离下验收一次，而不是只在模型查看器中验收。

# 10. 策划交付验收

程序开始实现一个新玩法系统前，策划至少应提供：

- 功能目的；
- 玩家操作；
- 状态和状态切换；
- 基础数据；
- 异常和边界规则；
- UI/反馈；
- AI 使用规则；
- 与其他系统的关系；
- 至少一个真实内容样例；
- 可执行的验收条件。

如果规则尚未确定，程序可以先提供扩展点或灰盒，但不得自行把临时假设写成永久游戏规则。

# 11. 提交前 DoD（Definition of Done）

一个正式任务在标记完成前至少满足：

- [ ] 基于最新 main 完成
- [ ] Godot Mono 4.7.1 环境验证
- [ ] C# 构建通过（如涉及 C#）
- [ ] 相关自动测试通过
- [ ] 相关 Godot 场景可运行
- [ ] 没有新增解析/资源加载错误
- [ ] 人工验收完成（如功能有可见行为）
- [ ] 策划规则和实际实现一致
- [ ] 美术资源来源/授权明确（如涉及资产）
- [ ] 文档已同步
- [ ] 不含缓存、密钥和无关文件
- [ ] commit 信息能够准确描述改动
- [ ] 正式结果已经进入 main
- [ ] CI 状态真实记录；没有 CI 时明确写“未有云端 CI 证据”

# 12. 验收报告规范

对外汇报“完成”时应至少说明：

```text
完成内容：
提交 SHA：
测试范围：
自动测试结果：
人工验收结果：
CI 结果：
已知限制：
```

禁止把以下内容混为一谈：

- 静态代码检查；
- 本地运行通过；
- 自动测试通过；
- 人工玩法验收通过；
- GitHub CI 通过。

只完成了哪一层，就准确报告哪一层。

# 13. 规范修改规则

本文件是项目统一规范，不应由普通功能提交顺带修改。

修改以下内容必须明确说明原因：

- Godot / .NET 版本；
- main / Git 提交流程；
- 架构边界；
- CI 门禁；
- 验收最低标准；
- 文档目录规则。

项目负责人最新明确决定优先于本文件；决定稳定后应及时回写本规范，保持“口头规则”和仓库规则一致。
