# 程序重构：多单位命令与部分成功纵向样例记录

日期：2026-08-14

对应进度：`QA-003`、`CMD-027`

## 1. 目标

在不修改导航寻路算法的前提下，验证 Godot 输入适配器、Match 级 `CommandRuntime` 和纯 C# `UnitCommandService` 能对同一批多单位命令返回可靠的逐单位结果。

本轮只验收命令是否被执行层接受，不把单位是否最终抵达、拥堵或绕行质量当作同步命令回执的一部分。

## 2. 测试场景

新增 `tests/manual/TestMultiUnitCommands.tscn`，包含：

- 两辆属于 Human 的可移动 Tank；
- 一个属于 Human、没有 `Movement` 的 CommandCenter；
- 一辆属于 Enemy 的 Tank；
- `PlainAndSimple` 地图原有障碍。

场景根节点继续命名为 `Match`。这是现有单位、Gateway 和多个 Legacy 子系统用于查找装配根的隐式场景契约，测试场景文件名不应改变该运行时节点名。

## 3. 批量强制移动结果

自动化测试将四个节点故意放入同一批 `ForceMoveUnits` 请求。正常玩家 UI 不会选中敌方单位，但直接构造混合所有权批次可以验证 Application 权限检查不会被输入层假设替代。

预期并已验证：

| 单位 | 同步结果 | 错误码 | 订单 |
|---|---|---|---|
| Human Tank A | 接受 | `None` | 独立 `UnitOrderId` |
| Human Tank B | 接受 | `None` | 与 A 不同的独立 `UnitOrderId` |
| Human CommandCenter | 拒绝 | `UnitCannotMove` | 无订单 |
| Enemy Tank | 拒绝 | `UnitNotOwned` | 无订单 |

批量汇总状态为 `PartiallyAccepted`。某个单位被拒绝不会回滚或阻止其他合法单位执行。

## 4. 稳定身份与结果顺序契约

核心服务的 `StableDistinct` 会：

1. 删除重复 `UnitId`；
2. 按稳定 GUID 排序；
3. 每个不同单位只返回一次结果。

因此 `CommandResult.UnitResults` 的顺序是确定性的稳定 ID 顺序，但不承诺与 UI 选择数组的顺序一致。Human HUD、规则 AI、未来 Agent 和语音反馈层必须通过 `unit_id` 关联单位结果，禁止用数组下标关联。

自动测试同时验证重复提交同一 Tank 时，端口只产生一份逐单位结果。

## 5. 停止移动部分成功

对两辆 Tank 和 CommandCenter 同时提交 `HaltMovement`：

- 两辆 Tank 接受，现有移动订单转换为 `Suspended`；
- CommandCenter 返回 `UnitCannotMove`；
- 批量状态为 `PartiallyAccepted`。

这验证了“保留任务、暂停且不自动恢复”语义可以逐单位应用。

## 6. 自动化验证

新增：

- `tests/automated/MultiUnitCommandSmokeTest.gd`；
- `tests/automated/MultiUnitCommandSmokeTest.tscn`。

Godot 4.7 Mono 无头测试连续运行 3 次，均为 0 failure、退出码 0。

退出时仍会报告既有 NavAgent/NavObstacle/NavMap、Renderer 和 ObjectDB 资源泄漏。这些属于已登记的测试退出清理问题，没有被本轮掩盖，也不影响命令断言的非零退出机制。

## 7. 当前边界

`QA-003` 的确定性多单位命令场景已经完成。`CMD-027` 仍保持“进行中”，原因是本轮完成的是同步接收回执；单位随后到达、目标失效、单位死亡、地形变化导致不可达等异步结果，仍需要建立统一事件接口和调用者可见性策略。

导航拥堵、狭窄通道、编队路径和 RVO 性能继续延期到重构完成后的导航专项分支。
