## 灰屏真正根因（第二轮，用户贴出调试器报错后定位）
- 报错：`Invalid access of index '1' on a base object of type 'PackedStringArray'`，Ra3Sidebar.gd 492–493，共 19 次。
- 根因：`_cost_caption()` 早已改成只返回单一 A 资源数字（如 "2400"，无 "/"），但 `_item_tooltip()` 还在 `cost_text.split("/")` 后取 `costs[1]` → 每个生产格子报错一次；调试器在这些错误上把游戏暂停，表现为灰屏 + FPS N/A + 左下角未布局的黑色控件。
- 修复：tooltip 改为 `lines.append("资源: %s" % cost_text)`。
- 本机复现验证：修复后 0 脚本错误，整局渲染正常（基地/新模型单位/侧栏/价签/小地图）。
- 排查经验：用户截图里"灰屏 + FPS N/A"很可能是调试器暂停游戏所致；拿编辑器调试器的报错栈是最快路径。

## 工人"只采矿不回城"排查（2026-09-03 傍晚）
- 结论：换模没有破坏功能。WorkerGatherSmokeTest（用的就是新 Buggy 模型的 Worker.tscn）全绿：采集→满载→回城→交付（日志"满载回城""交付 resource_b=2"）。
- 用户观察到的"一直采矿不回城"真实原因：config/balance/demo.balance.v1.json 里 worker gatherer `carryCapacity=200`，每次采集 tick 只 +1（A 每 1s / B 每 2s），装满一舱要 200s(A)/400s(B)，首趟返程要等 3.5~6.5 分钟——不是 bug 是平衡数值。
- 建议方向：把 carryCapacity 降到经典 RTS 量级（10~20）或提高每 tick 搬运量，等用户拍板。

## AI 工人开局乱跑 + 扎堆转圈（2026-09-03 晚，已修复）
- 复现手段：临时场景 Human+3AI 开局，每 3s 打印工人名字/位置/载货/导航目标（AIWATCH2）。
- 乱跑根因：AI 开局分配的 Gather 目标本来就正确（自家旁边的矿），但 `Movement._clamp_to_reachable` 在导航网格未同步完成时 `map_get_closest_point` 返回退化点（原点附近），目标被钳到 (0,0)，工人沿"出生点→地图原点"直线行军再折返——路径恰好穿过玩家基地，这就是"跑到我这再回去采矿"。折返由 Gather 自愈逻辑完成。
- 修复1（Movement.gd）：clamp 前先查 `map_get_closest_point_owner`，网格无效不钳；并加 `CLAMP_MAX_SNAP_DISTANCE_M=5.0`，吸附距离超 5m 视为网格异常，保持原目标。
- 扎堆转圈根因：`EconomyController._assign_idle_workers_to_resources` 只按资源"类型"(A/B)平衡，两个工人会分到同一个最近矿点 → RVO 拥塞转圈。
- 修复2（EconomyController.gd）：按资源节点 id 统计已分配人数，选择"(分配人数, 距离)"字典序最小的节点，工人自动摊开。
- 验证（AIWATCH2）：4 个 AI 工人开局直达矿点，无绕角行军；同玩家两工人分到不同矿点；20s 满 100 回城交付（Player_1/2/3 均有交付记录）；新造工人 Unit_16 正常加入。
- 回归：WorkerGather/RuleAiEconomyQuery/LocalAvoidance 均 0 失败。NavigationStabilitySmokeTest 2 失败为基线遗留（stash 验证），与技能 17 失败同属历史问题。
- 观察技巧：NavigationAgent 的 move 目标打印在 Moving.gd [MOVE]；Workers/Drones 每玩家开局各 1 无人机+2 工人，Unit 编号 = 4×玩家序 + (0=CC,1=Drone,2,3=Worker)。
